## 1. 起動不能ブロッカー — B-1 〜 B-29

「コンパイルも通り、レビューも通るのに、実行すると落ちる」類のもの。**実際に起動してみて初めて**すべてが明らかになった。

| B-1 🔴 | 6 サービスが起動直後に停止 | profile 専用ファイル内の `spring.profiles.active`（Boot 2.4+ で禁止） | 削除 + **ガードレールテスト** |
| B-2 🔴 | 5 サービスが起動不能 | `feign.*-url` プロパティがどこにも定義されていない | デフォルト値を定義 + `FEIGN_*_URL` で上書き |

| B-6 | Redisson 設定がすべてコメントアウト | — | 復元 |
| B-7 🔴 | 5 サービスが起動不能 | Redis プロパティ名の不一致 | コードが読む名前に統一 |
| B-8 🔴 | catalog スキーマが作成されない | カスタム EMF が `ddl-auto` を受け取れない | 受け渡しを配線 |

## 2. レジリエンス・ゲートウェイ・Kafka の信頼性

詳細: [docs/01](01-branch-issues.md) → [docs/02](02-improvements.md) ・ [docs/11](11-observability-and-kafka-reliability.md) ・ [docs/12](12-dlq-rollout-idempotency-alerts.md)

| Before | After |
|---|---|
| 🔴 ゲートウェイのサーキットブレーカーがコメントアウト、レートリミッターが未完成 | サーキットブレーカーを配線 + Redis トークンバケットのレートリミッターを有効化（429 を実測） |
| 🔴 Feign のタイムアウトなし → 遅いダウンストリームがワーカースレッドを枯渇させる → 連鎖障害 | 共通のタイムアウト標準（3s/5s） |
| 🔴 Kafka コンシューマーのエラー処理が皆無 — poison message 一つでコンシューマーが永遠に停止 | **全サービスに DLQ**（`DeadLetterPublishingRecoverer`）、隔離を実証（壊れたメッセージの後の正常メッセージが処理されることを確認） |
| 🔴 再配信時に**在庫の二重引き当て**（金銭的損失） | `processed_event` 冪等台帳（同一トランザクション）— 3 回再配信しても在庫は不変、自動テスト |
| 🟠 デプロイの healthcheck/再起動/リソース制限が皆無 | k8s マニフェスト一式（[k8s/](../k8s/README.md)）: プローブ・リソース・HPA・PDB |
| 🔴 **Outbox ポーラーがレプリカごとに同じイベントを発行** — 決済リクエストの二重発行。HPA が order・pay を max 3 で対象にしていたため、**負荷が上がるだけで自然に破綻する**状態だった | `FOR UPDATE SKIP LOCKED` による先取り + トランザクション内での同期発行。同時トランザクション 2 つで再現・検証（[docs/21](21-horizontal-scaling.md)）— ロックを外すとバッチ 4 件が 100% 重複する |
| 🔴 ブローカーが一瞬揺らぐと、そのイベントが**永久に消失**（FAILED と記録されるのに、スケジューラーは STARTED しか照会しない） | 一時的な失敗は状態を残して次のポーリングがリトライ。FAILED はリトライが無意味な場合に限る |
| 🔴 決済の重複検知が**一度も動作したことがない** — `"23000" == getSQLState()`（String を == で比較、値も PostgreSQL のものではない） | `DuplicateKeyException` で直接捕捉 — SQLState の文字列を手で比較しない |
| 🔴 Authorization ヘッダーがないと**バッチが丸ごと黙って消える**（WARN 1 行） | 例外を投げて DLT に残す。処理拒否の判断は維持しつつ、結果が見えるように |
| 🟠 全サービスが `replicas: 1` — 再起動・ノード交換のたびにダウンタイム | スケールしても安全な 8 種は **2**、状態を Pod に持つ chat・eureka は 1 固定 + ガードレール B-34 |

## 5. データ — パーティショニング・マイグレーション・性能

詳細: [docs/09](09-postgresql-partitioning-sharding.md) ・ [docs/19](19-local-performance-tuning.md) ・ [docs/20](20-schema-ownership.md)

| Before | After |
|---|---|
| 🔴 スキーマを Hibernate の `ddl-auto: update` が所有 — ①変更履歴がない ②本番 DB にレビューなしの DDL ③**制約を削除しない**（③はすでに事故を起こしていた — 下の色の項目） | **Flyway がすべてを所有**し、Hibernate は `validate` で検証のみ。ベースラインは手で書かず、Hibernate の DDL を[機械変換](../ops/tools/hbm2flyway.py) — 7 サービスすべてが空の DB で `validate` を通過することで実証、レガシー DB の再現環境では **184 個のスキーマ項目が不変**。逆戻りしたらガードレール B-33 が防ぐ |
| 🔴 Outbox テーブルの無限成長 | `created_at` による RANGE の月次パーティション — 古いパーティションを DETACH して、バックアップ/整理コストをアクティブ区間に比例させる |
| 🔴 **`ProductSku.color` が `@OneToOne`** — `color_id` のグローバル UNIQUE で SKU の総数が色の行数に縛られる。シードが 509=509 で制約を飽和させており、**商品を 1 件追加するだけでロード失敗**、色フィルターのファセットも無意味 | リポジトリのコードが一貫して共有の語彙を前提としている（`DISTINCT b.color`、`findByColor→Optional`、`ColorsFilter.jsx`、`ProductColor` のコメントアウトされた `@OneToMany`）ため、**マッピングの誤り**と判定 → `@ManyToOne` + [V4 マイグレーション](../catalog-service/src/main/resources/db/migration/V4__relax_product_sku_color_unique.sql)。制約を**名前ではなく定義**で探して削除し、消えるインデックスはエンティティの `@Table(indexes=)` で保全。回帰テストがアノテーション + `pg_constraint` の両方を検査 |
| 🟠 N+1 — 商品一覧が商品ごとに別クエリ | LAZY コレクション 4 種に `@BatchSize`、**SQL 件数の回帰テスト**で固定 |
| 🟠 コネクションプールが無制限という前提 | `datasource × pool × replicas ≤ max_connections` をガードレール（B-32）が算術的に検証 |
| 🟠 性能は推測 — シード 509 件ではインデックスの選択度が見えない | シード CSV を**分布を保ったまま増殖**（[生成器](../ops/tools/generate-catalog-data.py)）→ 5 万商品/55 万行で `EXPLAIN ANALYZE` を実測。名前検索が Seq Scan（8ms、48,800 行を破棄）であることを**数値で**確認 |
| 🟠 シャーディング戦略の不在 | 設計を文書化（適用は規模に達した時点で） |

## 10. 正直に: まだできていないこと

## 11. 2026-09 — 実務の基準に照らすと、何が足りず、何が不要だったか

### 11.1 セキュリティ — 足りなかったもの

| 問題（Before） | 実務の基準 | 変えたこと（After） |
|---|---|---|
| 🔴 **ログインした誰もが他人のメール・プロフィールを id で照会できた**（`/api/auth/user/email/{id}` など 3 つ、IDOR）。以前 `/user/id` 一つだけを塞いで兄弟を見落とし、判定も `User-Role` 一つしか見ていなかった | OWASP API1（BOLA）。内部専用 API は外部ルーティングから外すか別ポートに、サービス間は mTLS・サービストークン | 5 つのエンドポイントすべてに `InternalCallGuard.allowed`（3 つの身元ヘッダー）。拒否するときは存在しないユーザーと同じ 404。**残るギャップ**: ヘッダー判定は「サービスのポートが外部に開いていない」前提 — [docs/27 §9b・§14](27-security-review.md) |

| 🟠 漏洩した DB パスワードの生死を**知らなかった**。履歴スキャナーは JSON 形式を見られず「0 件」と報告 | 漏洩 = 即時破棄・交換、そして**実際に通用するかで確認**（値の比較ではなく）。スキャナー（gitleaks など）は形式ごとのルールを持つ | 対照群・陽性対照付きのログイン実測で死んだ値であることを確認。スキャナーに JSON ルールを追加（[docs/30 §6](30-git-history-secret-exposure.md)） |

| 🔴 **クーポンの発行・修正に権限チェックなし** — ログインした誰もが任意の割引率のクーポンを発行でき、決済の突合も通過 | 兄弟エンドポイントを全数確認、発行は管理者・システムのみ | 管理者専用（[docs/27 §5〜6](27-security-review.md)） |
| 🟠 退会が**chat のレプリカに届いていなかった**（メール・名前・写真が残存）、チャットの案内文にメール | 削除はレプリカまで伝播させ、表示名は識別子から派生させない | `user-deleted` の匿名化、案内・代替ニックネームからメールを除去（[docs/48 §6-⑤・⑥](48-user-replication-debt.md)） |

## 一行ずつの教訓

1. **「コンパイルできる」≠「起動する」、「起動する」≠「動作する」。** B-1〜14 は起動して初めて見え、B-13・19・24 は起動しても黙って壊れていた。
2. **最も高くつくバグはコードではなく設定にあり、レビューは設定を見られない。** だからガードレールテストがビルドのたびに見る。
3. **無効化したテストは、ないテストより悪い。** 常時赤の 6 件が本物の NPE 4 件を隠していた。
4. **検証していないバックアップ・可観測性・証明書は、ないのと同じである。** だから、すべて実際に事故を起こすか起動して確認した。
