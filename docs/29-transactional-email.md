# 29. トランザクションメール — 送信パイプラインを notification-service に集約する

**日本語** | [한국어](29-transactional-email.ko.md)

> 🕰️ **状態（2026-09-27）— 一部古い。** user-service の Outbox は現在動作しています(c31791a)。ただしメールの発行はまだ Outbox を経由しません。

分散メールサービス(別リポジトリ、System Design Interview Ch.23 の実装)の**送信側の半分**を
このプロジェクトに移植した記録である。メールボックス・Cassandra・MinIO・Elasticsearch は持ち込んでいない —
なぜそれらを持ち込まなかったかが、この文書の半分である。

---

## 1. 何が問題だったか

メールを送るコードが **user-service の中に、互いに異なる形で二組**あった。

| | 会員登録の確認メール | パスワード再設定メール |
|---|---|---|
| 場所 | `RegistrationListener` | `EmailService` |
| 形式 | MimeMessage、HTML + プレーンテキスト、UTF-8 | `SimpleMailMessage`、プレーンテキスト一行 |
| エンコーディング | 指定あり | **指定できない** — 韓国語の件名がクライアントによって文字化け |
| 非同期 | `@Async` + `AFTER_COMMIT` | **同期** — HTTP リクエストが SMTP の往復を待つ |
| リトライ | インプロセス 3 回、指数バックオフ | **なし** |
| 失敗すると | ERROR ログ一行、**メールは永久に消える** | `MailException` が上がり**リクエスト自体が 500** |

同じサービスが送る二つのメールの形が互いに違っていたこと自体がシグナルである。確認メールの方は
[docs/27](27-security-review.md) の作業時に一度手を入れたが、再設定メールは手を付けずそのまま
残っていた。**文面がコードの中に埋め込まれていると、こうしたずれは必ず生じる。**

さらに悪いことが二つあった。

**(1) 再設定メールの失敗はユーザーにとって最悪の状態を作る。** `EmailService` が投げた例外が
呼び出し元まで上がればトークン保存のトランザクションがロールバックされる — それならまだましだ。実際にはトークンを先に
保存し(`passwordResetTokenRepository.save`)、その後でメールを送っていたので、SMTP が失敗すると
**DB にはトークンがあるのにユーザーにはリンクがない**状態になった。

**(2) 通知チャネルが半分しかなかった。** notification-service は SMS 専用だった。`NotificationType`
に `smsWorthy` フラグがあり、ユーザーごとの受信設定もあるのに、**メールチャネル自体がなかった。** 注文
通知は SMS では届くのにメールでは届かず、受信拒否の設定も SMS にしか適用されなかった。

## 2. 移植したもの — そして移植しなかったもの

分散メールサービスから持ってきたのは**パターン一つ**である:

```
API サーバー → outgoing-mail トピック → mail-worker
                                  ├ 一時的な失敗 → リトライ
                                  └ 恒久的な失敗 → DLQ (リトライしない)
```

この構造こそ、このプロジェクトになかったものである。だからこれだけを持ってきた。

### 持ってこなかったものとその理由

| 持ってこなかったもの | 理由 |
|---|---|
| **Cassandra** (`emails`, `folders`, `unread_emails`) | メールボックスのドメインである。こちらはメールを**送るだけ**で保存しない |
| **MinIO** (添付ファイル) | トランザクションメールに添付ファイルはない |
| **Elasticsearch** (メール全文検索) | 上と同じ。検索するメールボックスがない |
| **受信 SMTP / IMAP** | こちらは送信専用である |
| **WebSocket リアルタイムプッシュ** | notification-service がすでにアプリ内通知で行っている |

新たに必要になったインフラは**ない。** Kafka も PostgreSQL もすでにある。24GB の MacBook で
Cassandra(ヒープをまともに割り当てれば 2~4GB)と MinIO をさらに立ち上げることが実質的な障壁だったが、
そのコストを一切払わずに必要なものだけを得た。

### 原本と違う作りにした箇所

原本の `OutgoingMailConsumer` は Spring Kafka の `@RetryableTopic` を使ってリトライトピック
(`outgoing-mail-retry-0/1/2`)を自動生成する。**ここではその方式を使わなかった。**

理由はこのリポジトリがすでに経験した問題である([docs/21](21-horizontal-scaling.md))。コンシューマーの中で
外部 I/O を行い、失敗をコンシューマーのリトライで処理すると、**リトライのたびに副作用がもう一度ずつ
起きる。** メールではそれがそのまま重複送信になる。リトライトピックはこの問題をブローカー側に移すだけで
解決しない — リトライレコードを消費した瞬間にまた `send()` を呼ぶ。

そこで SMS と同じ構造を選んだ。**コンシューマーは DB に書くだけで、別のディスパッチャーが状態を見て
送る。**

```
user-service ──publish──▶ outgoing-mail ──▶ OutgoingMailListener
                                                  │ (保存のみ)
                                                  ▼
                                            mail_message (PENDING)
                                                  │
                          MailDispatcher ◀────────┘  @Scheduled
                          FOR UPDATE SKIP LOCKED
                                │
                                ├ SENT      → 終了、params 削除
                                ├ RETRYABLE → 次の周期
                                └ FAILED    → 終了、params 削除
```

`FOR UPDATE SKIP LOCKED` は Outbox ポーラーと同じ理由である。ロックがないとレプリカ二つが同じ
行を拾い、**同じメールが二通**届く。確認メール二通は煩わしい程度だが、**パスワード再設定
リンクが二つ有効なのはセキュリティ問題である。**

## 4. 設計判断いくつか

### 4.1 本文をコマンドに載せない

`OutgoingMailRequest` は**種類と値だけ**を運ぶ。件名・HTML はない。

```json
{ "kind": "REGISTRATION_CONFIRM",
  "params": { "confirmationUrl": "https://..." },
  "locale": "ko-KR" }
```

発行者がレンダリングして送ると文面がサービスごとに散らばる — **まさに今直している問題**である。
SMS はすでに `SmsTemplates` 一箇所でレンダリングしており、商用のトランザクションメールサービス(SES・SendGrid)
のテンプレート方式も同じである。

### 4.2 `params` は資格情報である

これがこの設計で最も気を遣った部分である。

`confirmationUrl` はそのリンクだけでアカウントを有効化できる。`resetUrl` はパスワードを変更
できる。user-service はトークンを **SHA-256 ハッシュでのみ**保存しているが
([docs/27](27-security-review.md))、ここに原文のリンクが残っていれば、その防御が丸ごと無意味になる。

露出経路を一つずつ塞いだ。

| 経路 | 対応 |
|---|---|
| ログ | `OutgoingMailRequest.toString()` が params を**キー名だけ**残して伏せる。`MailMessage.toString()` も同じ。送信器は本文の長さだけを出力する |
| Kafka トピック | mTLS はすでに有効。**トピックの保持期間を短く取ること** — §6 参照 |
| DB (正常経路) | 終了状態(`SENT`/`FAILED`)に達した瞬間に `clearParams()` が NULL にする |
| DB (異常経路) | 最後まで送信されなかった行は 24 時間後に `scrubStaleParams()` が消す。リンク自体が 24 時間で失効するので、それ以降持っている理由がない |

行自体は残す。「なぜこのユーザーにメールが届かなかったか」は後からでも見られなければならない。消すのは
資格情報だけである。

**冪等キーにトークンを使わないこと**も同じ理由である。トークンをキーにすると、その値が
`mail_message.source_event_id` カラムとログに平文で残る。

### 4.3 一時的な失敗と恒久的な失敗

この区別が曖昧になると、どちらの方向にも壊れる。

- **すべてリトライ** → 存在しないアドレスに送り続ける。ハードバウンスが溜まると受信サーバーが
  **送信ドメインをスパムとして学習**する。正常なメールまで迷惑メールフォルダに行く。
- **すべて諦める** → メールサーバーが少し揺らいだだけなのに、ユーザーは確認メールを永久に受け取れない。

`SmtpMailSender.classifyOne` は**確実なシグナルから**見る。

1. **SMTP 応答コード** — あれば最も正確である。5xx は恒久的、4xx は一時的
2. **`SendFailedException.getInvalidAddresses()`** — サーバーが「このアドレスは無効だ」と言ったもの
3. **ネットワーク例外** — `ConnectException` / `SocketTimeoutException` / `UnknownHostException` は明らかに一時的

1 番は**リフレクションで読む。** コードを持っている `SMTPSendFailedException` は jakarta.mail の
*API* ではなく実装(Angus Mail)のクラスなので、コンパイル時に参照すると実装を差し替えられ
なくなる。かといって諦めると、4xx/5xx を区別する最も正確な根拠を失う。そこで**あれば使い、
なければ次の根拠に移る**形で読む。

### 4.4 リトライ上限が SMS より大きい (5 回 vs 3 回)

SMS は試行のたびに料金がかかるので 3 回が妥当である。メールはそうではないし、もっと重要な理由がある —
**グレイリスティング**。一部の受信サーバーは初めて来た送信者をわざと一度拒否してリトライを待つ
(スパムボットはリトライしないという前提)。上限が小さいと、そうしたサーバーには最初のメールが永久に届かない。

### 4.5 受信拒否で止められないメール

`MailKind.isTransactional()` が区別する。

登録確認とパスワード再設定は**ユーザーがたった今自分で要求した結果**である。これを受信拒否で止めると
ユーザーが自分でアカウントに入れなくなる — 受信拒否の趣旨と正反対である。韓国の情報通信網法・日本の
特定電子メール法が求める受信同意も**広告**メールに対するものであって、本人が要求した情報提供
メールに対するものではない。

セキュリティ通知(`SECURITY_ALERT`)が設定を無視するのは別の理由である: 攻撃者が先に通知をオフに
してから作業できてはならない。SMS も同じルールである。

逆方向もある。**チャットメッセージと友達のログインはメールで送らない。** 活発な会話一つが
メールボックスを数十通で埋め、それはユーザーにとってスパムであり、受信サーバーがこちらをスパム送信者として
学習する原因になる。

### 4.6 メールアドレスをどこから得るか

notification-service にはユーザーテーブルがない。経路は三つあった。

1. **毎回 user-service に問い合わせる** — 通知ごとに同期呼び出しが付く
2. **ユーザー作成イベントを購読して複製する** — 正攻法だが、既存ユーザーは埋まらない
3. **ゲートウェイが付ける `User-Email` ヘッダー** ← 採用

3 番を使う。そのヘッダーはゲートウェイが JWT から取り出して付け、クライアントが送った同名のヘッダーは
ゲートウェイが削除する([docs/27](27-security-review.md)) — 偽造できない。ユーザーが通知一覧
(`GET /api/notifications`)や設定画面を一度でも開けば埋まる。

**限界は明確である。** ログイン後に通知 API を一度も呼んでいないユーザーには通知メールが
送られない。登録確認・パスワード再設定はアドレスがコマンドに載って来るので影響を受けない。

バッジ照会(`/unread-count`)にはこの記録を入れなかった。画面ごとに呼ばれる経路なので、照会が一つ
増える。

### 4.7 デフォルトの送信器が `logging` である理由

SMS と同じ形だが根拠が違う。SMS は件数課金なので「知らないうちに料金がかかる」ことが
問題だった。メールはたいてい無料だが、**取り消せず評判が残る** — 設定が不十分なままデプロイされ、
テストデータのアドレスにメールが送られると、そのハードバウンスが送信ドメインにそのまま溜まり、一度
スパムに分類されたドメインを元に戻すには数週間かかる。

`MailConfig` は `provider=smtp` なのに `from` が空だと**起動を止める。** From が空だと
JavaMail が SMTP アカウントのアドレスで代替するが、そうすると SPF/DKIM のアラインメントが崩れて正常なメールがスパムに
分類される。

## 5. 残っていること (正直に)

### 5.1 発行失敗の窓 — user-service の Outbox が死んでいる

`OutgoingMailProducer.publish()` が失敗すると(ブローカーに到達できないと)メールは依然として消える。
以前より窓がずっと狭くなっただけである — 同じクラスタ内のブローカーに書き込むことと外部の SMTP プロバイダーに
往復することでは、失敗確率が違う。

この窓を完全に閉じるには、ユーザー保存と**同じトランザクション**にメールリクエストを書かなければならない。
user-service に Outbox があるにはある:

- `message/model/OutboxEvent` — エンティティあり
- `message/repository/jpa/OutboxEventRepository` — リポジトリあり
- `message/OutboxScheduler` — **インターフェースだけで実装がない**
- `UserServiceImpl:510` — `//outboxEventRepository.save(event);` **コメントアウトされている**

つまり**殻だけあって動作しない。** order-service・pay-service には動作するリレーが
あるので(`PaymentOutboxScheduler`, `OrderOutboxScheduler`)、それを手本に復活させればよい。
今回の作業範囲外なので手を付けなかった。

### 5.2 バウンス処理がない

`SENT` は「こちらの MTA が受け付けた」までしか意味しない。受信箱への到達は**バウンスメールとフィードバックループ**を
受け取って初めて分かる。SMS の DLR と同じ構造で、一緒にロードマップに残る。

これがないと「送ったと表示されるのに届かない」を追跡できない。状態名がその事実を隠さない
よう、`SENT` の意味をコードのコメントとこの文書に明記しておいた。

### 5.3 トピックの保持期間

`outgoing-mail` トピックには有効な確認リンクが流れる。**保持期間を短く取らなければならない。**
トークンは 24 時間で失効するので、それより短ければ十分である。

```bash
kafka-configs --alter --entity-type topics --entity-name outgoing-mail \
  --add-config retention.ms=3600000   # 1時間
```

DLT(`outgoing-mail.DLT`)も同じである。

### 5.4 フロントエンドの受信拒否 UI

`PATCH /api/notifications/preferences` が `emailEnabled` を受け取る。
`notificationApi.updatePreferences(patch)` がそのまま通すので API は準備できているが、
設定画面自体がまだない。

## 6. デプロイ順序

1. **notification-service が先。** V3 マイグレーションが `mail_message` を作り、
   `outgoing-mail` コンシューマーが起動する。
2. **その次に user-service。** 先に上げると、発行したメッセージを受け取るコンシューマーがない。トピックに溜まって
   いて後で処理されるので消失ではないが、その間に登録したユーザーは確認メールを遅れて受け取る。
3. トピックの保持期間の設定 (§5.3)。
4. 実際の送信を有効にするとき: `MAIL_PROVIDER=smtp` + `MAIL_FROM` + `MAIL_HOST`/`MAIL_USERNAME`/
   `MAIL_PASSWORD` (k8s/47, k8s/20-secret)。**三つのうち一つでも欠けると起動が失敗する** —
   中途半端に設定された状態で黙って動くよりましである。

`MAIL_HOST` は user-service の Secret から notification-service に**移された。** メールを
実際に送る側が接続情報を持つのが正しい。

全区間テスト(`MailChannelIntegrationTest`)が検証するのはロジックではなく**継ぎ目**である。
user-service が作る `OutgoingMailRequest` を実際に Jackson でシリアライズしてリスナーに入れる —
フィールド名が一つでもずれればここで引っかかる。この契約は二つのサービスが**別々にデプロイされるので**
コンパイラが守ってくれない。

### 作業中に起動テストが捕まえたバグ

`MailConfig` の Bean 名を `mailSender` にしたところ、Spring Boot の
`MailSenderPropertiesConfiguration` が同じ名前で `JavaMailSenderImpl` を登録し、
`BeanDefinitionOverrideException` で**アプリケーションがまったく起動しなかった。**
`notificationMailSender` に変えて解決した。

一緒に明らかになったこと: Boot の条件は「`spring.mail.host` プロパティが存在するか」だが、yml が
`${MAIL_HOST:}` のように空のデフォルト値を与えると、**空文字列も「存在」とみなされる。** そのため JavaMailSender
Bean は作られるがホストがない。`MailConfig` がホストを別途チェックするようにした — そうしないと
`provider=smtp` で有効にしたとき、毎回の送信が不明なエラーで失敗し、キューだけが溜まる。

## 7-1. 本番で明らかになったこと — 「成功したのに届かない」の解剖

再デプロイ後、「登録はできたのにメールが届かない」という報告が入った。追跡してみると**バグが三つ**あり、
三つともそれぞれは静かだった。静かな失敗が重なると、症状が一つにしか見えないというのが要点である。

### ① 埋めていない設定が起動チェックを通過した

`k8s/20-secret.example.yaml` をコピーして使いながら `MAIL_HOST` を埋めなかった。その値
`"REPLACE_ME_smtp_host"` は**空ではないので** `isBlank()` チェックを通過し、サービスは
こう出力して正常に起動した:

```
INFO  c.p.n.config.MailConfig - 메일 발송기: smtp (실제 발송) from=…
```

**空の設定は止めるのに、埋めていない設定は通してしまったことが問題だった。** 後者のほうがはるかによくある
ミスなのにそうだった — 空にするには消す必要があるが、埋めないのは何もしなければよい。

→ `Placeholders.rejectUnfilled` が `REPLACE_ME` を起動時点で捕まえる。失敗の時点が原因に
近いほど Pod が CrashLoopBackOff で目立ち、メッセージがどのキーなのかをすぐに教えてくれる。
🔒 メッセージには**キー名だけ**を入れる — このチェックが見る値には `MAIL_PASSWORD` が混ざっており、
例外メッセージはログに出る。

### ② 🔴 リトライ予算が 20 秒で燃え尽きた — リトライは名ばかりだった

`MailDispatcher` は上限を 5 回とし、その理由をコメントに書いておいた:

> グレイリスティングを使う受信サーバーは、初めて来た送信者をわざと一度拒否してリトライを待つ —
> 上限が小さいと、そうしたサーバーには最初のメールが永久に届かない。

ところが**行ごとのバックオフがなかった。** `claimForSend` は上限に達していない行を 5 秒ごとに無条件で再び
拾っていた。本番のログがそのまま示している:

```
04:12:10 [MAIL:retryable] … 04:12:15 … 04:12:20 … 04:12:25 … 04:12:30 재시도 상한 도달, 포기
```

グレイリスティングは通常**数分**待たないと解除されない。**コメントが防ぐと言っていたまさにその失敗がそのまま
起きた。** SMS も同じ形だった(3 回 × 5 秒 = 15 秒)。

**上限は「何回」で、バックオフは「いつ」である。どちらか一方だけではリトライは無意味である** — 同じ
瞬間に五回叩くのは一回叩くのと結果が同じで、原因が一時的であるほどそうである。

→ `V5__retry_backoff.sql` が `next_attempt_at`(メール)・`sms_next_attempt_at`(SMS)を追加し、
先取りクエリが `(… is null or … <= :now)` で絞り込む。間隔は試行ごとに二倍になる —
メール 1・2・4・8 分(窓 ≈15 分)、SMS 30 秒・1 分。`is null` を併せて見ることは省略できない:
新しい行とこのカラムがなかった頃の行はどちらも null なので、抜かすと**それらの行が永久に選ばれない。**

### ③ 諦めるときに試行回数を二度数えていた

`recordAttempt(RETRYABLE)` の後に `recordAttempt(FAILED)` を呼んでいたため、一回の送信が二回として
記録された。`attempts` が上限より 1 大きい値で残り、後から見る人が上限を超えたものと
読んでしまう。→ 試行回数を増やさない `giveUp` / `giveUpSms` を別に用意した。

### なぜこの三つが一つの症状にしか見えなかったか

| 段階 | そのとき見えたもの | 実際 |
|---|---|---|
| 起動 | `메일 발송기: smtp (실제 발송)` | ホストがプレースホルダー |
| キュー登録 | `메일 큐 등록: kind=REGISTRATION_CONFIRM` | 正常 |
| 送信 | (ERROR ではない) WARN 5 行、25 秒 | DNS 解決の失敗 |
| 結果 | `mail_message.status = FAILED` | 誰も見ていない |

どの段階も嘘はついていなかったが、どの段階も**探しに行かなければ見えなかった。**
`LoggingMailSender` が dry-run でも `MailResult.sent()` を返すこと(§5)と同じ種類の
問題である — 成功に見える失敗が最も長生きする。

## 7-2. メールが届かなかったときにユーザーが抜け出す道

上の三つを直せば今回の症状は消える。それでもメールは**いつか必ず**届かない —
迷惑メールフォルダに入り、受信サーバーが拒否し、ユーザーがアドレスを打ち間違える。そのときユーザーが自分で
抜け出せるかを点検したところ、バックエンドはすべてできているのに**画面がなかった。**

### 何がなかったか

| | 状態 |
|---|---|
| `POST /api/auth/public/resend-verification` | 実装済み。**フロントから呼んでいる箇所 0 件** |
| `/verification-failed?reason=…` リダイレクト | サーバーが送る。**フロントにルートなし** → ルーターのエラー画面 |
| `/signin?verified=1` | サーバーが送る。**誰も読まない** → 認証成功が分からない |

ログイン失敗の文言は「확인 메일 재발송을 이용해 주세요」と案内しているのに、利用する画面が
なかった。リンクは 24 時間で失効し、同じアドレスでの再登録もブロックされるので、メールを受け取れなかったアカウントは
**袋小路**だった。`/forgot` ルートがなくてパスワードを取り戻せなかったのと同じ種類の穴である。

→ `ResendVerification` コンポーネントを作り、`/verification-failed` 画面とログイン失敗の箇所の
両方に付けた。`?verified=1` も読んで成功を知らせる。

### 🐛 そしてステータスコード一つがユーザーに嘘をつかせていた

`POST /api/auth/public/register` の重複チェックが **`200 OK`** を返していた。フロントの
`useMutation` は 2xx を成功とみなすので `onSuccess` が実行され、画面には
**「인증 메일을 보냈습니다」**のトーストが表示された後、ログイン画面に遷移した。本文に入っていた
`"The same user Id exists"` は誰の目にも触れなかった。

サーバーは事実を語っていたが、**その事実が届きようのない場所に置かれていた。** 409 に変え、
文言も英語の診断文から「이미 가입된 이메일입니다. 로그인해 주세요. 가입 확인 메일을 받지
못했다면 확인 메일 재발송을 이용해 주세요.」に変えた — 今は実際にユーザーが読む。

### 漏洩について

- **登録エンドポイントはアドレスの登録有無を明かす。** 防ぐには「확인 메일을 보냈습니다」とだけ
  答え、既存ユーザーには案内メールを送るフローが必要だが、そうするとタイプミスで他人のアドレスを
  入れた人が、なぜ登録できないのか永久に分からない。代償のほうが大きいと判断して明かすことにしたが、
  **認証済みかどうかは区別しない** — 未認証アカウントかどうかを教えれば、それは新たな漏洩である。
- **再送エンドポイントは何も明かさない。** 未登録・認証済み・未認証のいずれも同じ 200 と
  同じ文言である。だから画面も「送ったかどうか」を推測せず、サーバーの文言をそのまま使う。
- **ログイン失敗の `code` はパスワードが合った後にだけ返される。** 画面が再送フォームを出すかどうか
  決めるにはシグナルが必要だが、韓国語の文言を比較すると、文言を手直しした瞬間に黙って壊れる。
  そこで `code: "email_not_verified"` を返すが、`DisabledException` にだけ付ける —
  他の失敗にも付くと、その値一つで「登録済みでまだ未認証」が分かってしまう。

### メールゲートを有効にする順序

`APP_REQUIRE_EMAIL_VERIFICATION` のデフォルト値は **`false`** で、そのため今は登録と同時に
`enabled = true` である — 確認メールは送られるが何もブロックしない。有効にするときは順序が重要である:

1. `MAIL_*` を埋めて、**実際にメールが届くことを確認**
2. その後で `APP_REQUIRE_EMAIL_VERIFICATION=true`

逆にすると新規登録者が全員ロックされる。非常口は
`UPDATE users.users SET enabled = true WHERE email = '...';` である。

> 参考: `users.email_verified` カラムは**誰も読みも書きもしない死んだカラム**である。
> 実際のフラグは `enabled` である。

## 7-3. パスワード再設定 — 両端とも切れていた

登録確認の経路を直したついでに隣の経路を点検したところ、**パスワード再設定は最初から最後まで
動作したことがなかった。** メールが送られていなかったせいで隠れていただけである。

```
ForgotPage ──▶ /forgot-password ──▶ メール ──▶ /reset-password?token=… ──▶ ???
                 ✗ リクエスト形式の不一致                   ✗ その画面がない
```

- **リクエストが通っていなかった。** コントローラーは `@RequestParam String email` なのに、画面は
  `application/json` ボディで送っていた。`@RequestParam` はクエリ文字列・フォームしか読まないので、常に
  **400 "Required request parameter 'email' is not present"** だった。
- **リンクを押しても行き先がなかった。** フロント全体に `reset-password` という文字列が **0 件**。
  `/forgot`・`/verification-failed` と同じ種類の穴である。

### そして保護レベルが逆さまだった

|  | 登録確認トークン | パスワード再設定トークン (before) |
|---|---|---|
| 保存 | SHA-256 ハッシュ | 🔴 **平文** |
| ユーザーあたり | 1 個 (`user_id` UNIQUE + `refresh()`) | 🔴 要求するたびに新しい行 |
| 列挙防止 | すべての場合で同じ 200 | 🔴 未登録 → **500**、登録済み → **200** |
| できること | アカウントの有効化 | **アカウント乗っ取り** |

**より強力なトークンがより弱く保護されていた。** DB ダンプ一回で有効な再設定リンクが
すべて露出し、そのリンク一つでアカウントを奪える。列挙の問題も `resend-verification`
では念入りに防いでおきながら、肝心のパスワード再設定に穴が開いていた。

→ `V10__password_reset_hardening.sql` + `PasswordResetToken.hash()`。平文の行はマイグレーションが
削除する — 死んだ行として残すと**平文の資格情報が DB に残る**(失うものはない: それらのリンクは
画面がなかったので、そもそも使えなかった)。

### 🐛 ログイン状態での変更は失敗を成功と報告していた

```java
if (passwordEncoder.matches(currPassword, user.getPassword())) {
    user.setPassword(...);  userRepository.save(user);
}
// else がない — そのまま抜ける
```

戻り値の型が void なので、コントローラーはそのまま `200 "Password updated"` を返していた。**現在のパスワードを
間違えて入れると何も起きないのに、成功と答えていた。** ユーザーは次のログインで初めて
気づき、そのときには何が悪かったのか分からない。レスポンスが素の文字列なので、画面の
`data.message` が常に undefined だったことも併せて直した。

### セッション無効化 — なぜ時刻でフィルタするのか

パスワードを変えても**既存のセッションが生きていた。** 取り戻しに来る人の半分はアカウントを
盗まれて来るのであり、攻撃者のセッションが残っていれば取り戻したことにならない。

トークンを探して消す方法は、この構造では使えない:

- リフレッシュトークンは Redis に **sessionId でのみ**保存されており、「このユーザーのすべてのセッション」を逆引きで
  探せない。
- `RedisSessionManager` は名前に反して**インメモリの `HashMap`** なので、レプリカごとにばらばらに動く。

そこで `users.password_changed_at` を設け、**それより前に発行された**リフレッシュトークンを
`RefreshTokenController` が拒否する — DB 一箇所だけを見るので、レプリカ数とは無関係である。

> ⚠️ アクセストークンは署名だけで検証されるので、残りの寿命(デフォルト 15 分)の間は生きている。その後
> 更新がブロックされてログアウトされる。**即時遮断ではない** — 完全な即時遮断はすべてのリクエストごとに DB を
> 見る構造でなければならず、そのコストはこのサービスに合わない。
>
> ⚠️ カラムのデフォルト値を `now()` にしない。そうしていたらデプロイの瞬間に**全員がログアウトされる。**
> null は「一度も変更したことがない」であり、どのトークンも拒否しない。

### 運用メモ

管理者アカウントのパスワードは画面ではなく `ops/30-admin-account.sh password <이메일>` で
再設定する — 対話型入力で、argv・ログ・一時ファイルのどこにも平文を残さず、アプリと同じ
BCrypt(strength 10)でハッシュ化する。このスクリプトも `password_changed_at` を併せて設定するよう
直した: 抜かすとこの経路でだけ既存セッションが生き残り、アプリと動作が食い違うが、アカウントを盗まれて
管理者が代わりに変えてあげる状況こそ、このスクリプトを使うケースである。
