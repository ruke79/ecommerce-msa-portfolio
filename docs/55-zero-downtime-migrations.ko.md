|---|---|---|---|---|

## 1. 왜 여러 릴리스인가 — 이 클러스터의 배포가 가진 성질

| 성질 | 어디서 | 그래서 생기는 일 |
|---|---|---|
| 롤링 업데이트, 레플리카 1개 | k8s Deployment | 새 파드가 준비될 때까지 **옛 파드와 새 파드가 함께 돈다** — 몇 초가 아니라 기동·Flyway·Eureka 등록·Kafka 합류 동안(최대 5분, `k8s/4x-*.yaml` 의 startupProbe) |
| 서비스를 거의 동시에 교체 | `ops/28-deploy.sh` (user-service 먼저, gateway 나중, 나머지는 한꺼번에) | "읽는 쪽 먼저 배포" 를 **순서로 지킬 수 없다** |
| 기동할 때 Flyway 가 마이그레이션 | `application-common.yml` | 새 파드의 마이그레이션이 도는 순간, **옛 파드는 아직 그 DB 로 요청을 처리 중**이다 |
| Hibernate `validate` | 같은 곳 | 엔티티가 매핑한 컬럼이 없으면 기동 실패. 그리고 매핑한 컬럼은 **모든 SELECT 에 들어간다** |
| Avro 단일 객체 인코딩, 레지스트리 없음 | `common/.../kafka/avro/` | 레코드에 작성 스키마의 **지문**이 붙고, 읽는 쪽은 **아는 지문만** 읽는다. 필드 하나만 바꿔도 지문이 바뀐다 |
| 실패한 메시지는 DLT 로 | `KafkaDltConfig`, DLT 보존 14일(`ops/13`) | 못 읽은 레코드는 사라지지 않지만 **처리되지도 않는다** — 결제 요청이면 결제가 반영되지 않는다 |
| saga-projection 은 못 읽는 레코드에서 멈춘다 | 예전: Kafka Streams 기본값. 지금: 모르는 작성 스키마일 때만(§8) | 롤링 중이면 새 파드가 이어받는다. 깨진 레코드는 건너뛴다 |

그래서 "옛 것과 새 것이 섞이는 몇 분" 이 모든 전환의 설계 조건이다. 섞이는 방향은 셋이다.

| 축 | 옛 파드 ↔ 새 파드 사이에서 깨지는 것 | 깨지는 모양 |
|---|---|---|
| **DB 스키마** | 새 파드가 컬럼을 지우면 옛 파드의 SELECT · 옛 파드가 옛 컬럼에만 쓰면 새 파드는 못 본다 | 주문 조회 전부 500 · 결제 이중 발행 |
| **메시지 스키마** | 새 프로듀서의 지문을 옛 소비자가 모른다 | 결제 요청 DLT · 스트림 정지 |
| **서비스 간 API** | 새 호출자가 새 헤더만 보내면 옛 피호출자는 401 · 그 반대 | 주문 생성·쿠폰 견적 실패 |

해법은 하나다 — **expand-contract**. 넓히기(둘 다 받는다) → 옮기기 → 좁히기(새 것만). 좁히기는 **반드시 다른
릴리스**다. 이 문서의 모든 시나리오는 이 원칙을 세 축에 각각 적용한 것이다.

## 2. 시나리오 ① 신원: 이메일 → 사용자 id (R1 → R2)

### 왜

신원이 이메일이었다. 서비스마다 "이메일 → id" 를 user-service 에 다시 물었고, 그 호출에 쓸 **사용자 토큰을 Kafka
메시지와 URL 에** 실었다. 본문의 이메일을 믿는 엔드포인트(`/savecart`, `/applycoupon`)는 남의 것을 건드릴 수 있었다.
토큰의 `uid` 는 게이트웨이가 이미 `User-Id` 헤더로 넘기고 있었다 — **토큰이 나르는 것을 다시 묻지 않는다.**

### 과정

**R1 — 넓히기 + 옮기기.** 받는 쪽은 새 것(`User-Id`)을 읽고, 보내는 쪽은 옛 것까지 함께 보낸다.

| 전환 코드 | 누구를 위해 | 없으면 |
|---|---|---|
| `getCartDuringRollout` — `User-Id` 와 옛 `User-Email` 을 함께 | 새 order·coupon → **옛 cart** | 옛 cart 가 401 → 주문 생성·쿠폰 견적 실패 |
| coupon 견적의 이메일 대체 경로 + order 가 `email` 도 보냄 | 옛 order → 새 coupon, 새 order → 옛 coupon | 견적 실패 → 주문 생성 실패 |
| user-service `/user/segments` 가 `userId`·`email` 둘 다 | 옛 coupon → 새 user-service | 기획전 대상 판정 실패 |
| `LegacyAuthorizationHeader`(`Authorization: Bearer none`) | 옛 pay·order 의 "헤더가 **있는가**" 검사 | 결제 요청·응답이 DLT |
| chat 기동 백필 + `chat.legacy_sender_email`(V5 가 옮겨 둔 매핑) | 몽고의 옛 메시지(발신자가 이메일) | 옛 대화의 발신자를 영영 모른다 |

chat V5 는 `member.email` 을 지우는데 **백필보다 먼저** 돈다(Flyway 는 기동 전, 백필은 기동 후). 그래서 매핑을 전용
테이블로 옮긴 뒤 컬럼을 지웠고, 백필은 몽고에 이메일이 하나도 남지 않으면 그 테이블을 비운다 — 두 번 배포하고 사람이
확인할 일을 코드가 순서대로 한다.

**R2 — 좁히기.** 전환 코드를 전부 지우고, 롤백용으로 남겨 둔 테이블 둘(`chat.legacy_sender_email`, `orders.customer`)을 지운다.

### 🔴 chat V6 — 데이터로 확인하는 가드

매핑 테이블에 행이 남아 있다 = 백필이 끝나지 않았다(R1 을 건너뛰었거나 백필이 몽고에 닿지 못했다). 그때 지우면 옛
발신자를 영영 되찾지 못한다. 그래서 V6 는 **행이 있으면 지우지 않고 예외로 실패**한다. PostgreSQL 은 DDL 도
트랜잭션이라 아무것도 바뀌지 않고, 새 파드가 준비되지 못해 옛 파드가 계속 돈다.

🐛 PG16 에 직접 적용해서 잡은 버그: 처음 쓴 `IF to_regclass(...) IS NOT NULL AND EXISTS (SELECT 1 FROM 그테이블)` 은
**테이블이 없는 새 DB 에서 실패**했다. PL/pgSQL 은 조건식 전체를 한 번에 계획하므로 `AND` 가 단락 평가되기 전에
"relation does not exist" 가 난다. 중첩 `IF` 로 고쳤다. 단위 테스트로는 절대 보이지 않는 종류다.

### 알려진 창 — R1 의 메시지 스키마

R1 은 일곱 토픽의 스키마를 바꿨다(`order`·`product-update`·`cart-empty`·`cart-rollback`·`coupon-use`·`chat`·
`user-created` — 토큰·이메일 제거). **이때는 아래 §4 의 "옛 작성 스키마로 쓰기" 를 몰랐다.** R0 의 소비자는 새 지문을
모르므로, R1 의 롤링 중에 쓰인 레코드 일부는 DLT 로 간다. 데이터는 잃지 않는다 — **R1 배포 뒤 일곱 토픽의 DLT 를
재처리한다**(docs/11 §3, 처리는 멱등하다). saga-projection 은 모르는 스키마에서 멈췄다가 새 파드로 교체되며 그 레코드부터
다시 읽는다(§8).

## 3. 시나리오 ② order 의 옛 결제 컬럼 `paypal_order_id` (R2 → R3)

### 왜

결제수단을 넓힐 때(V4) PayPal 전용 컬럼을 이름만 바꾸지 않고 제공자 중립 컬럼 둘을 **더했다** — rename 은 롤백을 깨고,
유니크 인덱스가 걸린 컬럼이라 더 위험했다. 그 뒤로 코드는 두 컬럼에 모두 쓰고 모두 읽었다. 옛 컬럼을 치울 차례였다.

### 과정 — 왜 한 번에 지우지 않나

"다음 릴리스에 지운다" 를 한 번에 하면 **같은 창이 반대 방향으로 열린다.** 컬럼을 지우는 새 파드의 Flyway 가 도는
순간, 옛 파드는 그 컬럼을 매핑하고 있고 Hibernate 는 매핑한 컬럼을 모든 SELECT 에 넣는다 → **주문 조회가 전부 실패**.

| 단계 | 릴리스 | 한 일 | 되돌리기 |
|---|---|---|---|
| 1 | R2 (`8f4a131`) | 엔티티가 옛 컬럼을 **매핑하지 않는다**. 멱등 검사·결제된 주문 취소 거절·환불 알림이 새 컬럼만 본다. **V17** 이 옛 컬럼에만 남은 값을 옮긴다(V4 의 롤링 중 옛 이미지가 쓴 행) | 안전 — 복사뿐, 옛 이미지는 두 컬럼을 다 본다 |
| 2 | R3 (`b655c81`) | **V18** 이 컬럼과 인덱스를 지운다 | `ROLLBACK-UNSAFE` |

1단계가 핵심이다: **"코드가 안 쓴다" 와 "컬럼이 없다" 를 다른 릴리스에 둔다.** 1단계의 롤링 중 옛 파드는 두 컬럼에
쓰고, 새 파드는 새 컬럼만 쓴다 — 둘 다 문제없다. 2단계의 롤링 중 옛 파드는 1단계라 그 컬럼을 매핑하지 않는다.

### 🔴 order V18 — 시간으로 확인하는 가드

2단계가 안전한 조건은 "1단계가 **이미** 다 굴러갔다" 인데, 이것은 데이터로 드러나지 않는다. 대신 **Flyway 이력**에
드러난다: V17 의 `installed_on` 이 **이번 실행에서 막** 찍혔다면 1단계와 2단계가 한 배포로 올라온 것이다.

```
V17 적용 시각 > 이 DB 의 첫 마이그레이션 + 10분   -- 이미 운영 중이던 DB 이고
    그리고 > 지금 − 30분                          -- 방금 적용됐다
→ RAISE EXCEPTION (지우지 않는다)
```

- 새 DB(모든 마이그레이션이 한 번에 도는 경우)는 첫 마이그레이션과 V17 이 붙어 있어 통과 — 옛 파드가 없다.
- 이력 테이블이 없으면 통과(fail-open) — 가드는 보조 장치다.
- 실패하면 새 파드가 뜨지 않는다. 30분 뒤 다시 배포하면 통과한다.
- PG16 에서 네 경우 확인: 건너뜀 → 거부·컬럼 남음 / 1단계 2시간 뒤 → 삭제 / 새 DB → 통과 / 이력 없음 → 통과.

## 4. 시나리오 ③ pay 의 제공자 중립화 + 결제 요청 v3 (R2 → R3)

### 왜

`pay.payment` 는 PayPal 참조만 적었다. 🐛 그리고 조사해 보니 **다른 제공자의 참조는 전해지지도 않았다** — 결제 요청
DTO 에는 `paymentProvider`·`providerPaymentId` 가 있었지만 **Avro 스키마에 그 필드가 없어** 릴레이 경로에서 매핑이
조용히 버렸다. 컴파일도 테스트도 통과하는 종류의 어긋남이다.

그래서 DB 컬럼(pay)과 메시지 스키마(order → pay) **두 축을 동시에** 넓혀야 했다.

### 메시지 스키마에 필드를 더하기 — "읽기는 새 것, 쓰기는 옛 것"

필드를 더하면 지문이 바뀐다. 새 order 가 곧바로 v3 로 쓰면 롤링 중 옛 pay 는 결제 요청을 **DLT 로** 보내고(결제가
반영되지 않는다) 옛 saga-projection 은 **멈춘다.** 배포 순서로 "읽는 쪽 먼저" 를 지킬 수 없으니, 한 릴리스 안에서
읽기와 쓰기를 떼어 놓는다.

| 릴리스 | 생성 클래스 | order 가 쓰는 스키마 | 소비자가 아는 스키마 |
|---|---|---|---|
| R2 (A) | v3 | **v2** — `new BinaryMessageEncoder<>(SpecificData.getForClass(..), v2스키마)` | v1 · v2 · **v3** |
| R3 (B) | v3 | **v3** | v1 · v2 · v3 |

A 에서 v3 레코드를 v2 스키마로 쓸 수 있는 이유: 새 필드를 **끝에만** 붙였다. v2 필드의 위치가 같으니 인코더가 위치로
값을 꺼내도 맞다(새 필드만 빠진다). 테스트가 "v2 만 아는 제네릭 디코더가 새 order 의 바이트를 읽는다" 를 고정한다.

### DB 는 order 와 같은 두 단계

| 단계 | pay | 되돌리기 |
|---|---|---|
| A (R2) | **V5** — 컬럼 둘 추가, `payment_type` 에서 제공자(CASH → BANK_TRANSFER), `paypal_order_id` 에서 참조를 옮긴다. 엔티티는 새 컬럼만 매핑. 제공자 필드가 없는 v2 레코드면 결제수단·PayPal 참조에서 정한다 | 안전 |
| B (R3) | **V6** — A 의 롤링 중 옛 파드가 쓴 행을 **한 번 더** 옮기고 컬럼을 지운 뒤, 컬럼과 함께 사라진 `idx_payment` 를 다시 만든다. V18 과 같은 시간 가드(V5 기준) | `ROLLBACK-UNSAFE` |

"한 번 더 옮긴다" 가 중요하다 — 넓히기 마이그레이션이 옮긴 **뒤에도** 롤링 중 옛 파드는 옛 컬럼에만 쓴다. 좁히기
직전의 재이관이 그 창을 닫는다.

**가드 하나가 두 위험을 막는다.** R3 에서 order V18 이 실패하면 새 order 파드가 뜨지 않는다 → **v3 레코드도 나가지
않는다.** DB 가드가 메시지 스키마의 순서까지 지킨다(쓰는 쪽이 order 이기 때문에 가능한 일이다).

## 5. 시나리오 ④ 결제 요청에서 필드 빼기 — v4 (R3 → R4 → R5)

### 왜 방향이 반대인가

필드를 **뺄 때**는 §4 의 수가 통하지 않는다. `paypalOrderId` 는 4번째 필드라, 빼면 **뒤 필드의 위치가 모두 밀린다** —
v4 클래스를 v3 스키마로 쓰면 값이 엉뚱한 칸에 들어간다. 그래서 반대로 간다: **생성 클래스는 옛 것(v3)으로 둔 채, 다음
스키마 v4 를 디코더 저장소에 먼저 넣는다.**

| 릴리스 | 생성 클래스 | order 가 쓰는 스키마 | 소비자가 아는 스키마 |
|---|---|---|---|
| R3 (C1) | v3 | v3 | v1 · v2 · v3 · **v4**(`avro-next/`) |
| R4 (C2) | **v4** | **v4** | v1 · v2 · v3(`avro-history/`) · v4 |

저장소는 지문으로 작성 스키마를 찾을 뿐이라 "옛" 과 "다음" 을 구분하지 않는다. 읽을 때는 Avro 의 스키마 해석(v4 → v3)이
빠진 필드를 기본값으로 채운다. `avro-next/` 의 v4 는 손으로 둔 파일이라, 지금 스키마에서 `paypalOrderId` 만 뺀 것인지
테스트가 **정규형으로** 대조한다(생성 클래스의 스키마에는 `avro.java.string` 같은 속성이 붙어 있어 그냥 비교하면 다르다).

### 🔴 릴리스 표지 — DB 를 바꾸지 않는 릴리스의 가드

C2 의 가드는 "C1 이 이미 배포됐는가" 를 알아야 하는데 C1 은 DB 를 바꾸지 않는다. 그래서 **아무 일도 하지 않는
마이그레이션**(order **V19**, `SELECT 1`)을 두었다 — Flyway 이력의 적용 시각이 곧 C1 의 배포 시각이다. C2 의 **V20**
(가드 전용)이 그것을 V18 과 같은 방식으로 본다. 두 파일 모두 아무것도 바꾸지 않지만 **지우면 안 된다.**

### 치른 값

v2 레코드(R2 이전의 order 가 쓴 것)의 PayPal 참조는 옛 필드에만 있었고 그 필드는 v4 에서 빠졌다 — R4 이후 그런
레코드를 읽으면 참조가 비어 있다. 그런 레코드는 DLT 재처리로만 올 수 있고, 결제의 원본 참조는 order 의
`provider_payment_id` 에 있다. 이 손실을 막으려면 디코더의 읽기 스키마를 따로 두어야 하는데, 그 복잡도에 비해 얻는 것이
작다고 판단했다.

### C3 — 조건이 "순서" 가 아니라 "시간" 인 단계

v1·v2 이력 스키마와 pay 의 v2 대체 경로는 **그 레코드가 사라진 뒤에만** 지울 수 있다 — 토픽 7일, DLT 14일. C2 와
한 커밋에 묶으면 시간 가드가 14일 동안 **배포 전체를** 막는다. **서로 다른 조건은 서로 다른 릴리스에 둔다.** C3 는
R3 배포 날짜가 정해진 뒤, pay V6 의 적용 시각을 보는 14일 가드와 함께 만든다.

## 7. 교훈

1. **"다음 릴리스에 지운다" 는 계획이 아니라 부채다.** 전환 코드는 주석과 함께 영원히 남기 쉽고, 남으면 이미 없앤
   모양(이메일 신원, 헤더 존재 검사)이 되살아날 입구가 된다. 좁히기도 계획에 넣고, 되살아나지 못하게 테스트로 막는다
   (`User-Email` 을 싣는 Feign 이 없다, 엔티티가 옛 컬럼을 매핑하지 않는다).
2. **롤링 배포의 창은 양방향이다.** 넓힐 때는 "새 파드가 옛 데이터를 읽는가", 좁힐 때는 "옛 파드가 새 DB 에서 도는가".
   V17 의 교훈은 두 번째다 — 처음엔 한 번에 지우려 했다.
3. **사람이 기억해야 하는 순서는 코드가 확인하게 한다.** "R1 을 먼저 배포하세요" 는 문서에 쓰면 잊힌다. 마이그레이션이
   Flyway 이력과 데이터를 보고 멈추게 했다. 멈춤은 안전한 실패다 — DDL 트랜잭션 덕에 아무것도 바뀌지 않고, 옛 파드가
   계속 돈다.
4. **가드는 새 환경을 막으면 안 된다.** 새 DB 에서는 모든 마이그레이션이 한 번에 도는 게 정상이다. 시간 가드의
   "첫 마이그레이션 + 10분" 조건이 그것을 가른다. 이력이 없으면 통과(fail-open) — 가드가 배포를 영구히 막는 것보다 낫다.
5. **조건이 다른 변경은 다른 릴리스에.** 순서 조건(C2)과 시간 조건(C3)을 묶으면 시간 가드가 순서 조건까지 인질로 잡는다.
6. **레지스트리 없는 Avro 는 호환성 규칙을 사람이 지켜야 한다.** 필드는 끝에만 더하고 기본값을 둔다. 더할 때는 한
   릴리스 동안 옛 작성 스키마로 쓴다. 뺄 때는 다음 스키마를 먼저 알린다. R1 은 이것을 몰라 일곱 토픽에 DLT 창을 남겼다.
7. **DTO 와 스키마는 따로 논다.** `providerPaymentId` 는 DTO 에만 있었고 아무도 몰랐다. 전선을 한 번 왕복해 보는
   테스트가 필드마다 있었다면 드러났을 것이다 → 만들었다(`AvroMappingContract`, §8).
8. **실제 DB 에 돌려 본다.** PL/pgSQL 의 `AND` 가 단락 평가되지 않는 것, 컬럼을 지우면 그 컬럼을 포함한 인덱스가 함께
   사라지는 것 — 둘 다 PG16 에 적용해 보고서야 알았다.
9. **가드 하나가 여러 축을 지킬 수 있다.** 쓰는 쪽(order)의 DB 가드가 실패하면 새 스키마의 레코드도 나가지 않는다.
   가드를 어디에 두느냐는 "누가 새 모양을 **만들어 내는가**" 로 정한다.

## 8. 남은 것

- **R1 배포 뒤 DLT 재처리** — `order`·`product-update`·`cart-empty`·`cart-rollback`·`coupon-use`·`chat`·`user-created`.
- **C3** — v1·v2 이력 스키마와 pay 의 v2 대체 경로 삭제(R3 후 14일), 이어서 v3 이력(R4 후 14일). 14일 가드를 함께.
- ✅ **DTO ↔ Avro 필드 대조 테스트** — `AvroMappingContract`(common 의 test fixtures). 매핑마다 두 가지를 본다:
  **이름**(DTO 의 필드와 스키마의 필드, 목록 안 중첩 레코드까지)과 **왕복**(모든 필드를 기본값이 아닌 값 — 19자리 id,
  마지막 열거값, 밀리초까지의 시각 — 으로 채워 `toRecord → encoder → decoder → toDto` 를 돌리고 같은 값이 돌아오는가).
  토픽 목록은 `AvroMappings.byTopic()` 에서 오므로 새 토픽은 자동으로 들어온다. chat 의 매핑은 chat-service 에 있어
  `ChatMessageAvroContractTest` 가 같은 검사를 한다. 일부러 싣지 않는 필드는 **경로 → 이유**로만 뺄 수 있다. 검사가
  실제로 잡는지도 고정했다 — 결제 요청의 옛 버그(매핑이 `providerPaymentId` 를 옮기지 않음)와 DTO 에만 필드를 더한 경우.
  지금 매핑 열 개는 모두 통과한다(제외 없음).
- ✅ **saga-projection 의 역직렬화 예외 처리기** — `SagaDeserializationExceptionHandler`. 실패를 둘로 나눈다.
  - **모르는 작성 스키마면 멈춘다.** 이 파드보다 새 프로듀서가 쓴 레코드다. 건너뛰면 EOS 로 오프셋이 커밋되어 롤링 중
    새 파드도 다시 읽지 않는다 — 프로젝션이 그 기록을 **영영 잃는다.** 멈추면 새 파드가 마지막 커밋부터 읽는다. "무조건
    건너뛰기(LogAndContinue)" 가 오히려 나쁜 경우다.
  - **그 밖의 깨진 레코드는 건너뛴다.** 몇 번을 다시 읽어도 같으니 멈추면 뒤의 모든 주문이 인질이 된다. 좌표(토픽·
    파티션·오프셋)와 예외 종류만 로그에 남긴다(값은 남기지 않는다).
  - DLT 는 두지 않았다 — 원본은 입력 토픽에 그대로 있고(보존 기간 동안), 프로젝션은 입력 토픽에서 다시 접어 재구성할 수
    있다(`kafka-streams-application-reset`). `order.DLT` 는 pay 의 것이라 섞으면 재처리가 pay 로 다시 흘러간다.
  - 계수기 `saga_projection_deserialization_failures_total{topic, action=skipped|halted}` 와 경보 둘
    (`SagaProjectionHalted` 10분 지속 시 critical, `SagaProjectionSkippedRecords` warning). Prometheus 가 saga-projection 을
    수집하지 않고 있어 대상도 더했다.
  - 테스트(TopologyTestDriver, 운영 설정 그대로): 깨진 레코드 뒤의 주문이 계속 접히고 계수기가 오른다, 모르는 스키마면
    멈춘다, 처리기가 없으면 깨진 레코드 하나에 멈춘다(예전 동작).
- **스키마 레지스트리** — §4·§5 의 수작업(옛 작성 스키마, 다음 스키마, 이력 파일)을 호환성 규칙이 대신한다. 규모가
  커지면 이것이 정답이다.
