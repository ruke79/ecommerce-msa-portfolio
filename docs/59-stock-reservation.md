# 59. 決済前の在庫予約

**日本語** | [한국어](59-stock-reservation.ko.md)

> docs/53 §7 の次の段階。§7 は過剰販売が**起きた後**数秒以内にお金を返す。この文書は過剰販売が**起きないように**
> 注文作成時に在庫を確保しておく側である。§7 の補償はそのまま残し、セーフティネットとして使う。

## 1. 何が問題だったか

在庫は**決済の後に**差し引かれる(Saga の `product-update`)。その間、何も在庫を押さえていなかった:

- 最後の 1 個を二人が注文すると、二人とも決済画面まで進む。二人とも決済し、遅い方は数秒後に自動返金を受ける。
  お客様にとっては「決済された → 返金された」の二度の通知である。決済手数料は返金しても戻ってこない PG が多い。
- 🔴 **銀行振込は自動返金ができない**(docs/53 §7)。入金期限の 48 時間のあいだ在庫を確保しないので、入金している間に売れた商品に
  お客様がお金を送り、運用者が手作業で返金しなければならなかった。
- 決済画面で「今決済すれば受け取れる」という約束ができなかった。

## 2. どう変えたか — ひと目で

```
注文作成 ──▶ order 保存(id が予約のキー) ──▶ catalog POST /api/internal/stock/reservations  (30分)
                                                  ├─ HELD   → orders.stock_hold_until を記録して決済画面へ
                                                  ├─ SHORT  → 作ったばかりの注文を削除して 400 "재고가 부족해 주문하지 못했습니다: …"
                                                  └─ 到達できない → ブロックしない(fail-open) — §7 の補償が後ろを支える
銀行振込の開始 ──▶ 同じ予約を入金期限 + 1時間(49時間)に延長。足りなければ入金案内を出さない
決済完了 ──▶ Saga の product-update(eventId order-<id>) ──▶ catalog が差し引きながらその注文の予約を同じトランザクションで COMMITTED
キャンセル・期限切れ・Saga ロールバック ──▶ コミット後に POST /api/internal/stock/reservations/{orderId}/release
期限超過 ──▶ catalog の期限切れジョブ(60秒)が HELD → RELEASED
```

## 3. catalog — 予約は在庫の持ち主が持つ

`product.stock_reservation`(V14): `order_id`·`product_id`·`color_id`·`size`·`qty`·`status`(HELD|COMMITTED|RELEASED)·`expires_at`.
`UNIQUE(order_id, product_id, color_id, size)` — 同じ注文が再度確保すると、新しい行ではなくその行を更新する。

| 決定 | 理由 |
|---|---|
| **残数 = `quantity` − 他の注文の有効な HELD の合計** | `quantity` カラムを予約時に減らすと、決済前の離脱のたびに戻さなければならず、戻し忘れがあると在庫が消える。予約は別に数え、実際の差し引きは今と同じく決済後に一度だけである。期限切れの HELD はジョブが片付ける前でも合計から外れる(`expires_at > now`) |
| **全部か無か** | 3 行のうち 1 行だけ確保された注文は決済できない注文である。1 行でも足りなければ何も確保せず、足りない行(要求数・残数)を返す |
| SKU の行を `PESSIMISTIC_WRITE` で、**ソートされた順序で**ロックする | 決済後の差し引きと同じロックなので、予約と差し引きが順番待ちになる。二つの注文が同じ二つの SKU を逆順でロックするとデッドロックが起きる — `(productId, colorId, size)` 順でロックする |
| 確定は**差し引きと同じトランザクション** | `product-update` が差し引きながら、その注文(`order-<id>` から読む — docs/53 §7 と同じキー)の予約を COMMITTED に。差し引き時の残数は「その注文を除いた」他の注文の予約だけを引く — 自分の予約を引くと自分が買えなくなる |
| 有効時間は 1 分 ~ 72 時間に切り詰める | 呼び出し側のミスで永遠の予約ができないように |
| 内部 API は `/api/internal/**` — 内部呼び出しまたは管理者のみ | `AdminWriteInterceptor` が**読み取りまで**ブロックする(`InternalCallGuard.allowed`)。ゲートウェイが身元ヘッダーを付けたリクエスト(=外部)は拒否される |
| 再入荷(`restock`)イベントは予約と無関係 | 増やす側は誰の予約にも触れない |
| 予約合計・期限切れ更新は**ネイティブ SQL に `status = 'HELD'` リテラル** | 🐛 最初は JPQL で状態をバインド値として渡していた。PostgreSQL の汎用プラン(同じ文を何度も実行すると使われるもの)はバインド値では部分インデックス(`WHERE status = 'HELD'`)の条件を証明できず、**テーブル全体をスキャンしていた** — PG16 `plan_cache_mode = force_generic_plan` で確認(20 万行、Parallel Seq Scan)。この照会は SKU のロックを握ったまま動き、テーブルには確定・解放済みの行が溜まる一方である。リテラルに変えた後、三つの照会(オプション別合計・商品別合計・期限切れ更新)すべてが部分インデックスを使う |

## 4. order — いつ確保し、いつ解放するか

| 時点 | 動作 | 足りなければ | 到達できなければ |
|---|---|---|---|
| 注文作成 | 同じ顧客の先行する決済前注文が確保したものを先に解放し、保存直後に 30 分(`order.stock-hold.checkout-minutes`)予約 | 作ったばかりの注文を**削除して** 400。文言に商品・オプション・残数(「티셔츠(M) 남은 수량 1개」 / 「품절」) | 注文は作られる。`order_stock_hold_total{result="unavailable"}` + 警告ログ |
| 銀行振込の開始 | 入金期限 + 1 時間に延長 | 入金案内を**出さない**(400「재고가 부족해 입금을 시작하지 못했습니다: …」) | 案内は出す |
| PortOne バーチャル口座の発行 | 延長 | ⚠️ 警告のみ — 口座はすでに PG が発行済み | 警告 |
| PayPal キャンセル · 銀行振込キャンセル · 入金期限切れ · Saga ロールバック | **コミット後に**解放 | — | 解放の失敗は握りつぶす — 期限切れジョブが後ろを支える |
| 決済完了 | 何もしない — catalog が差し引きながら確定 | — | — |

| 決定 | 理由 |
|---|---|
| 注文を**先に保存してから**確保する | 予約のキーが注文 id である。先に確保するには一時キーが必要で、そのキーを注文に移す段階がまた失敗しうる |
| 足りなければ注文を**削除する**(状態を CANCELED にしない) | 決済も外部発行もなかった注文である。残すと注文一覧に「キャンセル済み」が溜まり、お客様はキャンセルした覚えがない。カートはそのままなので、数量を直して再注文できる |
| 削除は四段階すべてに**「決済前・決済参照なし」**を条件として付ける | 注文と住所が互いを指している(`orders.order_address_id` ↔ `order_address.order_id`)ので順番に削除する。条件のおかげで誤って呼んでも決済済みの注文は削除されない — PG16 で決済前/決済済み/決済参照あり の三つの注文で確認 |
| catalog に到達できなければ**ブロックしない**(fail-open) | 予約は過剰販売を**減らす**仕組みであり、防ぐ仕組みとしては §7 の補償がすでにある。catalog が少し遅いだけで注文全体を止めるほうが高くつく |
| 解放は**コミット後**(`afterCommit`) | キャンセルのトランザクションがロールバックされたのに予約だけ解放されると、生きている注文の在庫を他人が持っていく |
| 予約時刻を注文に記録する(`orders.stock_hold_until`, V22) | 決済画面が「いつまでに決済すればよいか」を伝える根拠。catalog に再度問い合わせない |
| 🐛 新しい注文を作ると**同じ顧客の先行する決済前注文の予約を解放する** | カートは決済の後にしか空にならない。注文して決済画面から戻り、再度注文すると、前の注文の予約が新しい注文にとっては「他人の予約」となり、最後の 1 個を買ったお客様が**自分の予約に阻まれて**「재고가 부족해 주문하지 못했습니다」を受け取っていた。前の注文はそのまま残し(決済はできる)、保持時刻だけを現在に繰り上げる — 決済画面が「재고가 보장되지 않습니다」と伝える。入金待ち(UNPAID)は入金期限までの約束なので触らない。顧客別の照会なので `orders.customer_id` インデックスを追加した(V23 — 既存の `idx_order` は `tracking_id` が先頭なので使えない) |

## 5. お客様に見える残数 — 商品詳細・カート追加・一覧カード

商品詳細(`GET /api/product/{slug}`)、カート追加時の照会(`GET /api/cart/{id}`・`/api/cart/info`)、一覧カード(検索 `GET /api/search`、
ホーム `GET /api/content/home`、特集 `GET /api/content/events/{slug}`)の残数は **現在の実在庫 − 他の注文の生きている予約**である。
オプションごとに `onHold`(実在庫のうち確保されている数)も載せる。

| 決定 | 理由 |
|---|---|
| **レスポンス直前に**引く(`StockAvailability`) — キャッシュ(`products`・`search_cache`)はそのまま | 予約は分単位で生まれては消える。キャッシュされた値に入れると、予約が解放されてもキャッシュが変わるまで「0 個」が残る。レスポンスごとに商品あたり一度、部分インデックスを使う照会(§3)で読む。キャッシュされたオブジェクトには触らず、コピーを修正する |
| コントローラーで — **トランザクションの外** | トランザクション内で照会が失敗すると、例外を握りつぶしてもそのトランザクションが rollback-only になり、レスポンス全体が失敗する |
| 照会が失敗したら実在庫のまま | 残数表示のせいで商品画面が壊れてはならない。注文段階の予約がどのみち正確に弾く |
| `onHold` は 0 なら**載せない**(`@JsonInclude(NON_DEFAULT)`) | `products` キャッシュのシリアライザは未知のフィールドで失敗する。キャッシュされた DTO では常に 0 なので JSON に現れない — このフィールドを知らない古い Pod がローリング中にキャッシュを読んでも壊れない。DTO に `ignoreUnknown` も付けた(次回のために) |
| 確保数は**実在庫まで** | 管理者が在庫を減らして、実在庫より多く確保されていることがありうる。残数がマイナスにならない |
| 🔒 管理者の一覧・編集(`/api/product/products`, `/product/edit/…`)では**引かない** | 引いた値を編集画面が受け取って保存すると、実在庫が減る |
| 🐛 数量もキャッシュではなく**現在の値**(`size_id` で合わせる) | ホームカードの元になるカテゴリ一覧キャッシュ(`products`、カテゴリキー)は**有効期限がなく、在庫が変わってもクリアしない** — その中の実在庫数量からしていつのものか分からない。予約だけ引くと「昔の数量 − 今の予約」になる。一まとまり(詳細一つ、一覧 1 ページ、ホーム全体)について、サイズ別の現在数量を一度 + 予約合計を一度読む — 商品ごとには読まない。二つの読み取りは別々に失敗する(一方が読めなくても他方は反映) |
| 外部キーインデックス(V15 — `product_sku.product_id`, `product_size.skuproduct_id`) | PostgreSQL は外部キーにインデックスを作らないが、基準スキーマ(V5)に抜けていた。現在数量の照会だけでなく、詳細の遅延ロード、差し引き・予約の SKU ロック照会(`findForStockUpdate`)もこの経路なので、すべてテーブル全体をスキャンしていた。PG16 で二つのインデックスを使うことを確認 |

フロント(`components/product/Infos.jsx`):

- 選んだサイズが 0 個でも `onHold > 0` なら品切れではない — 「다른 고객이 결제 중인 재고입니다. 결제되지 않으면 곧 다시 구매할 수
  있어요.」を表示し、**再入荷通知は勧めない**(再入荷通知は実在庫が 0 をまたぐときにだけ送られ、予約が解放されて戻ることでは
  届かない)。
- カート追加直前の照会で 0 個になっていたら(画面を開いた後に誰かが確保した)同じ案内。🐛 以前のチェック順では 0 個も「在庫より多い数量」として
  表示されていた — 0 個を先に見る。
- **カート画面**は追加時に受け取った数量を持ち続けていた(数日前の値でありうる — 「sold out」表示もその値で行っていた)。今は画面に
  入るときと別のタブから戻るときに `GET /api/stock?items=상품id:색상id:사이즈`(予約と同じキー — カート項目はサイズの連番では
  なく名前・色 id を持つ)で**現在の**在庫を受け取り、項目を更新する(`syncStock` — ユーザーの編集ではないので、カートの状態・追加した
  数量はそのまま)。項目ごとに `판매 종료`・`품절`・`결제 중`・`남은 수량 N개 — 수량을 줄여 주세요` を知らせ、`+` は残数で
  止まる。選んだ項目の中に現在の在庫で買えないものがあれば注文書に進まない(注文段階の予約がどのみち拒否する)。
  レスポンスにないオプションは販売終了(`UNAVAILABLE`)とみなす — そのため在庫を**読めなければ 503**(空の結果と区別)で、画面は持っている値を
  そのまま残す。
- **一覧カード**(`components/home/ProductCard.jsx`、判定は `util/stock.js`)は選んだ色のサイズを合算してバッジを一つ付ける:
  `품절`(残りも確保分もない、または管理者が品切れにした — 写真をぼかす)、`결제 진행 중`(残りはないが誰かが決済中)、
  `N개 남음`(3 個以下)。十分あればバッジはなく、レスポンスに数量がなければ何も言わない — 分からないものを品切れとは言わない。

## 5-1. フロント — 決済画面の案内

`components/order/StockHoldNotice.jsx` が注文決済画面(`Payment.jsx`)に描画する。

- 期限前: 「주문하신 상품의 재고를 **9/25 오후 3:30** 까지 잡아 두었습니다. 이 시간 안에 결제해 주세요.」
- 期限後: 「재고 보관 시간이 지났습니다. 지금 결제할 수는 있지만 재고가 보장되지 않습니다 — 결제 뒤 재고가 모자라면 모자란
  수량만큼 환불됩니다.」画面を開いたまま期限が過ぎると、その瞬間に文言が変わる。
- 予約時刻がなければ(fail-open で作られた注文、機能がオフ)描画しない — 確保したと言う根拠がない。
- 決済前(`NOT_PROCESSED`)と入金待ち(`UNPAID`)でのみ表示される。
- 注文作成が在庫不足で拒否されると、既存の注文サマリー画面(`Summary.jsx`)がサーバーの文言をそのまま表示する。

## 6. 限界 — 正直に

- ~~一覧・詳細を開いた後にできた予約は画面に反映されない~~ → §9: 詳細は戻ってきたとき・1 分ごとに読み直す。一覧は react-query の
  ウィンドウフォーカス時の再取得(staleTime 60 秒経過後)で追従する。
- 一覧のレスポンスごとに DB を二度読む(インデックス照会、1 ページ単位)。キャッシュは商品情報・価格のためのものとして残り、在庫だけがキャッシュを迂回する。
- 商品の**状態**(`SOLD_OUT` など)は依然としてキャッシュの値である — 状態は管理者が変更するときにキャッシュを更新する経路が別にある。
- 先行する注文の予約を新しい注文に引き渡すのは**同じ顧客**基準である。新しい注文が別の理由で不足して拒否されても、前の注文の予約はすでに
  解放されている — 前の注文は決済できるが保証はない(決済画面がそう伝える)。
- **予約が期限切れになった後の決済は依然として可能である。** その場合は §7 の不足検出・自動部分返金に落ちる(銀行振込は手動)。決済画面が
  そう伝えてくれる。
- **PortOne のバーチャル口座は発行後には止められない。** 口座は PG の決済ウィンドウ内で発行され、こちらはその後で知る。§9 で決済ウィンドウを開く
  **瞬間に**予約を新たに確保し、足りなければウィンドウを開かないようにした — 残る隙間は、ウィンドウを開いてから発行までの数分(その間予約は確保されている)と
  catalog に到達できなかった場合(fail-open)だけである。それでも足りなければ入金後に §7 の経路で「手動返金が必要」。
- **fail-open の間に作られた注文には予約がない。** `order_stock_hold_total{result="unavailable"}` が増えたら、その時間帯の過剰販売は
  §7 の補償に頼っているという意味である。
- カート段階では確保しない。カートは長く滞留するので在庫を拘束するコストが大きい — 実務でもたいてい決済段階で確保する。

## 7. 運用

| 設定 | デフォルト値 | 意味 |
|---|---|---|
| `order.stock-hold.enabled` | `true` | `false` なら予約しない — 以前の動作(§7 の補償のみ) |
| `order.stock-hold.checkout-minutes` | `30` | 決済画面で確保しておく時間 |
| `catalog.stock-reservation.expiry-check-ms` | `60000` | 期限切れジョブの周期 |

- メトリクス: `order_stock_hold_total{result=held|short|unavailable|disabled}`。`short` は注文段階で防いだ過剰販売、
  `unavailable` は fail-open で通過した注文。
- 現在確保されている在庫:
  ```sql
  select product_id, color_id, size, sum(qty)
    from product.stock_reservation
   where status = 'HELD' and expires_at > now()
   group by 1, 2, 3 order by 4 desc;
  ```
- デプロイ順序: **catalog が先**(V14・V15 と内部 API)、次に order(V22・V23)。order が先に起動すると予約呼び出しが 404 になり fail-open で通過する —
  止まりはしないが、その間の注文には予約がない。

## 9. 開いたままの画面 · 決済ウィンドウの直前 (後続)

| 何を | 前 | 後 |
|---|---|---|
| 商品詳細の残数 | 開いた瞬間の値 — その後にできた予約はリロードするまで見えなかった | `useRevalidateWhileVisible` — タブに戻ってきたときと表示中は 1 分ごとに loader を再実行する(非表示タブでは動かない) |
| 決済ウィンドウを開くとき | 注文時に確保した 30 分が過ぎていたら、予約なしで決済ウィンドウが開いていた。バーチャル口座は**存在しない商品に対して口座が発行**されることがありえた | `POST /api/order/payment/stock-hold/{trackingId}` — PortOne(V1・V2)・Stripe の決済ウィンドウを開く直前に予約を新たに 30 分確保する。足りなければ 400「재고가 부족해 결제를 시작하지 못했습니다: …」で**ウィンドウを開かない**。確保できたら注文の `stockHoldUntil` を新しい値に — 画面の案内も変わる |

- 決済前(NOT_PROCESSED)の注文のみ、🔒 注文者のみ(そうでなければ 404)。catalog に到達できないかネットワークエラーならブロックしない(fail-open — 注文
  作成と同じ)。
- PayPal はボタンが SDK 内で注文を作るので差し込む場所が異なる — 今回は入れなかった。カードなので不足分の自動返金が受け止める。
- バーチャル口座発行 Webhook での延長(§4)はそのまま — 発行されたら入金期限まで延ばす。

## 10. 🔴 すべての注文が「品切れ」だった — 注文品目の商品 id がカートの**行** id だった (2026-09-26)

**症状**: 商品画面は在庫があると言うのに、注文すると `在庫が不足しているため注文できませんでした：Italian Olive Oil() 품절`。

**原因**: order-service が注文品目を作るとき `.productId(Long.parseLong(p.getId()))` だった。`CartProductDto.id` は**カートの行 id**
(`cart_product_id`, TSID)である — その DTO のコメントにも「商品 id ではない」と書かれており、商品 id は `productId` である。行 id はどの商品も
指さないので、catalog は SKU を見つけられず残数を 0 と答えた。最初(2025-10)からそうで、この値で行う処理が**すべて**
空回りしていた:

| 使う場所 | どう間違っていたか |
|---|---|
| 在庫予約(今回のデプロイから) | SKU なし → 0 → **すべての注文が「品切れ」**で阻まれる |
| 決済後の差し引き(docs/53 §7) | 商品なし → 全量不足 → **決済した注文がすべて自動返金** |
| 決済後のカートのクリア | 商品 id が違って行を見つけられない → 注文した商品がカートに残る |
| レビューの「購入者のみ」(docs/57) | 受け取った商品の照会が常に空 → レビュー 403 |

**修正**: `getProductId()` を使う(`OrderDataService.requireProductId` — 空なら注文を作らない、行 id で代用しない)。
`productId` フィールドができる前に Redis に入ったカートのコピーには値がないので、`OrderService.fillMissingProductIds` がトランザクションの
外で cart に行 id で問い合わせて埋める。

**ガード**: `OrderProductIdTest`(3) · B-66(order・coupon・pay で `CartProductDto` の `getId()` を `.productId(` に入れると失敗 —
元に戻すと失敗することを確認)。

**すでに作られた注文**: `order_product.product_id` に行 id が入っている。不足分の自動返金(docs/53 §7)ができた後に決済された注文は
上の表のとおりすでに全量返金された(管理者注文画面の不足数量)。それ以前に決済された注文は在庫が差し引かれないまま残っている。いずれにせよ
それらの品目はレビュー対象にならない。

## 11. サイズのない商品 — 名前が空のサイズ行が複数 (2026-09-26)

食品・生活用品はサイズ行の名前が空である。シードの SKU 509 個のうち 403 個がそうで、そのうち 315 個は **1 つの SKU に名前が空の行が 2~4 個**ある
(価格・数量が互いに異なる行)。オプションは(商品、色、サイズ**名**)でやりとりするので、これらの行は互いに区別されない。

| どこで | 何が間違っていたか | 修正 |
|---|---|---|
| catalog のサイズ照会(`findBySkuSkuproductIdAndSize`) | 「一つ」を期待 → 名前が空の行が二つ以上あると例外 → 在庫予約・決済後の差し引きが失敗 | `findFirst…OrderBySizeIdAsc` — 同じ名前なら**最初の行**。カート(`CartService.sizeIndexOf`)も同じ名前の最初の行を使う |
| `ProductSku.sizes`・`Product.skus` | 順序がなかった(List は DB が返したまま、Set はハッシュ順) — それなのに画面・カートは**インデックス**(`?style=1&size=0`)でやりとりする | `@OrderBy`(size_id·skuproduct_id) |
| `ProductSku` の equals/hashCode | 宣言がなく、`BaseEntity` の `@Data`(監査フィールド・version)を継承していた — 在庫が変わると hashCode が変わり Set の順序がロードごとに変わり、監査フィールドが同じ二つの SKU は一つにまとめられうる状態だった | id のみで等価、hashCode は定数 |
| 商品画面 | 空の丸が並んで表示され、選ばないと「사이즈를 선택하세요」で追加がブロックされた。別の丸を選ぶと画面の価格とカートの価格(最初の行)が異なった | `sizeless` ならサイズ選択を描画せず最初の行(0)を使う |
| レビュー | サイズが必須(画面・サーバー)なので**レビューを書けなかった**。カードには「사이즈:」だけ、絞り込みには空の項目。着用感(「정사이즈」)もオリーブオイルに尋ねていた | 選ぶサイズがなければサイズ・着用感を尋ねない(サーバー: サイズが空なら着用感も空を許容、サイズを選んだら着用感は必須)、カード・絞り込みから外す |

同じ名前の 2 行目以降は、今やどこからも選べない — もともとカートが最初の行に置き換えて追加していたので、新たに失うものはない。
それらの行が別々の商品(容量など)なら、管理者画面で名前を付ける必要がある(例: `250ml`・`1L`)。

**ガード**: `ProductSkuIdentityTest`(4) · `StockReservationServiceTest.sizelessOption` · `ReviewServiceTest.sizelessProductCanBeReviewed`·`fitRequiredWhenSized` · `ReviewCard.test.jsx`(2) ·
`util/sizes.test.js`(3) · `Infos.test.jsx`(+4) · `Review.test.jsx`(+1) · `pages/Product.test.jsx`(+2).

**デプロイ後に一度**: 商品キャッシュ(`product`・`products` は有効期限がない)に古い順序の SKU リストが残っていると、画面(キャッシュ)とカート追加(新たに
読む)のスタイルインデックスがずれることがある。catalog のキャッシュをクリアする(値は再び埋められる):

```bash

  REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli --scan --pattern "$c::*" | xargs -r -n 200 env REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli del >/dev/null; done; echo done'
```
