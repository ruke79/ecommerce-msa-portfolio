# 30. git 履歴からの資格情報漏洩 — 対応記録

**日本語** | [한국어](30-git-history-secret-exposure.ko.md)

> 🕰️ **状態（2026-09-27）— 一部古い。** §5 で推奨した CI でのシークレットスキャンは導入しました（[docs/57 §6](57-remaining-priorities.md)）。

公開リポジトリの git 履歴に **生きているサードパーティの資格情報**が含まれているのを発見した。
作業ツリーはすでにクリーンだったが（[docs/13](13-secrets-dbha-es-search.md)、[ops/01](../ops/README.md)）、
**履歴には手を付けていなかったため**、コミット SHA さえ分かればブラウザでそのまま読めてしまう。

```
https://github.com/ruke79/ecommerce-msa/blob/<SHA>/backend/src/main/resources/application.properties
```

### ⚠️ `REACT_APP_*` に入ったシークレットは git の問題ではない

`REACT_APP_PAYPAL_CLIENT_SECRET`、`REACT_APP_CLOUDINARY_SECRET` がフロントエンドの `.env` に
あった。Create React App は **`REACT_APP_` プレフィックスの付いた値をビルド時にバンドルへそのまま
埋め込む。** つまりこの 2 つの値は

- git 履歴だけでなく、**デプロイされたサイトを開いたすべての訪問者のブラウザ**に届いており、
- それは **履歴を整理しても取り戻せない。** すでに出回ったバンドルは回収できない。

そもそもクライアントシークレットをフロントエンドに置いてはならない — 決済承認・メディア削除のような操作は
サーバーが行うべきである。**失効以外に対応方法がない唯一の項目**である。

**露出期間: 約 2 年**（リポジトリ作成 2024-08-12 〜 発見 2026-07-29）。
リポジトリは `public` で、**フォークは 0 個**である — この一点だけが唯一の救いである（§4 参照）。

現在の HEAD はクリーンである。問題はすべて履歴にのみある。

## 2. 「履歴から消せばいいのでは」— だめである

最初に整理すべき誤解である。**履歴の書き換えは漏洩をなかったことにはしない。**

**(1) 値は依然として有効である。** git から消しても、AWS キーは AWS で、アプリパスワードは Google で
そのまま生きている。消すのは *コピーの一つ* であって *資格情報* ではない。

**(2) 消しても GitHub からすぐには消えない。** force-push の後も GitHub は古いコミットオブジェクトを
**SHA でアクセス可能な状態のまま保持する。** つまり問題の URL は、整理してプッシュした後も開ける。
実際に塞ぐには GitHub Support に GC を依頼する必要がある（§4）。

**(3) コピーはすでに広まっている。** クローンした人、ミラー、キャッシュ、そして何より **自動スクレイパー**。
公開リポジトリをリアルタイムで走査して資格情報を収集するボットがいくつもあり、AKIA キーは通常プッシュから
数分以内に捕まる。2 年あれば「誰かがすでに見た」ことを前提にしなければならない。

**(4) フォークがあれば永久に残る。** GitHub はフォークネットワークのオブジェクトを整理しない。
このリポジトリはフォーク 0 個なので、この経路は幸い閉じているが、確認せずに安心してよいことではない。

> **結論: 唯一の本当の解決策は失効・再発行である。** 履歴の整理はその後の後片付けである。
> 順序を逆にすると「片付けたという感覚」だけが得られ、リスクはそのまま残る。

## 4. 履歴の整理手順

```bash
# 0) 現状確認（値は絶対に出力しない）
ops/20-scan-history-secrets.sh

# 1) 整理 — 新しいミラークローンで実行し、プッシュはしない
pip install git-filter-repo
ops/21-purge-history-secrets.sh --workdir /tmp/purge

# 2) 結果を自分で確認してから force-push（⚠️ 元に戻せない）
cd /tmp/purge/repo.git
git remote add origin https://github.com/ruke79/ecommerce-msa.git
git push --force --all origin
git push --force --tags origin

# 3) 既存のクローンをすべて捨てて再クローン
#    ⚠️ 古いクローンから push すると、消したコミットが復活する

# 4) GitHub Support に GC を依頼 — これがないと古い SHA で読め続ける
#    https://support.github.com/contact
```

### 2 つの方式 — どちらを使うか

| | `ops/21`（git-filter-repo） | `ops/22`（BFG Repo-Cleaner） |
|---|---|---|
| やること | 値だけを `***REMOVED***` に置換 | **ファイルを丸ごと削除** + 残った値を置換 |
| ファイル | 残る（その時点の設定を見られる） | 消える |
| パス指定 | 可能（`--path`） | **不可 — 名前でのみマッチ** |
| HEAD の保護 | なし（すべて書き換え） | デフォルトで有効 |

**BFG の落とし穴 2 つ**を知らないと、「実行したのにそのまま」になる。

1. **名前でマッチする。** `--delete-files application.properties` はリポジトリのどこにあっても
   その名前をすべて消す。このリポジトリの履歴では 8 つのパスにあった。「backend/ のものだけ」は BFG では
   できない — それが必要なら `ops/21` を使う。
2. **HEAD コミットを保護する。** 現在のコミットに残っているファイルは消されない。つまり **作業ツリーを
   先に整理した後でしか**正しく動作しない。`ops/22` は実行前にこれを確認し、残っていれば
   中断する。

このリポジトリは HEAD に `application.properties` が 0 個だったので、BFG ですべて消すことができた。

### 4.5 🚨 force-push したのにファイルがそのまま読める — `refs/pull/*`

**実際に実行して確認した結果である。これがこの文書で最も重要な項目である。**

ブランチ 5 つをすべて書き換えて force-push した。ブランチ基準では完璧だった —
`application.properties` の参照 0 件、問題の 2 コミットは消滅、HEAD ツリーは元とバイト単位で一致。

ところがリモートを **新たにクローンしてみると、コミットが 785 個ではなく 1,299 個**あり、ファイルがそのまま読めた。

```
refs/pull/1/head   11件
refs/pull/2/head   11件
refs/pull/3/head   18件
refs/pull/4/head   42件   ← 報告された 2 コミットはどちらもここから到達可能
```

**クローズされた PR の参照が古いコミットを掴んでいる。** そしてこれはクライアントからは手を出せない:

```
$ git push --force origin 'refs/pull/4/head:refs/pull/4/head'
error: RPC failed; HTTP 403
```

`refs/pull/*` は **GitHub が管理する読み取り専用の参照**である。消すことも上書きすることもできない。
BFG はローカルクローンの PR 参照まで正しく書き換えたが（残存 0 件）、**それを押し込む方法がない。**

普通のクローンは `refs/pull` を取得しないので、通常の検査では見えない。そこで
`ops/20 --remote` を作った — リモートを `--mirror` で新たに取得し、PR 参照まで検査する。
**整理後は必ずこれで確認しなければならない。** ブランチだけを見て「終わった」と言えば虚偽の報告になる。

#### だから残る選択肢は 3 つだけである

| 方法 | 効果 | 代償 |
|---|---|---|
| **① GitHub Support に GC を依頼** | 正攻法。PR 参照と到達不能オブジェクトを整理してくれる | 人が処理するので即時ではない（通常数日） |
| **② リポジトリを非公開に切り替え** | **今すぐ**匿名アクセスが断たれる | 削除ではない。コラボレーター・自分は引き続き見られる |
| **③ リポジトリを削除して再作成** | 確実かつ即時。`refs/pull/*` がリポジトリと一緒に消える | PR・Issue・スターの履歴がすべて消える |

このリポジトリはスター 0・フォーク 0 なので、③のコストは大きくない。ただし、オープンな PR 2 つと Issue が消える。

**最も早い緩和策は②である。** ①を申請し、その間に②で公開露出を断つ組み合わせを勧める。

### 整理方式

値ではなく **パターン**で置換する。漏洩した値をファイルにまとめて書くよくあるやり方は、そのファイル自体が
すべてのシークレットを一箇所に集めたリストになってしまう — 整理しようとして、かえって漏洩面を作るようなものである。

ファイルは消さずに、値だけを `***REMOVED***` に変える。履歴の構造がそのまま維持されるので、後で
「この時点でどんな設定があったか」を見ることができる。

### 検証で見つかったもの 2 つ

スクリプトを実際に回してみなければ、どちらも見逃していたはずの問題である。

**(1) 部分置換。** 最初のルールは値を `[^\s#]+` で捉えていた。ところが **Google のアプリパスワードは
`abcd efgh ijkl mnop` のように空白で区切られた 4 つの塊で発行される。** 最初の空白で止まるパターンは
最初の塊だけを隠し、残りを残してしまう:

```
spring.mail.password=***REMOVED*** ... 残りの 3 つの塊がそのまま     ← ほとんど残った
```

`[^\r\n]+` に直した。**部分置換は置換しないより悪い** — 消したと錯覚させるからである。

**(2) スキャナーが自分の目印に騙された。** 上記の残りかすをスキャナーが通過させた。`***REMOVED` を
無視リストに入れたところ、*前半だけ*置換された値まで素通りしたのである。今は目印が **行末にある
ときだけ**無視する。整理完了の報告が虚偽になる失敗パターンであり、最も危険な種類だった。

**(3) `\s*` が改行を食った。** 値のパターンを `client-secret\s*[=:]\s*…` と書いたところ、
値が空の行で `\s*` が改行まで飲み込み、**次の行の内容を値として捉えた。** コメント 1 行
（`#  client-secret:`）が漏洩として報告された。区切り文字の後は `[ \t]*` で同じ行に限定した。

**(4) スキャナーが自分自身を漏洩として報告した。** パターンの定義そのものがパターンに引っかかる。パスで除外
せず、ファイル内の目印（`SECRET-SCANNER-SELF-EXCLUDE`）で除外する — 名前が変わっても、履歴の
古いバージョンを検査するときも動作しなければならないからである。

**そしてこの文書自体が一度引っかかった。** 上記 (1) の例に実際のパスワードの断片をそのまま
貼り付けていたのを、コミット直前にスキャナーが捉えた — 漏洩を整理する文書が漏洩を生むところだった。

### BFG でやり直しながら捉えたもの — 最も危険だったバグ

**整理ルールが現在のコードを壊した。**

`jwtSecret: ${JWT_SECRET_KEY}` は 17 文字である。JWT ルールが「16 文字以上」を捉えるので引っかかり、
`jwtSecret:***REMOVED***` になった。`${...}` を除外する否定先読みを入れたのに通過してしまった —
**バックトラック**のせいである。前の `[ \t]*` が空白を 1 つ少なく食う方へ戻ると、先読みの位置が
空白に移って条件を回避する。

さらに悪いのは、**スキャナーがこれを通過させた**点である。スキャナーは `${...}` を誤検知として無視するように
なっていたので、置換された後はそもそも検査対象ではなかった。そのままプッシュしていたら **全サービスが起動
不能**になっていただろう。

三重に防いだ。

1. **値を非空白文字で始まるよう固定**（`[^\s\r\n][^\r\n]*`）。バックトラックで空白が減ると、
   すぐ後ろが空白なのでマッチ自体が失敗する — 先読みを回避できない。
2. **BFG の blob 保護を復活させた。** 最初は `--no-blob-protection` で切っていたが、それこそが
   この事故を防ぐための機能だった。HEAD の blob には手を付けない。
3. **HEAD の整合性チェック**を両方のスクリプトに入れた。前提は単純である — HEAD はすでにクリーンなので、
   整理後も **一文字も変わってはならない。** 変わっていればルールが過剰なのであり、スクリプトは
   プッシュの案内に進まず中断する。

このチェックがなければ、「再検査通過」という青信号を見てそのままプッシュしていただろう。

### 既知の過剰置換（履歴限定）

履歴の古い Java ファイル 1 箇所で、`@Value("${kakao.client-secret:...}")` の行末まで消えて
閉じ括弧がなくなった。**現在のコードには影響がなく**（HEAD ツリーが元とバイト単位で同一であることを
確認した）、過去の履歴なのでそのままにする。値を行末まで食うルールの代償である。

## 5. 再発防止

| | |
|---|---|
| `ops/20 --head` | コミット前の点検用。現在のチェックアウトだけを走査するので速い |
| CI | `.github/workflows` に `ops/20 --head` を追加すれば、新たな漏洩を PR の段階で止められる |
| GitHub Push Protection | リポジトリの Settings → Code security → **Push protection** を有効にすると、GitHub がプッシュ自体を止める。無料の公開リポジトリもサポートしている |
| `.gitignore` | `kafka-secrets.properties`、`k8s/20-secret.yaml`、`certs/`、`observability/secrets/` はすでに除外されている |
| 設定規約 | すべての資格情報は `${ENV_VAR}` 参照のみ。リテラルは `k8s/20-secret.example.yaml` の `REPLACE_ME` プレースホルダーのみ |

スキャナーは誤検知を積極的に除外する（`${...}`、`secretKeyRef:`、テスト用のダミーキー
`0123456789…`）。**毎回同じ項目が赤く表示されるスキャナーは誰も回さなくなり、結局
「どうせ誤検知だろう」と本物の漏洩を見過ごすことになるからである。**

### この過程でバックアップを一度誤って作った

削除直前に `git bundle create --all` でバックアップを取ったが、`--all` がバックアップ用に取っておいた
`refs/backup-before-purge/*`（**書き換え前の元データ**）まで含めてしまった。1,340 コミットに
`application.properties` 42 件が入ったそのバンドルを「整理版」と呼んでいた。
復元して再検査する段階で発覚した。

整理が終わった今、その汚染された参照とバンドルは削除した — 残しておけば、いつか誰かがプッシュして
復活させてしまう。

整理スクリプトは準備済みで検証も済んでいるが、**プッシュはしていない。** force-push は元に戻せず、
すべてのコミット SHA を変えるので、人が判断して実行すべきことである。

## 7. 訂正 — PayPal はシークレットではなかった

この文書は最初、`REACT_APP_PAYPAL_CLIENT_SECRET` を 🔴 に分類していた。**変数名だけを見て
判断したもので、値を確認していなかった。** 後で確認したところ、間違っていた。

履歴の値を（出力せずに）形だけ比較した結果:

```
REACT_APP_PAYPAL_CLIENT_ID       AS… 長さ 80
REACT_APP_PAYPAL_CLIENT_SECRET   AS… 長さ 80     ← 同じ値
```

- 2 つの変数が **同じ値**を持っていた — `_SECRET` 側にクライアント ID を貼り付けていたのである
- PayPal のクライアント ID は `A`、シークレットは `E` で始まる。この値は `AS…` である
- そして **バックエンドのどこにも PayPal API の呼び出しがなかった** — シークレットを使う消費者自体がなかった

クライアント ID は PayPal JS SDK が URL クエリで受け取る **公開値**である。フロントのバンドルに埋め込まれて
すべての訪問者が見るのが正常な動作であり、git に残っていても漏洩ではない。

### 残っているもの（問題なし）

履歴の `frontend/dist/main.bundle.js` にそのクライアント ID が入っている。**ビルド成果物なので
正常である。** ただし、`ops/20` スキャナーがこれを捉えられない理由は知っておくこと — バンドルの中では
`KEY=値` の形ではなく裸の文字列なので、パターンに引っかからない。スキャナーの限界であってバグではない。

### この誤分類が覆い隠していた本当の問題

「シークレットがなぜどこにも使われていないのか？」を掘り下げていくうちに、はるかに重大なものを見つけた — **サーバーが決済を
検証していなかった。** シークレットがなかった理由はそれだった。docs/35 参照。

> 教訓: 資格情報のリスクは **名前ではなく値と用途**で判断しなければならない。名前だけを見ると、
> 存在しないリスクを作り出し（ここ）、本当のリスクを見逃す（docs/35）。
