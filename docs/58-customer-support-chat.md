# 58. カスタマーサポートチャット — 顧客 ↔ カスタマーサポートチーム

**日本語** | [한국어](58-customer-support-chat.ko.md)

> 既存のチャット（`/chat`）は **友だち同士で会話する** 形である。誰でもルームを作れ、ルーム一覧は全員に見え、入れば
> 参加者になる。ショッピングモールの「カスタマーサポートへの問い合わせ」はその正反対だ — 会話は **顧客本人とオペレーターだけ** が見るべきで、誰が担当したかと
> 終わったかどうかが必要である。友だちチャットは後で別途手を入れることにし、相談は別機能として作った。

## 1. 決定 — 部署・従業員のスキーマを別に作らない

質問: *「顧客対応サービスチーム所属の従業員をユーザーとして追加しないといけないよね。ショッピングモールの部署、従業員情報用のスキーマが別に必要だろうか？」*

**必要なものだけを置く。**

| 必要なもの | どうやって | 理由 |
|---|---|---|
| オペレーターもログインする人 | 既存アカウント + ロール `ROLE_SUPPORT`（user V13） | 認証・トークン・ゲートウェイがすでにある。オペレーター専用の **業務アカウント** を作り、ロールだけを与える |
| ロールの付与 | 既存の管理者 API `PUT /api/admin/update-role?userId=…&roleName=ROLE_SUPPORT` | 新しい API は不要。ユーザーあたりロールは 1 つなので（users.users.role_id）、オペレーターは一般の買い物をしないアカウントでなければならない |
| 顧客に見せる名前 | そのアカウントのニックネーム（chat.member にすでに複製される） | 個人アカウントではなく業務アカウントなので、ニックネームがそのまま「オペレーター表示名」になる |
| 所属チーム | 今は "고객지원팀"（カスタマーサポートチーム）1 つ — コード定数 | チームが複数になり **問い合わせをチーム別に振り分けて受ける必要が出たとき** にテーブルへ切り出す（§7） |
| 社員番号・連絡先・職級・給与 | **置かない** | ショッピングモールの責務ではない（人事システムのもの）。使わない個人情報は漏れることもない |

つまり新しいスキーマは **相談そのもの**（`chat.support_thread`、chat V7）だけで、人に関するものはロール 1 つがすべてである。

## 2. モデル

```
chat.support_thread
  thread_id · customer_id · agent_id · status(WAITING|ACTIVE|CLOSED)
  awaiting_reply · last_message_preview · last_message_at · created_at · assigned_at · closed_at
```

- **顧客ごとに開いている相談は 1 つ** — 部分ユニークインデックス `(customer_id) WHERE status <> 'CLOSED'`。2 つのタブで同時に
  「상담 시작하기」（相談を始める）を押しても 1 つである（アプリケーションは衝突したら読み直す）。
- **状態と担当者が食い違うことはない** — CHECK: 相談中なら担当者がいて、待機中ならいない。
- メッセージ本文は友だちチャットと同じ MongoDB の `chat` コレクションに `roomId = "support-<thread_id>"` で蓄積される。配信も同じ
  パイプラインである（Kafka `chat` → 保存 → `/sub/chat/room/support-<id>` ブロードキャスト）。新しく作ったのは **権限** である。

```
顧客            相談開始 ─► WAITING ─(オペレーター: 상담 맡기)─► ACTIVE ─(誰でも: 상담 종료)─► CLOSED
                   │                                                            │
                   └──────────────────── 待機中でも終了可能 ─────────────────┘
               終了後に再度問い合わせ → 新しいスレッド
```

## 3. 権限 — サーバーが強制する

| 行動 | 顧客本人 | オペレーター・管理者 | その他のログインユーザー |
|---|---|---|---|
| 履歴の閲覧・購読 | ✅ | ✅ すべての相談 | ❌ **404**（存在することすら知らせない） |
| メッセージ送信 | ✅（開いている相談） | ✅ **担当者のみ** | ❌ |
| 相談の担当 | ❌ | ✅ 待機中のもの | ❌ |
| 終了 | ✅ | ✅ | ❌ |
| デスク一覧 | ❌ 403 | ✅ | ❌ 403 |

- 身元・ロールは **検証済みのトークン** からのみ — REST は `Authorization`、STOMP は CONNECT 時にセッションに置いた uid・role。
- **担当は条件付き更新**（`UPDATE … WHERE status='WAITING'`）— 2 人のオペレーターが同時に押しても 1 行/0 行で 1 人だけになる。
  遅れた側は 409 "다른 상담원이 이미 맡은 상담입니다."（別のオペレーターがすでに担当している相談です。）
- 担当していないオペレーターは **読めても発言はできない** — 待機中の問い合わせに誰が先に答えたのかが曖昧にならないように。
- メッセージ種別はサーバーが `TEXT_TALK` に固定し、画像 URL は捨てる — クライアントが "상담원이 연결되었습니다"（オペレーターにつながりました）
  という案内を真似したり、任意の URL を相手の画面に描画させたりできない。接続・終了の案内はサーバーが **チームの名義で、コミット後に**
  出す（ロールバックされた割り当ての案内が出ないように）。

### 🔒 この作業で塞いだ既存の穴 2 つ

1. **ワイルドカード購読。** デフォルトの STOMP ブローカーは購読アドレスを **パターン** でマッチする（AntPathMatcher）。`/sub/**` を購読すると
   **すべてのルームのすべてのメッセージ** が届いた — 友だちチャットルームはもともと公開なので目立たなかったが、相談を同じブローカーに載せた瞬間に
   漏えい経路になる。今は購読アドレスは `^/sub/chat/room/[A-Za-z0-9-]{1,64}$` の 1 つの形だけを受け付ける。
2. **ヘッダーで判定していた購読。** SUBSCRIBE は `roomId` ネイティブヘッダーだけを見ていた。ヘッダーには公開ルーム、アドレスには他人の相談を
   書けば、ヘッダーだけを見る検査は通過する。権限は **実際の購読アドレス** で判定し、相談ならヘッダーとアドレスが一致しなければならない。

そして友だちチャットの履歴 API（`GET /api/chat/room/{roomId}`）はルームへの参加を確認しない（公開ルームが前提）— 相談ルームの
id に対しては 404 を返す。相談履歴は本人・オペレーターだけが読める `/api/chat/support/threads/{id}/messages` でのみ読む。

🐛 おまけ: chat のエラーレスポンス `ApiResponse` に getter がなく、Jackson がシリアライズできなかった — エラー文言が画面に届いた
ことがなかった。`@Getter` を付けた。

## 4. API

| メソッド | パス（`/chat-service/api/chat/support`） | 誰が |
|---|---|---|
| GET | `/threads/mine` — 開いている相談、なければ 204 | 顧客 |
| POST | `/threads/mine` — 問い合わせる（あればそれ） | 顧客 |
| GET | `/threads/mine/history` — 過去の相談 10 件 | 顧客 |
| GET | `/threads/{id}` · `/threads/{id}/messages?cursor=` | 本人・オペレーター |
| POST | `/threads/{id}/close` | 本人・オペレーター |
| GET | `/desk/threads?view=WAITING\|MINE\|ACTIVE\|CLOSED` | オペレーター |
| POST | `/desk/threads/{id}/claim` | オペレーター |

送信は STOMP `/pub/chat/message` `{ roomId: "support-<id>", content }` — 送信者は載せない（サーバーがセッションから取る）。

## 5. 画面

- **顧客** `/support`（フッター「1:1 고객센터 상담」（1:1 カスタマーサポート相談））: 相談がなければ「상담 시작하기」（相談を始める）。待機中なら黄色の案内、オペレーターが
  担当すると「상담원 ○○」（オペレーター ○○）に変わる（接続案内を受け取ったら状態を読み直す）。終了すると入力欄の代わりに「새로 문의하기」（新しく問い合わせる）。
- **相談デスク** `/support/desk`（ヘッダーのアカウントメニュー — オペレーター・管理者にだけ見える）: 左に待機・自分の担当・全体・終了のタブと
  「답변 필요」（要返信）（最後の発言が顧客）の表示、右に会話。待機中なら「상담 맡기」（相談を担当する）を押さないと入力欄が開かない。
- ルートガード `ProtectedRoute supportOnly` は **UI のガードにすぎない** — 同じルールをサーバーが強制する。オペレーターは管理者
  画面（`adminOnly`）には入れない。

user-service のパス権限に `SUPPORT` を加えた（`/api/user/**`, `/api/auth/user/**`, `/api/auth/logout`, `/api/sse`）—
漏らすとオペレーターのアカウントは **ログアウトすら 403** になる。

## 6. 運用

- デプロイ順序は問わない。user V13（ロール追加）と chat V7（テーブル追加）は互いを待たない。ただし **オペレーターのロールを
  付与する前に** user-service が新しいイメージでなければならない — 古いイメージ（AppRole に ROLE_SUPPORT がない）はそのユーザーを読めない
  （V13 の ROLLBACK-UNSAFE コメント）。
- オペレーターの作り方: 業務用メールアドレスで登録 → 管理者が `PUT /api/admin/update-role?userId=<id>&roleName=ROLE_SUPPORT`
  → そのアカウントのニックネームを顧客に見せる名前に（例: "민지"）。再ログインしないとトークンに新しいロールが載らない。
- 新しい問い合わせ・新しいメッセージはデスクにリアルタイムで届く（§9）。一覧はセーフティネットとして 30 秒ごとにも読み直す。

## 7. 残っているもの

- **チーム・割り当てルール** — チームが複数になったら（注文・配送 / 決済・返金）、そのときに `support_team` とスレッドの `team_id`、問い合わせ種別の
  選択を加える。自動割り当て（ラウンドロビン・負荷基準）もそのとき。
- ~~🐛 既存チャットのカーソル（辞書順 "9" > "10"）~~ → **修正した（§11-④）。**
- ファイル・画像の添付なし。~~相談の満足度・メモなし~~ → **§11 で追加した。** タグはまだない（問い合わせ種別がその一部を担う）。

## 9. オペレーターへのリアルタイム通知

最初はデスクの一覧を 5 秒ごとに読み直していた。新しい問い合わせは最大 5 秒遅れて見え、別のタブで作業しているオペレーターはまったく気づかなかった。

### 流れ

```
顧客 "相談開始"      ── SupportService.openOrGet ─────────────┐
顧客メッセージ       ── Kafka chat → MessageConsumer(保存後) ──┤
オペレーター担当     ── SupportService.claim(コミット後) ─────────┼─► /sub/support/desk  { threadId, kind, senderId, at }
誰でも終了           ── SupportService.close(コミット後) ─────────┘        kind = NEW_THREAD | MESSAGE | CLAIMED | CLOSED
```

- **本文は載せない** — 番号と種類だけである。画面は受け取ったら一覧を読み直す。本文を載せると「このアドレスを購読
  できるか」がそのまま「すべての相談を読めるか」になり、権限判定を REST と STOMP の 2 か所で揃えなければならなくなる。
- 購読は **オペレーター・管理者のみ**（StompHandler — CONNECT 時にトークンから読んだロール）。
- メッセージ通知は **保存された後**（コンシューマー）に出す — オペレーターが通知を見て開いたとき、そのメッセージが履歴にある。
- 通知が失敗しても相談（保存・割り当て・終了）は元に戻さない。一覧は 30 秒ごとにも読み直すので、取りこぼした通知はその間に揃う。
- chat-service は Pod 1 つである（`replicas: 1` — インメモリブローカー）。複数になれば、友だちチャットとあわせて外部ブローカーリレーが必要になる。

### 画面

| 何 | いつ |
|---|---|
| トースト "새 문의가 도착했습니다."（新しい問い合わせが届きました。） | 新しい問い合わせ — すべてのオペレーター |
| トースト "○○ 님의 새 메시지"（○○ さんの新しいメッセージ） | **自分が担当した** 相談で **顧客が** 発言し、その相談を今開いていないとき |
| ブラウザ通知 | 上の 2 つのいずれかで、タブが背面にあるとき。「브라우저 알림 켜기」（ブラウザ通知をオンにする）で権限を得る |
| タブのバッジ | 待機数、自分の担当のうち返信が必要な数 |
| ウィンドウタイトル `(3) …` | 2 つのバッジの合計 — 別のタブで作業していても見える |

### 🔒 あわせて塞いだ既存の穴 — ブローカーアドレスへの直接 SEND

STOMP クライアントが `/pub/**`（アプリケーションアドレス）ではなく `/sub/**`（ブローカーアドレス）へ SEND すると、デフォルトのブローカーはそれを
**コントローラーを経由せずそのまま購読者に配信する。** コントローラーが行っていた送信者の上書きと相談の権限検査をすべて飛ばし、
任意のルーム（他人の相談を含む）に任意の送信者・任意の内容を入れることができた。デスク通知のアドレスに偽の「新しい問い合わせ」をばらまくこともできる。
今は SEND は `/pub/` で始まるアドレスだけを受け付ける。

## 10. 顧客への返信通知

オペレーターが返信しても、顧客が相談画面を離れていると知る術がなかった。

```
オペレーターのメッセージ ─ Kafka chat → MessageConsumer(保存後) → SupportReplyNotifier
      ├─ 送信者が顧客本人？                  → 送らない
      ├─ 顧客が今その相談を購読中？          → 送らない（すでに画面に表示された）
      ├─ 同じ相談に 60 秒以内に送った？      → 送らない（3 行の返信 = 通知 1 通）
      └─ support-reply { receiverId, threadId, messageId, senderName } (キー = 相談番号)
                 → notification-service → 通知 "고객지원팀 답변" (リンク /support, 種類 CHAT_MESSAGE)
```

- **本文は載せない** — 通知テーブル・メールに相談内容（口座番号・住所のようなもの）が残らないように。通知は「返信が来た」とだけ伝え、
  内容は本人だけが開く相談画面で読む。受け取る側もイベントの本文フィールドを使わない（テストで固定）。
- **新しいトピックである理由** — 友だちチャットの `chat` トピック（Avro）に受信者を加えると、スキーマバージョン・履歴・1 リリースの間の旧スキーマでの書き込みが
  ついてくる（docs/55）。相談にしかない事柄なので、小さな JSON トピック 1 つに切り出した。DLT 一覧（ops/02）に加えた（B-41）。
- **種類は `CHAT_MESSAGE`** — 新しい種類を作ると、通知設定画面・SMS・メールの分岐・DB CHECK をすべて増やさなければならない。顧客の「チャット
  通知」設定にそのまま従い、SMS は送られない。相談の返信をメールでも送る必要があるなら、そのときに種類を分ける。
- **「見ている」** ことは STOMP の購読で分かる（`SupportPresence` — SUBSCRIBE で記録し、UNSUBSCRIBE・DISCONNECT で消す）。メモリに
  置く — chat-service は Pod 1 つである。再起動で空になったら「通知がもう 1 通多い」側に間違える。
- **タブを背面に置いた顧客** — 購読中なのでベル通知は来ない。代わりに相談画面がウィンドウタイトルに `(1)` を付け、タブに戻ると
  消す。
- 発行が失敗しても相談メッセージの保存・配信は元に戻さず、失敗は 60 秒の制限に数えない（次の返信が改めて通知する）。

検証: `SupportReplyNotifierTest`（7 — 本文なし・本人除外・見ていれば除外・他人の購読は無関係・60 秒のまとめ・失敗後の再試行・
友だちチャットの無視）、`StompHandlerSupportSubscribeTest` +2（購読・解除・切断、拒否された購読は記録しない）、
notification `SupportReplyNotificationTest`（3）、フロントのウィンドウタイトル（1）。B-41（DLT 一覧）・発行キーのガードを通過。

## 11. 改修 — 1対1サポート画面 · 問い合わせ種別 · 順番待ち · 満足度 · オペレーターツール (2026-09-27)

ユーザーからの報告：「顧客対応用なのに実際はグループチャットになっていて、UI が重なって見えるメニューもある。」

### ① 原因 — 二つのチャットが混ざっていた

- 1対1サポート（`/support`）はすでにあったが、**フッターの「顧客チャット」とホームのショートカット（「販売者とリアルタイムで相談」）がグループチャット（`/chat`）**
  に飛んでいた。お客様はサポートではなく、誰でも入れる公開ルームに入っていた。
- `/chat` はサイトのヘッダーなしでビューポート全体（100vw × 100vh）を覆い、中の入力欄（`position: fixed`、幅 50%）· 会話エリア
  （`absolute`、幅 50%）· 下へボタン（`fixed`、**z-index 200** — アプリ全体で最も高かった）· 右メニューの画面カバー
  （`fixed inset-0`）· 一覧項目の画像（`absolute; left: 120px`）が互いに、そしてヘッダーのメニューと重なっていた。

### ② グループチャットは残し、重なりだけをなくした

- **機能はそのまま**（ルーム一覧 · 検索 · ルーム作成 · 会話 · もっと見る）。名前を「コミュニティチャット」に変え、上部に「1対1サポートへ」を置く。
- サイトのレイアウト（ヘッダー · フッター）内の **カード 1 枚** に移した（`isolation: isolate` — 中の z-index がヘッダーのメニューの上に漏れない）。
  中はすべてフロー（flex）配置：入力欄 · 会話エリアはカード内、下へボタンは会話欄内の `absolute`（z-index 5）。
- サイトのヘッダーと同じ役割をしていた **右メニュー（ホーム · ルーム一覧 · ログアウト · 動作しない設定、外部アバター画像）** は外した。
- 吹き出し横の時刻が `-70px` 固定だったので、「오후 10:46」のように長い時刻が吹き出しを覆っていた → 吹き出しの端に付ける。
- ルームは **ダブルクリック** でしか開けなかった → クリック · Enter · Space。狭い画面ではルームを開くと一覧を畳む。
- 🐛 ルーム履歴の応答が配列でないと（ゲートウェイの HTML エラーページなど）`.reverse()` が例外を投げ、**画面全体がエラー画面**になっていた → 空の履歴として扱う。
- 導線：ホームのショートカット → `/support`（「サポートチームと1対1でリアルタイム相談」）、フッターは「1:1 カスタマーサポート」と「コミュニティチャット」を分けて置く。

### ④ オペレーターデスク（`/support/desk`）

- 3 列：**一覧**（待機 · 自分の担当 · 全体 · 終了 + 種別の絞り込み · 検索）/ **会話** / **お問い合わせ情報**（お客様 · 過去の相談数 · 種別 ·
  開始 · 割り当て · 終了時刻 · お客様の評価 · 内部メモ）。狭い画面では一覧 ↔ 会話、情報はドロワーで。
- **定型文** — ご挨拶 · 確認中 · 注文番号の確認 · お時間をいただく · 対応完了 · 締めの挨拶。入力欄に **入れるだけ**（直してから送る）。お客様の名前が入る。
- 🔒 **内部メモ** — オペレーター同士だけ。返却 · 交代時に次の担当者へ残す。
- **返却** — 担当中の相談を待機列に戻す。お客様には「担当者が交代します」の案内、ほかのオペレーターにはトースト通知（RELEASED）。
- 🐛 カーソル — メッセージ id が数字を入れた **文字列** なので、並べ替え · 比較が辞書順だった（§7）。「最新 20 件」でさえ桁数が変わると
  古いメッセージを選んでいた（`12, 11, 10` であるべきものが `9, 8, 12`）。二つの照会に Mongo の collation `numericOrdering` をかけた —
  グループチャットも同じ照会なので一緒に直る。実際の Mongo 7（Testcontainers）で検証し、collation を外すとテストが上の順序で失敗する。

### ⑦ 残っているもの

- 相談中の **入力中表示 · 既読表示** はない — STOMP の新しい宛先と購読ルール（StompHandler）が必要。
- 添付（画像 · ファイル）はない — 保存先 · 悪性ファイル検査が先。
- 受付時間の文言は辞書に固定 — 実際の受付時間が変わったら辞書を直す（設定値に移せる）。
- コミュニティチャットのルームは依然として **ログインした誰でも作れる**（保存の要望）。通報 · 管理機能はない。
