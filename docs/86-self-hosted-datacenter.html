ecommerce-msa オンプレミス構成案

今は OCI Ampere ノード一台と Cloudflare Tunnel で動いている ecommerce-msa を自社データセンターへ移すときのハードウェアとネットワークの構成です。リポジトリの実測値と設計判断から出発しました。

読む前に — この構成案の前提

  • リポジトリには SLO と目標トラフィックがありません。以下の仕様はリポジトリの実測値から推定した出発点で、実機で測り直して調整する必要があります。
  • 実測値は デスクトップ一台の上の VM が CPU を分け合う実習クラスタで得たものです。リポジトリの文書(docs/83)も絶対値として使わないよう書いています。
  • リポジトリの運用判断は PostgreSQL · MongoDB をマネージドに任せることです(docs/23)。自社データセンターにはマネージドがないので、DB の冗長化を自前で行う必要があります。これが今と最も大きく変わる点です。

データノードをこう決めた理由

項目リポジトリの実測 · 判断だから
容量商品 2,108B · 注文約 1,100B · ユーザー約 1,012B。商品 2,000 万 ≈ 39GiB(投入中は WAL の余裕 59GiB が必要)、1 億 ≈ 196GiB。docs/19 · docs/83 · docs/79PG 用の NVMe 2×1.92TB RAID1 なら 1 億商品でも余裕があります。
メモリ本番(商品 200 万)でフィルターの count 一回がランダムブロック読み 11 万回、42.9 秒。その件数数えは d837605d7902 でなくしましたが、まれな条件は今もカテゴリを走査します。docs/83 §2.8 · docs/85 §8作業集合が RAM に収まる必要があります。PG に 64GB 以上を与えます。
接続DB を使うサービス 9 個(catalog はデータソース 2 個)× プール 5 × HPA 最大 3 → 最悪約 140。実習の PG は max_connections=300。負荷測定で接続待ちは CPU 不足の症状でした — まずプールを増やすことはしません。docs/83プーラーを使うならトランザクションモードは禁止です(ops/25 の警告)。HPA の最大を上げたらこの計算からやり直します。
ディスクの分離PG と Kafka はどちらも fsync が多いです。同じノードでも NVMe の組は分けます。
k8s の外に置くexternal オーバーレイが既にあり、ConfigMap のエンドポイントを変えるだけです。コードはそのままです。docs/32 · k8s-overlays/externalk3s のアップグレードやノード障害がデータに及ばず、VLAN のファイアウォールでアクセスを強制できます。
バックアップDB 5.6GB → base.tar.gz 821MB(約 15%)、復元 1 分 52 秒。WAL アーカイブは今は同じボリュームに溜まります。docs/22 · ops/29pgBackRest か WAL-G でバックアップサーバーへ WAL を送り続けます。お金が絡むデータの RPO 5 分の目標のためです。

もっと小さく始めるなら 32 コア · 256GB のサーバー 3 台に k3s(サーバー兼エージェント)とデータ VM を同居させる方法もあります。費用は約 1/3 ですが、一台が落ちるとアプリと DB メンバーを同時に失います。

2 · ネットワーク

インバウンドのポートなしで、VLAN 五つで

青い点線は論理的な経路です。実際のパケットはファイアウォールと ISP を経て出ます。MGMT は実際には別の OOB スイッチにつながります。

外部からの入口 — Cloudflare Tunnel をそのまま維持することを勧めます

  • 今の構造は インバウンドのポート 0 個です。cloudflared 2 個が別々のノードから外へ接続します。k8s-overlays/prod/cloudflared.yaml
  • 決済 Webhook(Stripe、PortOne)と OAuth のコールバックもこのトンネルで入ってきます。だから公開 IP、DMZ、外向きの TLS 証明書が要りません。
  • データセンターのファイアウォールは cloudflared のアウトバウンド 7844(TCP/UDP)だけを開ければ済みます。

Cloudflare を外して自前の公開 IP · L4 LB で受けるなら、コードも変える必要があります。流入制限が CF-Connecting-IP を「エッジが上書きするので偽装できない」と信頼しています(CustomUserKeyResolver)。トンネルがなければ、このヘッダーはクライアントが自由に送れます。ほかに Ingress の host、ACME 証明書、WAF と DDoS 対策が新たに必要です。

帯域と遅延

  • 内部:アプリのトラフィックは小さいです。実習の天井が成功毎秒約 1,400 件の小さな JSON です(docs/83)。10GbE でも足り、25GbE は複製とバックアップの余裕です。
  • インターネット:最大の変数は画像です。今はブラウザが S3 から直接取るので自社回線を通りません。画像を MinIO でデータセンター内に入れると画像のバイトがすべて自社回線を通るので、回線はその基準で決める必要があります。
  • 遅延:一つの要求が照会を 20 回ほど送ります。往復 30ms なら 600ms になります(docs/32)。アプリと DB は同じラック · 同じ L2 に置き、同期複製を別サイトまで伸ばさないでください。
  • 共通インフラ:内部 DNS と NTP が必要です。JWT、TOTP 二段階認証、Kafka、証明書がすべて時計に依存します。電源は二重電源、A/B PDU、UPS で。

進める順序

  1. 上の 1〜4 を先にリポジトリで直します。メッセージ · キャッシュ · ドキュメントストア · DB の冗長化です。
  2. 実機で ops/53(k6)で測り直します。実習の数値は 12 コア · 24 スレッドを VM が分け合った結果なので、専用のハードウェアでは天井が変わります。
  3. その結果でワーカーの台数と HPA の最大値を調整します。今の最大 3 は実習の大きさに合わせた値で、変えたら PG の接続数の計算もやり直します。
