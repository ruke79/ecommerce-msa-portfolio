### 1.1 お知らせの掲載 → 通知: なぜ「お知らせ型」の構造が別に必要だったか

いちばん単純な方法は、お知らせが公開されるときに **ユーザー数だけ `notification` 行を作る** ことだ。
その方法は使わなかった。ユーザーが 10 万人なら、お知らせ 1 件で 10 万 insert になり、テーブルは
ユーザー数 × お知らせ数に膨らみ、お知らせの内容を直すと 10 万行をすべて直さなければならない。

代わりに **お知らせごとに 1 行**（`notification.broadcast_notification`）を置き、個人ごとには
「読んだか」だけを別に残す（`notification.broadcast_read`）。既読行は **ユーザーが実際に
何かをしたときにだけ** 作られるので、お知らせを掲載しても即座に作られる行は 0 だ。

| 部品 | 場所 |
|---|---|
| 発行 — お知らせが **非公開→公開に切り替わった瞬間にだけ** | `catalog-service` `NoticePublishedProducer`（コミット後に発行） |
| トピック | `notice-published`（`ops/02` に登録 — ガードレール B-41） |
| 受信 | `notification-service` `BroadcastEventListener` |
| 保存 | `BroadcastNotification` ＋ `BroadcastRead`（`V4__broadcast_notification.sql`） |
| 一覧 | `GET /api/notifications` — 個人通知と **合わせて** 時間の降順、各項目に `scope` |
| バッジ | `GET /unread-count` — 2 つの出どころの合計 |
| 既読・非表示 | `PATCH /broadcasts/{id}/read`、`DELETE /broadcasts/{id}`（自分の一覧からだけ消える） |
| 管理者の送信 | `POST /api/notifications/admin/broadcasts` ＋ `/admin/broadcast` 画面 |
| 認可 | `AdminOnlyInterceptor` — `/api/notifications/admin` プレフィックス配下は **読み取りまで** 管理者のみ |

注意点が 2 つ:

- **`scope` を画面が必ず見なければならない。** 2 つのテーブルがそれぞれ TSID を使うので、id だけでは
  区別できない。間違った経路に送ると 404 になるか — もっと悪いことに — たまたま同じ id の
  他人の個人通知に触れてしまう。
- **時刻は UTC に統一する。** 合わせてソートする一覧なので、片方だけシステムのタイムゾーンだとそちらが
  常に上に来て、画面はそれを UTC として解釈し、いつまでも「たった今」と表示する。
  `UtcClockGuardrailTest` がこのサービス全体を検査する。

全体通知は **メール・SMS では送られない。** 全ユーザーに SMS を送るのは料金
事故であり、一斉メールは送信元の評判を下げる。`MailKind`・`SmsTemplates` の exhaustive switch
が、新しい通知の種類を追加するときにこの判断を強制的にやり直させる。

## 1. お知らせ — ある。ただし通知と切れている

| 層 | 状態 |
|---|---|
| モデル `Notice`（title、body、pinned、published、publishedAt） | ✅ `catalog-service/model/Notice.java` |
| `NoticeService` · `NoticeRepository` | ✅ あり |
| 管理画面 `/admin/notice` | ✅ `pages/admin/Notices.jsx`、ルート登録済み |
| 公開一覧 `/notice`、詳細 `/notice/:id` | ✅ `pages/notice/NoticeList.jsx`、`NoticeDetail.jsx` |

**欠けているもの:** お知らせを掲載しても（`published = true`）**誰にも知らせない。**
`NoticeService` に Kafka の発行が 1 行もない。ユーザーは `/notice` に自分で入って初めて知る。

→ 掲載時に `notice` トピックにイベントを 1 つ発行し、`notification-service` がそれを受けて
`NotificationType.NOTICE_PUBLISHED`（新設）の通知を作ればよい。通知のインフラはすでに全部揃っている。

## 2. 通知 — ほぼ全部ある。ところが **8 種のうち 3 種は作る側がない**

### あるもの

|---|---|
| `notification-service`（独立サービス） | ✅ |
| REST API — 一覧・未読数・既読処理・全件既読・削除・受信設定 | ✅ `NotificationController` `/api/notifications` |
| 受信設定 `NotificationPreference`（メール／SMS のチャネル別） | ✅ |
| メールテンプレート `MailTemplates`（KR/JP の二言語） | ✅ |
| SMS テンプレート `SmsTemplates`（KR/JP） | ✅ |
| 携帯電話認証 `/phone/verification` | ✅ |
| SSE リアルタイムプッシュ | ✅ `user-service/NotificationController` `/api/sse` |
| フロントのベルアイコン | ✅ `NotificationBell.jsx` — **ヘッダーにマウントされている**（`Header.jsx:69`） |
| フロントの API クライアント ＋ テスト | ✅ `api/notificationApi.js` |

### 🔴 欠けているもの: 通知の種類 8 個のうち 3 個は **生成される経路がない**

`NotificationEventListener` が実際に購読しているトピックは 4 つだけだ:

| トピック | 作る通知 |
|---|---|
| `payment` | `PAYMENT_COMPLETED` / `PAYMENT_FAILED` |
| `order` | `ORDER_PLACED` |
| `chat` | `CHAT_MESSAGE` |
| `user-presence` | `FRIEND_ONLINE` |

残りの 3 つは **メールの件名・SMS の文言・受信設定のポリシー・テストまで全部作っておきながら、作る側がない**:

- **`SHIPPING_UPDATED`** — `delivery-service` の `DeliveryStatusPublisher` が
  `delivery-status` トピックに配送状態を発行している。ところが **このトピックを購読するリスナーが
  コードベース全体に存在しない。** 配送状態が Kafka に出ていって、そのまま消える。
  → `NotificationEventListener` に `@KafkaListener(topics = "delivery-status")` を 1 つ足せばよい。
  3 行の作業で「発送しました」通知が丸ごと生まれる。**コストパフォーマンスが最も良い。**
- **`COUPON_ISSUED`** — `coupon-service` がクーポン発行イベントを発行していない
- **`SECURITY_ALERT`** — 新しいデバイスでのログインを検知するロジック自体がない。
  `NotificationPreference` は「セキュリティ通知はユーザーがオフにしても送る」という例外処理までしてある

`useInfiniteScroll` · カーソルページング（docs/43 D1）と **まったく同じパターン** だ — 土台を全部作って、
最後の一マスをつながなかった。

### 欠けているもの: 管理者が通知を直接送れない

今の通知は **すべてシステムイベントからだけ** 生まれる。管理者が

- 特定のユーザーへの個別通知
- 全体／セグメント向けのお知らせ的な通知

を送る経路がない。`/admin/notification` 画面 ＋ `POST /api/notifications/broadcast`
（管理者専用）が必要だ。ただし全体送信はユーザー数だけ行が作られるので、個人ごとの行を
作らずに、「お知らせ型通知」は別テーブル ＋ 既読表示だけを個人ごとに置く設計が正しい。

## 3. イベント／特集 — **これは本当にない**

「イベント」をセール・特集・タイムセールのような販促と捉えると、それに該当する概念がコードにない。
いちばん近いもの:

| 既存の機能 | できること | できないこと |
|---|---|---|
| `content.home_section`（`/admin/home`） | ホームにセクションを配置 | 期間、対象、割引率がない |
| `Banner`（`/admin/banner`） | バナー画像 ＋ リンク | 画像にすぎない |
| `coupon-service` | クーポンの発行／使用 | 自動発行の条件、期間キャンペーンがない |
| `ProductSku.discount` | 商品ごとの割引率 | 商品ごとに直接直す必要がある。期間もない |

必要な最小モデル:

```
content.event
  ├ id, title, slug
  ├ starts_at, ends_at          ← 今どこにもないもの: 期間
  ├ banner_image_url, link_url
  ├ status (DRAFT / SCHEDULED / ACTIVE / ENDED)
  └ event_product (event_id, product_id, discount_rate)
```

管理画面（`/admin/event`）で作り、スケジューラーが `starts_at` に `ACTIVE` に変えながら
`event` トピックに発行 → `notification-service` が `EVENT_STARTED` 通知を作る。

**注意点が一つ。** 期間割引を `ProductSku.discount` に上書きしてはいけない。イベントが終わるときに
元の値に戻す必要があるが、その間に管理者が商品を修正すると、復元が元の値を上書きしてしまう。
割引は **イベント側に置き、照会時点で合成** しなければならない。

### 3.1 実装 — 照会時に合成

上の警告どおりに作った。`product_sku.discount` には **最後まで手を付けない** — 常に
「特集とは無関係な常時割引」という一つの意味だけを持つ。

| 部品 | 場所 |
|---|---|
| スキーマ | `catalog-service` `V11__event.sql` — `content.event` ＋ `content.event_product` |
| モデル | `Event`（状態・期間） ＋ `EventProduct`（`@Embeddable` の値型） |
| 状態 | `EventStatus` DRAFT → SCHEDULED → ACTIVE → ENDED |
| 割引の合成 | `EventPricing` — productId→割引率のマップを 1 分ごとに更新し、照会結果に上乗せする |
| 遷移 | `EventScheduler`（1 分） ＋ `EventService.advanceDueEvents` |
| 通知 | `EventStartedProducer` → `event-started` → `BroadcastEventListener.onEventStarted` |
| 管理者 | `/api/content/admin/events` ＋ `/admin/event` 画面 |
| 公開 | `/api/content/events`、`/api/content/events/{slug}` ＋ `/event`、`/event/:slug` |

**合成ポイントは一つだ。** `ProductService.convertToDto` — エンティティから DTO へ行く唯一の
通り道だ。以前は照会経路ごとに `ProductMapper::toDto` を直接呼んでいたが、それだと新しい経路が
できるたびに合成を 1 行ずつ足す必要があり、抜かすと **その画面だけ定価を表示する。** カートの
経路（`toCartProductInfo`）は DTO の形が違うので別に上乗せする — そこが実際に請求される金額だ。

**常時割引と特集割引のうち大きいほうを使う。** 代替案はどちらも実際に問題を生む:

- *特集が上書きする* → 常時 40% の商品を 20% の特集に入れると **価格が上がる。**
  管理者はセールを追加したのに、顧客は値上がりしたのを見る。
- *累積* → 40% と 20% が 52% になる。誰もその数字を意図しておらず、特集に商品を
  入れることが危険な行為になる。

**キャッシュ。** 合成された値が Redis に入る。そのままにしておくと、特集が終わった後も TTL が過ぎる
まで割引価格が見え — もっと悪いことに — その価格でカートに入ってしまう。スケジューラーが状態を
遷移させるとき（開始・**終了の両方**）に商品キャッシュを空にする。

**マルチインスタンス。** インスタンスが 2 つならスケジューラーも 2 つで、両方が開始通知を発行するとすべての
ユーザーが同じ通知を 2 つ受け取る。`EventRepository.transition` が
`where status = 'SCHEDULED'` の条件付き UPDATE なので、先に到着した 1 つだけが 1 を受け取り、その 1 つだけが
発行する（実際の PostgreSQL 16 で 2 回目の UPDATE が 0 を返すことを確認した）。

#### 一緒に直したもの — 🐛 バックエンドの割引価格の計算式

`ProductService.toCartProductInfo` が `price - price / discount` を使っていた。「定価から
定価を割引率で割った値を引く」という意味で何の意味もなく、**割引率が大きいほど割引幅が
小さくなっていた** — 10,000 ウォンに 50% 割引なら 9,800 ウォン（=2%）、70% 割引なら 9,857 ウォン（=1.4%）。

フロントエンド（`util/pricing.js`）はすでに直っていて、**この経路だけが残っていた。** そのため詳細
画面は 50% の割引価格を表示するのに、カートに入れると 2% の割引価格が入っていた — 同じ商品の
価格が画面ごとに違っていた。特集の割引もこの計算を通るので、先に正した。

### 3.2 カテゴリ対象 · 顧客層 · 付属クーポン

§3.1 の「まだないもの」3 つをつないだ。3 つは別々に見えるが、**一つの決定** から来ている:
セグメント割引を陳列価格ではなく **クーポンで** 提供するということだ。

#### 🔴 なぜセグメントで陳列価格を分けないのか

いちばん直感的な実装は「新規会員にだけ 20% 安く見せる」ことだ。使わなかった。理由は 3 つある。

1. **商品の照会には身元がない。** ゲートウェイの catalog-service 公開ルートには
   `JwtAuthorization` が付いていない — 付けると非会員が商品を見られない。一覧と詳細を描画するとき、
   サーバーは見ている人が誰なのかを知らない。
2. **キャッシュがセグメントの数だけ分かれる。** 商品一覧は Redis にキャッシュされる。人ごとに価格が違えば
   キャッシュキーにセグメントを入れる必要があり、セグメントが増えるたびにヒット率が下がる。
3. **画面ごとに価格が変わる。** 身元がわかる画面とわからない画面が混ざると、さっき直した
   「一覧で 30% を見て入ったのに詳細は定価」というバグが **構造的に** よみがえる。

だからセグメント割引はクーポンで提供する。クーポンは決済時点で適用され、そのときは身元が確実で、
陳列価格は誰が見ても同じだ。実際のコマースが「新規会員は追加 20%」をクーポンで提供する理由でもある。

#### カテゴリ単位の対象

| | |
|---|---|
| スキーマ | `content.event_category`（V12） |
| モデル | `EventCategory`（`@Embeddable`、`EventProduct` と同じ値型） |
| 展開 | `EventPricing.expandCategories` — 照会時点で商品へ |

**展開した結果は保存しない。** 保存するとその瞬間に一覧が固まり、特集が始まった後にその
カテゴリに登録された商品が漏れる — 管理者はカテゴリを指定したつもりなのに新商品だけが
定価のまま残り、その事実は顧客からの問い合わせでようやく明らかになる。

商品単位の指定はなくしていない。同じカテゴリの中で一部だけさらに割り引くケースがある。重なった場合は
**高い割引率** が勝つ — 順序とは無関係だ。

#### 対象顧客層

`AudienceSegment`（ALL · NEW_USER · EXISTING_USER、`common`）。**クーポンを誰が受け取れる
か** だけを分ける。

判定は **user-service** が行う（`SegmentService`、`GET /api/auth/user/segments`）。「新規とは
何日までか」は自分たちのポリシーで、登録日もそちらだけが持っている — 登録日を渡してそれぞれが計算すると、基準を
30 日から 14 日に変えるときに 1 か所を漏らす。

2 つの点に特に気をつけた:

- **登録日がなければ新規ではない。** `createdAt` は監査フィールドなので空のことがあり、そのとき
  新規とみなすと **すべての古いアカウントが新規専用の特典を受け取る。** 特典を誤って与えるほうが、与え損ねる
  ほうより元に戻しにくい。
- **セグメントを確認できなければ与えない。** user-service の照会が失敗したときに通してしまうと、
  対象でない人にクーポンが出ていく。

#### 付属クーポン — ばらまかずに受け取ってもらう

```
ユーザーが「クーポンを受け取る」
  → coupon-service  POST /api/coupon/events/{slug}/claim
  → catalog         GET  /api/content/events/{slug}/coupon-offer   (条件・状態)
  → user-service    GET  /api/auth/user/segments                   (対象判定)
  → coupon 発行
```

**開始時に全ユーザーへは発行しない。** そうするとユーザー数だけ coupon 行ができる —
お知らせ通知で個人ごとの行を作らないことにしたのと同じ問題で、しかも大半は使われない。
受け取った人だけに行ができれば、書き込み量が実際の関心に比例する。

**重複受け取りの防御は新しく作らなかった。** coupon テーブルの `uk_coupon_name_user_id` が、一人が
同じ名前のクーポンを 2 回持てないようにすでに防いでいる。「すでに受け取った」は **200** だ —
ユーザーから見れば成功と変わらない。

**条件は受け取るたびに catalog に問い合わせる。** Kafka であらかじめ押し込んでおくと、特集が早く終了したときに
クーポン側がそれを知らずに発行し続ける。受け取りはまれな操作なので、そのとき問い合わせるほうが常に正しく安い。
状態の判定を coupon-service がやり直さないのも同じ理由だ — 同じルールが 2 か所にあると、
いつかずれる。

**クーポンの適用範囲は特集の対象を引き継ぐ。** 商品を指定したならその商品にだけ、カテゴリを
指定したならそのカテゴリにだけ。広げると「この特集のクーポン」が無関係な商品に効いてしまい、管理者が意図した
割引幅を超える。

#### 🐛 一緒に直したもの — メールアドレスでクーポンを発行する経路が一度も動作したことがない

`CouponService.create` は重複チェックでだけメールアドレスを数値 id に変換し、肝心のクーポン作成時には
`Long.parseLong(request.getUserId())` を再び呼んでいた — メールアドレスを数値としてパースするので
`NumberFormatException` だ。チェックは通って保存で爆発する形なので、「メールアドレスでクーポンを
発行する」コードがあるのに実際には 500 しか出なかった。解決した id を最後まで持っていくように直した。

#### まだないもの

- **サブカテゴリ単位の指定** — 対象は最上位カテゴリだ。クーポンの `CouponScope.CATEGORY` と
  同じ単位に揃えた。

## 3.3 購入履歴と顧客ランク

セグメントが登録時点の一つしか見ていなかったのを **3 つの軸** に広げた — 登録時点／購入履歴／ランク。
障害になっていたのは判定ロジックではなく **データ** だった。注文は order-service にあり、ランクの基準は
user-service のポリシーなので、この 2 つをどうつなぐかがこの作業のすべてだ。

### ランクは何で決めるか

直近 **3 か月の実決済額** だ。生涯累計ではない — 5 年前に一度大きく買って去った人と、
先月も買っている人が同じランクなら、ランクが「現在の顧客」を指せない。基準金額は
設定（`user.tier.*`）で、デフォルト値は 20 万／50 万／150 万ウォンだ。

**Amazon を参考にしたというのは**、名前ではなく姿勢のことだ。Amazon 式ランクの特徴は、ランクを自慢の種に
しないこと — ポイント・バッジ・「次のランクまであといくら」のような仕掛けで消費を迫らず、
ランクはもっぱら **特典が届く形** でだけ表に出る。だからランク画面は作らず、
ランクは特集クーポンの対象条件としてだけ使われる。降格も知らせない —「ランクが下がりました」
という通知は、ユーザーにできることが消費しかない通告だ。

### 🔴 なぜリアルタイムではなくバッチなのか

セグメントの照会は **クーポン発行の経路** にある。そこで order-service を同期呼び出しすると、注文
サービスの障害がそのままクーポン発行の障害になる。そしてランクはもともとリアルタイムである理由のない
値だ — 実際のランク制度はすべて日／月単位で更新している。

1 日 1 回（UTC 19:10 = KST 04:10）バッチが `users.users` にランクを書き込み、読む側は保存された
値だけを見る。代償は正直に書いておく: **今日大きな注文をした人は明日ゴールドになる。**
管理画面にもそう書いておいた。

### 🔴 半分しか受け取っていない一覧で降格しない

order-service は **最近購入がある顧客だけ** を返す。そのため「レスポンスにない」は 2 つの
意味になりうる — ウィンドウから外れた（降格すべき）か、まだ受け取っていない（降格してはいけない）か。
この 2 つを混ぜると、**通信障害一つで全顧客のランクが吹き飛ぶ。** すでに発行された上位ランクのクーポンは
回収できないので、事実上元に戻す方法のない事故だ。

だからバッチが最後まで回りきれなければ、降格を **スキップする。** カーソルを使い切ったときだけ降格し、
その基準は **回の開始時刻** だ（終了時刻にすると、今昇格させたばかりの人まで元に
下がってしまう）。降格対象を探す根拠が `tier_computed_at` なので、監査フィールドのように見えるが、
消すと降格が止まる。

### ランクのセグメントはすべて「以上」だ

ゴールド会員は `TIER_SILVER` と `TIER_GOLD` を **両方** 持つ。そうすれば受け取る側が **単純な
包含チェック** だけで「シルバー以上」を判定でき、ランクの高低を知っている場所が `CustomerTier`
一つに保たれる。逆にしていたら — ゴールドが `TIER_GOLD` だけを持つなら — 「シルバー以上のクーポン」を
ゴールド会員が受け取れないという、ユーザーに説明できない動作になる。

そのおかげで「一般ランクのみ」のような条件はこの軸では作れない。意図的だ。ランクの低い人を
ピンポイントで狙う販促は、`NEVER_PURCHASED` のように **行動** で表現するほうが正確で、
ユーザーにとっても不快感が少ない。

### 購入履歴は生涯基準だ

`PURCHASED` / `NEVER_PURCHASED` には期間のウィンドウがない。ランクは直近 3 か月を見るので、長く休んでいた
常連は一般ランクに落ちるが、その人が **初回購入クーポン** まで受け取ってはいけない。そのため
降格時に `recent_paid_amount` は 0 に戻すが、`lifetime_order_count` には手を付け
ない。

`NEW_USER` とも違う。登録は 2 年前なのにまだ初回注文がない人が `NEVER_PURCHASED`
であり、昨日登録してすぐ買った人はそうではない。初回購入を促すクーポンの本当の対象は、登録日
ではなくこちらだ。

### 🔒 全顧客の決済金額を抜き取れないように

`GET /api/order/internal/purchase-stats` は `/api/auth/user/id` と同じルールで塞ぐ —
ゲートウェイを通ったリクエストには `User-Role` ヘッダーが付くので、**ヘッダーがある = 外部からのリクエスト** であり、
そのときは管理者だけを許可する。個別の注文照会には所有権チェックがあるが、集計には「自分のもの」という
概念がないので、ここで塞がなければ塞ぐ場所がない。

渡すのは **合計だけ** だ。注文を丸ごと渡すと配送先・連絡先・商品までサービス境界を
越えるが、ランクを付けるのに必要なのは合計であって明細ではない。

### 一緒に整理したもの — 「決済済みの注文」の定義

売上・購入履歴・ランクがそれぞれ状態を列挙していると、いつかずれる。`OrderStatus.PAID_STATUSES`
一つにまとめ、**決済済みのほうを列挙する** — 状態が一つ増えたときに除外する方式だと新しい状態が
静かに売上に計上され、列挙する方式だと静かに外れる。お金を水増しするほうがはるかに悪い
失敗だ。フロントエンドの `util/orderStatus.js` も同じ方向で、言語が違って共有できないので、
サーバー側に **状態が増えると失敗するテスト** を置いた。

### 3.4 ランク画面 — 「なぜ自分はこのランクなのか」に答える

ランク条件のクーポンができた以上、「なぜ自分はもらえないのか」に答える場所が必要だった。プロフィール画面の下に
`TierStatus` セクションとして入れた。別タブを作らなかったのも選択だ — タブになるとその画面の
名前が「ランク」になり、ランク自体が目的のように見える。

#### 🔴 この画面に **ないもの** が設計だ

進捗ゲージも、「ゴールドまであと 32 万ウォンです」もない。計算して入れるのは簡単で、入れた瞬間に
画面の性格が変わる — **「あなたの特典」が「あなたがもっと使うべき金額」になる。** ランクを
スコアのように展示しないことが §3.3 で決めたトーンであり、画面がそのトーンを守ってはじめて筋が通る。

その代わり **根拠はすべて示す**: 現在のランク、判定に使われた金額、基準金額、最後の計算時刻。
「なぜ自分はシルバーなのか」に画面が答えられなければ、その質問はカスタマーサポートへ行く。

ユーザーがその数字で自分で引き算するのは妨げない。**知りたい人に隠すことと、
こちらから先に突きつけることは違う** — 前者は説明で、後者は誘導だ。テストがこの線を
固定する（`/남았습니다|까지 [\d,]+원|더 구매|달성/` が画面にあってはならない）。

⏱️ **更新時点を必ず書く。** ランクは 1 日 1 回付け直されるので、「今日大きな注文を
したのに、なぜそのままなのか」が必ず出てくる。画面があらかじめ答えておく。

🔒 本人のものだけを見る。ランクはその人の **消費規模** をそのまま露わにする値だ。基準金額も
サーバーが返す — 画面にハードコーディングすると、設定を変えた日から案内が嘘になる。

### 3.5 送料の分離 — ランク特典より先にやるべきことだった

「ランク別の送料無料」を入れようとして確認したこと:

- 送料は **商品ごとに** 付く（`product.getShipping()`）
- cart-service が `computeCartTotal` で `price×qty + shipping` として **合算してしまう**
- `CartProductDto` に **shipping フィールドがなかった** — カートが別のサービスに渡るときに
  送料の情報が消える
- `Order.shippingPrice` は宣言されているが **一度も埋められたことがない**（常に 0）
- `OrderDto.shippingPrice` もあるのに **移す行がなかった** — 2 つの穴が互いを隠し合っていた

つまり注文時点でサーバーが知っているのは「送料込みの合計額」一つだけだった。送料無料以前に、
**ユーザーが送料をいくら払うのかが決済画面でわからない** ことのほうが急を要する問題だった。

#### 🐛 一緒に明らかになったもの — クーポンが送料まで割り引いていた

送料が合計額に溶け込んでいるので、scope によって割引の基準が分かれていた:

| クーポン | 割引の基準 | 結果 |
|---|---|---|
| 制約 **なし** のクーポン | `cartTotal`（送料込み） | **送料まで割引** |
| 制約 **あり** のクーポン | 対象行の `price×qty` | 送料は割り引かない |

同じカートなのに、クーポンの種類が違うだけで割引額が違っていた。計算機のコメントにも
「cart-service の cartTotal と行の合計がずれたら（送料の処理など）」と書かれていた —
わかってはいたが、分離できなかったのでそのままにしていた箇所だ。

今は **どちらの場合も対象行の商品金額の合計** が基準だ。`scope=ALL` は「すべての行が
対象」というだけで特別な経路ではないので、計算機から分岐が消えた。

⚠️ この変更で、制約なしのクーポンの割引額は **送料の分だけ減る**。与える額が減る方向なので
元に戻しやすく、送料を割り引いていたほうが意図されたことはない。

#### 画面

決済サマリーが **商品金額／送料／合計** の 3 行になった。0 ウォンを「無料」と言い換えない
— 本当に 0 ウォンなのか、まだ計算されていないのかが区別できない。

古いカートキャッシュには `shipping` がないので `null` で来る。そのときは **0 とみなす** — 送料を
ないものとみなすほうが安全だ。逆に推測すると、商品金額が実際より小さく表示される。

#### これでランク別の送料無料は 1 行だ

`OrderPricing` が送料を別に把握しているので、ランクを問い合わせてその値を 0 にすればよい。
残っているのは **販促ポリシー**（どのランクからか、最低注文額があるか）だけだ。

#### 常時割引率は依然としてクーポンでのみ

陳列価格をランクで分けるのは §3.2 の理由で不可能だ（公開ルートに身元がない、
Redis キャッシュの分割、画面ごとに価格が変わるバグの再発）。そのためランク別の常時割引は
**月次の自動発行クーポン** が現実的な形だ。

### まだないもの

- **ランク別の送料免除** — コードはもう準備できた。ポリシーを決めるだけだ。
- **ランククーポンの月次自動発行** — バッチ一つで済むが、割引率・発行日を決める必要がある。
- **インスタンスが複数あるとバッチが複数回回る** — 結果が同じ演算なので壊れはしないが、
  order-service をその分多く呼ぶ。単一ノードなので今は問題がなく、増えたら
  `user.tier.scheduler-enabled` で 1 インスタンスでだけオンにすればよい。

## 4. `SECURITY_ALERT` — 新しいデバイスでのログイン

`NotificationType.SECURITY_ALERT` は、メールの件名・SMS の文言・メール種別のマッピングはもちろん、
受信設定に **「セキュリティ通知はユーザーがオフにしても送る」** という例外まで入っていた
（`NotificationPreference.shouldSendSms`）。すべて揃えておきながら **発行する側だけ** がなかったので、
アカウントが乗っ取られてもユーザーには知る方法がなかった。

なかったのは「このログインは初めて見るデバイスか」に答える根拠 — 比較するための履歴だ。

| 部品 | 場所 |
|---|---|
| スキーマ | `user-service` `V8__known_device.sql` — `users.known_device` |
| 識別 | `DeviceIdentity` — デバイス Cookie（乱数） · ラベル · IP のマスキング |
| 判断 | `DeviceRecognitionService` — 新しいデバイスか、知らせるべきか |
| 発行 | `SecurityAlertProducer` → `security-alert` トピック |
| 受信 | `NotificationEventListener.onSecurityAlert` |
| 画面 | `GET/DELETE /api/user/profile/devices` ＋ セキュリティ設定の `LoginDevices` |

### デバイスを何で識別するか — Cookie 一つ

ブラウザに httpOnly Cookie として埋め込む **乱数** だ。User-Agent や IP でフィンガープリントを作る方式は使わ
なかった:

- IP はモバイルでは頻繁に変わる — 地下鉄でログインするたびに「新しいデバイス」になる
- User-Agent はブラウザが更新されるたびに変わる

どちらか一つでもフィンガープリントに入れると **通知がノイズになり、ノイズになるとユーザーは本物の警告も
無視する。** Cookie を消すと新しいデバイスとして捕捉されるが、それは誤検知ではない — Cookie を消したブラウザは、
サーバーから見れば初めて見るブラウザと区別がつかない。

### 🔒 トークンをハッシュで保存する理由

この値は認証手段ではない。知っていてもログインはできない。しかし **セキュリティ通知をオフにできる
値** だ — パスワードをすでに知っている攻撃者がこれまで知れば、通知なしに静かに入ってくる。DB が
漏れてもその能力まで一緒に漏れないよう、SHA-256 だけを保存する（登録確認トークンと同じルール）。
`DeviceDto` がその値をレスポンスから外すのも同じ理由だ。

### ノイズの調整

- **最初のデバイスには知らせない。** 登録して初めてログインした人に「新しいデバイス」は意味を
  なさない — 比較するデバイスがない。第一印象が無駄な警告だと、後の本物の警告も無視される。
- **デバイス数に上限を設ける**（デフォルト 20）。なければ、Cookie を消すブラウザ一つがこのユーザーの
  行を無限に増やす。
- **同時ログインは一度だけ知らせる。** 同じユーザーが同時に 2 回ログインすると、どちらも「新しいデバイス」
  とみなして保存を試みる。`uk_known_device` が片方を止め、止められた側は知らせない。

### 個人情報

- IP は **マスキングして保存する**（`203.0.113.xxx`）。原文はどこにも残らない — 保存にも、
  発行にも、レスポンスにも。
- User-Agent の原文の代わりに `"Chrome · Windows"` のようなラベルだけを残す。
- ログにメールアドレス・IP を残さない。事実（userId、deviceId）だけを残す。

### ⚠️ IP は表示専用だ

`X-Forwarded-For` はクライアントが偽造できる — ゲートウェイの `CustomUserKeyResolver` が
同じ理由でこのヘッダーを **捨てている**（レートリミット回避のシナリオ）。ここで使う理由は、この値が
もっぱら通知の文言にだけ入り、**どんな判定にも使われない** からだ。偽造しても、自分の
通知の IP 表示を変えるだけで、新しいデバイスかどうかは Cookie が決める。

### どんな失敗もログインを妨げない

デバイスの記録はログインにとって **付随的** なものだ。ここで例外が上がると、パスワードを正しく入れたユーザーが
ログインできない — セキュリティ通知を付けようとしてサービスを止めることになり、それははるかに悪い。
発行のタイムアウトも 3 秒と短く取った（ログインのレスポンス経路だ）。

### ⚠️「記憶を消す」はログアウトではない

そのデバイスでログインしている状態があれば、そのまま残る。意味は「次にそのデバイスでログインしたら新しい
デバイスとみなして再び知らせる」だけだ。文言が「ログアウトさせる」と読めてしまうと、ユーザーは対処したと
信じてそれ以上何もしない — 本当に必要なのはパスワードの変更で、画面がそう
伝えている。

### まだないもの

- **ソーシャルログインの経路** には付けていない。`OAuth2SuccessHandler` はリダイレクトで終わる
  別のフローなので（アクセストークンも作らない）、同じ場所に入れられない。
- **位置（都市・国）** がない。IP → 地域の変換には外部 DB が必要で、マスキングされた IP では
  精度が落ちる。今はマスキングされた IP だけを表示する。
- **セッションの強制終了** がない。通知を受け取ったユーザーが取れる対処はパスワードの変更だ。
