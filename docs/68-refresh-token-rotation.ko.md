# 68. 리프레시 토큰 회전 · 재사용 감지

[日本語](68-refresh-token-rotation.md) | **한국어**

> 작성일: 2026-09-28 · 상태: ✅ 적용(배포 대기) · ⚠️ 배포 뒤 **모든 사용자가 한 번 다시 로그인**한다(§6)
>
> 관련: [51 로깅](51-logging.ko.md) · [57 남은 우선순위](57-remaining-priorities.ko.md) ·
> RFC 9700(OAuth 2.0 Security BCP) §4.14.2

## 0. 요약

| | 전 | 후 |
|---|---|---|
| 갱신할 때 옛 토큰 | **지우지 않았다** — 수명(14일)까지 계속 새 토큰을 받아 냈다 | 비교 후 삭제(Redis Lua, 원자적) — **한 번만** 쓸 수 있다 |
| 갱신의 판단 | 세션 키가 **있는가** | 저장된 값과 **같은가** |
| 이미 쓴 토큰이 다시 오면 | 새 토큰을 또 줬다(모름) | **재사용 감지** — 그 로그인의 묶음 전체를 끊는다 |
| 동시 갱신(탭 두 개) | — | 20초 유예: 두 번째 요청은 **같은** 새 토큰을 받는다 |
| 로그아웃 | 지금 낸 토큰의 키 하나만 삭제 | **묶음 전체**를 끊는다 |
| 모든 기기에서 로그아웃 | 없음(비밀번호 변경뿐) | 보안 설정 화면의 버튼 — 사용자의 모든 묶음을 끊는다(§8) |
| 관측 | 없음 | `auth_refresh_total{result}` + 경보 `RefreshTokenReuseDetected` |
| 사용자 알림 | 없음 | 재사용이면 계정 주인에게 **앱 · 메일 · SMS**(수신 설정과 무관, §3.1) |

## 1. 무엇이 문제였나

외부 분석("토큰을 갱신해도 이전 리프레시 토큰이 계속 유효하고, 재사용 감지도 없다")을 코드로 확인했다. 맞았고, 로그아웃 문제가 하나 더 있었다.

- `RefreshTokenController` — `findByUserId(sessionId, email).isPresent()` 로 **키가 있는지만** 봤다.
- 그 뒤 `createRefreshToken()` 이 **새 sessionId** 로 새 키를 만들었다. 옛 키를 지우는 줄이 없었다.
- 결과: 한 번 로그인하고 열 번 갱신하면 **살아 있는 리프레시 토큰이 열한 개.** 어느 것이 복사돼 나가도 14일 동안 새 액세스 토큰을 받아 낸다.
- 재사용을 알아챌 방법이 없었다 — "이미 쓴 토큰" 이라는 개념 자체가 없었다.
- `AuthLogoutFilter` 는 **지금 낸 토큰의 키**만 지웠다. 갱신 전의 옛 토큰(각자 다른 키)은 로그아웃 뒤에도 살아 있었다 —
  "탈취가 의심되면 로그아웃하세요" 가 통하지 않았다.
- 모든 세션을 끊는 길은 비밀번호 변경(`passwordChangedAt` 비교) 하나뿐이었다.

## 2. 설계

### 2.1 묶음(family)

로그인할 때 묶음 id(UUID)를 만들어 리프레시 JWT 의 `fam` 클레임에 넣는다. 갱신한 토큰은 **같은 묶음**을 잇는다.
"이 로그인" 을 가리키는 이름이 생겨야 "이 로그인 전체를 끊는다" 가 가능하다.

### 2.2 Redis 키

| 키 | 값 | TTL |
|---|---|---|
| `<sessionId>` (기존) | 리프레시 토큰의 **SHA-256**(§10) | 토큰 수명 |
| `rt:grace:<옛 sessionId>` | `PENDING` → 새 토큰의 **암호문**(§10) | `auth.refresh.grace-ms`(20초) |
| `rt:fam:<family>` | 묶음의 지금 sessionId | 토큰 수명 |
| `rt:revoked:<family>` | 끊긴 표시 | 토큰 수명 — 그 뒤에는 어차피 모든 토큰이 만료다 |

### 2.3 회전 (`RefreshTokenService.rotate`)

```lua
-- KEYS[1] = sessionId, KEYS[2] = rt:grace:sessionId, ARGV = 받은 토큰, PENDING, grace-ms
local v = redis.call('GET', KEYS[1])
if not v then return 0 end            -- 없다 → 유예 또는 재사용
if v ~= ARGV[1] then return -1 end    -- 값이 다르다 → 거절
redis.call('DEL', KEYS[1])
redis.call('SET', KEYS[2], ARGV[2], 'PX', ARGV[3])
return 1                              -- 이 요청이 회전한다
```

GET 과 DEL 을 따로 부르면 동시에 온 두 요청이 둘 다 "있다" 를 보고 둘 다 새 토큰을 받는다. Lua 는 Redis 에서 한 덩어리로 돌므로 **정확히 하나만 1 을 받는다**
(8개 스레드로 실제 Redis 에 부딪혀 확인 — `RefreshTokenRotationTest.concurrentRefreshRotatesOnce`).

| 순서 | 조건 | 결과 | 응답 |
|---|---|---|---|
| 1 | `fam` 없음 | `LEGACY` — 회전 이전에 발급된 토큰 | 400 `refresh token expired` |
| 2 | 묶음이 끊겼다 | `REVOKED` | 400 `invalid refresh token` |
| 3 | Lua = 1 | `ROTATED` — 같은 묶음으로 새 토큰, 유예 키에 새 토큰 기록 | 200 + 새 쿠키 |
| 4 | Lua = -1 | `REJECTED` — 끊지 않는다 | 400 |
| 5 | 유예 키에 새 토큰 | `GRACE` — **방금 발급한 그 토큰**을 돌려준다(새로 만들지 않는다) | 200 + 같은 쿠키 |
| 6 | 유예 키가 계속 `PENDING`(2초) | `REJECTED` — 도둑이라 단정할 근거가 없다. 끊지 않는다 | 400 |
| 7 | 키도 유예도 없다 | `REUSED` — **묶음 전체를 끊는다** | 400 |

400 이면 쿠키도 지운다. 프론트의 `TokenRefresher` 는 200 이 아니면 로그아웃으로 가므로 프론트 변경은 없다.

### 2.4 재사용이면 왜 둘 다 끊나

서명 · 만료가 멀쩡한 토큰이 이미 회전된 뒤에 다시 왔다 = 같은 토큰을 가진 쪽이 **둘**이다. 서버는 어느 쪽이 정상 사용자인지 모른다.
그래서 묶음을 끊는다 — 도둑이 이미 회전해 받아 간 새 토큰도 함께 죽는다. 정상 사용자는 다시 로그인하면 된다(RFC 9700 §4.14.2).

### 2.5 유예(grace)가 필요한 이유

탭 두 개가 거의 동시에 만료를 맞으면 같은 리프레시 쿠키로 두 번 갱신한다. 두 번째는 형식상 재사용이다. 유예가 없으면
**정상 사용자가 탭 두 개를 열었다는 이유로 로그아웃된다.** 20초 안에 온 같은 토큰에는 첫 요청이 받은 새 토큰을 그대로 준다.
두 탭은 같은 쿠키 저장소를 쓰므로 결과도 같은 쿠키다.

유예는 20초 동안 옛 토큰이 쓰일 수 있다는 뜻이지만 **새 토큰을 새로 만들지는 않는다** — 도둑이 20초 안에 쓰면 정상 사용자와 같은 토큰을 받고, 둘 중 먼저 다음 회전을 한 쪽 때문에 다른 쪽이 재사용으로 걸린다.

### 2.6 로그아웃

`AuthLogoutFilter` 가 `revoke(token)` 을 부른다 — 묶음을 끊고 그 키도 지운다. 이미 회전된 옛 토큰으로 로그아웃해도 뜻은 같다("이 로그인을 끝내라") —
묶음을 끊고, 응답은 전처럼 "not found" 거절이다.

## 3. 로그 · 지표 · 경보

- 로그: 재사용이면 `WARN [auth] 리프레시 토큰 재사용 감지 … userId=7`. **토큰 · 이메일은 남기지 않는다**(docs/51).
- 지표: `auth_refresh_total{result="rotated|grace|reused|revoked|legacy|rejected"}`.
- 경보: `observability/alert-rules.yml` 의 `auth-security` → `RefreshTokenReuseDetected`(15분 안에 1건 이상, warning).

| 보이는 것 | 뜻 |
|---|---|
| `grace` 가 꾸준히 조금 | 정상(탭 여러 개) |
| `legacy` 가 배포 직후 몰렸다가 0 으로 | 정상 — §6 |
| `reused` 한 사용자 반복 | 그 사용자의 기기 · 브라우저 확장 · 공유 PC 유출 |
| `reused` 여러 사용자 동시 | 서버 쪽 유출(로그 · 프록시 · 백업). 쿠키는 HttpOnly 라 XSS 로는 읽히지 않는다 |
| `rejected` 증가 | Redis 지연(PENDING 이 2초를 넘김) — 도둑이 아니라 인프라 |

### 3.1 사용자 알림 — "보안을 위해 로그인이 해제되었습니다"

재사용을 감지하면 user-service 가 기존 `security-alert` 토픽에 발행하고, notification-service 가 **`SECURITY_ALERT`** 로 만든다.
새 종류를 만들지 않은 이유: `SECURITY_ALERT` 는 이미 **수신 설정을 무시하고** 앱 · 메일 · SMS 로 나간다(공격자가 먼저 알림을 꺼 버리는 것을 막는다).
DB 체크 제약 · 설정 화면 · 프론트 아이콘도 그대로 쓴다.

```json
{"alert":"refresh-reuse","customerId":7,"email":"…","occurredAt":"…","eventId":"security:refresh-reuse:<묶음 id 의 SHA-256 앞 32자>"}
```

| 결정 | 이유 |
|---|---|
| 받는 사람 = 계정 주인(주소는 DB 에서) | 재사용을 일으킨 쪽이 누구든 메일은 주인에게 간다. 토큰의 subject 를 믿지 않는다 |
| `eventId` = 묶음 해시 | 묶음은 한 번만 끊기므로 알림도 하나(동시 감지 · 카프카 재전달에도). 묶음 id 원문(토큰의 클레임)은 싣지 않는다 |
| 문구에 "토큰" · "재사용" 이 없다 | 사용자에게 뜻이 없다. 일어난 일(로그인 해제) · 이유(다른 곳에서 쓰인 흔적) · 할 일(다시 로그인, 아니면 비밀번호 변경)만 |
| 발행 실패는 응답을 바꾸지 않는다 | 묶음은 이미 끊겼다. 알림은 부가 기능 — 카프카 장애가 인증을 멈추면 안 된다 |
| 정상 사용자도 받는다 | 어느 쪽이 도둑인지 모르고 둘 다 끊었기 때문이다. 그래서 겁주지 않되 할 일은 분명히 쓴다 |

🐛 **함께 고친 것** — 메일 제목과 SMS 문구가 `SECURITY_ALERT` 종류로 고정("새로운 기기에서 로그인되었습니다")이라, 다른 보안 사건도 새 기기 메일로 나갈 구조였다.
이제 제목 · 문자가 **알림 제목**을 따른다. 새 기기 메일은 본문에 같은 문장이 두 번 찍히던 것도 사라졌고, 끝 문장이 "수신 설정은 마이페이지에서"(끌 수 없는 메일인데 거짓말)에서
"보안 알림은 수신 설정과 관계없이 발송됩니다" 로 바뀌었다.

## 6. 배포 — 모두 한 번 다시 로그인한다

배포 전에 발급된 리프레시 토큰에는 `fam` 이 없다. 이것들이 바로 "수명까지 계속 쓸 수 있는" 옛 토큰이므로 받아 주지 않는다(`LEGACY`).
**배포 뒤 첫 갱신에서 모든 사용자가 로그인 화면으로 간다.** 한 번뿐이다.

- 공지가 필요하면 "보안 개선으로 한 번 다시 로그인해 주세요".
- 되돌리기(롤백): 옛 버전은 `fam` 을 모르고 키만 보므로 새 토큰도 그대로 쓴다. 회전 전 동작으로 돌아갈 뿐 데이터 문제는 없다.
  `rt:*` 키는 TTL 로 사라진다.
- 배포 순서: **notification-service 를 user-service 와 같이 또는 먼저.** 옛 notification-service 는 `alert` 를 모르므로 로그인 해제 이벤트를
  "새로운 기기에서 로그인되었습니다" 로 보낸다. 반대 순서(알림 먼저)는 문제없다 — 새 알림 서비스는 `alert` 가 없는 예전 이벤트를 새 기기로 처리한다.

## 7. 남은 것

- HTTP 요청의 **즉시** 차단 — 채팅 · 알림 같은 긴 연결은 이제 즉시 끊긴다(§9). 일반 HTTP 요청은 여전히 액세스 토큰 만료(최대 15분)까지다.
  즉시 끊으려면 게이트웨이가 요청마다 "이 사용자의 로그인 해제 시각"(§9 의 `auth:cutoff:*`)을 봐야 한다 — 모든 요청에 Redis 조회가 붙는다.
  15분 액세스 토큰 + 회전 + 긴 연결 즉시 차단으로 충분하다고 판단해 두지 않았다.

## 8. 모든 기기에서 로그아웃

보안 설정 화면(`/profile/security`)의 "로그인 기기" 아래. "새로운 기기에서 로그인되었습니다" · "보안을 위해 로그인이 해제되었습니다" 알림을 받은 사용자가
**당장 할 수 있는 조치**다. 예전에는 비밀번호 변경뿐이었다 — 바로 위 "기억 지우기" 는 로그아웃이 아니고, 로그아웃은 지금 기기 하나만 끊었다.

### 8.1 사용자 → 묶음 색인

세션 키는 sessionId 로만 저장돼 "이 사용자의 모든 로그인" 을 거꾸로 찾을 수 없었다. 로그인 · 갱신마다 묶음 id 를 집합에 넣는다.

| 키 | 값 | TTL |
|---|---|---|
| `rt:user:<userId>` | 묶음 id 집합 | 토큰 수명 — 로그인 · 갱신마다 다시 센다. 마지막 활동 뒤 수명이 지나면 안의 토큰도 모두 만료다 |

- **로그인할 때 끝난 묶음을 뺀다**(`rt:fam` 이 없는 것 = 끊겼거나 만료). 안 빼면 매일 로그인하는 사용자의 집합이 끝없이 자란다 — TTL 이 매번 다시 세어지므로 통째로 사라지지도 않는다.
- 배포 전에 로그인한 묶음은 색인에 없다 — 문제없다. 그 토큰은 `fam` 이 없어 어차피 받아 주지 않는다(§6).

### 8.2 동작

`POST /api/user/profile/sessions/revoke-all` → `RefreshTokenService.revokeAll(userId)`: 집합의 묶음을 모두 끊고(§2.6 과 같은 `revokeFamily`) 집합을 지운다.

| 결정 | 이유 |
|---|---|
| 신원은 토큰에서만 | 사용자 id 를 받으면 남의 로그인을 끊을 수 있다 |
| **이 기기도** 로그아웃 | 이 기기가 도둑의 것일 수도 있고, 다시 로그인하는 비용은 작다. 리프레시 쿠키도 지운다 |
| 두 번 누르게(확인) | 이 기기도 로그아웃되기 때문 |
| "즉시" 가 아니라 "최대 15분 안에" | 다른 기기가 이미 가진 액세스 토큰은 수명까지 유효하다(게이트웨이는 서명만 본다). 화면이 거짓말을 하지 않는다 |
| 재사용 알림을 보내지 않는다 | 끊긴 기기가 갱신하면 `REVOKED` 다. 끊는 순간 회전 중이던 요청이 키를 못 찾아도, 재사용으로 판정하기 전에 묶음이 끊겼는지 다시 본다 — 사용자가 한 일에 "탈취 의심" 메일이 가지 않는다 |
| 지표 `auth_logout_all_total` | 평소보다 많으면 알림(재사용 · 새 기기)이 실제로 사람을 움직이고 있다는 뜻이기도, 계정 공격의 신호이기도 하다 |

## 9. 긴 연결(채팅 · 알림)을 로그인에 묶는다

### 9.1 무엇이 문제였나

HTTP 요청은 매번 액세스 토큰을 보여 주므로 토큰 만료(최대 15분)가 상한이다. 긴 연결은 **연결할 때 한 번만** 토큰을 본다.

| 연결 | 전 | 후 |
|---|---|---|
| 채팅 WebSocket(chat-service STOMP) | CONNECT 뒤 **끊길 때까지** — 상한 없음 | 토큰 `exp` 에 close **4401** · 로그인 해제면 **즉시** |
| 알림 SSE(user-service) | 30분(`app.sse.timeout-ms`) | `min(30분, 토큰 exp)` · 로그인 해제면 **즉시** |

"모든 기기에서 로그아웃" 이나 재사용 감지로 로그인을 끊어도 열려 있는 채팅은 방의 메시지를 계속 받았다.

### 9.2 두 겹

1. **만료에 묶는다** — chat-service 는 CONNECT 때 **자기가 검증한 JWT 의 `exp`** 에 닫기를 예약한다(`LiveSessionRegistry`). 게이트웨이가 넘긴 헤더가 아니다 —
   헤더를 쓰면 클라이언트가 먼 미래 값을 넣지 못하게 게이트웨이가 지우고 덮어써야 하고, 그 약속이 한 번 깨지면 상한이 사라진다.
   SUBSCRIBE · SEND 도 만료가 지났으면 거절한다(예약이 몇 ms 늦어도 막는 두 번째 겹).
2. **로그인 해제는 즉시** — user-service 가 `revokeAll` · 재사용 감지 때
   - Redis `auth:cutoff:<userId>` = 지금(epoch 초), TTL = 액세스 토큰 수명 + 1분
   - pub/sub `auth:session-revoked` 에 사용자 id

   를 보낸다(common `SessionRevocation`). chat-service 와 user-service SSE 는 그 사용자의 연결을 4401 / `Reauth` 로 닫고, **이후 CONNECT · 구독에서 `iat` 가 그 시각보다
   이른 토큰을 거절한다** — 닫기만 하면 옛 토큰(아직 15분 유효)으로 곧장 다시 붙기 때문이다.

### 9.3 4401 = "갱신하고 다시 붙어라"

- 프론트는 원래 만료 10초 전에 토큰을 갱신하고, 토큰이 바뀌면 채팅 · 알림이 새 토큰으로 다시 붙는다. 그래서 **정상 사용자는 만료 닫기를 보지 않는다** —
  다시 붙지 않는 클라이언트(백그라운드 탭 · 도둑)만 여기서 끊긴다.
- 서버가 4401 / `Reauth` 로 닫으면 프론트는 같은 토큰으로 재연결하지 않고(`stompProvider` · `Notification.js`) **갱신을 한 번 부탁한다**(`authEvents` → `TokenRefresher`,
  여러 연결이 동시에 닫혀도 갱신은 한 번).
  - 로그인이 살아 있는 기기 → 새 토큰 → 다시 붙는다. 사용자 단위로 넓게 닫아도 해가 없는 이유다(재사용 감지 때 같은 사람의 다른 기기도 잠깐 끊겼다 붙는다).
  - 끊긴 기기 → 갱신 실패 → 로그인 화면.

### 9.4 정직한 한계

| 항목 | 값 |
|---|---|
| 긴 연결 — 로그인 해제 뒤 | 즉시(pub/sub 전달 시간) |
| 긴 연결 — 토큰 만료 뒤 | 즉시(예약) |
| 일반 HTTP — 로그인 해제 뒤 | 최대 15분(§7) |
| `iat` 가 초 단위 | 해제한 **같은 초**에 발급된 옛 토큰은 통과한다 — 1초 이내의 창 |
| Redis 장애 | 해제 표시를 못 읽으면 막지 않는다(채팅 전체를 멈추지 않는다). 만료 묶기가 여전히 최대 15분 상한을 건다 |

### 9.5 테스트

- chat-service `LiveSessionRegistryTest` 5 — 만료에 4401, 사용자 단위 닫기(다른 사용자 무관), 스스로 끊긴 연결의 예약 해제, 해제 시각 판정, Redis 장애 시 통과.
- chat-service `StompHandlerSubscribeTest` +3 — CONNECT 가 만료 예약, 해제 이전 토큰의 CONNECT 거절, 만료 뒤 SUBSCRIBE 거절.

- user-service `NotificationSessionRoutingTest` +4 — 스트림이 토큰 만료를 넘지 않음, 해제 이전 토큰 거절, 이후 토큰 허용, 그 사용자의 스트림만 닫힘.

## 10. 토큰은 해시로만 저장한다

### 10.1 무엇이 문제였나

| Redis 키 | 전 | 후 |
|---|---|---|
| `<sessionId>` | 리프레시 JWT **원문** | 원문의 **SHA-256**(hex) |
| `rt:grace:<옛 sessionId>` (20초) | 새 리프레시 JWT **원문** | 새 토큰의 **AES-256-GCM 암호문** |
| 액세스 토큰 "블랙리스트" | 로그아웃 때 액세스 토큰 **원문을 키로** — 읽는 곳이 없었다 | **삭제** |

Redis 덤프(백업 파일 · 잘못 열린 포트 · 스냅샷)가 새면 원문을 쿠키에 넣어 그대로 로그인할 수 있었다. 해시로는 토큰을 만들 수 없다.
비교는 받은 토큰을 해시해서 Lua 안에서 한다(§2.3 의 `ARGV[1]` 이 이제 해시). JWT 는 서명 덕에 엔트로피가 충분하므로 솔트 · 느린 해시(bcrypt)는 필요 없다 — 그건 사람이 고른 비밀번호용이다.

### 10.2 해시와 동시 갱신 유예가 부딪히는 이유

동시 갱신 유예(§2.5)는 이렇게 돈다.

1. 탭 A 와 탭 B 가 **같은** 리프레시 쿠키 R1 로 거의 동시에 갱신한다.
2. A 가 먼저 회전한다 — R1 을 지우고 새 토큰 R2 를 만든다. 브라우저에 R2 쿠키를 심는다.
3. B 의 요청은 R1 을 들고 조금 늦게 온다. R1 은 이미 없다 — 형식상 **재사용**이다.
4. 유예가 없으면 B 때문에 묶음이 끊겨 **정상 사용자가 로그아웃**된다. 새 R3 를 만들어 주면 R2 · R3 두 개가 살아 회전의 의미가 사라진다.
5. 그래서 B 에게는 **A 가 받은 바로 그 R2** 를 돌려준다(쿠키 저장소가 하나라 결과도 같다).

5번이 문제다. 서버가 20초 동안 R2 의 **원문을 꺼낼 수 있어야** 한다. 해시는 한 방향이라 `SHA-256(R2)` 에서 R2 를 되돌릴 수 없다.
그래서 "해시만 저장" 을 하면서 유예를 유지하려면 세 가지 중 하나를 골라야 한다.

| 방법 | 대가 |
|---|---|
| A. 유예 20초만 원문 저장 | "해시만" 이 그 20초 동안 거짓. 그 순간의 덤프에는 원문이 있다 |
| **B. 유예 값만 서버 키로 암호화** ← 선택 | 키 관리가 하나 는다 — 여기서는 JWT 비밀에서 파생해 새 비밀이 없다 |
| C. 유예를 없애고 프론트가 탭 간 갱신을 하나로 모은다(Web Locks · BroadcastChannel) | 모든 클라이언트가 협조해야 한다. 한 탭이라도 어기면(구버전 탭, 앱) 정상 사용자가 끊긴다 |

### 10.3 B 의 구현(`GraceTokenCipher`)

- **AES-256-GCM** — 기밀성과 위변조 검출을 함께. IV 12바이트 무작위, 태그 128비트. 저장 형식 `v1:` + base64(iv ‖ 암호문 ‖ 태그).
- **키는 Redis 에 없다** — `HMAC-SHA256(JWT 비밀, "refresh-grace-v1")` 로 용도별 파생(2FA 대기 토큰과 같은 방식). 새 비밀 · 새 Secret 이 없다.
- **AAD = 옛 세션 id** — 다른 유예 키의 암호문을 옮겨 붙이면 풀리지 않는다.
- 풀리지 않으면(위변조 · 형식 오류 · 키가 바뀜) `REJECTED` — 재사용 증거가 아니므로 묶음은 끊지 않는다.

**남는 위험의 크기** — Redis 덤프만 가진 공격자: 해시와 암호문뿐이라 쓸 것이 없다. JWT 비밀까지 가진 공격자: 이미 **아무 액세스 토큰이나 위조**할 수 있다.
그러므로 암호화 키를 JWT 비밀에서 파생해도 공격자가 새로 얻는 것은 없다. 이 설계가 "우려 없이" 인 이유다 — 원문이 저장소에 머무는 순간이 없다.

### 10.4 배포

- §6 과 함께 배포하면 추가 영향은 없다(모두 한 번 다시 로그인).
- 회전(§2)만 먼저 배포했다면: 그 사이 로그인한 사람의 Redis 값은 원문이라 해시와 맞지 않는다 → `REJECTED` → 한 번 더 로그인. 끊지는 않는다.
- 롤백: 옛 버전은 값이 **있는지**만 봤으므로 해시가 들어 있어도 그대로 동작한다.

### 10.5 테스트

- `GraceTokenCipherTest` 6 — 왕복, 저장 값에 원문 없음 · 매번 다른 암호문, 다른 세션으로 못 풂(AAD), 한 글자 변조 검출, 다른 비밀로 못 풂, 형식 오류는 null.
- `RefreshTokenRotationTest`(실제 Redis) +2 — **Redis 전체를 훑어** 어떤 키 · 값에도 토큰 원문(서명 부분)이 없다(유예 중 포함), 위변조된 유예 값은 거절하되 끊지 않는다.
  저장을 원문으로 되돌리면 이 테스트가 실패하는 것을 확인했다.


## 11. 탭 사이 로그인 상태를 맞춘다 (2026-10-01)

리프레시 토큰은 HttpOnly 쿠키라 **모든 탭이 같이 쓴다.** 그런데 액세스 토큰과 "로그인됨" 표시는 탭마다 메모리에 따로 있어서 탭끼리 어긋났다.

| 증상 | 원인 |
|---|---|
| 한 탭에서 로그아웃해도 다른 탭은 액세스 토큰이 끝날 때까지 로그인된 화면 — 그동안 주문 버튼도 눌렸다 | 다른 탭은 로그아웃을 모른다 |
| 한 탭에서 로그인해도 열려 있던 탭은 새로고침할 때까지 로그인 화면 | 같은 이유 |
| 한 탭은 "세션 만료", 다른 탭은 멀쩡 — 같은 쿠키인데 | 탭마다 따로 판단한다 |
| 🐛 마이페이지 옆 메뉴의 "로그아웃" 은 화면 표시만 지웠다 — 서버의 리프레시 토큰 · 쿠키가 남아 새로고침하면 다시 로그인 | 서버 로그아웃을 부르지 않았다 |

**원칙: 로그인 상태는 브라우저에 하나다. 탭 사이에는 "바뀌었다" 는 사실만 보내고, 토큰은 보내지 않는다**(`frontend/src/util/authSync.js`).

- **로그인(토큰 갱신 포함) → `signed-in`(사용자 id).** 받은 탭이 로그아웃 상태면 **공유 쿠키로 자기 토큰을 직접 받는다** — "세션 만료" 에 멈춰 있던 탭이 작성 중이던 화면 그대로 살아난다. 같은 사용자로 로그인돼 있으면 아무것도 하지 않는다 — 갱신마다 오는 알림이 갱신 연쇄를 일으키지 않게. 다른 사용자로 바뀌었으면 새로고침한다 — 앞 사용자의 장바구니 · 폼을 남기지 않는다.
- **로그아웃 → `signed-out`.** 로그인돼 있던 탭이 로그아웃할 때만 보낸다 — 처음 열린 탭의 복구 실패(쿠키 없음)가 다른 탭의 멀쩡한 로그인을 끊지 않게. 받은 탭은 로그아웃하고 안내를 띄운다. 세션이 끝나 갱신이 실패한 경우도 같은 경로라, 한 탭이 알면 모든 탭이 같이 끝난다.
- **받은 알림으로는 다시 알리지 않는다**(`broadcast: false`) — 탭끼리 주고받기가 멈추지 않는 것을 막는다. 처음 복구 중(PENDING)인 탭은 끼어들지 않는다 — 리프레시 토큰이 겹쳐 두 번 회전하지 않게.
- 🔒 메시지에는 종류 · 사용자 id · 출처 탭 · 시각만 있다. BroadcastChannel 이 없는 브라우저는 localStorage 의 storage 이벤트로 대신하는데, 값을 쓰자마자 지운다 — 액세스 토큰을 메모리에만 두는 이유(XSS 한 번에 세션이 넘어간다)를 여기서 깨지 않는다.
- 옆 메뉴 로그아웃은 헤더와 같은 `useLogout`(서버 로그아웃 → 화면 · 다른 탭 정리)으로 바꿨다.

**가드**: `authSync.test.js`(토큰이 들어갈 자리가 없다 · 자기 메시지 무시 · storage 대체 경로는 아무것도 남기지 않는다) · `AuthContext.sync.test.jsx`(로그인돼 있던 탭의 로그아웃만 알린다 · 따라 할 때는 알리지 않는다) · `TokenRefresher.sync.test.jsx`(다른 탭을 따라 로그아웃 · 로그아웃 상태 탭은 자기 토큰을 받는다 · 같은 사용자는 무시 · 다른 사용자면 새로고침 · PENDING 은 끼어들지 않는다). "로그인돼 있던 탭만" 조건이나 `broadcast: false` 를 빼면 해당 테스트가 실패한다.

## 12. 로그인의 절대 수명(30일) · 시계가 틀린 PC (2026-10-01)

**① 절대 수명.** 리프레시 토큰은 갱신마다 새로 14일을 받았다 — 가끔 쓰기만 하면 **로그인이 끝나지 않았다.** 탈취된 토큰도 도둑이 주기적으로
갱신하면 영원히 산다(재사용 감지는 정상 사용자가 옛 토큰을 다시 낼 때만 걸린다). 금융 · 쇼핑몰은 보통 "마지막 사용 후 N일" 과 함께
"최초 로그인 후 최대 M일" 을 둔다.

- 리프레시 토큰에 **최초 로그인 시각 `auth_time`**(OIDC 와 같은 이름)을 넣고, 회전해도 그대로 이어받는다.
- 만료 = min(지금 + 14일, `auth_time` + 30일). 쿠키 Max-Age 도 토큰의 남은 수명으로 — 30일째가 가까우면 14일보다 짧다.
- 30일이 지나면 새 토큰을 만들어도 이미 만료라 갱신으로 늘릴 수 없다. 회전 직전에도 다시 확인한다(운영자가 수명을 줄인 경우 등) —
  지났으면 묶음을 끊고 `refresh token expired`(400) → 프론트는 "다시 로그인해 주세요".
- `auth_time` 이 없는 토큰(이 변경 이전 발급)은 발급 시각을 대신 쓴다 — 배포 순간 아무도 로그아웃되지 않는다.
- 설정: `spring.app.jwtRefreshAbsoluteMs`(환경 변수 `JWT_REFRESH_ABSOLUTE_MS`, 기본 30일).

**② 시계가 틀린 PC.** 선제 갱신 시점을 `exp(서버 시계) − Date.now()(PC 시계)` 로 계산했다. PC 시계가 액세스 토큰 수명(15분)보다 앞서면
막 받은 토큰도 만료로 보여 **즉시 갱신이 끝없이 돌았다** — 갱신마다 리프레시 토큰이 회전하니 서버도 같이 바빴다. 이제 두 시계를 섞지 않고
토큰의 수명(`exp − iat`, 둘 다 서버 시계)만큼 기다린다(`refreshDelayMs`). 무엇이 어긋나도 최소 5초 간격. PC 시계가 느린 쪽은 401 → 갱신 → 재시도가 받는다.

**가드**: `AbsoluteLifetimeTest`(새 로그인 14일 · 25일째 로그인의 갱신은 남은 5일 · 31일째는 새로 만든 토큰도 만료 · 29일째는 아직) ·
`RefreshTokenRotationTest`(실제 Redis: 두 번 회전해도 `auth_time` 그대로 — 이어받지 않게 바꾸면 실패 확인 · 수명을 줄이면 SESSION_ENDED 로
묶음을 끊는다) · `refreshDelay.test.js`(PC 시계가 하루 앞서도 즉시 갱신하지 않는다 — 예전 계산으로 되돌리면 실패 확인).

## 13. 관리자가 막은 계정 · 실패한 로그아웃 (2026-10-01)

**① 관리자가 계정을 정지 · 잠금 · 만료해도 이미 로그인한 사용자는 계속 썼다.** 관리 기능이 DB 값만 바꾸고, 갱신 경로는 계정 상태를 보지 않았다
— 막히는 것은 새 로그인뿐이라 악성 사용자를 정지해도 최대 30일 동안 주문 · 채팅을 계속했다.

- 막는 순간 모든 로그인 묶음을 끊고 채팅 · 알림 연결도 닫는다(`UserServiceImpl.endSessions` → `revokeAll`). 풀 때는 건드리지 않는다.
- 갱신 경로도 `enabled` · `accountNonLocked` · `accountNonExpired` · `credentialsNonExpired` 를 다시 본다 — 막혔으면 그 묶음을 끊고 400
  `account disabled`(프론트는 로그아웃). 끊는 단계가 실패해도 다음 갱신에서 끊긴다.
- **로그인 5회 실패의 자동 잠금은 보지 않는다.** 그것은 다른 필드(`lockExpiresAt`)다 — 보면 공격자가 비밀번호를 일부러 틀려 정상 사용자의 다른
  기기 로그인까지 끊을 수 있다.

**② 로그아웃 요청이 실패하면 화면이 로그인 상태로 남았다.** "로그아웃하지 못했습니다" 만 띄웠다 — 공용 PC 의 사용자는 로그아웃된 줄 알고 자리를 뜬다.

- 실패해도 화면(과 다른 탭)은 **바로** 로그아웃한다. 리프레시 쿠키는 HttpOnly 라 화면이 지울 수 없으므로, 그대로 두면 다음 접속의 자동 복구가
  다시 로그인시킨다. 그래서 표시(`ecommerce-pending-logout`, 값 "1" 뿐)를 남긴다.
- 다음 접속은 자동 복구 대신 **서버 로그아웃을 먼저 마무리**한다 — 로그아웃 API 는 게이트웨이가 액세스 토큰을 요구하므로 한 번 갱신해 받은
  토큰으로 부르고, 그 토큰은 화면 상태에 넣지 않는다. 서버가 답했으면 표시를 지우고, 네트워크가 아직이면 표시를 남긴 채 로그아웃 상태로 둔다.
- 새로 로그인하기 시작하면(로그인 성공 · 소셜 로그인 버튼) 표시를 지운다 — 남겨 두면 다음 접속이 새 로그인을 끊는다.

**가드**: `AdminBlockEndsSessionsTest`(막으면 끊고 풀면 안 끊는다) · `RefreshTokenRotationControllerTest`(정지 · 잠금 · 계정 만료 · 자격 증명 만료
각각 갱신 거절 + 묶음 끊기) · `useLogout.test.jsx`(실패해도 화면 로그아웃 + 표시) · `TokenRefresher.pendingLogout.test.jsx`(다음 접속에서 서버
로그아웃 마무리 · 이미 끝난 세션이면 표시만 지움 · 네트워크가 아직이면 표시를 남기고 로그아웃 상태 · 표시가 없으면 예전처럼 복구). 각 단계를 빼면
해당 테스트가 실패하는 것을 확인했다.
