# 58. 고객센터 채팅 — 고객 ↔ 고객지원팀

[日本語](58-customer-support-chat.md) | **한국어**

> 기존 채팅(`/chat`)은 **친구끼리 대화하는** 모양이다. 누구나 방을 만들고, 방 목록은 모두에게 보이고, 들어가면
> 참여자가 된다. 쇼핑몰의 "고객센터 문의" 는 정반대다 — 대화는 **고객 본인과 상담원만** 봐야 하고, 누가 맡았는지와
> 끝났는지가 있어야 한다. 친구 채팅은 나중에 따로 손보기로 하고, 상담은 별도 기능으로 만들었다.

## 1. 결정 — 부서·직원 스키마를 따로 만들지 않는다

질문: *"고객대응 서비스팀 소속의 직원을 사용자로 추가해야겠지. 쇼핑몰 부서, 직원 정보용 스키마가 따로 필요할까?"*

**필요한 것만 둔다.**

| 필요한 것 | 어떻게 | 이유 |
|---|---|---|
| 상담원도 로그인하는 사람 | 기존 계정 + 역할 `ROLE_SUPPORT`(user V13) | 인증·토큰·게이트웨이가 이미 있다. 상담원 전용 **업무 계정**을 만들어 역할만 준다 |
| 역할 부여 | 기존 관리자 API `PUT /api/admin/update-role?userId=…&roleName=ROLE_SUPPORT` | 새 API 가 필요 없다. 사용자당 역할이 하나라(users.users.role_id) 상담원은 일반 쇼핑을 하지 않는 계정이어야 한다 |
| 고객에게 보일 이름 | 그 계정의 닉네임(chat.member 에 이미 복제된다) | 개인 계정이 아니라 업무 계정이므로 닉네임이 곧 "상담원 표시 이름" 이다 |
| 소속 팀 | 지금은 "고객지원팀" 하나 — 코드 상수 | 팀이 여럿이 되어 **문의를 팀별로 나눠 받아야 할 때** 테이블로 뺀다(§7) |
| 사번·연락처·직급·급여 | **두지 않는다** | 쇼핑몰의 책임이 아니다(인사 시스템의 것). 쓰지 않는 개인정보는 새지도 않는다 |

즉 새 스키마는 **상담 자체**(`chat.support_thread`, chat V7)뿐이고, 사람에 관한 것은 역할 하나가 전부다.

## 2. 모델

```
chat.support_thread
  thread_id · customer_id · agent_id · status(WAITING|ACTIVE|CLOSED)
  awaiting_reply · last_message_preview · last_message_at · created_at · assigned_at · closed_at
```

- **고객당 열린 상담은 하나** — 부분 유니크 인덱스 `(customer_id) WHERE status <> 'CLOSED'`. 두 탭에서 동시에
  "상담 시작하기" 를 눌러도 하나다(애플리케이션은 충돌하면 다시 읽는다).
- **상태와 담당자가 어긋날 수 없다** — CHECK: 상담 중이면 담당자가 있고, 대기 중이면 없다.
- 메시지 본문은 친구 채팅과 같은 MongoDB `chat` 컬렉션에 `roomId = "support-<thread_id>"` 로 쌓인다. 전달도 같은
  파이프라인이다(Kafka `chat` → 저장 → `/sub/chat/room/support-<id>` 브로드캐스트). 새로 만든 것은 **권한**이다.

```
고객            상담 시작 ─► WAITING ─(상담원: 상담 맡기)─► ACTIVE ─(누구든: 상담 종료)─► CLOSED
                   │                                                            │
                   └──────────────────── 대기 중에도 종료 가능 ─────────────────┘
               종료 뒤 다시 문의 → 새 스레드
```

## 3. 권한 — 서버가 강제한다

| 행동 | 고객 본인 | 상담원·관리자 | 그 밖의 로그인 사용자 |
|---|---|---|---|
| 기록 읽기·구독 | ✅ | ✅ 모든 상담 | ❌ **404**(있는지조차 알리지 않는다) |
| 메시지 보내기 | ✅(열린 상담) | ✅ **맡은 사람만** | ❌ |
| 상담 맡기 | ❌ | ✅ 대기 중인 것 | ❌ |
| 종료 | ✅ | ✅ | ❌ |
| 데스크 목록 | ❌ 403 | ✅ | ❌ 403 |

- 신원·역할은 **검증된 토큰**에서만 — REST 는 `Authorization`, STOMP 는 CONNECT 때 세션에 둔 uid·role.
- **맡기는 조건부 갱신**(`UPDATE … WHERE status='WAITING'`) — 두 상담원이 동시에 눌러도 1행/0행으로 한 명만 된다.
  늦은 쪽은 409 "다른 상담원이 이미 맡은 상담입니다."
- 맡지 않은 상담원은 **읽을 수는 있어도 말할 수 없다** — 대기 중인 문의에 누가 먼저 답했는지 모호해지지 않게.
- 메시지 유형은 서버가 `TEXT_TALK` 으로 고정하고 이미지 URL 은 버린다 — 클라이언트가 "상담원이 연결되었습니다"
  안내를 흉내 내거나 임의 URL 을 상대 화면에 그리게 하지 못한다. 연결·종료 안내는 서버가 **팀 명의로, 커밋 뒤에**
  낸다(롤백된 배정의 안내가 나가지 않게).

### 🔒 이 작업에서 막은 기존 구멍 둘

1. **와일드카드 구독.** 기본 STOMP 브로커는 구독 주소를 **패턴**으로 맞춘다(AntPathMatcher). `/sub/**` 를 구독하면
   **모든 방의 모든 메시지**가 왔다 — 친구 채팅방은 원래 공개라 티가 안 났지만, 상담을 같은 브로커에 싣는 순간
   유출 경로가 된다. 이제 구독 주소는 `^/sub/chat/room/[A-Za-z0-9-]{1,64}$` 한 모양만 받는다.
2. **헤더로 판정하던 구독.** SUBSCRIBE 는 `roomId` 네이티브 헤더만 봤다. 헤더에는 공개 방, 주소에는 남의 상담을
   적으면 헤더만 보는 검사는 통과한다. 권한은 **실제 구독 주소**로 판정하고, 상담이면 헤더와 주소가 같아야 한다.

그리고 친구 채팅의 기록 API(`GET /api/chat/room/{roomId}`)는 방 참여를 확인하지 않는다(공개 방 전제) — 상담 방
id 로는 404 를 준다. 상담 기록은 본인·상담원만 되는 `/api/chat/support/threads/{id}/messages` 로만 읽는다.

🐛 덤: chat 의 에러 응답 `ApiResponse` 에 getter 가 없어 Jackson 이 직렬화하지 못했다 — 에러 문구가 화면에 닿은
적이 없다. `@Getter` 를 붙였다.

## 4. API

| 메서드 | 경로(`/chat-service/api/chat/support`) | 누가 |
|---|---|---|
| GET | `/threads/mine` — 열린 상담, 없으면 204 | 고객 |
| POST | `/threads/mine` — 문의하기(있으면 그것) | 고객 |
| GET | `/threads/mine/history` — 지난 상담 10개 | 고객 |
| GET | `/threads/{id}` · `/threads/{id}/messages?cursor=` | 본인·상담원 |
| POST | `/threads/{id}/close` | 본인·상담원 |
| GET | `/desk/threads?view=WAITING\|MINE\|ACTIVE\|CLOSED` | 상담원 |
| POST | `/desk/threads/{id}/claim` | 상담원 |

보내기는 STOMP `/pub/chat/message` `{ roomId: "support-<id>", content }` — 발신자는 싣지 않는다(서버가 세션에서).

## 5. 화면

- **고객** `/support` (푸터 "1:1 고객센터 상담"): 상담이 없으면 "상담 시작하기". 대기 중이면 노란 안내, 상담원이
  맡으면 "상담원 ○○" 로 바뀐다(연결 안내를 받으면 상태를 다시 읽는다). 종료하면 입력창 대신 "새로 문의하기".
- **상담 데스크** `/support/desk` (헤더 계정 메뉴 — 상담원·관리자에게만 보인다): 왼쪽 대기·내 담당·전체·종료 탭과
  "답변 필요"(마지막 말을 고객이 했다) 표시, 오른쪽 대화. 대기 중이면 "상담 맡기" 를 눌러야 입력창이 열린다.
- 라우트 가드 `ProtectedRoute supportOnly` 는 **UI 가드일 뿐**이다 — 같은 규칙을 서버가 강제한다. 상담원은 관리자
  화면(`adminOnly`)에 들어가지 못한다.

user-service 의 경로 권한에 `SUPPORT` 를 더했다(`/api/user/**`, `/api/auth/user/**`, `/api/auth/logout`, `/api/sse`) —
빠뜨리면 상담원 계정은 **로그아웃조차 403** 이다.

## 6. 운영

- 배포 순서는 상관없다. user V13(역할 추가)과 chat V7(테이블 추가)은 서로 기다리지 않는다. 다만 **상담원 역할을
  부여하기 전에** user-service 가 새 이미지여야 한다 — 옛 이미지(AppRole 에 ROLE_SUPPORT 없음)는 그 사용자를 읽지
  못한다(V13 의 ROLLBACK-UNSAFE 주석).
- 상담원 만들기: 업무용 이메일로 가입 → 관리자가 `PUT /api/admin/update-role?userId=<id>&roleName=ROLE_SUPPORT`
  → 그 계정의 닉네임을 고객에게 보일 이름으로(예: "민지"). 다시 로그인해야 토큰에 새 역할이 실린다.
- 새 문의·새 메시지는 데스크에 실시간으로 온다(§9). 목록은 안전망으로 30초마다도 다시 읽는다.

## 7. 남은 것

- **팀·배정 규칙** — 팀이 여럿이 되면(주문·배송 / 결제·환불) 그때 `support_team` 과 스레드의 `team_id`, 문의 유형
  선택을 더한다. 자동 배정(라운드로빈·부하 기준)도 그때.
- ~~🐛 기존 채팅의 커서(사전순 "9" > "10")~~ → **고쳤다(§11-④).**
- 파일·이미지 첨부 없음. ~~상담 만족도·메모 없음~~ → **§11 에서 더했다.** 태그는 아직 없다(문의 유형이 그 일부를 맡는다).

## 9. 상담원 실시간 알림

처음에는 데스크 목록을 5초마다 다시 읽었다. 새 문의는 최대 5초 늦게 보였고, 다른 탭에서 일하는 상담원은 아예 몰랐다.

### 흐름

```
고객 "상담 시작"  ── SupportService.openOrGet ─────────────┐
고객 메시지       ── Kafka chat → MessageConsumer(저장 뒤) ──┤
상담원 맡기       ── SupportService.claim(커밋 뒤) ─────────┼─► /sub/support/desk  { threadId, kind, senderId, at }
누구든 종료       ── SupportService.close(커밋 뒤) ─────────┘        kind = NEW_THREAD | MESSAGE | CLAIMED | CLOSED
```

- **본문은 싣지 않는다** — 번호와 종류뿐이다. 화면은 받고 목록을 다시 읽는다. 본문을 실으면 "이 주소를 구독할 수
  있는가" 가 곧 "모든 상담을 읽을 수 있는가" 가 되어, 권한 판정을 REST 와 STOMP 두 곳에서 맞춰야 한다.
- 구독은 **상담원·관리자만**(StompHandler — CONNECT 때 토큰에서 읽은 역할).
- 메시지 알림은 **저장된 뒤**(소비자)에 낸다 — 상담원이 알림을 보고 열었을 때 그 메시지가 기록에 있다.
- 알림이 실패해도 상담(저장·배정·종료)은 되돌리지 않는다. 목록은 30초마다도 다시 읽으므로 놓친 알림은 그 안에 맞춰진다.
- chat-service 는 파드 하나다(`replicas: 1` — 인메모리 브로커). 여럿이 되면 친구 채팅과 함께 외부 브로커 릴레이가 필요하다.

### 화면

| 무엇 | 언제 |
|---|---|
| 토스트 "새 문의가 도착했습니다." | 새 문의 — 모든 상담원 |
| 토스트 "○○ 님의 새 메시지" | **내가 맡은** 상담에 **고객이** 말했고, 그 상담을 지금 열어 두지 않았을 때 |
| 브라우저 알림 | 위 둘 중 하나이고 탭이 뒤에 있을 때. "브라우저 알림 켜기" 로 권한을 받는다 |
| 탭 배지 | 대기 수, 내 담당 중 답변이 필요한 수 |
| 창 제목 `(3) …` | 두 배지의 합 — 다른 탭에서 일하다가도 보인다 |

### 🔒 함께 막은 기존 구멍 — 브로커 주소로의 직접 SEND

STOMP 클라이언트가 `/pub/**`(애플리케이션 주소)가 아니라 `/sub/**`(브로커 주소)로 SEND 하면, 기본 브로커는 그것을
**컨트롤러를 거치지 않고 그대로 구독자에게 배달한다.** 컨트롤러가 하던 발신자 덮어쓰기와 상담 권한 검사를 모두 건너뛰고,
아무 방(남의 상담 포함)에 아무 발신자·아무 내용이나 넣을 수 있었다. 데스크 알림 주소에 가짜 "새 문의" 를 뿌릴 수도 있다.
이제 SEND 는 `/pub/` 로 시작하는 주소만 받는다.

## 10. 고객 답변 알림

상담원이 답했는데 고객이 상담 화면을 떠나 있으면 알 길이 없었다.

```
상담원 메시지 ─ Kafka chat → MessageConsumer(저장 뒤) → SupportReplyNotifier
      ├─ 보낸 사람이 고객 본인?              → 안 보냄
      ├─ 고객이 지금 그 상담을 구독 중?       → 안 보냄(이미 화면에 떴다)
      ├─ 같은 상담에 60초 안에 보냈다?        → 안 보냄(세 줄 답변 = 알림 한 통)
      └─ support-reply { receiverId, threadId, messageId, senderName } (키 = 상담 번호)
                 → notification-service → 알림 "고객지원팀 답변" (링크 /support, 종류 CHAT_MESSAGE)
```

- **본문은 싣지 않는다** — 알림 테이블·메일에 상담 내용(계좌번호·주소 같은 것)이 남지 않게. 알림은 "답이 왔다" 만 말하고,
  내용은 본인만 여는 상담 화면에서 읽는다. 받는 쪽도 이벤트의 본문 필드를 쓰지 않는다(테스트로 고정).
- **새 토픽인 이유** — 친구 채팅의 `chat` 토픽(Avro)에 수신자를 더하면 스키마 버전·이력·한 릴리스 동안의 옛 스키마 쓰기가
  따라온다(docs/55). 상담에만 있는 일이라 작은 JSON 토픽 하나로 뗐다. DLT 목록(ops/02)에 더했다(B-41).
- **종류는 `CHAT_MESSAGE`** — 새 종류를 만들면 알림 설정 화면·SMS·메일 분기·DB CHECK 를 모두 늘려야 한다. 고객의 "채팅
  알림" 설정을 그대로 따르고, 문자는 나가지 않는다. 상담 답변을 메일로도 보내야 한다면 그때 종류를 뗀다.
- **"보고 있다"** 는 STOMP 구독으로 안다(`SupportPresence` — SUBSCRIBE 에 적고 UNSUBSCRIBE·DISCONNECT 에 지운다). 메모리에
  둔다 — chat-service 는 파드 하나다. 재시작으로 비면 "알림 한 통 더" 쪽으로 틀린다.
- **탭을 뒤에 둔 고객** — 구독 중이라 벨 알림은 오지 않는다. 대신 상담 화면이 창 제목에 `(1)` 을 붙이고, 탭으로 돌아오면
  지운다.
- 발행이 실패해도 상담 메시지의 저장·전달은 되돌리지 않고, 실패는 60초 제한에 세지 않는다(다음 답변이 다시 알린다).

검증: `SupportReplyNotifierTest`(7 — 본문 없음·본인 제외·보고 있으면 제외·다른 사람의 구독은 무관·60초 묶음·실패 뒤 재시도·
친구 채팅 무시), `StompHandlerSupportSubscribeTest` +2(구독·해지·끊김, 거절된 구독은 적지 않음),
notification `SupportReplyNotificationTest`(3), 프론트 창 제목(1). B-41(DLT 목록)·발행 키 가드 통과.

## 11. 개편 — 1:1 상담 화면 · 문의 유형 · 대기 순번 · 만족도 · 상담원 도구 (2026-09-27)

사용자 보고: "고객 대응용인데 실제로는 단체 대화방으로 되어 있고, UI 가 겹쳐 보이는 메뉴도 있다."

### ① 원인 — 두 채팅이 섞여 있었다

- 1:1 상담(`/support`)은 이미 있었는데, **푸터 "고객 채팅" 과 홈 바로가기("판매자와 실시간 상담")가 단체 대화방(`/chat`)**
  으로 갔다. 손님은 상담 대신 누구나 들어오는 공개 방에 들어갔다.
- `/chat` 은 사이트 헤더 없이 뷰포트 전체(100vw × 100vh)를 덮었고, 안의 입력줄(`position: fixed`, 폭 50%) · 대화 영역
  (`absolute`, 폭 50%) · 아래로 버튼(`fixed`, **z-index 200** — 앱 전체에서 가장 높았다) · 오른쪽 메뉴의 화면 덮개
  (`fixed inset-0`) · 목록 항목 이미지(`absolute; left: 120px`)가 서로, 그리고 헤더 메뉴와 겹쳤다.

### ② 단체 대화방은 보존하고, 겹침만 없앴다

- **기능은 그대로**(방 목록 · 검색 · 방 만들기 · 대화 · 더 보기). 이름을 "커뮤니티 채팅" 으로 바꾸고, 머리에 "1:1 상담으로 가기" 를 둔다.
- 사이트 레이아웃(헤더 · 푸터) 안의 **카드 한 장**으로 옮겼다(`isolation: isolate` — 안의 z-index 가 헤더 메뉴 위로 새지 않는다).
  안쪽은 전부 흐름(flex) 배치다: 입력줄 · 대화 영역은 카드 안, 아래로 버튼은 대화 칸 안의 `absolute`(z-index 5).
- 사이트 헤더와 같은 일을 하던 **오른쪽 메뉴(홈 · 방 목록 · 로그아웃 · 동작하지 않는 설정, 외부 아바타 이미지)**는 뺐다.
- 말풍선 옆 시각이 `-70px` 고정이라 "오후 10:46" 처럼 긴 시각이 말풍선을 덮었다 → 말풍선 끝에 붙인다.
- 방은 **더블클릭**으로만 열렸다 → 클릭 · Enter · Space. 좁은 화면에서는 방을 열면 목록을 접는다.
- 🐛 방 기록 응답이 배열이 아니면(게이트웨이의 HTML 오류 페이지 등) `.reverse()` 가 던져 **화면 전체가 오류 화면**으로 갔다 → 빈 기록으로 다룬다.
- 진입 링크: 홈 바로가기 → `/support`("고객지원팀과 1:1 실시간 상담"), 푸터는 "1:1 고객 상담" 과 "커뮤니티 채팅" 을 나눠 둔다.

### ③ 고객 화면(`/support`)

| 전 | 후 |
|---|---|
| "상담 시작하기" 버튼 하나 | **문의 유형**(주문 · 배송 · 결제·환불 · 상품 · 회원·계정 · 기타)을 고르고 시작 |
| 대기 중 안내 한 줄 | **대기 순번**("대기 순번 3번째") — 나보다 먼저 연 대기 문의 수 + 1 |
| 말풍선 나열 | 날짜 구분선 · 같은 사람의 연속 말 묶음 · 상담원 동그라미(첫 글자) · 상태 · 유형 표시 |
| 새 메시지가 오면 무조건 맨 아래로 | 위를 읽는 중이면 자리를 지키고 **"새 메시지 N"** 만 띄운다. "더 보기" 뒤에도 읽던 자리 유지 |
| 종료 뒤 안내 한 줄 | **만족도(별 1~5 + 한 줄 의견)** — 한 번 |
| 지난 상담을 볼 곳이 없었다(API 는 있었다) | 오른쪽 **지난 상담** 목록 → 누르면 그때 대화를 읽기 전용으로 |
| — | 상담 안내(운영 시간 · 답변 · "카드 번호·비밀번호를 적지 마세요"), 실시간 연결 표시, Enter/Shift+Enter 안내, 글자 수 |

### ④ 상담 데스크(`/support/desk`)

- 세 칸: **목록**(대기 · 내 담당 · 전체 · 종료 + 유형 거르기 · 검색) / **대화** / **상담 정보**(고객 · 지난 상담 수 · 유형 ·
  시작 · 배정 · 종료 시각 · 고객 평가 · 내부 메모). 좁은 화면에서는 목록 ↔ 대화, 정보는 서랍으로.
- **빠른 답변** — 첫인사 · 확인 중 · 주문번호 요청 · 시간 필요 · 처리 완료 · 마무리. 입력칸에 **넣기만** 한다(고쳐서 보낸다). 고객 이름이 들어간다.
- 🔒 **내부 메모** — 상담원끼리만. 반납 · 교대 때 다음 상담원에게 남긴다.
- **반납** — 맡은 상담을 다시 대기열로. 고객에게는 "상담원이 바뀝니다" 안내, 다른 상담원에게는 토스트 알림(RELEASED).
- 🐛 커서 — 메시지 id 가 숫자를 담은 **문자열**이라 정렬 · 비교가 사전순이었다(§7). "최신 20개" 조차 자릿수가 바뀌면
  옛 메시지를 골랐다(`12, 11, 10` 이어야 할 것이 `9, 8, 12`). 두 조회에 Mongo collation `numericOrdering` 을 걸었다 —
  단체 대화방도 같은 조회라 함께 고쳐진다. 실제 Mongo 7(Testcontainers)로 검증했고, collation 을 빼면 테스트가 위 순서로 실패한다.

### ⑤ 서버 (API · 모델)

| API | 누가 | 규칙 |
|---|---|---|
| `POST /threads/mine` 본문 `{topic}` | 고객 | 선택. 없거나 모르는 값이면 OTHER(옛 화면 호환). 이미 열린 상담이 있으면 유형을 바꾸지 않는다 |
| `POST /threads/{id}/rating` `{score, comment}` | **고객 본인** | 종료된 상담에만(046), 한 번(047), 1~5 · 500자(048). 상담원 · 남은 404 |
| `GET /desk/threads?view=&topic=` | 상담원 | 유형 거르기. "내 담당" 은 유형과 무관하게 전부 |
| `PUT /desk/threads/{id}/note` `{note}` | 상담원 | 2000자(049). 비우면 지운다 |
| `POST /desk/threads/{id}/release` | 맡은 상담원 · 관리자 | 상담 중인 것만(050). 대기로 돌리고 안내 · RELEASED |

- `SupportThreadDto` 에 `topic` · `queuePosition`(대기 중인 고객 화면에만) · `rating` · `ratingComment` · `ratedAt` · `assignedAt`,
  데스크 상세에만 `customerPastThreads`.
- 🔒 **`internalNote` 는 데스크 응답에만** — 고객 응답(현재 · 지난 · 하나 · 평가)에서는 언제나 null 이고 JSON 에서도 빠진다
  (`@JsonInclude(NON_NULL)`). 테스트가 고객 응답의 JSON 문자열에 메모 본문이 없는지까지 본다. 메모 · 의견 본문은 로그에 남기지 않는다.
- 마이그레이션 **V8** — 열 더하기뿐(`topic` 기본값 'OTHER' · 평가 · 메모 · CHECK 2개 · 대기 순번용 부분 인덱스). 옛 이미지로 되돌려도 돈다.
- 새 안내 문구 "상담원이 바뀝니다. 잠시만 기다려 주세요." — `ChatNotices.FORMATS` 와 화면(`chatNotice.js`)에 같은 글자로 더했다(계약 테스트).
- 오류 코드 046~050 은 일본어 카탈로그(`client-text.ja.txt`)에도.

### ⑦ 남은 것

- 상담 중 **입력 중 표시 · 읽음 표시** 없음 — STOMP 새 목적지와 구독 규칙(StompHandler)이 필요하다.
- 첨부(이미지 · 파일) 없음 — 저장소 · 악성 파일 검사가 먼저다.
- 운영 시간 문구는 사전에 고정 — 실제 운영 시간이 바뀌면 사전을 고친다(설정 값으로 옮길 수 있다).
- 커뮤니티 채팅 방은 여전히 **로그인한 누구나 만들 수 있다**(보존 요청). 신고 · 관리 기능은 없다.
