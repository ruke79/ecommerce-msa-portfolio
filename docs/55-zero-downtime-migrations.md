## 0. ひと目で — デプロイ列車

**リリースはコミットの接頭辞である。** あるコミットでイメージをビルドすると、その前のコミットがすべて入る。だから「この変更はあの
変更の後に」は **どのコミットで区切ってビルドするか** で決まる。下の境界で区切り、1 段ずつ上げる。

| リリース | ビルドするコミット | 入るもの | 前のリリースとの条件 | 守る仕組み |
|---|---|---|---|---|
| **R0**（本番稼働中） | `95007cf` | — | — | — |
| **R1** 移行 | `1227834` | 身元を uid に（order・chat・cart・coupon）、Saga メッセージからトークンを除去（スキーマ v2 を 5 つ + chat・user-created）、旧 Pod 用の **移行コード**（2 ヘッダーでの呼び出し・メールアドレスの代替経路・偽の `Authorization` 目印・旧送信者のバックフィル） | — | 移行コード · 履歴スキーマ |
| **R2** 整理 + 拡張 | `6b8cf08` | 移行コードの削除（`36d4620`）、order の旧決済カラム第 1 段階（`8f4a131`）、pay のプロバイダー中立 A + 決済リクエスト v3 の **読み取り**（`6b8cf08`） | R1 が完全にロールアウトした後 | chat **V6** — バックフィルが終わっていなければ止まる（データガード） |
| **R3** 縮小 | `0836bb9` | 決済リクエスト v3 の **書き込み** + 旧決済カラムの削除（`b655c81`）、決済リクエスト v4 を **次のスキーマとして** デコーダーに先行投入（`0836bb9`） | R2 が完全にロールアウトした後 | order **V18** · pay **V6** — R2 を飛ばすと止まる（時間ガード） |
| **R4** フィールド削除 | `d982f3b` | 決済リクエスト v4 の **書き込み**（`paypalOrderId` の除去） | R3 が完全にロールアウトした後 | order **V20** — R3 を飛ばすと止まる（リリース目印 V19） |
| **R5** 履歴の整理 | （未作成） | v1・v2 の読み取り経路の削除、続いて v3 | R3 の **14 日** 後、v3 は R4 の 14 日後 | 作るときに同じ時間ガード（DLT の保持期間） |

「完全にロールアウトした後」とは、新しい Pod がすべて準備完了し、旧 Pod がすべて停止した後である。ガードは **30 分** で見る。

## 1. なぜ複数のリリースなのか — このクラスターのデプロイが持つ性質

| 性質 | どこで | その結果起きること |
|---|---|---|
| ローリングアップデート、レプリカ 1 つ | k8s Deployment | 新しい Pod が準備できるまで **旧 Pod と新 Pod が一緒に動く** — 数秒ではなく、起動・Flyway・Eureka 登録・Kafka 参加の間（最大 5 分、`k8s/4x-*.yaml` の startupProbe） |
| サービスをほぼ同時に入れ替え | `ops/28-deploy.sh`（user-service が先、gateway が後、残りは一斉） | 「読む側を先にデプロイ」を **順序で守ることができない** |
| 起動時に Flyway がマイグレーション | `application-common.yml` | 新しい Pod のマイグレーションが走る瞬間、**旧 Pod はまだその DB でリクエストを処理中** である |
| Hibernate `validate` | 同じ場所 | エンティティがマッピングしたカラムがなければ起動失敗。そしてマッピングしたカラムは **すべての SELECT に入る** |
| Avro 単一オブジェクトエンコーディング、レジストリなし | `common/.../kafka/avro/` | レコードに書き込みスキーマの **フィンガープリント** が付き、読む側は **知っているフィンガープリントだけ** を読む。フィールドを 1 つ変えるだけでもフィンガープリントが変わる |
| 失敗したメッセージは DLT へ | `KafkaDltConfig`、DLT の保持 14 日（`ops/13`） | 読めなかったレコードは消えないが **処理もされない** — 決済リクエストなら決済が反映されない |
| saga-projection は読めないレコードで止まる | 以前: Kafka Streams のデフォルト値。現在: 未知の書き込みスキーマのときだけ（§8） | ローリング中なら新しい Pod が引き継ぐ。壊れたレコードは飛ばす |

だから「旧いものと新しいものが混在する数分間」がすべての移行の設計条件である。混在の方向は 3 つある。

| 軸 | 旧 Pod ↔ 新 Pod の間で壊れるもの | 壊れ方 |
|---|---|---|
| **DB スキーマ** | 新 Pod がカラムを消すと旧 Pod の SELECT · 旧 Pod が旧カラムにだけ書くと新 Pod からは見えない | 注文照会がすべて 500 · 決済の二重発行 |
| **メッセージスキーマ** | 新しいプロデューサーのフィンガープリントを旧コンシューマーが知らない | 決済リクエストが DLT · ストリームの停止 |
| **サービス間 API** | 新しい呼び出し元が新しいヘッダーだけを送ると旧い呼び出し先は 401 · その逆も | 注文作成・クーポン見積もりの失敗 |

解法は 1 つである — **expand-contract**。拡張（両方を受け付ける）→ 移行 → 縮小（新しいものだけ）。縮小は **必ず別の
リリース** である。このドキュメントのすべてのシナリオは、この原則を 3 つの軸それぞれに適用したものである。

## 2. シナリオ ① 身元: メールアドレス → ユーザー id（R1 → R2）

### なぜ

身元がメールアドレスだった。サービスごとに「メールアドレス → id」を user-service に問い合わせ直し、その呼び出しに使う **ユーザートークンを Kafka
メッセージと URL に** 載せていた。本文のメールアドレスを信じるエンドポイント（`/savecart`, `/applycoupon`）は他人のものに触れることができた。
トークンの `uid` はゲートウェイがすでに `User-Id` ヘッダーで渡していた — **トークンが運んでいるものを改めて問い合わせない。**

### 過程

**R1 — 拡張 + 移行。** 受ける側は新しいもの（`User-Id`）を読み、送る側は旧いものも一緒に送る。

| 移行コード | 誰のために | なければ |
|---|---|---|
| `getCartDuringRollout` — `User-Id` と旧 `User-Email` を一緒に | 新 order・coupon → **旧 cart** | 旧 cart が 401 → 注文作成・クーポン見積もりの失敗 |
| coupon 見積もりのメールアドレス代替経路 + order が `email` も送る | 旧 order → 新 coupon、新 order → 旧 coupon | 見積もり失敗 → 注文作成失敗 |
| user-service `/user/segments` が `userId`・`email` の両方を | 旧 coupon → 新 user-service | 特集の対象判定の失敗 |
| `LegacyAuthorizationHeader`（`Authorization: Bearer none`） | 旧 pay・order の「ヘッダーが **あるか**」の検査 | 決済リクエスト・レスポンスが DLT |
| chat 起動時のバックフィル + `chat.legacy_sender_email`（V5 が移しておいたマッピング） | Mongo の旧メッセージ（送信者がメールアドレス） | 旧い会話の送信者が永遠に分からない |

chat V5 は `member.email` を消すが、**バックフィルより先に** 走る（Flyway は起動前、バックフィルは起動後）。そこでマッピングを専用
テーブルに移してからカラムを消し、バックフィルは Mongo にメールアドレスが 1 つも残っていなければそのテーブルを空にする — 2 回デプロイして人が
確認すべきことを、コードが順番に行う。

**R2 — 縮小。** 移行コードをすべて消し、ロールバック用に残しておいた 2 つのテーブル（`chat.legacy_sender_email`, `orders.customer`）を消す。

### 🔴 chat V6 — データで確認するガード

マッピングテーブルに行が残っている = バックフィルが終わっていない（R1 を飛ばしたか、バックフィルが Mongo に届かなかった）。そのときに消すと旧い
送信者を永遠に取り戻せない。そこで V6 は **行があれば消さずに例外で失敗** する。PostgreSQL は DDL も
トランザクションなので何も変わらず、新しい Pod が準備完了にならないので旧 Pod が動き続ける。

🐛 PG16 に直接適用して見つけたバグ: 最初に書いた `IF to_regclass(...) IS NOT NULL AND EXISTS (SELECT 1 FROM 그테이블)` は
**テーブルが存在しない新しい DB で失敗** した。PL/pgSQL は条件式全体を一度に計画するため、`AND` が短絡評価される前に
"relation does not exist" が発生する。ネストした `IF` で直した。単体テストでは決して見えない種類のものである。

### 既知のウィンドウ — R1 のメッセージスキーマ

R1 は 7 つのトピックのスキーマを変えた（`order`・`product-update`・`cart-empty`・`cart-rollback`・`coupon-use`・`chat`・
`user-created` — トークン・メールアドレスの除去）。**このときは下記 §4 の「旧い書き込みスキーマで書く」を知らなかった。** R0 のコンシューマーは新しいフィンガープリントを
知らないので、R1 のローリング中に書かれたレコードの一部は DLT へ行く。データは失われない — **R1 のデプロイ後に 7 つのトピックの DLT を
再処理する**（docs/11 §3、処理は冪等である）。saga-projection は未知のスキーマで止まり、新しい Pod に入れ替わるとそのレコードから
読み直す（§8）。

## 3. シナリオ ② order の旧決済カラム `paypal_order_id`（R2 → R3）

### なぜ

決済手段を広げたとき（V4）、PayPal 専用カラムの名前を変えるのではなく、プロバイダー中立のカラムを 2 つ **追加した** — rename はロールバックを壊し、
ユニークインデックスがかかったカラムなのでなおさら危険だった。その後、コードは両方のカラムに書き、両方から読んでいた。旧カラムを片付ける番だった。

### 過程 — なぜ一度に消さないのか

「次のリリースで消す」を一度にやると、**同じウィンドウが逆方向に開く。** カラムを消す新 Pod の Flyway が走る
瞬間、旧 Pod はそのカラムをマッピングしており、Hibernate はマッピングしたカラムをすべての SELECT に入れる → **注文照会がすべて失敗**。

| 段階 | リリース | やったこと | 元に戻す |
|---|---|---|---|
| 1 | R2（`8f4a131`） | エンティティが旧カラムを **マッピングしない**。冪等性の検査・決済済み注文のキャンセル拒否・返金通知が新しいカラムだけを見る。**V17** が旧カラムにだけ残った値を移す（V4 のローリング中に旧イメージが書いた行） | 安全 — コピーのみ、旧イメージは両方のカラムを見る |
| 2 | R3（`b655c81`） | **V18** がカラムとインデックスを消す | `ROLLBACK-UNSAFE` |

第 1 段階が核心である: **「コードが使わない」と「カラムがない」を別のリリースに置く。** 第 1 段階のローリング中、旧 Pod は両方のカラムに
書き、新 Pod は新しいカラムだけに書く — どちらも問題ない。第 2 段階のローリング中、旧 Pod は第 1 段階なのでそのカラムをマッピングしていない。

### 🔴 order V18 — 時間で確認するガード

第 2 段階が安全である条件は「第 1 段階が **すでに** 完全にロールアウトした」ことだが、これはデータには現れない。代わりに **Flyway の履歴** に
現れる: V17 の `installed_on` が **今回の実行でたった今** 記録されたなら、第 1 段階と第 2 段階が 1 回のデプロイで上がってきたということである。

```
V17 の適用時刻 > この DB の最初のマイグレーション + 10分   -- すでに本番稼働中だった DB であり
    かつ > 現在 − 30分                                    -- たった今適用された
→ RAISE EXCEPTION (消さない)
```

- 新しい DB（すべてのマイグレーションが一度に走る場合）は最初のマイグレーションと V17 が隣接しているので通過 — 旧 Pod がない。
- 履歴テーブルがなければ通過（fail-open）— ガードは補助装置である。
- 失敗すると新しい Pod は起動しない。30 分後に再度デプロイすれば通過する。
- PG16 で 4 つのケースを確認: 飛ばした → 拒否・カラムが残る / 第 1 段階の 2 時間後 → 削除 / 新しい DB → 通過 / 履歴なし → 通過。

## 4. シナリオ ③ pay のプロバイダー中立化 + 決済リクエスト v3（R2 → R3）

### なぜ

`pay.payment` は PayPal の参照だけを記録していた。🐛 そして調べてみると **他のプロバイダーの参照は伝わってすらいなかった** — 決済リクエストの
DTO には `paymentProvider`・`providerPaymentId` があったが、**Avro スキーマにそのフィールドがなく**、リレー経路でマッピングが
静かに捨てていた。コンパイルもテストも通る種類の食い違いである。

そのため DB カラム（pay）とメッセージスキーマ（order → pay）の **2 つの軸を同時に** 拡張する必要があった。

### メッセージスキーマにフィールドを追加する — 「読み取りは新しいもの、書き込みは旧いもの」

フィールドを追加するとフィンガープリントが変わる。新しい order がすぐに v3 で書くと、ローリング中の旧 pay は決済リクエストを **DLT へ** 送り（決済が
反映されない）、旧 saga-projection は **止まる。** デプロイ順序で「読む側を先に」を守れないので、1 つのリリースの中で
読み取りと書き込みを切り離す。

| リリース | 生成クラス | order が書くスキーマ | コンシューマーが知っているスキーマ |
|---|---|---|---|
| R2 (A) | v3 | **v2** — `new BinaryMessageEncoder<>(SpecificData.getForClass(..), v2스키마)` | v1 · v2 · **v3** |
| R3 (B) | v3 | **v3** | v1 · v2 · v3 |

A で v3 レコードを v2 スキーマで書ける理由: 新しいフィールドを **末尾にだけ** 付けた。v2 フィールドの位置が同じなので、エンコーダーが位置で
値を取り出しても合う（新しいフィールドだけが抜ける）。テストが「v2 しか知らない汎用デコーダーが新しい order のバイトを読める」を固定する。

### DB は order と同じ 2 段階

| 段階 | pay | 元に戻す |
|---|---|---|
| A (R2) | **V5** — カラムを 2 つ追加し、`payment_type` からプロバイダーを（CASH → BANK_TRANSFER）、`paypal_order_id` から参照を移す。エンティティは新しいカラムだけをマッピング。プロバイダーフィールドのない v2 レコードなら、決済手段・PayPal 参照から決める | 安全 |
| B (R3) | **V6** — A のローリング中に旧 Pod が書いた行を **もう一度** 移し、カラムを消した後、カラムと一緒に消えた `idx_payment` を作り直す。V18 と同じ時間ガード（V5 基準） | `ROLLBACK-UNSAFE` |

「もう一度移す」が重要である — 拡張マイグレーションが移した **後でも**、ローリング中の旧 Pod は旧カラムにだけ書く。縮小
直前の再移行がそのウィンドウを閉じる。

**1 つのガードが 2 つの危険を防ぐ。** R3 で order V18 が失敗すると新しい order の Pod は起動しない → **v3 レコードも出て
いかない。** DB ガードがメッセージスキーマの順序まで守る（書く側が order だからこそ可能なことである）。

## 5. シナリオ ④ 決済リクエストからフィールドを抜く — v4（R3 → R4 → R5）

### なぜ方向が逆なのか

フィールドを **抜くとき** は §4 の手が通用しない。`paypalOrderId` は 4 番目のフィールドなので、抜くと **後ろのフィールドの位置がすべてずれる** —
v4 クラスを v3 スキーマで書くと値が見当違いの欄に入る。そこで逆に進む: **生成クラスは旧いもの（v3）のままにして、次の
スキーマ v4 をデコーダーのリポジトリに先に入れる。**

| リリース | 生成クラス | order が書くスキーマ | コンシューマーが知っているスキーマ |
|---|---|---|---|
| R3 (C1) | v3 | v3 | v1 · v2 · v3 · **v4**（`avro-next/`） |
| R4 (C2) | **v4** | **v4** | v1 · v2 · v3（`avro-history/`） · v4 |

リポジトリはフィンガープリントで書き込みスキーマを探すだけなので、「旧」と「次」を区別しない。読むときは Avro のスキーマ解決（v4 → v3）が
抜けたフィールドをデフォルト値で埋める。`avro-next/` の v4 は手で置いたファイルなので、現在のスキーマから `paypalOrderId` だけを抜いたものかどうかを
テストが **正規形で** 照合する（生成クラスのスキーマには `avro.java.string` のような属性が付いていて、そのまま比較すると異なる）。

### 🔴 リリース目印 — DB を変えないリリースのガード

C2 のガードは「C1 がすでにデプロイされたか」を知る必要があるが、C1 は DB を変えない。そこで **何もしない
マイグレーション**（order **V19**、`SELECT 1`）を置いた — Flyway 履歴の適用時刻がそのまま C1 のデプロイ時刻である。C2 の **V20**
（ガード専用）がそれを V18 と同じ方式で見る。どちらのファイルも何も変えないが、**消してはならない。**

### 払った代償

v2 レコード（R2 以前の order が書いたもの）の PayPal 参照は旧フィールドにしかなく、そのフィールドは v4 で抜けた — R4 以降にそういう
レコードを読むと参照が空になる。そうしたレコードは DLT の再処理でしか来ることがなく、決済の元の参照は order の
`provider_payment_id` にある。この損失を防ぐにはデコーダーの読み取りスキーマを別に持つ必要があるが、その複雑さに比べて得るものが
小さいと判断した。

### C3 — 条件が「順序」ではなく「時間」である段階

v1・v2 の履歴スキーマと pay の v2 代替経路は、**そのレコードが消えた後にしか** 消せない — トピック 7 日、DLT 14 日。C2 と
1 つのコミットにまとめると、時間ガードが 14 日間 **デプロイ全体を** 止めてしまう。**異なる条件は異なるリリースに置く。** C3 は
R3 のデプロイ日が決まった後、pay V6 の適用時刻を見る 14 日ガードと一緒に作る。

## 6. 仕組みのまとめ

| 仕組み | 何を防ぐか | どこ |
|---|---|---|
| **expand-contract** | 旧・新 Pod が混在するウィンドウのすべて | すべてのシナリオ |
| 2 つの形を一緒に送る / 受ける | サービス間 API のウィンドウ（ヘッダー・パラメーター） | R1 の移行コード |
| **「コードが使わない」と「存在しない」を別のリリースに** | カラム削除の瞬間の旧 Pod の SELECT 失敗 | order V17 → V18、pay V5 → V6 |
| 縮小直前の再移行 | 拡張後も旧 Pod が旧カラムに書いた行 | pay V6 の UPDATE |
| 履歴スキーマ（`avro-history/`） | 新しいコンシューマーが旧いレコードを読めないこと | `AvroSchemaHistory` |
| **旧い書き込みスキーマで書く**（フィールド追加） | 旧いコンシューマーが新しいレコードを読めないこと | `PaymentRequestAvroMapping`（A） |
| **次のスキーマを先に知らせる**（フィールド削除） | 同上、フィールドの位置がずれる場合 | `avro-next/`（C1） |
| **データガード** — 行が残っていれば停止 | 前の段階がデータ作業を終えていないのに消すこと | chat V6 |
| **時間ガード** — 前の段階のマイグレーションがたった今適用されたなら停止 | 2 つのリリースを 1 回のデプロイで上げること | order V18・V20、pay V6 |
| **リリース目印** — 何もしないマイグレーション | DB を変えないリリースを時間ガードが見られないこと | order V19 |
| `-- ROLLBACK-UNSAFE:` の宣言 | 元に戻せないという事実を知らないままロールバックすること | ガード B-54 |
| PG16 に直接適用 | 構文・計画段階でしか現れない SQL のバグ | すべてのマイグレーション |

## 7. 教訓

1. **「次のリリースで消す」は計画ではなく負債である。** 移行コードはコメントと一緒に永遠に残りやすく、残るとすでに無くした
   形（メールアドレスでの身元、ヘッダーの存在検査）が復活する入り口になる。縮小も計画に入れ、復活できないようテストで塞ぐ
   （`User-Email` を載せる Feign がない、エンティティが旧カラムをマッピングしない）。
2. **ローリングデプロイのウィンドウは双方向である。** 拡張するときは「新しい Pod が旧いデータを読めるか」、縮小するときは「旧 Pod が新しい DB で動くか」。
   V17 の教訓は 2 つ目である — 最初は一度に消そうとしていた。
3. **人が覚えておくべき順序はコードに確認させる。** 「R1 を先にデプロイしてください」はドキュメントに書くと忘れられる。マイグレーションが
   Flyway の履歴とデータを見て止まるようにした。停止は安全な失敗である — DDL トランザクションのおかげで何も変わらず、旧 Pod が
   動き続ける。
4. **ガードは新しい環境を止めてはならない。** 新しい DB ではすべてのマイグレーションが一度に走るのが正常である。時間ガードの
   「最初のマイグレーション + 10 分」という条件がそれを区別する。履歴がなければ通過（fail-open）— ガードがデプロイを永久に止めるよりましである。
5. **条件が異なる変更は別のリリースに。** 順序の条件（C2）と時間の条件（C3）をまとめると、時間ガードが順序の条件まで人質に取る。
6. **レジストリのない Avro は互換性ルールを人が守らなければならない。** フィールドは末尾にだけ追加し、デフォルト値を置く。追加するときは 1
   リリースの間、旧い書き込みスキーマで書く。抜くときは次のスキーマを先に知らせる。R1 はこれを知らず、7 つのトピックに DLT のウィンドウを残した。
7. **DTO とスキーマは別々に動く。** `providerPaymentId` は DTO にしかなく、誰も気づかなかった。ワイヤーを一度往復させてみる
   テストがフィールドごとにあれば露見していただろう → 作った（`AvroMappingContract`、§8）。
8. **実際の DB で動かしてみる。** PL/pgSQL の `AND` が短絡評価されないこと、カラムを消すとそのカラムを含むインデックスも一緒に
   消えること — どちらも PG16 に適用してみて初めて分かった。
9. **1 つのガードが複数の軸を守りうる。** 書く側（order）の DB ガードが失敗すれば、新しいスキーマのレコードも出ていかない。
   ガードをどこに置くかは「誰が新しい形を **生み出すのか**」で決める。

## 8. 残っているもの

- **R1 デプロイ後の DLT 再処理** — `order`・`product-update`・`cart-empty`・`cart-rollback`・`coupon-use`・`chat`・`user-created`。
- **C3** — v1・v2 の履歴スキーマと pay の v2 代替経路の削除（R3 の 14 日後）、続いて v3 の履歴（R4 の 14 日後）。14 日ガードと一緒に。
- ✅ **DTO ↔ Avro のフィールド照合テスト** — `AvroMappingContract`（common の test fixtures）。マッピングごとに 2 つを見る:
  **名前**（DTO のフィールドとスキーマのフィールド、リスト内のネストしたレコードまで）と **往復**（すべてのフィールドをデフォルト値ではない値 — 19 桁の id、
  最後の列挙値、ミリ秒までの時刻 — で埋めて `toRecord → encoder → decoder → toDto` を回し、同じ値が戻ってくるか）。
  トピック一覧は `AvroMappings.byTopic()` から来るので、新しいトピックは自動的に入る。chat のマッピングは chat-service にあるので
  `ChatMessageAvroContractTest` が同じ検査を行う。意図的に載せないフィールドは **パス → 理由** の形でのみ除外できる。検査が
  実際に捕まえるかどうかも固定した — 決済リクエストの旧バグ（マッピングが `providerPaymentId` を移さない）と、DTO にだけフィールドを追加したケース。
  現在のマッピング 10 個はすべて通過する（除外なし）。
- ✅ **saga-projection のデシリアライズ例外ハンドラー** — `SagaDeserializationExceptionHandler`。失敗を 2 つに分ける。
  - **未知の書き込みスキーマなら止まる。** この Pod より新しいプロデューサーが書いたレコードである。飛ばすと EOS でオフセットがコミットされ、ローリング中の
    新しい Pod も読み直さない — プロジェクションがその記録を **永遠に失う。** 止まれば新しい Pod が最後のコミットから読む。「無条件に
    飛ばす（LogAndContinue）」がかえって悪いケースである。
  - **それ以外の壊れたレコードは飛ばす。** 何度読み直しても同じなので、止まると後ろのすべての注文が人質になる。座標（トピック・
    パーティション・オフセット）と例外の種類だけをログに残す（値は残さない）。
  - DLT は置かなかった — 元データは入力トピックにそのまま残っており（保持期間の間）、プロジェクションは入力トピックから畳み直して再構成
    できる（`kafka-streams-application-reset`）。`order.DLT` は pay のものなので、混ぜると再処理が pay に再び流れてしまう。
  - カウンター `saga_projection_deserialization_failures_total{topic, action=skipped|halted}` とアラート 2 つ
    （`SagaProjectionHalted` が 10 分継続で critical、`SagaProjectionSkippedRecords` warning）。Prometheus が saga-projection を
    収集していなかったので、対象も追加した。
  - テスト（TopologyTestDriver、本番の設定そのまま）: 壊れたレコードの後ろの注文が引き続き畳まれカウンターが上がる、未知のスキーマなら
    止まる、ハンドラーがなければ壊れたレコード 1 つで止まる（以前の動作）。
- **スキーマレジストリ** — §4・§5 の手作業（旧い書き込みスキーマ、次のスキーマ、履歴ファイル）を互換性ルールが肩代わりする。規模が
  大きくなればこれが正解である。
