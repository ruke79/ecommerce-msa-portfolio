# 88. 페더레이션(기능 분할)의 네 가지 단점 — ecommerce-msa 에서 읽기

[日本語](88-federation-tradeoffs.md) | **한국어**

> 📝 **상태(2026-11-01) — 분석 기록.** 시스템 설계에서 흔히 꼽는 페더레이션의 단점 네 가지가 이 레포의 어디에 실제로 나타나는지 근거(2026-11-01 `6455c20f`)로 모았습니다. 다른 세션의 분석을 원문과 대조해 고친 판입니다(§6). 같은 날 낡은 문서 세 곳도 고쳤습니다 — docs/09(DB 10개 · metadb · catalog 파티셔닝 근거), docs/32(커넥션 140 · 150).

**페더레이션**은 DB 하나를 기능별로 쪼개는 것입니다(사용자 DB · 상품 DB · 주문 DB …). ecommerce-msa 의 "서비스마다 DB 하나" 가 바로 이것이고, 레포도 그렇게 부릅니다 — "이것은 이미 **샤딩의 1단계(기능적 분할)**"([docs/09](09-postgresql-partitioning-sharding.ko.md) §1.1). DB 는 10개입니다(`userdb productdb metadb cartdb orderdb paydb coupondb chatdb notificationdb deliverydb` — k8s/90 pg-init). 다만 **물리적으로는 PostgreSQL 한 대**입니다(docs/09 §1.2). 즉 **논리적 페더레이션은 했고 물리적 분리는 하지 않은** 상태라, 단점 2 · 3 은 이미 겪고 있고 4 는 서버를 나누는 순간 본격적으로 겪습니다.

## 한눈에

| 단점 | 이 레포의 상태 | 대표 사례 | 대책 |
|---|---|---|---|
| 1. 거대한 테이블엔 효과 없음 | **겪고 있음** — productdb 만 자란다 | 상품 200만에서 필터 개수 세기 42.9초(→ 개수 세기는 없앰). 지금은 맞는 것이 드문 필터가 카테고리를 끝까지 훑어 5초 상한 503 | 질의 모양을 고친다 — 가격 범위 열 + 복합 인덱스(docs/85 §8-1), 검색 엔진(`catalog.search-engine`), 앞단 캐시(docs/87) |
| 2. 앱이 어느 DB 인지 정해야 함 | **겪었음** — DB 2개인 catalog | `@Primary` 때문에 배치 메타가 엉뚱한 DB 로, 새 환경에서 배치 잡 전부 실패 | 배치 메타를 productdb 에 두기로(V3), DB 목록 가드 B-40 |
| 3. DB 사이 조인이 복잡 | **설계로 감수** — 서버 링크 대신 호출 · 복제 · 사가 · 읽기 모델 | 주문 목록 Feign 30번(→ 묶음 호출), 사용자 복제 정합성(docs/48 한 편) | 비정규화 복사, 사가 + 아웃박스, 읽기 모델(docs/76) |
| 4. 하드웨어 · 복잡성 증가 | **복잡성은 이미, 하드웨어는 서버를 나눌 때** | 커넥션 = 데이터소스 × 풀 × 레플리카 — 풀 설정이 없던 시절 240 > 100 예측 | 풀 5 · `max_connections` 300 · 가드 B-32, 분리는 orderdb+paydb · productdb 부터(docs/09) |

## 1. "거대한 테이블이 필요하면 효과가 없다"

페더레이션은 테이블을 **다른 DB 로 옮길** 뿐 **작게 만들지는** 않습니다. 상품 DB 를 떼어 내도 그 안의 상품 표는 그대로 큽니다.

| 상품 수 | 표 + 인덱스 | 레포의 평가 |
|---|---|---|
| 50만(실측) | 1.0 GiB, 상품당 약 2.1KB | — (docs/19 §5.1) |
| 100만 | 약 2 GiB | 메모리 안쪽 끝(docs/83 — 실습 클러스터 기준) |
| 1,000만 | 약 20 GiB | **메모리 밖** — 디스크 읽기가 섞인다 |
| 1억 | 약 196 GiB | 실습 VM 에는 넣을 수 없다(data-node 디스크 97G — 일반적인 불가능이 아니다) |

DB 를 나눈 것은 이 문제에 도움이 되지 않았습니다. 운영(상품 200만)에서 필터 검색의 개수 세기가 상품마다 EXISTS 를 55,395번 돌려 42.9초였습니다 — "인덱스는 제대로 타고 있었고(통계도 정확), 일 자체가 컸습니다"([docs/62](62-engineering-casebook.ko.md)). 그 개수 세기는 `d837605d7902` 에서 없앴고(한 쪽 + 1), 지금 남은 것은 **맞는 상품이 드문 조건**이 카테고리를 끝까지 훑는 일입니다(docs/83 §2.8).

**파티셔닝 · 읽기 복제본이 답이 아닌 이유.** catalog 를 파티셔닝에서 뺀 docs/09 §4.1 의 근거("상품 250건")는 낡았지만(2026-11-01 정정), 파티셔닝이 이 문제를 풀지도 않습니다 — 카테고리 안을 상품마다 훑는 일의 양은 그대로입니다. 읽기 복제본은 읽기를 나눌 뿐 복제본마다 같은 큰 표 · 작업 집합을 가집니다. 레포의 대책은 **질의 모양**을 고치는 쪽입니다.

- 적용: 개수 세기 제거 · 하한 > 상한 · 다른 상위의 하위는 DB 에 묻지 않고 0건(docs/85 §0).
- 판단 대기: 상품마다 화면 가격 최저 · 최고 열 + `(category_id, 최저가)` 인덱스 — 무정지 이행 계획까지(docs/85 §8 · §8-1).
- 선택지: 검색 엔진(OpenSearch — 플래그 `catalog.search-engine`, docs/74), 패싯 개수 · 앞단 캐시(docs/85 §8 · docs/87).
- 하드웨어 쪽: 작업 집합이 RAM 에 들어가게 — PG 64GB 이상(docs/86).

큰 표를 다루는 레포의 원칙(docs/09): 아웃박스 넷은 월별 파티셔닝을 이미 적용했다 — 이유는 "데이터가 커서" 가 아니라 "**지울 방법이 없어서**"(오래된 파티션을 통째로 뗀다). 주문 · 결제의 월별 파티셔닝은 계획, 수평 샤딩은 "마지막 수단" 이고 샤드 키 후보는 `user_id`. docs/87 §3 도 같은 순서다(주문 수억 건까지 월별 파티셔닝, 그 위에서 샤딩).

## 2. "어느 DB 에서 읽고 쓸지 애플리케이션이 정해야 한다"

DB 가 둘 이상이면 코드가 데이터소스 · 트랜잭션 매니저 · 리포지토리 패키지를 맞게 짝지어야 하고, 틀리면 엉뚱한 DB 에 씁니다. 대부분의 서비스는 DB 가 하나지만 **catalog 는 둘(productdb + metadb)** 입니다.

- `DataSourceConfig`(productdb, `@Primary`)가 `repository.jpa.data` 를, `MetaDataSourceConfig`(metadb)가 `repository.jpa.meta` 를 맡는다 — 그런데 **`repository.jpa.meta` 패키지는 없다.**
- 의도는 "Spring Batch 메타는 metadb" 였지만 JobRepository 는 `@Primary` 를 쓰므로 **실제로는 productdb 를 보고 있었고**, meta 스키마를 만드는 곳이 없어 **새 환경에서 모든 배치 잡이 실패**했다(catalog V3 주석). 결정은 metadb 로 옮기지 않고 productdb 의 `meta` 스키마에 두는 것 — 두 번째 Flyway 대상을 들일 이득이 없다([docs/16 §7](16-saga-e2e-and-observability-verification.ko.md)).
- 그래서 **metadb 는 연결 풀만 차지하고 쓰이지 않는다**(커넥션 계산에는 들어간다 — §4).
- 같은 곳의 다른 결함: 직접 만든 두 데이터소스가 `initializeDataSourceBuilder()` 로 URL · 계정만 읽어 yml 의 `hikari.*` 가 하나도 적용되지 않았다 — 풀 5 대신 Hikari 기본 10(`CatalogDataSourcePools`, 2026-10-19).

서버를 나누면 이 짝짓기가 서비스 전체로 퍼집니다. 지금은 `POSTGRES_HOST` 하나만 바꾸면 10개 데이터소스가 한꺼번에 따라오지만(docs/32 §5), 나누면 서비스마다 다른 호스트를 정확히 짝지어야 합니다. 비슷한 실수를 막는 장치는 이미 있습니다 — pg-init 의 DB 목록이 JDBC URL 과 어긋나 notificationdb · deliverydb 서비스만 기동에 실패한 뒤, 가드 B-40 이 두 목록을 대조합니다.

## 3. "두 DB 의 데이터를 조인하려면 서버 링크가 필요해 복잡하다"

레포는 서버 링크(`dblink` · `postgres_fdw`)를 쓰지 않습니다 — 0건. 원칙은 "서비스 사이는 **논리 참조**(DB 가 달라 FK 가 없다 — 정합성은 사가 · 아웃박스 · 대사 배치가 맞춘다)"([docs/69](69-erd.ko.md)). 대신 모놀리스라면 JOIN 한 번이었을 일을 다섯 가지로 풉니다.

| 모놀리스라면 | ecommerce-msa 는 | 치른 대가 |
|---|---|---|
| `orders JOIN products`(주문 목록의 색상) | catalog 를 HTTP(Feign)로 | 처음엔 상품마다 — 주문 10건 × 상품 3개 = **Feign 30번**([docs/38](38-code-review.ko.md)). 지금은 묶음 호출, catalog 가 죽으면 색상 없이 |
| `orders JOIN users`(관리자 화면의 고객 이메일) | user-service 를 한 번에 | 실패하면 이메일 없이(`OrderService.attachCustomerEmails`) |
| 주문 시점의 상품명 · 가격 | `OrderProduct` 에 이름 · 이미지 · 가격 · skuCode **복사** | 상품이 바뀌어도 주문은 옛값 — 의도된 동작 |
| `JOIN users`(닉네임 등) | `user-created` 이벤트로 사용자 **복제** | 한 이벤트를 세 서비스가 받고, 놓치면 서비스마다 다르게 깨졌다 — order 는 복제를 그만두고 JWT 의 `User-Id` 를, chat 은 닉네임 때문에 유지하며 아웃박스 · 대사 · 변경 전파([docs/48](48-user-replication-debt.ko.md)) |
| 트랜잭션 하나로 주문 + 결제 | **사가 + 아웃박스**(order → Kafka → pay → 응답) | 결제 → PAID 까지 0 ~ 20초(docs/56). 대신 "크로스 샤드 2PC 가 구조적으로 이미 없다"(docs/09) |

조회 전용 화면에는 Kafka Streams 읽기 모델(saga-projection, [docs/76](76-order-status-read-model.ko.md))도 쓰지만, 주문 목록 전체를 옮기지는 않았습니다 — "읽기 모델에 복제하면 비용은 크고 얻는 것은 적다".

## 4. "하드웨어와 복잡성이 추가로 필요하다"

서버는 하나인데도 이미 늘어난 것들:

- **커넥션** = 데이터소스 × 풀 × 레플리카.
  - 풀 설정이 없던 시절: 8 × 10 × 3 = 240 — 기본 `max_connections` 100 을 넘어 스케일아웃 순간 늦게 뜬 파드가 `FATAL: sorry, too many clients already` 로 뜨지 못한다는 **예측**(docs/19 §3 — 계산으로 찾은 것이고 장애 기록은 아니다).
  - 지금: 데이터소스 10(catalog 2) · 풀 5 · HPA 최대 3, chat 은 1개 고정 → (9 × 3 + 1) × 5 = **140**, `max_connections` 300. docs/32 의 150 은 chat 을 3으로 친 단순 상한이다.
  - 가드 B-32 가 빌드마다 "데이터소스 × 풀 × 레플리카 ≤ 200" 을 본다. 쓰이지 않는 metadb 풀도 이 계산에 들어간다(§2).
- **서비스마다 따로 있는 것** — 아웃박스 표와 폴러, 파티션 유지 잡, Flyway 이력. 파티션 유지 잡이 cart · order 에서 한 번도 돌지 않은 일이 있었다(docs/09). DB 가 늘면 이런 빈틈도 는다.
- **복원 확인은 DB 마다** — 백업은 서버 단위로 하나지만, 첫 운영 복원 훈련은 `postgres` DB 만 세다가 "테이블 0개" 로 실패했다(k8s/85 restore-drill).

서버까지 나누면 하드웨어가 붙습니다. 지금 한 대에 모은 대가는 "같은 WAL · 버퍼를 두고 경쟁", 디스크가 차면 "전 서비스 정지" 이고(docs/09), 레포의 다음 단계는 "`orderdb`+`paydb`(쓰기 핵심)와 `productdb`(읽기 핵심)를 다른 인스턴스로" 입니다(docs/09 §5.2). AWS 상정안은 "쓰기 DB 는 서비스마다 하나의 Aurora 로 시작한다" 이고 Aurora 비용을 여러 DB 합으로 월 $3,000 ~ 6,000 으로 잡았습니다(docs/87 §3 · §4). 자체 데이터센터 구성안(docs/86)은 데이터 노드 3대에 Patroni 클러스터 하나를 두는 그림이고 서버 분리는 다루지 않습니다 — 나누는 순간 클러스터 · 백업 · 감시가 DB 그룹 수만큼 곱해진다는 점은 이 문서의 추론입니다.

## 5. 정리

ecommerce-msa 는 이 단점들을 알고 감수한 구조입니다 — 얻은 것은 서비스별 독립 배포와 스키마 소유권입니다. 1번(큰 테이블)의 대책은 페더레이션 밖에 있고 레포에 이미 계획이 있습니다(§1). 2 · 4번은 DB 를 서버로 나눌 때 다시 커지므로, 나누기 전에 데이터소스 짝짓기(B-40 같은 대조)와 커넥션 계산(B-32)을 서버 단위로 늘려야 합니다.
