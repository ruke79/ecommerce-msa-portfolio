# 88. フェデレーション(機能分割)の四つの欠点 — ecommerce-msa で読む

**日本語** | [한국어](88-federation-tradeoffs.ko.md)

> 📝 **状態(2026-11-01)— 分析の記録。** システム設計でよく挙げられるフェデレーションの欠点四つが、このリポジトリのどこに実際に現れるかを根拠(2026-11-01 `6455c20f`)で集めました。別セッションの分析を原文と突き合わせて直した版です(§6)。同じ日に古い文書三か所も直しました — docs/09(DB 10 個 · metadb · catalog のパーティショニングの根拠)、docs/32(接続数 140 · 150)。

**フェデレーション**は DB 一つを機能ごとに分けることです(ユーザー DB · 商品 DB · 注文 DB …)。ecommerce-msa の「サービスごとに DB 一つ」がまさにこれで、リポジトリもそう呼んでいます —「これは既に**シャーディングの第 1 段階(機能的分割)**」([docs/09](09-postgresql-partitioning-sharding.md) §1.1)。DB は 10 個です(`userdb productdb metadb cartdb orderdb paydb coupondb chatdb notificationdb deliverydb` — k8s/90 の pg-init)。ただし**物理的には PostgreSQL 一台**です(docs/09 §1.2)。つまり**論理的なフェデレーションは済み、物理的な分離はまだ**の状態で、欠点 2 · 3 は既に経験しており、4 はサーバーを分けた瞬間に本格的に経験します。

## ひと目で

| 欠点 | このリポジトリの状態 | 代表的な事例 | 対策 |
|---|---|---|---|
| 1. 巨大なテーブルには効かない | **経験中** — productdb だけが育つ | 商品 200 万でフィルターの件数数えが 42.9 秒(→ 件数数えは撤去)。今は合う商品がまれなフィルターがカテゴリを最後まで走査し 5 秒上限で 503 | 照会の形を直す — 価格範囲の列 + 複合インデックス(docs/85 §8-1)、検索エンジン(`catalog.search-engine`)、前段のキャッシュ(docs/87) |
| 2. アプリがどの DB かを決める必要 | **経験済み** — DB 二つの catalog | `@Primary` のせいでバッチのメタが別の DB へ、新しい環境でバッチジョブがすべて失敗 | バッチのメタは productdb に置くと決定(V3)、DB 一覧のガード B-40 |
| 3. DB をまたぐ結合が複雑 | **設計で受け入れ** — サーバーリンクの代わりに呼び出し · 複製 · サガ · 読み取りモデル | 注文一覧で Feign 30 回(→ まとめ呼び出し)、ユーザー複製の整合性(docs/48 一本) | 非正規化のコピー、サガ + アウトボックス、読み取りモデル(docs/76) |
| 4. ハードウェア · 複雑さの増加 | **複雑さは既に、ハードウェアはサーバーを分けるとき** | 接続数 = データソース × プール × レプリカ — プール設定がなかった頃 240 > 100 の予測 | プール 5 · `max_connections` 300 · ガード B-32、分離は orderdb+paydb · productdb から(docs/09) |

## 1. 「巨大なテーブルが必要ならフェデレーションは効かない」

フェデレーションはテーブルを**別の DB へ移す**だけで**小さくはしません**。商品 DB を切り出しても、その中の商品表は大きいままです。

| 商品数 | 表 + インデックス | リポジトリの評価 |
|---|---|---|
| 50 万(実測) | 1.0 GiB、商品あたり約 2.1KB | — (docs/19 §5.1) |
| 100 万 | 約 2 GiB | メモリの内側の端(docs/83 — 実習クラスタ基準) |
| 1,000 万 | 約 20 GiB | **メモリの外** — ディスク読みが混じる |
| 1 億 | 約 196 GiB | 実習 VM には入らない(data-node ディスク 97G — 一般的に不可能という意味ではない) |

DB を分けたことはこの問題の助けになりませんでした。本番(商品 200 万)でフィルター検索の件数数えが商品ごとに EXISTS を 55,395 回回して 42.9 秒 —「インデックスは正しく使われ(統計も正確)、仕事そのものが大きかった」([docs/62](62-engineering-casebook.md))。その件数数えは `d837605d7902` でなくし(1 ページ + 1)、今残っているのは**合う商品がまれな条件**がカテゴリを最後まで走査することです(docs/83 §2.8)。

**パーティショニング · 読み取りレプリカが答えでない理由。** catalog をパーティショニングから外した docs/09 §4.1 の根拠(「商品 250 件」)は古く、2026-11-14 に本番の商品 200 万を基準に書き直しましたが(結論は同じ — パーティショニングしない)、パーティショニングはこの問題を解きもしません — カテゴリ内を商品ごとに走査する仕事の量は同じです。読み取りレプリカは読み取りを分けるだけで、レプリカごとに同じ大きな表 · 作業集合を持ちます。リポジトリの対策は**照会の形**を直す方向です。

- 適用済み: 件数数えの撤去 · 下限 > 上限 · 別の親のサブカテゴリは DB に聞かず 0 件(docs/85 §0)。
- 判断待ち: 商品ごとの画面価格の最低 · 最高の列 + `(category_id, 最低価格)` インデックス — 無停止の移行計画まで(docs/85 §8 · §8-1)。
- 選択肢: 検索エンジン(OpenSearch — フラグ `catalog.search-engine`、docs/74)、ファセット件数 · 前段のキャッシュ(docs/85 §8 · docs/87)。
- ハードウェア側: 作業集合が RAM に収まるように — PG に 64GB 以上(docs/86)。

大きな表を扱うリポジトリの原則(docs/09): アウトボックス四つは月ごとのパーティショニングを適用済み — 理由は「データが大きいから」ではなく「**消す方法がないから**」(古いパーティションを丸ごと外す)。注文 · 決済の月ごとのパーティショニングは計画、水平シャーディングは「最後の手段」でシャードキーの候補は `user_id`。docs/87 §3 も同じ順序です(注文数億件まで月ごとのパーティショニング、その先でシャーディング)。

> 🕰️ この分析のときは古い月を外すジョブはまだなかった(未来の月を作るだけ)。2026-11-14 に `OutboxPartitionMaintainer` が今月 + 前の 3 か月だけを残し、それより古い月は行がすべて `COMPLETED` のとき `DETACH` → `DROP` するようになった — 次のデプロイ待ち([docs/09 §4.6](09-postgresql-partitioning-sharding.md))。

## 2. 「どの DB で読み書きするかをアプリケーションが決める必要がある」

DB が二つ以上あると、コードがデータソース · トランザクションマネージャー · リポジトリのパッケージを正しく組み合わせる必要があり、間違えると別の DB に書きます。ほとんどのサービスは DB 一つですが、**catalog は二つ(productdb + metadb)** です。

- `DataSourceConfig`(productdb、`@Primary`)が `repository.jpa.data` を、`MetaDataSourceConfig`(metadb)が `repository.jpa.meta` を担う — ところが **`repository.jpa.meta` パッケージは存在しない。**
- 意図は「Spring Batch のメタは metadb」だったが、JobRepository は `@Primary` を使うので**実際には productdb を見ていて**、meta スキーマを作る所がなく**新しい環境ですべてのバッチジョブが失敗**した(catalog V3 のコメント)。決定は metadb に移さず productdb の `meta` スキーマに置くこと — 二つ目の Flyway 対象を入れる利点がない([docs/16 §7](16-saga-e2e-and-observability-verification.md))。
- だから **metadb は接続プールを占めるだけで使われていない**(接続数の計算には入る — §4)。
- 同じ所の別の欠陥: 自前で作った二つのデータソースが `initializeDataSourceBuilder()` で URL · アカウントだけを読み、yml の `hikari.*` が一つも適用されていなかった — プール 5 の代わりに Hikari 既定の 10(`CatalogDataSourcePools`、2026-10-19)。

サーバーを分けると、この組み合わせがサービス全体に広がります。今は `POSTGRES_HOST` 一つを変えれば 10 個のデータソースがまとめて付いてきますが(docs/32 §5)、分けるとサービスごとに別のホストを正しく組み合わせる必要があります。似た間違いを防ぐ仕組みは既にあります — pg-init の DB 一覧が JDBC URL とずれて notificationdb · deliverydb のサービスだけ起動に失敗した後、ガード B-40 が二つの一覧を突き合わせています。

## 3. 「二つの DB のデータを結合するにはサーバーリンクが必要で複雑」

リポジトリはサーバーリンク(`dblink` · `postgres_fdw`)を使いません — 0 件。原則は「サービス間は**論理参照**(DB が違うので FK がない — 整合性はサガ · アウトボックス · 突き合わせバッチが合わせる)」([docs/69](69-erd.md))。代わりに、モノリスなら JOIN 一回だったことを五つの方法で解いています。

| モノリスなら | ecommerce-msa は | 払った代価 |
|---|---|---|
| `orders JOIN products`(注文一覧の色) | catalog を HTTP(Feign)で | 最初は商品ごと — 注文 10 件 × 商品 3 個 = **Feign 30 回**([docs/38](38-code-review.md))。今はまとめ呼び出し、catalog が落ちたら色なしで |
| `orders JOIN users`(管理画面の顧客メール) | user-service を一回で | 失敗したらメールなしで(`OrderService.attachCustomerEmails`) |
| 注文時点の商品名 · 価格 | `OrderProduct` に名前 · 画像 · 価格 · skuCode を**コピー** | 商品が変わっても注文は古い値 — 意図した動作 |
| `JOIN users`(ニックネームなど) | `user-created` イベントでユーザーを**複製** | 一つのイベントを三つのサービスが受け、取りこぼすとサービスごとに違う壊れ方をした — order は複製をやめて JWT の `User-Id` を、chat はニックネームのために維持しアウトボックス · 突き合わせ · 変更の伝播([docs/48](48-user-replication-debt.md)) |
| 一つのトランザクションで注文 + 決済 | **サガ + アウトボックス**(order → Kafka → pay → 応答) | 決済 → PAID まで 0 〜 20 秒(docs/56)。代わりに「シャードをまたぐ 2PC が構造的に既にない」(docs/09) |

照会専用の画面には Kafka Streams の読み取りモデル(saga-projection、[docs/76](76-order-status-read-model.md))も使いますが、注文一覧全体は移していません —「読み取りモデルに複製すると費用は大きく得るものは少ない」。

## 4. 「ハードウェアと複雑さが追加で必要」

サーバーは一台なのに既に増えたもの:

- **接続数** = データソース × プール × レプリカ。
  - プール設定がなかった頃: 8 × 10 × 3 = 240 — 既定の `max_connections` 100 を超え、スケールアウトの瞬間に遅れて起動した Pod が `FATAL: sorry, too many clients already` で起動できないという**予測**(docs/19 §3 — 計算で見つけたもので、障害の記録ではない)。
  - この分析のとき: データソース 10(catalog 2)· プール 5 · HPA 最大 3、chat は 1 個固定 → (9 × 3 + 1) × 5 = **140**、`max_connections` 300。docs/32 の 150 は chat を 3 と数えた単純な上限だった。→ 同じ日に chat を Redis のファンアウトで増やせるようにし(docs/21 §2-1)、今は 10 × 5 × 3 = **150**。
  - ガード B-32 がビルドごとに「データソース × プール × レプリカ ≤ 200」を見る。使われていない metadb のプールもこの計算に入る(§2)。
- **サービスごとに別々にあるもの** — アウトボックスの表とポーラー、パーティション維持ジョブ、Flyway の履歴。パーティション維持ジョブが cart · order で一度も動いていなかったことがある(docs/09)。DB が増えればこうした隙間も増える。
- **復元の確認は DB ごと** — バックアップはサーバー単位で一つだが、最初の本番の復元訓練は `postgres` DB だけを数えて「テーブル 0 個」で失敗した(k8s/85 の restore-drill)。

サーバーまで分けるとハードウェアが付いてきます。今一台にまとめた代価は「同じ WAL · バッファを巡る競合」、ディスクが埋まると「全サービス停止」で(docs/09)、リポジトリの次の段階は「`orderdb`+`paydb`(書き込みの中核)と `productdb`(読み取りの中核)を別のインスタンスへ」です(docs/09 §5.2)。AWS の想定案は「書き込み DB はサービスごとに一つの Aurora から始める」で、Aurora の費用を複数 DB の合計で月 $3,000 〜 6,000 と見ています(docs/87 §3 · §4)。自社データセンターの構成案(docs/86)はデータノード 3 台に Patroni クラスタ一つを置く絵で、サーバーの分離は扱っていません — 分けた瞬間にクラスタ · バックアップ · 監視が DB のグループ数だけ掛け算になるという点は、この文書の推論です。

## 5. まとめ

ecommerce-msa はこれらの欠点を知った上で受け入れた構造です — 得たものはサービスごとの独立したデプロイとスキーマの所有権です。1 番(大きな表)の対策はフェデレーションの外にあり、リポジトリに既に計画があります(§1)。2 · 4 番は DB をサーバーに分けるときに再び大きくなるので、分ける前にデータソースの組み合わせ(B-40 のような突き合わせ)と接続数の計算(B-32)をサーバー単位に広げる必要があります。
