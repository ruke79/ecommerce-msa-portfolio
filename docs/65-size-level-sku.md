# 65. サイズ単位の SKU — 在庫を別々に数える単位にコードを付ける

**日本語** | [한국어](65-size-level-sku.ko.md)

> 作成日: 2026-09-28 · 状態: ✅ 適用(デプロイ待ち)
>
> 関連: [59 決済前の在庫予約](59-stock-reservation.md) · [53 品切れと再入荷](53-restock-and-sold-out.md)

## 0. 要約

| | 前 | 後 |
|---|---|---|
| SKU コードが付いていた場所 | `product_sku`(= **色バリエーション**)の 1 行 | `product_size`(= **サイズの 1 行**)ごとに `sku_code` |
| 黒 270 と黒 280 | 同じコード | `RUN-BLK-270` · `RUN-BLK-280` |
| ルールの置き場所 | Java(`generateSku`、スタイルコードのみ) | DB 関数 `product.assign_size_sku_codes()` の **1 か所** |
| 注文明細 · 梱包リスト | 名前 · サイズ名だけ | SKU を注文時点の値としてコピーして記録 |
| 管理者が登録した商品のサイズ | 🐛 親なしで保存(どのスタイルにも属さない) | 親を指したまま保存 |

## 1. なぜ変えたか

SKU(Stock Keeping Unit)は **「倉庫で別々に数えるべき単位」** である。このスキーマで数量(`quantity`)と価格(`price`)を
持つのは `product_size` の 1 行だ。ところがコードは一段上の `product_sku`(色バリエーション)に付いていた。

- 黒 270 と黒 280 は在庫が別々なのにコードが同じだった。
- そのため注文明細に「何が出荷されたか」を **コード 1 つで** 書けなかった。倉庫管理(WMS) · バーコード連携の前提がなかった。

名前も整理した。

| 名前 | 意味 | 場所 |
|---|---|---|
| **スタイルコード** | 色バリエーションのコード(例: `FAS-100042`)。既存の `sku` フィールド · 列のまま | `product_sku.sku`、`ProductSkuDto.sku` |
| **SKU** | サイズ 1 行のコード(例: `FAS-100042-XL`) | `product_size.sku_code`、`ProductSizeDto.skuCode` など |

既存のフィールド名(`sku`)は API 互換のために変えず、コメントと管理画面の表記を「スタイルコード」に直した。

## 2. 識別子は変えていない

カート行 · 注文明細 · 在庫予約 · 在庫引き当て(Avro `product-update`) · 再入荷通知はすべて
**(商品 id、色 id、サイズ名)** で動く。今回の変更はこのキーに **手を付けない。**

- SKU は **識別子ではなく記録** である。注文時点の値をコピーしておくのは、商品名 · 価格のスナップショットと同じ理由だ。
- 識別キーまで SKU に変えるには、Avro スキーマ · 予約テーブル · 再入荷購読 · カート行の検索をすべて移す、複数リリースに
  わたる expand-contract 移行が必要になる。得られるもの(キーを 1 つに統一)に比べてリスクが大きいため、今回は行わなかった。

## 3. ルール — DB 関数の 1 か所 (catalog V17)

`product.assign_size_sku_codes()` は **空の** `sku_code` だけを埋め、埋めた行数を返す。

| # | ケース | コード |
|---|---|---|
| ① | サイズ名が空(本 · 食品 — サイズのない商品) | スタイルコードそのまま — スタイル 1 つがそのまま在庫単位 |
| ② | 通常 | `<スタイルコード>-<サイズ>`。大文字、英数字以外の連続は `-` 1 つ(`"270 mm"` → `270-MM`) |
| ③ | 英数字を 1 つも含まない名前(`"프리"` など) | スタイル内の連番 `-S<n>` — SKU は ASCII にする |
| ④ | 同じコードが 2 つ以上(同じスタイルに同じサイズ名が 2 行 — シードに実在する) | 最初の行だけそのコード、残りは `<コード>-dup-<size_id>` |
| ⑤ | 親がない、またはスタイルコードが NULL | 空のままにする |

- **一度決めたコードは変えない。**過去の注文 · 返品 · 会計がそのコードを持っている。後でサイズ名が変わってもコードはそのままだ。
- ④で `-2` にしない理由: サイズ `"2"` のコードと衝突する。小文字の `dup` は②が作れない形なので再衝突しない(V7 と同じ方式)。
- 最後の防衛線は部分 UNIQUE インデックス `uq_product_size_sku_code` である。

**なぜ DB 関数か:** 同じルールを Java と SQL(既存行のバックフィル)に二度書くと、いつか食い違う。呼び出し元は 3 つ。

| 呼び出し元 | いつ |
|---|---|
| V17 マイグレーション | デプロイ時に既存行すべて |
| `ProductService.withSizeSkuCodes` | 管理者の商品登録直後(flush → 関数 → 埋まった値をメモリ上のエンティティに写す) |
| `BatchConfig.sizeSkuCodeStep` | CSV 一括登録の最終ステップ — ④は全体を見ないと決められないので、行ごとではなく一度に |

## 4. 流れ — カート → 注文 → 梱包リスト

```
catalog  product_size.sku_code (V17)
   │  /api/products/info (キャッシュなし)
   ▼
cart     cart_product.sku_code (V4)   入れるときに catalog の値で(本文は無視)、入れ直すと今の値に
   │  /checkout                         SKU が空の古い行は catalog から埋める(スタイルは色 id で選ぶ)
   ▼
order    order_product.sku_code (V24)  注文時点の値をコピー → 注文履歴 · 管理者の注文レスポンス
   │  /api/order/internal/orders/{id}/shipping
   ▼
delivery shipment_item.sku_code (V4)   配送作成時にコピー → 配送照会 · 管理者の配送画面
```

- **値の出どころは常に catalog である。**カート投入の本文の `skuCode` は無視する。信じると、顧客が書いたコードが注文明細と梱包リストに載る。
- **古いキャッシュ:** cart-service の Redis に SKU のないカートが残っている可能性がある。SKU が空の行が 1 つでもあれば、
  そのキャッシュは使わずに作り直す(そのとき catalog から埋める)。
- **なくても注文はできる:** コードのない商品(⑤)や補完に失敗した場合、SKU は NULL のまま、注文 · 配送は通常どおり進む。SKU は記録であって条件ではない。

## 5. 🐛 あわせて直したもの — 管理者が登録した商品のサイズが親なしで保存されていた

```java
request.getSizes().forEach(size -> ProductSizeMapper.toEntity(size).setSku(skuProject));  // ① 新しいオブジェクトに親を付けて捨てる
skuProject.setSizes(request.getSizes().stream().map(ProductSizeMapper::toEntity).toList()); // ② 作り直したオブジェクトを保存
```

`sizes` は `mappedBy="sku"` である。外部キーを持つのはサイズ側なので、②のオブジェクトに親がないと `product_size.skuproduct_id` が
NULL で保存される。**管理者が登録した商品はサイズのない商品になっていた。**詳細画面に価格がなく、カートに入れられなかった。
詳細 · 質問(`mappedBy="product"`)も同じ形だったので、あわせて直した(`sizesOf`、`attachDetailsAndQuestions`)。

> ⚠️ すでに本番で管理画面から登録した商品があれば、そのサイズ行は `skuproduct_id` が NULL である。どのスタイルのものかを
> 直接示す情報が DB にないため、マイグレーションでは自動復旧しない。代わりに **作成時刻** が手がかりになる —
> バグのあった流れはスタイル作成 → 画像アップロード(数秒) → サイズ作成の順なので、サイズは自分のスタイルの直後に作られ、
> そのスタイルにはサイズが 1 つもない。この推定でペアを提案し、人が確認したものだけを反映するスクリプトを用意した。
>
> ```bash
> kubectl -n postgres exec deploy/postgres -- \
>   pg_dump -U product -d productdb -t product.product_size -Fc > product_size-$(date +%Y%m%d-%H%M).dump   # まずバックアップ(その表だけ)
> ./ops/42-repair-orphan-sizes.sh status                   # 孤立サイズの数 — 0 なら終わり
> ./ops/42-repair-orphan-sizes.sh preview                  # ペア推定表(HIGH · CHECK · NONE) — 変更しない
> ./ops/42-repair-orphan-sizes.sh apply 901:77 902:77      # 確認したペアのみ — 1 トランザクション、1 つでも誤りがあれば全部戻す
> # その後、管理画面 › 商品 › その商品 › 「保存」 — キャッシュ · 検索インデックスを更新
> ```
>
> 元に戻す: `UPDATE product.product_size SET skuproduct_id = NULL, sku_code = NULL WHERE size_id IN (...);`
> — スクリプトが変えるのはこの 2 列だけである。
>
> NONE(根拠なし)はその商品を登録し直す。残った孤立行はどのスタイルにも属さないので画面には出ない。

## 7. 検証

- catalog: **実際の PostgreSQL**(Testcontainers)でルール 8 件 — ①〜⑤、不変、既存コードとの衝突、UNIQUE インデックス(`SizeSkuCodeMigrationTest`)。
  登録経路の回帰 1 件(親の参照 · 関数呼び出しの順序)。
- cart 6 件(catalog の値を記録 · 本文を無視 · 入れ直し · 古い行の補完 · 古いキャッシュの作り直し)、order 4 件(コピー · なくても注文可 · 配送明細 · 注文履歴のサイズ)、
  delivery はアサーションを追加。
- catalog · cart · order · delivery をコンテナで起動 — Flyway の適用 + Hibernate `validate` を通過。
- フロントの loader · 商品情報 · 在庫画面のテスト。

## 8. 残っているもの

- **バーコード(GTIN)** はない。実際の流通では GS1 から発行される世界共通の番号を SKU に対応付ける。付けるなら `product_size.gtin` を追加すればよい。
- **識別キーは依然としてサイズ名**である(§2)。サイズ名を変えるとカート · 予約のキーがずれる問題はそのままだ。
- 管理画面で SKU を直接直す機能は置いていない — 不変が原則である。
