# 23. 本番インフラの選択 — 決定に必要なことだけ

**日本語** | [한국어](23-infrastructure-decision.ko.md)

> 🕰️ **状態（2026-09-27）— 過去の記録。** 決定のための資料です。実際の決定は PostgreSQL · MongoDB はマネージド、Redis · Kafka はクラスター内、Elasticsearch は本番に置かない、です（[docs/32](32-external-managed-infra.md)）。

> このドキュメントは勧誘ではなく **決定のための資料** である。PostgreSQL・Kafka・Redis・MongoDB・Elasticsearch を
> マネージドで使うかクラスター内で動かすかによって、今後作るものがまったく変わるため、
> まずこのリポジトリが **実際に各依存関係で何を使っているか** から確認した。

## 0. まず — 良い知らせ

切り替えポイントが **1つのファイルに集まっている。** `k8s/10-configmap.yaml` の6行だ:

```yaml
POSTGRES_HOST: "postgres.postgres.svc.cluster.local"
POSTGRES_PORT: "5432"
KAFKA_URL:     "kafka.kafka.svc.cluster.local:9092"
SPRING_DATA_REDIS_HOST: "redis.redis.svc.cluster.local"
SPRING_DATA_REDIS_PORT: "6379"
MONGODB_HOST:  "mongodb.mongodb.svc.cluster.local:27017"
```

**どちらを選んでもアプリケーションコードは変わらない。** マネージドにすればこれらの値がベンダーの
エンドポイントになり、TLS/認証の設定がいくつか合わせて変わる。元に戻すのも同じ規模だ。
これはもともとうまくできていた部分で、決定を取り消し可能にしてくれる。

## 1. このリポジトリが各依存関係で実際に使っているもの

推測を排除するためにコードで直接確認した。これが選択を分ける実質的な要因である。

| 依存関係 | 実際の要件 | 選択への影響 |
|---|---|---|
| **PostgreSQL 16** | パーティショニング、Flyway、**PITR（WAL アーカイビング）**、`pg_basebackup` 用の replication 接続 | 🔴 **マネージド側に強く傾く** — §2 |
| **Elasticsearch 8** | `es-settings.json` が **`nori_tokenizer` を宣言** している | 🔴 **マネージド側に強く傾く** — §3 |
| **MongoDB 7** | 単純な CRUD + カーソルページネーション。replica set・トランザクション・change stream は **使っていない** | 🟡 どちらでも無理がない |
| **Kafka** | プロデューサー/コンシューマー + DLT。**Kafka Connect はデプロイされていない** — §4 | 🟡 どちらでも無理がない |
| **Redis 7** | Redisson 分散ロック（cart・chat・order・pay の4サービス）+ レートリミッター | 🟢 セルフホストが最も簡単 |

## 2. PostgreSQL — マネージドが有利な理由が具体的である

データ損失のリスクが最も大きい場所であり、先ほど ④ で経験したことがそのまま根拠になる。

バックアップの CronJob を作りながら、`pg_basebackup` が **replication 接続** を要求し、デフォルトの
`pg_hba.conf` にはその項目がないため初回実行で失敗することを確認した（[docs/22](22-alerting-and-backup-automation.md)）。
セルフホストだとこういうものが次々に出てくる:

- WAL アーカイビングの保存先（どこに溜めるか）と、そのストレージの保持・整理
- バックアップが **クラスターの外** になければならないという問題 — 今の PVC はクラスターと運命を共にする
- 自動 failover（CNPG がやってくれるが、オペレーター自体を運用しなければならない）
- マイナーバージョンのアップグレード、コネクション数のチューニング、`max_connections`（すでに B-32 ガードレールで計算中）

マネージド（RDS など）ならこのリストの大部分が消える。バックアップ・PITR・failover が標準で、
`k8s/85-backup-cronjobs.yaml` の postgres 部分は **不要になるか補助手段として残る。**

> ⚠️ ただし、マネージドだからといって復旧が検証されるわけではない。`ops/09` の復元訓練は **どちらでも**
> 回し続けなければならない。「バックアップがある」と「復旧できる」は依然として別の話だ。

## 3. Elasticsearch — これはほぼ決定的である

`common/src/main/resources/es/es-settings.json` が韓国語のアナライザーを宣言している:

```json
"custom_nori_tokenizer": { "type": "nori_tokenizer", ... }
```

ところが **公式の `elasticsearch` イメージには nori プラグインがない。** そのためこの項目が
[docs/00 §10](00-before-after.md) に「❌ 保留 — ES プラグインを自作・保守しなければならないため
意図的に先送り」として残っている。セルフホストを選ぶと **プラグインを入れたカスタムイメージを作り、
ES のバージョンごとに作り直さなければならない。**

マネージド（AWS OpenSearch、Elastic Cloud）は nori を標準で提供するか、コンソールで有効にできる。
つまり **マネージドを選べば保留項目が1つ自然に解消する。**

韓国語検索がこのサービスの中核機能であることを考えると、この差は小さくない。

## 4. Kafka — 見かけより要件が軽い

リポジトリのルートに Debezium コネクターの設定が4つコミットされている
（`*-outbox-connector-*.json`、`io.debezium.connector.postgresql.PostgresConnector`）。
マネージド Kafka を使う場合、Connect は別サービスなので（MSK Connect など）コスト・複雑さが加わる。

**ところが Kafka Connect はどの compose ファイルにもない。** 実際の Outbox の発行は
ポーリングスケジューラーが行っており（[docs/21](21-horizontal-scaling.md)）、その経路は先ほど SKIP LOCKED
による先取りで整理した。つまり **コネクター JSON はデプロイされない死んだ設定** である。

> 指摘しておくこと: この死んだ設定が **平文の DB パスワード漏えいの出どころ** だった（[docs/13](13-secrets-dbha-es-search.md)）。
> デプロイすらされないファイルが資格情報を漏えいさせたわけだ。どちらを選ぶにしても、CDC に移行する計画が
> ないなら、これらのファイルは整理したほうがよい。

したがって Kafka の要件は「プロデューサー・コンシューマー + DLT トピック」だけであり、セルフホスト（Strimzi）も現実的だ。
ただし Kafka の運用は ES の次に手間がかかる — リバランス、ディスク管理、ブローカーの交換。

## 5. Redis — 最も軽い側

Redisson 分散ロックを4つのサービスが使う。マネージド（ElastiCache）でもセルフホストでもうまく動作する。
データが失われても致命的ではない（リフレッシュトークン → 全員再ログイン、[docs/00 §10](00-before-after.md)）。

⚠️ マネージドで **クラスターモード** を有効にする場合、Redisson の設定をクラスター用に変える必要がある。
シングルノード/レプリケーションモードなら今の設定のままだ。

## 6. コスト — 構造だけ、数字は自分で確認すること

正確な料金をここに書くとすぐに古くなり、誤解を招く。**構造** だけを整理する。

| | マネージド | クラスター内 |
|---|---|---|
| 直接コスト | インスタンス + ストレージ + **IO/転送**（特に AZ 間の転送が意外と大きい） | ノードのコストのみ（同じノードに載せれば追加コストはほぼ 0） |
| 隠れたコスト | ベンダーロックイン、バージョンアップグレードの時期をベンダーが決める | **人の時間** — 障害対応・アップグレード・容量管理 |
| おおよその感覚 | 同スペックのセルフホストに比べ **2~3倍程度** がよくある | インフラ費は安いが、運用の人件費がたいていその差を上回る |

> 実際の金額はリージョン・インスタンス・ストレージ IOPS・転送量によって大きく変わるため、**各ベンダーの現在の
> 料金表で自分で計算** しなければならない。このドキュメントの数値は方向感をつかむためのものだ。
>
> 判断基準を1つ: **1人の人間がこのインフラを夜明けに復旧できるか。** チームに専任のインフラ担当が
> いないなら、マネージドのプレミアムはたいてい保険料として正当化される。

## 7. 推奨 — 混ぜる方向

事実を総合すると **依存関係ごとに分かれることが明確である。**

| 依存関係 | 推奨 | 決定的な理由 |
|---|---|---|
| PostgreSQL | 🔵 **マネージド** | データ損失リスクの第1位。PITR・failover・バックアップストレージを自前で運用する負担が最も大きい |
| Elasticsearch | 🔵 **マネージド** | **nori** — セルフホストだとカスタムイメージを保守し続けなければならない（だから今は保留状態） |
| MongoDB | 🔵 **マネージド** | チャットデータは再生成不可。特殊な機能を使わないので移行が最も単純 |
| Kafka | ⚪ **どちらも可能** | Connect 不要。予算が厳しければ Strimzi、手間を減らしたければ MSK |
| Redis | 🟢 **クラスター内** | 失われても致命的ではなく、運用負担が最も小さい。マネージドにしても構わない |

**つまり「混ぜる — DB だけマネージド」がこのリポジトリの事実関係に最もよく合う。**
ここに ES をマネージドとして含めることは nori のために特に得である。

## 8. 選択別の後続作業

| 選択 | 作るもの |
|---|---|
| **マネージド（一部/全部）** | エンドポイント・TLS・認証を外部化した ConfigMap のバリエーション + 移行チェックリスト + **接続検証スクリプト**（エンドポイントに実際に届き、権限が合っているかをデプロイ前に）。バックアップ CronJob をベンダーのバックアップと重複しないように調整 |
| **クラスター内** | CNPG の完成版（現在は `.example`）+ Strimzi（Kafka）+ Redis/Mongo/ES の本番マニフェスト、**k3s での実際の起動検証**。nori を含む ES イメージのビルドまで |
| **混ぜる** | 上の2つの該当部分 + 境界でよく起きる問題（マネージドの TLS 証明書の信頼、セキュリティグループ/ネットワークポリシー）を点検するスクリプト |

## 9. 決定と無関係に残るもの

どちらを選んでもこれらはそのままだ:

- `ops/01` DB パスワードのローテーション、`ops/11` ファイアウォールの点検 — 🔴 依然として最優先
- `ops/15` スキーマベースラインのリハーサル — `validate` のデプロイ前に必須
- `ops/09` 復元訓練 — マネージドだからといって復旧が検証されるわけではない
- `ops/17` アラートチャンネル — インフラと無関係
- chat-service・eureka-server の水平スケーリングの制約（[docs/21 §2](21-horizontal-scaling.md)）
