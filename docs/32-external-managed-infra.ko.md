# 32. 인프라를 클러스터 밖으로 — 관리형 무료 티어

[日本語](32-external-managed-infra.md) | **한국어**

배경: 클러스터를 가볍게 하려고 OCI 무료 PostgreSQL(HeatWave/Autonomous), Upstash Redis,
Confluent Cloud 무료 티어로 인프라를 옮기는 안을 검토했다.

먼저 처음 세운 가정의 사실 오류부터 고치고 시작한다. **후보 세 개 중 둘이 틀렸다.**

| 후보 | 실제 | 이 저장소에서 |
|---|---|---|
| OCI 무료 "PostgreSQL" — HeatWave | **MySQL** 이다 | ❌ 못 쓴다 |
| OCI 무료 "PostgreSQL" — Autonomous Database | **Oracle Database** 다 | ❌ 못 쓴다 |
| Upstash Redis | Redis 맞다 | ❌ 옮기지 않기로 했다 (§6) |
| Confluent Cloud | Kafka 맞다 | ⚠️ 상시 무료가 아니다 (§3) |

그래서 이 문서는 전환 작업 기록이 아니라 **무엇이 실제로 가능한지 확인한 결과**다.

---

## 1. 코드가 실제로 요구하는 것

옮길 수 있는지 판단하려면 코드가 무엇에 묶여 있는지부터 알아야 한다. 세어 봤다.

| | 근거 | 결론 |
|---|---|---|
| PostgreSQL 고유 기능 | `FOR UPDATE SKIP LOCKED` 38개 파일, `jsonb` 23곳, `PARTITION BY RANGE` 4곳, `GENERATED BY DEFAULT AS IDENTITY` 22곳, `PostgreSQLDialect` 34곳 | **PostgreSQL 이어야 한다.** MySQL·Oracle 은 후보에서 탈락 |
| 확장(extension) | `CREATE EXTENSION` **0건** | 관리형에서 막혀도 무관 ✅ |
| Redis | RedisTemplate 79, Redisson 53, `@Cacheable` 23, `RequestRateLimiter` 4 | 캐시만이 아니라 **분산 락**이 걸려 있다 |
| Kafka | 21개 설정 클래스, 트랜잭셔널 프로듀서, DLQ | 토픽 자동 생성·트랜잭션 지원이 필요하다 |
| Elasticsearch | `ops/03` 이 `korean_analyzer`(nori) 존재를 검증 | **플러그인 설치가 필요하다** |
| Kafka Connect | 루트의 `*-outbox-connector-*.json` 은 **어느 매니페스트에도 없다** | 아웃박스는 애플리케이션 폴러가 돌린다(docs/21). 관리형 커넥터 의존 없음 ✅ |

`SKIP LOCKED` 가 결정적이다. 아웃박스 폴러, 메일 디스패처(docs/29), SMS 디스패처가 전부
"여러 레플리카가 같은 테이블에서 서로 다른 행을 집는다"를 이걸로 구현한다. 없으면 레플리카
2개가 같은 메일을 두 번 보낸다.

## 2. 그런데 — 무엇을 아끼려는 건가

"클러스터가 훨씬 가벼워진다"는 전제를 먼저 검증했다. `kustomize build` 결과로 계산한
**CPU·메모리 요청 합계**다.

| 구성 | CPU 요청 | MEM 요청 | 4 OCPU / 24GB | 2 OCPU / 12GB |
|---|---:|---:|---|---|
| prod(HPA min=2) + 클러스터 내 인프라 5종 | 5,950m | 10,048Mi | 🔴 초과 | 🔴 초과 |
| prod(HPA min=2), 앱만 | 5,300m | 8,192Mi | 🔴 초과 | 🔴 초과 |
| **external**, 전부 1레플리카 + Kafka·ES·Redis | **3,350m** | **5,824Mi** | ✅ | 🔴 초과 |
| **oci 오버레이** + Kafka·Redis (ES 제외) | **1,000m** | **3,520Mi** | ✅ 여유 | ✅ |

> ⚠️ **한도가 테넌시마다 다르다.** 2026-06-15 부로 Always Free Ampere 한도가
> 4 OCPU/24GB → 2 OCPU/12GB 로 축소됐다고 공지 없이 문서만 바뀌었지만, **실제로는
> 4 OCPU/24GB 가 그대로 잡히는 계정이 있다.** 그러니 "이제 2/12 다"라고 단정하지 말고
> **본인 인스턴스에서 확인**할 것: `nproc` 과 `free -g`.
>
> 그래서 오버레이가 둘이다. `external` 은 4 OCPU 를 전제하고, `oci` 는 2 OCPU 에서도
> 들어가게 조인 것이다(docs/33 §4·§8).

**4 OCPU / 24GB 를 잡았다면 `external` 이 들어간다. 다만 여유는 거의 없다.**

⚠️ **실측이 추정보다 컸다.** 위 표의 3,350m 은 애플리케이션 매니페스트만 더한 값이다.
실제 4 OCPU 노드에서 잰 값은 **3,980m (99%)** 였다. 빠진 것들이 있었다:

| | CPU 요청 |
|---|---:|
| external 앱 13개 (Java 11×250m + frontend 100m + **cloudflared 2×50m**) | 2,950m |
| 남는 인프라 (redis 50 + kafka 200 + **elasticsearch 200**) | 450m |
| **k3s 내장** (CoreDNS 100 + metrics-server 100) | 200m |
| 실측과의 차이 — 노드에서 직접 확인할 것 | ~380m |
| **실측 합계** | **3,980m / 4,000m** |

**해석: 99% 는 "CPU 가 바쁘다"가 아니라 "스케줄러의 예약 장부가 찼다"는 뜻이다.**
요청은 예약이고, 실제 사용량과 무관하다. Spring Boot 서비스는 대개 유휴 시 10~50m 을
쓰므로 실사용률은 훨씬 낮다. 메모리 37% 도, 상한 555% 초과도 정상이다 —
**상한은 노드 용량을 넘어도 된다.**

그래서 당장 죽지는 않는다. 다만 **다음 한 가지가 반드시 막힌다:**

> ⚠️ **롤링 업데이트가 멈춘다.** `kubectl rollout restart` 나 이미지 교체는 기존 파드를
> 지우기 **전에** 새 파드를 띄운다(maxSurge). 20m 남은 상태에서는 새 파드가 `Pending` 에
> 걸려 롤아웃이 영원히 끝나지 않는다. HPA 도 당연히 못 올라간다.

### → 오버레이에서 해결했다

`external` 오버레이가 **CPU 요청을 100m 으로 낮춘다**(`patch-java-requests.yaml`).
상한은 그대로 1,000m 이다. 결과:

| | CPU 요청 |
|---|---:|
| 앱 13개 (Java 11×100m + frontend 100m + cloudflared 2×50m) | 1,300m |
| 인프라 (redis 50 + kafka 200 + elasticsearch 200) | 450m |
| k3s 내장 (CoreDNS + metrics-server) | 200m |
| **합계** | **약 1,950m / 4,000m** |

여유가 2,000m 쯤 남아 롤링 업데이트도, 핵심 서비스 2레플리카도 가능하다.

⚠️ **이 값을 `kubectl patch` 로 바꾸지 말 것.** 다음 `kubectl apply -k` 에 덮인다 —
실제로 그렇게 해서 99% 로 되돌아갔고 파드가 `Insufficient cpu` 로 스케줄되지 못했다.
바꿔야 하면 `patch-java-requests.yaml` 에서 바꾼다.

### 그래도 부족하면 — 효과가 큰 순서

```bash
# 지금 무엇이 차지하고 있는지부터 본다
kubectl get pods -A -o json | jq -r '
  .items[] | select(.status.phase=="Running")
  | [([.spec.containers[].resources.requests.cpu // "0"] | join("+")),
     .metadata.namespace + "/" + .metadata.name] | @tsv' | sort -rn | head -20
```

| 수단 | 아끼는 양 | 대가 |
|---|---:|---|
| **Java 요청을 250m → 60m** (`oci` 오버레이가 하는 것) | **~2,090m** | 부하가 몰리면 파드끼리 CPU 를 다툰다. 단일 노드에서는 어차피 그렇다 |
| Elasticsearch 삭제 | 200m | 한국어 형태소(nori) 검색 경로를 못 밟는다 |
| cloudflared 2 → 1 | 50m | 터널 롤아웃 시 짧은 단절 |

가장 큰 것은 첫 번째다. **250m 를 예약해 두고 20m 를 쓰는 것이 낭비**이고, 폭주를 막는
것은 요청이 아니라 상한(1,000m)이다. 요청만 낮추고 상한은 그대로 두면 된다:

```bash
kubectl -n ecommerce get deploy -o name | grep -E 'service|server' | xargs -I{} \
  kubectl -n ecommerce patch {} --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/requests/cpu","value":"80m"}]'
```

⚠️ 이건 명령형 패치라 다음 `kubectl apply -k` 에 덮인다. 계속 쓰려면 `k8s-overlays/oci` 를
쓰거나(상한까지 같이 조여진다) 별도 오버레이를 만든다.

### 레플리카 2 는 지금 안 된다

**레플리카 1은 이 저장소가 레플리카 2에서 잡아 온 동시성 버그를 재현하지 못한다**
(docs/31 §3). 원래 4 OCPU 의 여유로 핵심 두세 개를 2로 올릴 수 있다고 적었으나,
**실측 여유가 20m 이라 불가능하다.** 위 방법으로 요청을 낮춘 뒤에야 가능하다:

```bash
kubectl -n ecommerce scale deploy order-service catalog-service --replicas=2
```

⚠️ **HPA 를 적용했다면 `kubectl scale` 은 되돌려진다.** CPU 가 목표치 아래면 HPA 가
안정화 창(기본 5분) 뒤 `minReplicas` 로 다시 내린다. 그때는 HPA 를 고쳐야 한다:

```bash
kubectl -n ecommerce patch hpa order-service -p '{"spec":{"minReplicas":2}}'
```

⚠️ 서비스 이름은 `catalog-service` 다 — **`product-service` 라는 것은 없다.**

인프라 5종의 요청 합계는 **650m / 1,856Mi** 이고, 그중 밖으로 나갈 수 있는
PostgreSQL·MongoDB 는 **200m / 512Mi** 뿐이다(Redis 는 남긴다 — §6).

> **인프라를 밖으로 빼는 것만으로는 어림도 없다.** 4 OCPU 시절에도 초과분의 주범은
> 인프라가 아니라 **애플리케이션 레플리카**였고, 2 OCPU 가 된 지금은 격차가 더 벌어졌다.
> 실제로 효과가 큰 순서는 이렇다:
>
>   1. **레플리카를 1로** (HPA 미적용) — 5,300m → 2,900m
>   2. **요청·상한을 줄이고 JVM 힙을 명시** (oci 오버레이) — 2,900m → 750m
>   3. **Elasticsearch 를 빼기** — 200m/768Mi. 어차피 `SEARCH_ENGINE=postgres` 가 기본이다
>   4. 인프라 외부화 — 200m/512Mi. **가장 작다**
>
> 그래도 외부화를 하는 이유는 자원이 아니라 아래의 데이터 수명 때문이다.

`ops/23-oci-ampere-bootstrap.sh` 의 예전 주석("한 대에 들어가는 규모다")은 틀렸다.
이번에 계산해서 고쳤다.

그래도 외부화에는 자원 절감과 별개의 이득이 있다 — 그리고 그쪽이 사실 더 크다:

- **데이터가 노드 수명과 분리된다.** 지금 `90-dev-infra.yaml` 의 PostgreSQL 은
  `emptyDir` 다. 파드가 재시작하면 데이터가 사라진다. 프리티어 인스턴스가 재부팅되면 끝이다
- **백업·PITR·업그레이드가 provider 책임이 된다** (다만 §7의 대가를 보라)
- ES·Kafka 는 어차피 남으므로 노드는 여전히 스테이트풀이다 — 완전한 분리는 아니다

## 3. 무엇이 실제로 나갈 수 있나

| | 후보 | 판정 |
|---|---|---|
| PostgreSQL | Neon / Supabase / Aiven | ✅ **나간다.** 셋 다 진짜 PostgreSQL, 확장 불필요 |
| MongoDB | Atlas M0 | ✅ **나간다.** chat-service 는 문서 저장만 한다 |
| Redis | Upstash | ❌ **남는다.** 얻는 것이 50m/64Mi 뿐이라 위험을 감수할 이유가 없다 — §6 |
| Kafka | Confluent / Redpanda / Aiven | ❌ **남는다.** 상시 무료 관리형 Kafka 를 찾지 못했다 |
| Elasticsearch | Bonsai / Elastic Cloud | ❌ **남는다.** nori 플러그인 |

### Kafka 를 남기는 이유

Confluent Cloud 는 "무료 크레딧"이지 무료 티어가 아니다. Basic 클러스터는 기본요금이 없는
대신 **처리량·저장량으로 과금**되고, 신용카드가 필요하며, 크레딧 소진 후에는 청구된다.
Redpanda Serverless·Aiven 도 사정이 비슷하다(체험 기간 또는 사용량 과금).

포트폴리오 규모의 트래픽이면 실제 청구액은 작을 수 있다. 하지만 **"무료"라고 적어 두고
카드가 긁히는 것**은 이 문서가 하지 말아야 할 일이다. 그래서 기본값은 클러스터 내 Kafka다.

대신 **옮기고 싶을 때 옮길 수 있게는 만들어 뒀다** — §4의 SASL 지원이 그것이다.

> ⚠️ 무료 티어 조건은 자주 바뀐다. 이 표는 판단의 근거이지 가입 시점의 사실이 아니다.
> 가입 전에 각 provider 의 현재 요금 페이지를 직접 확인할 것.

### Elasticsearch 를 남기는 이유

`ops/03-enable-es-search.sh` 가 `korean_analyzer` 의 존재를 검증하고, 그건
`analysis-nori` 플러그인이 설치돼 있어야 한다. 관리형 ES 무료 티어는 대개 커스텀 플러그인
설치를 허용하지 않는다. 플러그인 없이 붙이면 색인 생성이 실패하거나 — 더 나쁘게 —
한국어 검색이 조용히 형편없어진다.

## 4. 코드를 고쳐야 했던 것 — 전부 같은 버그였다

관리형으로 붙이려다 **네 곳에서 같은 형태의 버그**를 만났다.

> 사설 CA 로 발급한 인증서 경로가 **비어 있어도 무조건 로딩한다.**

로컬은 평문(PLAINTEXT / `ssl.enabled=false`)이라 이 코드가 아예 실행되지 않았고,
클러스터 안에서는 경로가 실제 파일을 가리켰다. 그래서 **관리형으로 붙이는 순간에만** 터진다.
관리형 서비스는 하나같이 *공개 CA 인증서 + 비밀번호(또는 API 키)* 이고 클라이언트 인증서가
없기 때문이다.

| 곳 | 증상 | 고친 방법 |
|---|---|---|
| Kafka 설정 클래스 **24개** | `ssl.truststore.location=""` 를 그대로 넣어 빈 경로를 연다 | `KafkaSecuritySettings` 하나로 모으고 **비면 넣지 않는다** |
| `RedissonConfig` (cart·chat) | `new File("")` → 현재 작업 디렉터리를 트러스트스토어로 넘긴다 | 경로가 있을 때만 설정 |
| `RedisCacheConfig` (catalog·order) | 빈 경로를 `resourceLoader` 로 열어 `FileNotFoundException` | 경로가 있을 때만 `SslOptions` 생성 |
| `MongoSslConfig` (chat) | `mongodb+srv` 는 TLS 가 기본 → 사설 CA 조립 경로로 들어간다 | 경로가 비면 JVM 기본 신뢰 저장소로 TLS |

### 24개 복제의 정리

Kafka 설정 클래스 24개가 이 여섯 줄을 그대로 복제하고 있었다:

```java
.put(SslConfigs.SSL_KEYSTORE_LOCATION_CONFIG,   checkPath(keyStoreLocation))
.put(SslConfigs.SSL_KEYSTORE_PASSWORD_CONFIG,   keyStorePassword)
.put(SslConfigs.SSL_KEYSTORE_TYPE_CONFIG,       keyStoreType)
.put(SslConfigs.SSL_TRUSTSTORE_LOCATION_CONFIG, checkPath(trustStoreLocation))
...
```

이제 전부 `.putAll(securityProps())` 한 줄이고, 실제 계산은
`common/.../config/KafkaSecuritySettings.java` 가 한다. 규칙은 셋이다:

1. 프로토콜에 **필요한 키만** 넣는다. PLAINTEXT 면 `security.protocol` 하나뿐이다
2. 스토어 경로가 비면 **넣지 않는다** → JVM 기본 신뢰 저장소(공개 CA)
3. `SASL_*` 이면 `sasl.mechanism` + `sasl.jaas.config` 를 만든다.
   자격증명이 없으면 **기동 시점에 죽는다** — 브로커가 돌려주는 `Authentication failed` 에는
   원인 단서가 없기 때문이다

시크릿 안의 `"` 와 `\` 는 이스케이프한다. 관리형 API 시크릿에는 실제로 들어 있고, 그대로
두면 JAAS 파서가 문자열을 엉뚱한 곳에서 끊어 `Unable to find login module` 이라는
**전혀 무관한** 오류를 낸다.

키 이름은 Kafka 상수가 아니라 문자열이다 — common 을 의존하는 모듈 중에 Kafka 를 아예
안 쓰는 것(eureka-server, config-server)이 있어서 상수 하나 때문에 kafka-clients 를
그쪽 런타임까지 끌고 갈 이유가 없다. 대신 그 문자열이 실제 상수와 같은지는
`KafkaSecuritySettingsTest` 가 **테스트 클래스패스에서만** kafka-clients 를 가져와 검증한다.

가드레일 `B-35` 가 이 정리가 다시 흩어지는 것을 막는다: `KafkaSecuritySettings` 밖의
어떤 `src/main` 파일도 `SslConfigs.` / `SaslConfigs.` 를 쓰면 빌드가 실패한다.

## 5. 오버레이 — `k8s-overlays/external`

```
k8s/                      매니페스트 원본 (베이스)
k8s-overlays/dev/         레플리카 1, 요청 축소, 로컬 이미지
k8s-overlays/prod/        replicas 삭제(HPA 소유), 레지스트리 이미지, cloudflared
k8s-overlays/external/    ← prod 를 상속하고 엔드포인트만 갈아 끼운다
k8s-overlays/oci/         ← external 을 상속하고 2 OCPU/12GB 에 맞게 조인다 (docs/33 §4)
```

`external` 은 `../prod` 를 베이스로 삼는다(디렉터리 베이스라 참조 가능하다 — docs/31 §2의
제약이 여기서는 걸리지 않는다). 바꾸는 것은 `ecommerce-config` ConfigMap **한 장**뿐이다.

가능한 이유는 베이스가 JDBC URL 을 이렇게 쓰고 있었기 때문이다:

```yaml
value: "jdbc:postgresql://$(POSTGRES_HOST):$(POSTGRES_PORT)/userdb?sslmode=require"
```

`POSTGRES_HOST` 두 글자만 바꾸면 **10개 데이터소스가 한꺼번에 따라온다.** Deployment 를
하나도 건드리지 않는다.

바꾸는 키:

| 키 | 왜 |
|---|---|
| `POSTGRES_HOST` / `POSTGRES_PORT` | 관리형 엔드포인트 |
| `DB_POOL_SIZE: 3` | 10 데이터소스 × 3 × 레플리카 3 = 90. 기본값 5면 150이라 무료 티어 한도를 넘는다 |
| `SPRING_DATA_REDIS_*` | 관리형으로 옮길 때만. 기본 구성은 클러스터 안 Redis 라 그대로 둔다(§6) |
| `SPRING_DATA_REDIS_SSL_{TRUSTSTORE,KEYSTORE,CACERT}: ""` | **§4의 핵심.** 비워야 공개 CA 로 검증한다 |
| `SPRING_DATA_MONGODB_{CACERT,KEYSTORE}: ""` | 같은 이유 |

### 2 OCPU 박스에 올린다면 — `oci` 오버레이를 쓴다

`external` 은 여전히 prod 의 리소스 값(250m/384Mi × HPA min=2)을 쓰므로 **2 OCPU 에
들어가지 않는다**(§2 표). 그 위에 `k8s-overlays/oci` 를 얹는다:

```bash
kubectl apply -k k8s-overlays/oci
# ⚠️ k8s/70-autoscaling.yaml 은 적용하지 않는다 — replicas 필드가 없으면 기본값 1이다
```

⚠️ **레플리카 1에서는 이 저장소가 겪은 동시성 버그가 재현되지 않는다**(docs/31 §3).
그건 `ops/12-staging-rehearsal.sh` 로 따로 확인해야 한다.

### 남는 인프라만 띄우기

```bash
kubectl apply -f k8s/90-dev-infra.yaml     # 낱개 파일이라 오버레이가 참조 못 한다
kubectl -n postgres delete deploy postgres
kubectl -n mongodb  delete deploy mongodb
# ⚠️ redis 는 지우지 않는다 — 클러스터에 남긴다(§6)
```

## 6. Redis 는 클러스터에 남긴다 — 결정

처음에는 "확인해 봐야 안다"로 남겨 뒀는데, 확인 비용과 이득을 나란히 놓으면 결정이 먼저다.

### 무엇이 걸리나

`RedisTemplate`·`@Cacheable`·`RequestRateLimiter` 는 평범한 명령이라 문제될 것이 없다.
문제는 **Redisson** 이다(cart·chat 두 서비스, 53곳). 분산 락이 단순한 `SETNX` 가 아니다:

- 락 획득·해제를 **Lua 스크립트**(`EVAL`/`SCRIPT LOAD`)로 원자화한다
- 대기 중인 클라이언트를 깨우는 데 **pub/sub** 을 쓴다
- 커넥션 초기화 때 `CLIENT SETNAME`, `INFO replication` 같은 명령을 보낸다

관리형 Redis 가 이들 전부를 무료 플랜에서 지원하는지는 **계정 없이 확인할 수 없다.**

### 그래서 결정

| | |
|---|---|
| 밖으로 빼서 아끼는 것 | **50m CPU / 64Mi** — 인프라 5종 중 가장 적다 |
| 잃을 수 있는 것 | 장바구니 담기·채팅이 **락 단계에서 죽는다.** 그것도 배포한 뒤에 |
| Redis 가 들고 있는 것 | 캐시 · 락 · 레이트리밋 카운터 — **전부 재구성 가능하다** |

마지막 줄이 핵심이다. PostgreSQL·MongoDB 를 밖으로 뺀 진짜 이유는 자원이 아니라
**`emptyDir` 라 파드가 재시작하면 데이터가 사라지기 때문**이었다(§2). Redis 에는 그 이유가
적용되지 않는다. 캐시가 날아가면 다시 채워지고, 락은 애초에 휘발성이고, 레이트리밋
카운터가 초기화되는 것은 재시작 시 한 번뿐이다.

**이득이 가장 작고 위험이 가장 큰 것을 굳이 옮길 이유가 없다.** Redis 는 남긴다.

### 나중에 옮기고 싶어지면

코드는 이미 준비되어 있다 — §4 에서 `RedissonConfig`·`RedisCacheConfig` 의 빈 인증서 경로
문제를 고쳤고, `k8s-overlays/external` 의 ConfigMap 에 Redis 키가 주석과 함께 들어 있다.
결정만 바꾸면 된다. 확인 방법은 하나뿐이다:

```bash
KEEP=1 ./ops/13-k3s-deploy.sh
# cart-service 하나만 그 provider 로 돌리고 장바구니 담기(락 경로)를 눌러 본다
```

`ERR unknown command` 나 pub/sub 타임아웃이 나오면 그 provider 는 못 쓴다.
명령 수 한도도 함께 볼 것 — `@Cacheable` 23곳과 레이트리미터가 카운터를 빠르게 태운다.

## 7. 외부화가 **잃는** 것

| | 클러스터 안 | 관리형 무료 티어 |
|---|---|---|
| 지연 | 같은 노드, 0.1ms | 인터넷 왕복. **리전이 다르면 수십 ms** |
| 백업 | `ops/08` `ops/10` 이 돈다 | provider 책임. 무료 티어는 보존이 짧거나 없다 |
| `ops/09-restore-drill.sh` | 동작한다 | **동작하지 않는다** — 대상이 클러스터 안 PG 다 |
| `k8s/85-backup-cronjobs.yaml` | 동작한다 | **동작하지 않는다** |
| 노출면 | 클러스터 내부만 | **인터넷에 열린 엔드포인트**. 비밀번호가 방어선 |
| 유휴 정지 | 없다 | 무료 티어는 며칠 유휴면 정지된다(첫 요청이 콜드 스타트) |

지연은 특히 조심할 것. 이 저장소는 요청 하나에 여러 번 DB 를 왕복하고, N+1 가드
테스트(docs/19)까지 두고 있다. 같은 노드에서 0.1ms 이던 왕복이 30ms 가 되면
**쿼리 20개짜리 요청이 2ms 에서 600ms 가 된다.** 반드시 OCI 인스턴스와 **같은 리전**에
프로비저닝할 것.

그리고 접근 IP 제한을 걸 것(Neon: IP Allow, Aiven: Allowed IP). 무료 티어라 제한이
불가능하다면, 그건 비밀번호가 유일한 방어선이라는 뜻이다.

**확인하지 못함 (계정·환경이 없다)**

- **Neon·Supabase·Aiven 어느 곳에도 실제로 붙여 보지 않았다.** 검증은 PostgreSQL 16
  컨테이너를 "관리형인 척" 세워서 했다. 풀러(PgBouncer) 경로의 프리페어드 스테이트먼트
  문제(§ 아래)는 컨테이너로는 재현되지 않는다
- **Upstash 에 Redisson 을 붙여 보지 않았다.** 그래서 §6 은 "검증했다"가 아니라 **"옮기지 않기로 결정했다"** 이다. 옮기려면 그 검증이 먼저다
- **관리형 Kafka 에 붙여 보지 않았다.** SASL 코드 경로는 단위 테스트로만 검증했다
  (JAAS 문자열 생성·이스케이프·빈 스토어 생략). 실제 브로커 핸드셰이크는 미확인
- MongoDB Atlas 미검증
- 무료 티어 조건(용량·명령 수·유휴 정지)은 **문서 기준**이며 가입 시점에 다를 수 있다

**알려진 미해결 — 풀러(pooler) 엔드포인트**

Neon·Supabase 의 풀링 엔드포인트는 PgBouncer transaction 모드다. 이 모드는 **서버 사이드
프리페어드 스테이트먼트와 충돌**한다(pgjdbc 는 같은 문장을 5회 실행하면 자동으로 서버
프리페어로 전환한다). 증상은 산발적인
`ERROR: prepared statement "S_1" already exists` 다.

**기본 구성은 직결(direct) 엔드포인트라 여기에 해당하지 않는다.** 커넥션 계산도 맞는다 —
10 데이터소스 × `DB_POOL_SIZE=3` × 레플리카 1 = 30 으로 무료 티어 한도 안이다.

매니페스트에 `$(JDBC_EXTRA_PARAMS)` 같은 자리를 미리 심어 두지 **않은** 이유: 그 ConfigMap
키가 없으면 `$(...)` 가 문자 그대로 남아 **10개 데이터소스의 URL 이 전부 깨진다.** 지금
필요하지도 않은 기능을 위해 새 함정을 만드는 셈이다.

풀러가 실제로 필요해지면(레플리카를 늘려 커넥션이 모자랄 때) 30초면 켤 수 있다:

```bash
# 10개 데이터소스 URL 에 &prepareThreshold=0 를 덧붙인다
for d in user-service catalog-service cart-service order-service pay-service \
         coupon-service chat-service notification-service delivery-service; do
  kubectl -n ecommerce get deploy "$d" -o json \
    | python3 -c '
import json,sys
d=json.load(sys.stdin)
for c in d["spec"]["template"]["spec"]["containers"]:
    for e in c.get("env",[]):
        if e.get("name","").startswith("SPRING_DATASOURCE") and e["name"].endswith("_URL") \
           and "prepareThreshold" not in e.get("value",""):
            e["value"] += "&prepareThreshold=0"
json.dump(d,sys.stdout)' \
    | kubectl apply -f - 
done
```

⚠️ 증상이 **산발적**이라는 점이 함정이다. pgjdbc 는 같은 문장을 5회 실행한 뒤에야 서버
프리페어드로 전환하므로, 배포 직후에는 멀쩡하다가 트래픽이 쌓인 뒤에 터진다.
