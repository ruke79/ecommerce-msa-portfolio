# 50. `/browse` 정밀 분석 — 고친 것, 남긴 것, 추천·시맨틱 검색을 붙이려면

[日本語](50-browse-analysis.md) | **한국어**

배경: 앞으로 상품 추천·시맨틱 검색 같은 기능을 붙이기 전에 `/browse` 화면의 문제점과
개선점을 철저히 조사한다. 눈에 보이는 증상은 **상품 가격 범위 설정 UI 의 버그**였다.

가격 범위를 따라가 보니 **한 버그가 아니라 다섯 겹**이었고, 그 다섯 겹이 프론트 두 곳과
서버 두 곳에 나뉘어 있었다. 한 겹만 고치면 증상이 모양만 바꿔 남는 종류다.

---

## 1. 🔴 가격 필터가 "전부 보여주기"로 뒤집히던 경로

사용자가 보는 증상은 하나였다 — **가격대를 좁힐수록 상품이 줄다가, 어느 순간 카탈로그
전체가 돌아온다.** 원인은 넷이 사슬로 이어져 있었다.

| # | 어디 | 무엇 |
|---|---|---|
| ① | `HeadingFilter` | "500 이상" 버튼이 `price=500_` 을 만든다 (상한 없음) |
| ② | `browse.jsx` | `Number("") \|\| 0` — 비어 있는 상한이 **0** 이 된다 → `500 ~ 0` |
| ③ | `ProductSkuRepository` | `between 500 and 0` → **한 행도 안 나온다** |
| ④ | `SearchService` | 빈 목록이면 **조건을 통째로 버린다** → 전체 상품 |

④ 가 핵심이다. 조건이 이랬다:

```java
if (productIdsFromSku != null && !productIdsFromSku.isEmpty()) {
    builder.and(product.productId.in(productIdsFromSku));
}
```

**"맞는 게 없다" 가 "제한이 없다" 로 뒤집힌다.** 가격뿐 아니라 색상·사이즈도 같은 질의를
타므로, 재고에 없는 색을 고르면 역시 전체가 나왔다.

`null`(필터를 걸지 않음)과 `빈 목록`(걸었는데 매칭 없음)은 다른 뜻이다. 이제 갈라 둔다 —
빈 목록이면 불가능 조건(`productId = -1`)을 넣는다. ES 경로가 이미 쓰던 방식이다.

### 부수 효과: 조건 없는 풀스캔이 사라졌다

예전에는 가격·색상·사이즈를 **하나도 고르지 않아도** 그 SKU 질의를 매번 돌렸다. 조건이
없으니 결과는 "상품 전량의 id" 이고, 그것이 그대로 `in (...)` 에 들어갔다. 상품이 늘수록
커지는, 아무 일도 하지 않는 풀스캔 + 거대한 IN 절이다. 이제 걸었을 때만 돌린다.

### 열린 범위를 표현할 수 있게 했다

```sql
-- 예전: 둘 중 하나라도 null 이면 가격 조건이 통째로 사라진다
where ((:low_price is null or :high_price is null) or b.price between :low_price and :high_price)

-- 지금: 두 경계를 따로 본다
where (:low_price is null or b.price >= :low_price)
  and (:high_price is null or b.price <= :high_price)
```

그리고 프론트는 빈 경계를 **보내지 않는다**(0 이 아니다). axios 가 `undefined` 를 쿼리에서
빼고, 서버는 `null` 을 "그 경계 없음" 으로 읽는다. `500 이상` · `50 이하` 가 이제 표현된다.

## 2. 가격 범위 설정 UI — 눈에 보이던 세 가지

### ① 가격 칸을 비울 수 없었다

```jsx
value={minPrice || (priceParam)?.split("_")[0]}
```

지운 칸은 빈 문자열이고 **빈 문자열은 falsy** 다. 그래서 URL 의 옛 값이 곧바로 되살아난다 —
숫자를 지우면 그 자리에 방금 지운 값이 다시 나타난다. 입력칸의 주인을 state 하나로
정리하고, 바깥에서 URL 이 바뀔 때(Clear All · 뒤로가기 · 가격대 버튼)만 effect 가 맞춘다.

### ② 상한 칸이 양수를 거부했다

```jsx
<input type="number" placeholder="최대" max="0" />
```

위 칸의 `min="0"` 을 복사하며 **이름만 바뀐** 것이다. "최대 가격은 0 이하" 라는 제약이라
양수를 넣는 순간 입력칸이 유효하지 않은 상태가 되고, 브라우저 스피너가 0 위로 올라가지
않는다.

### ③ 어느 가격대를 골랐는지 알 수 없었다

다섯 개의 막대 버튼에 선택 표시가 없었다. 눌러도 툴팁만 뜨고 화면은 그대로다 — "눌리긴
한 건가" 를 상품 목록으로만 판단해야 했다. `aria-pressed` 와 색으로 표시한다(그리고 그
덕분에 테스트가 "무엇이 선택됐는가" 를 물어볼 수 있게 됐다).

> 다섯 벌 복사돼 있던 `<Tooltip>` 블록을 `PRICE_RANGES` 배열 하나로 접었다. ②번 같은
> 복사-수정 실수가 다섯 번 일어날 수 있던 자리다.

## 3. 🔴 켜지지 않던 필터 둘

### 별점 — 이름을 고친 뒤에도 한 겹이 남아 있었다

docs/40 에서 `searchParams.get("rate")` → `"rating"` 으로 고쳤다. 그런데 요청을 만들 때:

```js
const rating = ratingQuery !== "" ? { rating: Number(ratingQuery) } : {};
return { ..., shipping: shipping.shipping, rating, ... };
//                      ^^^^^^^^^^^^^^^^^ 풀어서 보냄   ^^^^^^ 객체 그대로
```

axios 는 그 객체를 **`rating[rating]=4`** 로 직렬화한다(실측). 서버에는 `rating` 이라는
파라미터가 도착하지 않고, 스프링은 float 기본값 0 으로 바인딩하며, `getRating() != 0.0f`
는 거짓 — 조건이 붙지 않는다. 바로 옆 `shipping` 은 풀어 보내고 있었는데 별점만 빠졌다.

> 이 버그를 **테스트가 고정하고 있었다.** `expect(...rating).toEqual({ rating: 4 })` — 틀린
> 모양을 회귀 테스트로 굳혀 둔 것이다. 지금은 숫자임을 검사한다.

### 무료배송 — 서버가 받기만 하고 쓰지 않았다

`SearchParamsRequest.shipping` 은 필드로 존재하고 요청에도 실려 갔지만,
`buildSearchPredicate` 에 **그 값을 읽는 줄이 없었다.** 체크박스는 URL 을 바꾸고 화면은
다시 그려지는데 결과는 그대로다. 별점과 같은 모양의 결함이다.

조건을 붙이되 `shipping <= :value` 로 둔다 — 화면은 0(무료)만 보내지만, 나중에 "3,000원
이하" 를 붙일 때 서버를 다시 고치지 않아도 된다. 배송비가 `null` 인 상품은 제외된다:
**모르는 값을 무료라고 말하지 않는다.**

### 체크 상태가 한 번도 켜지지 않았다

```js
const shippingParam = Number(searchParams.get('shipping'));  // 숫자
...
defaultChecked={shippingParam === "0"}                       // 문자열과 비교
```

`0 === "0"` 은 언제나 거짓이다. URL 에 필터가 걸린 채로 새로고침하면 **상품 목록은 걸러져
있는데 체크박스는 꺼져 있다.** 게다가 `defaultChecked` 라 반대 방향도 깨진다 — 한 번 켠
뒤 Clear All 을 눌러도 체크가 남는다.

## 4. 🔴 필터 이름을 정규식으로 읽던 코드

`browse.jsx` 의 `replaceQuery` — 여러 개 고를 수 있는 필터(`색상=Red_Blue`)에서 값 하나를
켜고 끄는 함수다. 안쪽이 이랬다:

```js
const valueCheck = existedQeury?.search(value);
```

[`String.prototype.search`](https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/String/search)
**의 인자는 RegExp 다.** 문자열을 주면 브라우저가 정규식으로 컴파일한다. 결과:

| 값 | 무슨 일이 | |
|---|---|---|
| `"C++"` · `"*Star"` · `"?"` | `SyntaxError: Nothing to repeat` | **필터를 그리는 중이라 화면이 죽는다** |
| `"A+B"` · `"(Pack)"` | 던지지 않는다 | 터지는 값과 아닌 값이 **눈으로 구분되지 않는다** |
| `"C.C"` | 조용히 틀린다 | `.` 이 아무 글자나 맞아 `"CXC"` 도 "선택됨" |
| `"Gre"` | 부분 일치를 선택으로 읽는다 | `색상=Green` 일 때 `Gre` 가 켜진 것처럼 보인다 |

값은 애초에 `_` 로 이어 붙인 **목록**이다. 목록으로 다루면 위의 넷이 한꺼번에 사라진다 —
문자열 검색을 할 이유가 처음부터 없었다. 브랜드 이름은 상품 데이터에서 오므로 이것은
**데이터가 채우는 입력**이고, URL 로도 직접 넣을 수 있다.

## 5. 🔴 ES 모드에서 새 상품이 검색에 안 나오던 이유

`ProductIndexService` 는 "배치 재색인 사이의 간극을 메운다" 는 목적으로 만들어졌다. 그런데:

| | 대상 |
|---|---|
| **쓰기** (`ProductDocumentRepository`) | `@Document(indexName = "products")` → 인덱스 **`products`** |
| **읽기** (`EsProductSearchService`) | 별칭 **`product-alias`** (실체는 `products-<타임스탬프>-products`) |

**쓰는 곳과 읽는 곳이 다른 인덱스였다.** 새로 등록한 상품은 다음 전체 재색인까지 검색에
나오지 않는다 — 이 클래스가 메우려던 바로 그 간극이다. 게다가 아무도 읽지 않는 `products`
인덱스가 동적 매핑으로 조용히 생겨 자란다. **실패 로그도 남지 않는다. 저장이 성공했기
때문이다.**

이제 별칭에 직접 쓴다. 별칭이 아직 없으면(전체 재색인을 한 번도 돌리지 않은 배포)
**쓰지 않고 경고만 남긴다** — 그 이름으로 쓰면 ES 가 같은 이름의 *인덱스*를 만들고, 그러면
나중에 배치의 별칭 롤오버가 **영구히** 실패한다(같은 이름의 인덱스와 별칭은 공존할 수 없다).

## 6. 고치지 않고 남긴 구조적 문제

여기부터는 버그가 아니라 **설계의 한계**다. 추천·시맨틱 검색을 붙일 때 정면으로 부딪히는
것들이라 먼저 적어 둔다.

### ① 정렬이 서버에 없다 — "가격 낮은 순"이 거짓말을 한다

`catalog-service` 의 검색은 정렬 파라미터를 받지 않는다. 정렬은 **브라우저가 이미 받아 둔
목록 안에서** 한다(`sortProducts`). 무한 스크롤이라 그 목록은 "지금까지 스크롤한 만큼"이다.

즉 **"가격 낮은 순" 은 전체 최저가가 아니라 "내가 본 것 중 최저가" 다.** 10개만 봤으면
10개 중 정렬이다. 사용자는 그것을 알 수 없다.

정렬·페이징은 **같은 층에 있어야** 한다. 서버가 정렬해서 페이징하지 않으면 페이지 경계에서
순서가 깨지고, 그것을 가리려고 프론트가 다시 정렬하는 지금 모양이 된다.

### ② offset 페이징 — 추천/관련도와 근본적으로 안 맞는다

`offset/limit` 은 정렬 기준이 안정적일 때만 맞는다. 관련도 점수나 추천 점수는 **요청마다
바뀔 수 있으므로**, 3페이지를 받는 사이 1페이지의 상품이 밀려 내려와 다시 나온다. 지금
`products` 를 합칠 때 `seen` Set 으로 중복을 걸러 내는 코드가 그 증상의 반창고다.

관련도 기반으로 가면 **search_after(커서) 페이징**이 사실상 필수다.

### ③ 파셋에 개수가 없고, 다른 필터를 반영하지 않는다

`getColors/getSizes/getDetails` 는 **`categoryId` 하나로만** 캐시된다. 즉 "지금 조건에서
고를 수 있는 색" 이 아니라 "이 카테고리의 모든 색" 이다. 개수도 없다.

그래서 **고르면 0건이 되는 선택지**가 그대로 남는다 — 위 ④ 번 버그가 그 상태에서
"전체 상품" 으로 뒤집혔으니, 사용자 입장에서는 더 혼란스러웠다. ES 의 aggregation 으로
옮기면 개수와 "지금 조건 기준" 이 함께 해결된다.

### ④ 접근성 — 필터가 키보드로 닿지 않는다

카테고리 칩은 `<span onClick>`, 하위 카테고리는 `<h5 onClick>` 이다. 탭으로 갈 수 없고
Enter 로 누를 수 없으며 스크린 리더가 버튼으로 읽지 않는다. `cursor-pointer` 만 있어서
**누를 수 있는 것처럼 보이기만 한다** — 하위 카테고리가 실제로 동작하지 않던 시절의
인상과 같은 뿌리다(docs/40).

### ⑤ 텍스트 검색의 Postgres 폴백은 선행 와일드카드 LIKE 다

`like '%검색어%'` 는 인덱스를 쓸 수 없다. ES 를 끄면 조용히 풀스캔으로 내려간다.
지금은 상품 수가 적어 드러나지 않는다.

## 7. 상품 추천·시맨틱 검색을 붙이려면

지금 코드에서 **무엇이 이미 되어 있고, 무엇이 막고 있는가** 만 적는다.

### 이미 되어 있는 것

- **ES 경로가 "관련도 검색 → id 목록 → Postgres 하이드레이션" 으로 분리돼 있다.**
  이 모양이 중요하다 — 점수를 매기는 주체를 바꿔도(BM25 → 벡터 → 추천 모델) **호출부가
  그대로다.** `SearchService` 는 "누군가 준 id 목록" 만 안다
- ES 장애 시 폴백이 있다. 새 엔진을 얹어도 꺼졌을 때 화면이 죽지 않는다
- 한/영/일 멀티필드(`nori` · `standard` · `kuromoji`)가 이미 매핑돼 있다
- 별칭 롤오버 방식의 무중단 재색인이 있다 — **새 매핑을 넣는 길이 이미 뚫려 있다**

### 막고 있는 것

| | 왜 막는가 |
|---|---|
| **정렬이 서버에 없다**(⑥①) | 시맨틱 검색의 출력은 **점수 순서** 그 자체다. 그 순서를 프론트가 다시 정렬하면 검색 결과가 아니다 |
| **offset 페이징**(⑥②) | 점수 기반 순서에서 페이지가 어긋난다 |
| **`ES_CANDIDATE_LIMIT = 1000` 후 Postgres 재필터** | ES 가 상위 1000개를 주고 그 뒤 필터를 걸면, **필터에 걸러진 만큼 결과가 빈다.** 지금은 상품이 적어 안 보인다. 필터를 ES 로 내리거나 후보 수를 조건에 맞춰 늘려야 한다 |
| **행동 로그가 없다** | 추천의 원료는 클릭·장바구니·구매다. `/browse` 는 지금 아무것도 남기지 않는다 |
| **`@Cacheable("search_cache")`** | 개인화된 결과를 넣으면 **남의 추천이 섞인다.** 개인화 응답은 이 캐시를 타면 안 된다 |

### 붙이는 순서 (제안)

1. **정렬·페이징을 서버로** — 다른 모든 것의 전제다. 지금은 `sortProducts` 가 프론트에
   있고, 그것을 지우는 것이 1단계다
2. **커서(`search_after`) 페이징** — 점수 순서를 페이지에 걸쳐 유지한다
3. **파셋을 ES aggregation 으로** — 개수가 생기고 "0건이 되는 선택지" 가 사라진다
4. **행동 로그** — `product-viewed` · `cart-added` 이벤트. 이미 Kafka·아웃박스가 있으므로
   **새 인프라가 필요 없다.** 추천을 언제 만들든 그때 데이터가 있어야 한다. 가장 먼저
   시작해도 되는 유일한 항목이다
5. **시맨틱 검색** — `ProductDocument` 에 `dense_vector` 필드를 추가하고 kNN 을 BM25 와
   섞는다(하이브리드). 별칭 롤오버가 있으니 **매핑 변경이 무중단으로 나간다.**
   임베딩 생성은 색인 파이프라인 안에 둔다 — 검색 시점에 만들면 응답 시간이 모델에 묶인다
6. **추천** — 4번이 쌓인 뒤. "함께 본 상품" 같은 것은 모델 없이 집계만으로도 시작할 수 있다

> ⚠️ 5번을 1·2번보다 먼저 하면 **시맨틱 검색의 순서가 화면에서 뒤집힌다.** 벡터 검색이
> 잘 동작해도 사용자는 "검색이 이상하다" 고 본다. 순서가 중요하다.

### 🔴 카테고리를 고르면 500 — `CAST(:ids AS BIGINT[])`

`/browse?category=1` 이 500 이었다. 색상·사이즈 메뉴의 네이티브 SQL 이

```sql
where a.product_id IN (SELECT unnest(CAST(:productIds AS BIGINT[])))
```

였는데, Hibernate 는 컬렉션 파라미터를 `(?, ?)` 로 펼친다. PostgreSQL 은
`CAST((1, 2) AS BIGINT[])` 를 받고 **"cannot cast type record to bigint[]"** 로 거절한다.
이 질의는 카테고리 id 가 있을 때만 돈다(`getColors(categoryId)`), 그리고 **그 카테고리에
상품이 있어야** 목록이 비지 않는다. 빈 DB 에서는 통과하므로 컨테이너 기동 테스트가 못
잡았고, 운영에 상품이 들어온 뒤에야 터졌다. 로컬 PostgreSQL 에 붙여 `findColorsByProductId(
List.of(1L, 2L))` 로 재현했다.

`in (:productIds)` 로 바꿨다 — Hibernate 의 확장이 곧 올바른 SQL 이다. 빈 목록은 서비스가
미리 거른다(`in ()` 은 SQL 오류). 덤으로, 카테고리가 없을 때 `null` 을 넘기던 것은
`unnest(NULL)` = **빈 목록**이라 전체 화면의 색상·사이즈 메뉴가 늘 비어 있었다 —
`findAllColors / findAllSizes` 로 갈랐다.

**가드**: `CatalogServiceApplicationTests.colorAndSizeMenuQueriesRunWithIds` — 비어 있지 않은
id 목록으로 실제 PostgreSQL 에서 실행한다(`-PwithContainers`). 데이터는 필요 없다. 옛 SQL 은
파싱 단계에서 죽었다.

**가드**: `SearchServiceUnitTest`(+3) · `browse.test.jsx`(+8) · `HeadingFilter.test.jsx`(+10).
서버 2건과 프론트 3건은 **옛 코드로 되돌려 실패하는 것을 확인**했다.

### 🔴 카테고리를 고르면 다른 필터가 전부 사라졌다 — 그리고 그 반대도 (2026-09 추가)

사용자 보고: `/browse?category=3` 에서 "선택하면 필터가 제대로 안 된다".

핸들러는 자기 필터 **하나만** 넘긴다 — `filter({ category })`. 나머지 열두 개는
`undefined` 다. 원래 토글은 값이 없으면 아무것도 하지 않았는데, "같은 값을 다시 눌러 끈다"
를 붙인 커밋(24d06b4)에서 `!param` 이면 **지우도록** 합쳐졌다. 그 뒤로 무엇을 누르든
**그것 하나만 남았다**: `?category=3` 에서 색상을 고르면 카테고리가 풀려 전체가 나오고,
검색어를 넣고 카테고리를 고르면 검색어가 사라졌다. 카테고리는 잠깐 걸렸다가 다음 클릭에
풀리니 "안 먹는다" 로 보였다.

`applyFilter(searchParams, changes)` 로 뽑아 규칙을 고정했다: **언급하지 않은 필터
(`undefined`)는 손대지 않는다**, 빈 값(`{}`·`""`·`null`)은 지운다, 같은 값은 끈다, 다른
값은 켠다. 상위 카테고리가 *다른 것으로 바뀌면* 하위는 지운다 — 이전 상위의 하위와 AND 로
묶이면 아무것도 안 나온다. 상위를 *끄기만* 하면 하위는 남는다(하위만으로도 유효한 조건).
덤으로 빵부스러기의 `searchParams.get('category') !== ""` — 없으면 `null` 이라 언제나 참,
빈 화살표가 남던 것 — 도 고쳤다.

**가드**: `browse.test.jsx` `applyFilter` 9건. 서버 쪽(`SearchService.buildSearchPredicate`)은
`category=3` 을 `product.category.categoryId = 3` 으로 제대로 걸고 있었다 — 이번 건은 전부
프론트다.

## 9. 하위 카테고리 필터가 엉뚱한 상품을 보여 주던 것 — 데이터였다 (2026-09-27)

"fashion → men's clothing" 을 누르면 침대 프레임 · 『앵무새 죽이기』 · 초콜릿 쿠키가 나왔다. 다른 하위 카테고리도 같았다.

- **코드는 맞았다.** 프론트는 `subCategory=<id>` 를 보내고, 서버는 `product_subcategory` 로 정확히 걸렀다.
- **시드 데이터가 무작위였다.** `product_subcategories.csv` 의 연결 499 건 중 **404 건(81%)이 상품과 다른 카테고리**의
  하위 카테고리였고(올리브유가 "테이블 · 스마트폰 · 음료"), 같은 카테고리 안의 연결도 맞지 않았다. 올바른 하위 카테고리에
  들어 있는 상품은 250 개 중 87 개뿐이었다.

고친 것:

| 무엇 | 어떻게 |
|---|---|
| 시드 CSV | 상품 이름 → **같은 카테고리의** 하위 카테고리로 다시 만들었다(220 건, 196 개 상품). 맞는 것이 없는 상품(TV · 스피커 · 올리브유 · 러그 …)은 잇지 않는다 — 하위 카테고리는 선택이다 |
