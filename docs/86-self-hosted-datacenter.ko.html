ecommerce-msa 온프레미스 구성안

지금 OCI Ampere 노드 한 대와 Cloudflare Tunnel 로 돌고 있는 ecommerce-msa 를 자체 데이터센터로 옮길 때의 하드웨어와 네트워크 구성입니다. 레포의 실측값과 설계 결정에서 출발했습니다.

읽기 전에 — 이 구성안의 전제

  • SLO · 처리량 목표는 2026-11-14 에 정했습니다(docs/91 — SLO 넷, 단계 2 끝 초당 1,000 · 단계 3 끝 5,000). 이 글을 쓸 때는 없었으므로 아래 사양은 레포 실측값에서 추정한 시작점이고, 실제 장비에서 다시 재서 조정해야 합니다.
  • 실측값은 데스크톱 한 대 위의 VM 들이 CPU 를 나눠 쓴 실습 클러스터에서 나왔습니다. 레포 문서(docs/83)도 절대 수치로 쓰지 말라고 적고 있습니다.
  • 레포의 운영 결정은 PostgreSQL · MongoDB 를 관리형에 맡기는 것입니다(docs/23). 자체 데이터센터에는 관리형이 없으므로 DB 이중화를 직접 해야 합니다. 이것이 지금과 가장 크게 달라지는 점입니다.

2 · 네트워크

인바운드 포트 없이, VLAN 다섯 개로

파란 점선은 논리 경로입니다. 실제 패킷은 방화벽과 ISP 를 거쳐 나갑니다. MGMT 는 실제로는 별도 OOB 스위치에 붙습니다.

외부 진입 — Cloudflare Tunnel 을 그대로 유지하기를 권합니다

  • 지금 구조가 인바운드 포트 0개입니다. cloudflared 2개가 서로 다른 노드에서 바깥으로 연결합니다.k8s-overlays/prod/cloudflared.yaml
  • 결제 웹훅(Stripe, PortOne)과 OAuth 콜백도 이 터널로 들어옵니다. 그래서 공인 IP, DMZ, 외부용 TLS 인증서가 필요 없습니다.
  • 데이터센터 방화벽은 cloudflared 의 아웃바운드 7844(TCP/UDP)만 열면 됩니다.

Cloudflare 를 빼고 자체 공인 IP · L4 LB 로 받는다면 코드도 바꿔야 합니다. 레이트 리미터가 CF-Connecting-IP 를 "엣지가 덮어쓰므로 조작할 수 없다" 고 신뢰합니다(CustomUserKeyResolver). 터널이 없으면 이 헤더는 클라이언트가 마음대로 보낼 수 있습니다. 그 밖에 Ingress host, ACME 인증서, WAF 와 DDoS 대응이 새로 필요합니다.

대역폭과 지연

  • 내부: 앱 트래픽은 작습니다. 실습 천장이 성공 초당 약 1,400건인 작은 JSON 입니다(docs/83). 10GbE 로도 충분하고, 25GbE 는 복제와 백업 여유분입니다.
  • 인터넷: 가장 큰 변수는 이미지입니다. 지금은 브라우저가 S3 에서 직접 받으니 우리 회선을 타지 않습니다. 이미지를 MinIO 로 데이터센터 안에 들이면 이미지 바이트가 전부 우리 회선을 타므로, 회선은 그 기준으로 잡아야 합니다.
  • 지연: 요청 하나가 쿼리를 20번가량 날립니다. 왕복 30ms 면 600ms 가 됩니다(docs/32). 앱과 DB 는 같은 랙 · 같은 L2 에 두고, 동기 복제를 다른 사이트까지 늘리지 마십시오.
  • 공통 인프라: 내부 DNS 와 NTP 가 필요합니다. JWT, TOTP 2단계 인증, Kafka, 인증서가 모두 시계에 의존합니다. 전원은 이중 전원공급장치, A/B PDU, UPS 로 잡습니다.

진행 순서

  1. 위 1~4번을 레포에서 먼저 고칩니다. 메시지 · 캐시 · 문서 저장소 · DB 의 이중화입니다.
  2. 실제 장비에서 ops/53(k6)으로 다시 잽니다. 실습 수치는 12코어 · 24스레드를 VM 들이 나눠 쓴 결과라, 전용 하드웨어에서는 천장이 달라집니다.
  3. 그 결과로 워커 대수와 HPA 최대치를 조정합니다. 지금의 최대 3은 실습 크기에 맞춘 값이고, 바꾸면 PG 커넥션 계산도 함께 다시 합니다.
