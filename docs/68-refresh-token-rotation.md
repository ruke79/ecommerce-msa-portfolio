## 0. 要約

| | 前 | 後 |
|---|---|---|
| 更新時の古いトークン | **消していなかった** — 寿命(14 日)まで新トークンを受け取り続けた | 比較して削除(Redis Lua、原子的) — **一度だけ**使える |
| 更新の判定 | セッションキーが**あるか** | 保存値と**同じか** |
| 使用済みトークンが再び来たら | また新トークンを渡していた(気づかない) | **再利用検知** — そのログインのファミリー全体を切る |
| 同時更新(タブ 2 つ) | — | 20 秒の猶予: 2 つ目のリクエストは**同じ**新トークンを受け取る |
| ログアウト | 提示したトークンのキー 1 つだけ削除 | **ファミリー全体**を切る |
| すべての端末からログアウト | なし(パスワード変更のみ) | セキュリティ設定画面のボタン — ユーザーの全ファミリーを切る(§8) |
| 観測 | なし | `auth_refresh_total{result}` + アラート `RefreshTokenReuseDetected` |
| ユーザー通知 | なし | 再利用ならアカウントの持ち主に**アプリ・メール・SMS**(受信設定に関係なく、§3.1) |

## 1. 何が問題だったか

外部の分析(「トークンを更新しても以前のリフレッシュトークンが有効なまま、再利用検知もない」)をコードで確認した。正しく、ログアウトにも問題がもう 1 つあった。

- `RefreshTokenController` — `findByUserId(sessionId, email).isPresent()` で**キーがあるかだけ**を見ていた。
- その後 `createRefreshToken()` が**新しい sessionId** で新しいキーを作った。古いキーを消す行がなかった。
- 結果: 一度ログインして 10 回更新すると、**生きているリフレッシュトークンが 11 個。** どれか 1 つが複製されれば 14 日間、新しいアクセストークンを取れる。
- 再利用に気づく手段がなかった — 「使用済みトークン」という概念自体がなかった。
- `AuthLogoutFilter` は**提示したトークンのキー**だけを消した。更新前の古いトークン(それぞれ別のキー)はログアウト後も生きていた —
  「盗まれた疑いがあればログアウトしてください」が効かなかった。
- 全セッションを切る手段はパスワード変更(`passwordChangedAt` の比較)だけだった。

## 2. 設計

### 2.1 ファミリー

ログイン時にファミリー id(UUID)を作り、リフレッシュ JWT の `fam` クレームに入れる。更新したトークンは**同じファミリー**を引き継ぐ。
「このログイン」を指す名前があって初めて「このログイン全体を切る」ができる。

### 2.2 Redis キー

| キー | 値 | TTL |
|---|---|---|
| `<sessionId>`(既存) | リフレッシュトークンの **SHA-256**(§10) | トークン寿命 |
| `rt:grace:<旧 sessionId>` | `PENDING` → 新トークンの**暗号文**(§10) | `auth.refresh.grace-ms`(20 秒) |
| `rt:fam:<family>` | ファミリーの現在の sessionId | トークン寿命 |
| `rt:revoked:<family>` | 切断済みの印 | トークン寿命 — それ以降はどのみち全トークンが期限切れ |

### 2.3 ローテーション(`RefreshTokenService.rotate`)

```lua
-- KEYS[1] = sessionId, KEYS[2] = rt:grace:sessionId, ARGV = 受け取ったトークン, PENDING, grace-ms
local v = redis.call('GET', KEYS[1])
if not v then return 0 end            -- ない → 猶予 または 再利用
if v ~= ARGV[1] then return -1 end    -- 値が違う → 拒否
redis.call('DEL', KEYS[1])
redis.call('SET', KEYS[2], ARGV[2], 'PX', ARGV[3])
return 1                              -- このリクエストがローテーションする
```

GET と DEL を別々に呼ぶと、同時に来た 2 つのリクエストが両方「ある」を見て両方新トークンを受け取る。Lua は Redis 上で 1 つの塊として実行されるので、**ちょうど 1 つだけが 1 を受け取る**
(8 スレッドで実 Redis にぶつけて確認 — `RefreshTokenRotationTest.concurrentRefreshRotatesOnce`)。

| 順 | 条件 | 結果 | 応答 |
|---|---|---|---|
| 1 | `fam` なし | `LEGACY` — ローテーション導入前に発行されたトークン | 400 `refresh token expired` |
| 2 | ファミリー切断済み | `REVOKED` | 400 `invalid refresh token` |
| 3 | Lua = 1 | `ROTATED` — 同じファミリーで新トークン、猶予キーに新トークンを記録 | 200 + 新しい Cookie |
| 4 | Lua = -1 | `REJECTED` — 切らない | 400 |
| 5 | 猶予キーに新トークン | `GRACE` — **直前に発行したそのトークン**を返す(新しく作らない) | 200 + 同じ Cookie |
| 6 | 猶予キーが `PENDING` のまま(2 秒) | `REJECTED` — 盗人と断定する根拠がない。切らない | 400 |
| 7 | キーも猶予もない | `REUSED` — **ファミリー全体を切る** | 400 |

400 なら Cookie も消す。フロントの `TokenRefresher` は 200 以外ならログアウトへ進むので、フロントの変更はない。

### 2.4 再利用なら、なぜ両方切るのか

署名・期限が正常なトークンが、ローテーション済みの後に再び来た = 同じトークンを持つ者が **2 人**いる。サーバーはどちらが正規ユーザーか分からない。
だからファミリーを切る — 盗人がすでにローテーションして得た新トークンも一緒に死ぬ。正規ユーザーは再ログインすればよい(RFC 9700 §4.14.2)。

### 2.5 猶予(grace)が必要な理由

タブ 2 つがほぼ同時に期限切れを迎えると、同じリフレッシュ Cookie で 2 回更新する。2 回目は形式上は再利用だ。猶予がなければ
**正規ユーザーがタブを 2 つ開いただけでログアウトされる。** 20 秒以内に来た同じトークンには、最初のリクエストが得た新トークンをそのまま渡す。
2 つのタブは同じ Cookie ストアを使うので、結果も同じ Cookie になる。

猶予は 20 秒間古いトークンが使えるという意味だが、**新トークンを新たに作りはしない** — 盗人が 20 秒以内に使えば正規ユーザーと同じトークンを受け取り、どちらかが先に次のローテーションをした時点で、もう一方が再利用として検知される。

### 2.6 ログアウト

`AuthLogoutFilter` が `revoke(token)` を呼ぶ — ファミリーを切り、そのキーも消す。ローテーション済みの古いトークンでログアウトしても意味は同じ(「このログインを終えよ」) —
ファミリーを切り、応答は以前どおり "not found" の拒否。

## 3. ログ・メトリクス・アラート

- ログ: 再利用なら `WARN [auth] 리프레시 토큰 재사용 감지 … userId=7`。**トークン・メールは残さない**(docs/51)。
- メトリクス: `auth_refresh_total{result="rotated|grace|reused|revoked|legacy|rejected"}`。
- アラート: `observability/alert-rules.yml` の `auth-security` → `RefreshTokenReuseDetected`(15 分以内に 1 件以上、warning)。

| 見えるもの | 意味 |
|---|---|
| `grace` が少しずつ継続 | 正常(複数タブ) |
| `legacy` がデプロイ直後に集中し 0 へ | 正常 — §6 |
| `reused` が同じユーザーで繰り返す | そのユーザーの端末・ブラウザ拡張・共用 PC からの流出 |
| `reused` が複数ユーザーで同時 | サーバー側の流出(ログ・プロキシ・バックアップ)。Cookie は HttpOnly なので XSS では読めない |
| `rejected` の増加 | Redis の遅延(PENDING が 2 秒超) — 盗人ではなくインフラ |

### 3.1 ユーザー通知 — 「セキュリティ保護のためログインを解除しました」

再利用を検知すると user-service が既存の `security-alert` トピックに発行し、notification-service が **`SECURITY_ALERT`** として作る。
新しい種類を作らなかった理由: `SECURITY_ALERT` はすでに**受信設定を無視して**アプリ・メール・SMS で送られる(攻撃者が先に通知を切るのを防ぐ)。
DB のチェック制約・設定画面・フロントのアイコンもそのまま使える。

```json
{"alert":"refresh-reuse","customerId":7,"email":"…","occurredAt":"…","eventId":"security:refresh-reuse:<ファミリー id の SHA-256 先頭 32 文字>"}
```

| 決定 | 理由 |
|---|---|
| 宛先 = アカウントの持ち主(アドレスは DB から) | 再利用を起こしたのが誰でも、メールは持ち主に届く。トークンの subject は信用しない |
| `eventId` = ファミリーのハッシュ | ファミリーは一度しか切られないので通知も一つ(同時検知・Kafka の再配信でも)。ファミリー id の原文(トークンのクレーム)は載せない |
| 文言に「トークン」「再利用」がない | ユーザーには意味がない。起きたこと(ログイン解除)・理由(別の場所で使われた形跡)・やること(再ログイン、心当たりがなければパスワード変更)だけ |
| 発行失敗は応答を変えない | ファミリーはすでに切れている。通知は付加機能 — Kafka の障害が認証を止めてはならない |
| 正規ユーザーも受け取る | どちらが盗人か分からず両方切ったから。怖がらせず、やることははっきり書く |

🐛 **併せて直したもの** — メールの件名と SMS の文言が `SECURITY_ALERT` の種類で固定(「新しい端末からのログイン」)だったため、別のセキュリティ事象も新端末のメールとして送られる構造だった。
今は件名・SMS が**通知タイトル**に従う。新端末メールで本文に同じ文が 2 回出ていたのも消え、末尾の文が「受信設定はマイページから」(切れないメールなのに誤り)から
「セキュリティ通知は受信設定にかかわらず送信されます」に変わった。

## 6. デプロイ — 全員が一度だけ再ログインする

デプロイ前に発行されたリフレッシュトークンには `fam` がない。これこそ「寿命まで使い続けられる」古いトークンなので受け付けない(`LEGACY`)。
**デプロイ後の最初の更新で、全ユーザーがログイン画面に移る。** 一度だけだ。

- 告知するなら「セキュリティ改善のため、一度だけ再ログインしてください」。
- ロールバック: 旧バージョンは `fam` を知らずキーだけを見るので、新トークンもそのまま使える。ローテーション前の動作に戻るだけで、データの問題はない。
  `rt:*` キーは TTL で消える。
- デプロイ順: **notification-service を user-service と同時か先に。** 旧 notification-service は `alert` を知らないため、ログイン解除のイベントを
  「新しい端末からのログイン」として送ってしまう。逆の順序(通知が先)は問題ない — 新しい通知サービスは `alert` のない旧イベントを新端末として扱う。

## 7. 残り

- HTTP リクエストの**即時**遮断 — チャット・通知のような長い接続は即時に切れるようになった(§9)。通常の HTTP リクエストは引き続きアクセストークンの期限(最大 15 分)まで。
  即時に切るには、ゲートウェイがリクエストごとに「このユーザーのログイン解除時刻」(§9 の `auth:cutoff:*`)を見る必要がある — すべてのリクエストに Redis 参照が付く。
  15 分のアクセストークン + ローテーション + 長い接続の即時遮断で十分と判断し、入れていない。

## 8. すべての端末からログアウト

セキュリティ設定画面(`/profile/security`)の「ログイン端末」の下。「新しい端末からのログイン」「セキュリティ保護のためログインを解除しました」の通知を受けたユーザーが
**すぐに取れる対処**だ。以前はパスワード変更しかなかった — すぐ上の「記録を消す」はログアウトではなく、ログアウトは今の端末 1 つしか切らなかった。

### 8.1 ユーザー → ファミリーの索引

セッションキーは sessionId だけで保存されており、「このユーザーのすべてのログイン」を逆引きできなかった。ログイン・更新のたびにファミリー id を集合に入れる。

| キー | 値 | TTL |
|---|---|---|
| `rt:user:<userId>` | ファミリー id の集合 | トークン寿命 — ログイン・更新のたびに数え直す。最後の活動から寿命が過ぎれば中のトークンもすべて期限切れ |

- **ログイン時に終わったファミリーを外す**(`rt:fam` がないもの = 切断済みか期限切れ)。外さないと毎日ログインするユーザーの集合が際限なく増える — TTL が毎回数え直されるので丸ごと消えることもない。
- デプロイ前にログインしたファミリーは索引にない — 問題ない。そのトークンは `fam` がなく、どのみち受け付けない(§6)。

### 8.2 動作

`POST /api/user/profile/sessions/revoke-all` → `RefreshTokenService.revokeAll(userId)`: 集合のファミリーをすべて切り(§2.6 と同じ `revokeFamily`)、集合を消す。

| 決定 | 理由 |
|---|---|
| 本人の身元はトークンからのみ | ユーザー id を受け取ると他人のログインを切れてしまう |
| **この端末も**ログアウト | この端末が盗人のものかもしれず、再ログインのコストは小さい。リフレッシュ Cookie も消す |
| 2 回押させる(確認) | この端末もログアウトされるため |
| 「即時」ではなく「最大 15 分以内」 | 他の端末が持つアクセストークンは寿命まで有効(ゲートウェイは署名だけを見る)。画面は嘘をつかない |
| 再利用通知を送らない | 切られた端末が更新すると `REVOKED`。切った瞬間にローテーション中だったリクエストがキーを見つけられなくても、再利用と判定する前にファミリーが切断済みかを見直す — ユーザー自身の操作に「盗難の疑い」メールは届かない |
| メトリクス `auth_logout_all_total` | 普段より多ければ、通知(再利用・新端末)が実際に人を動かしている印でもあり、アカウント攻撃の兆候でもある |

### 8.3 テスト

- `RefreshTokenRotationTest`(実 Redis) +4 — ログイン 2 つ(1 つは更新まで)がすべて切れる・再利用通知なし・他ユーザーに影響なし・ログイン時の索引整理と TTL・切るものがなければ 0。
- `SessionControllerTest` 3 件 — トークンの持ち主のものだけ、Cookie 削除、未ログインか持ち主がいなければ 401。
- フロント `SignOutEverywhere.test.jsx` 5 件 — 1 回では切らない(確認)、「最大 15 分以内」の文言、確認するとこの端末をログアウト、キャンセル、失敗したらこの端末をログアウトさせない。

## 9. 長い接続(チャット・通知)をログインに結びつける

### 9.1 何が問題だったか

HTTP リクエストは毎回アクセストークンを提示するので、トークンの期限(最大 15 分)が上限になる。長い接続は**接続時に一度だけ**トークンを見る。

| 接続 | 前 | 後 |
|---|---|---|
| チャット WebSocket(chat-service STOMP) | CONNECT 後、**切れるまで** — 上限なし | トークンの `exp` で close **4401**・ログイン解除なら**即時** |
| 通知 SSE(user-service) | 30 分(`app.sse.timeout-ms`) | `min(30 分, トークン exp)`・ログイン解除なら**即時** |

「すべての端末からログアウト」や再利用検知でログインを切っても、開いているチャットはルームのメッセージを受け取り続けていた。

### 9.2 二重の仕組み

1. **期限に結びつける** — chat-service は CONNECT 時に**自分で検証した JWT の `exp`** で閉じる予約をする(`LiveSessionRegistry`)。ゲートウェイが渡すヘッダーではない —
   ヘッダーを使うなら、クライアントが遠い未来の値を入れられないようゲートウェイが消して上書きしなければならず、その約束が一度崩れると上限が消える。
   SUBSCRIBE・SEND も期限切れなら拒否する(予約が数 ms 遅れても防ぐ二重目)。
2. **ログイン解除は即時** — user-service が `revokeAll`・再利用検知のときに
   - Redis `auth:cutoff:<userId>` = 現在(epoch 秒)、TTL = アクセストークン寿命 + 1 分
   - pub/sub `auth:session-revoked` にユーザー id

   を送る(common `SessionRevocation`)。chat-service と user-service の SSE はそのユーザーの接続を 4401 / `Reauth` で閉じ、**以降の CONNECT・購読で `iat` がその時刻より
   早いトークンを拒否する** — 閉じるだけでは、古いトークン(まだ 15 分有効)ですぐ張り直されるからだ。

### 9.3 4401 = 「更新してから張り直せ」

- フロントはもともと期限の 10 秒前にトークンを更新し、トークンが変わるとチャット・通知が新しいトークンで張り直す。だから**正規ユーザーは期限による切断を見ない** —
  張り直さないクライアント(バックグラウンドのタブ・盗人)だけがここで切れる。
- サーバーが 4401 / `Reauth` で閉じると、フロントは同じトークンで再接続せず(`stompProvider`・`Notification.js`)、**更新を一度だけ頼む**(`authEvents` → `TokenRefresher`、
  複数の接続が同時に閉じても更新は一度)。
  - ログインが生きている端末 → 新トークン → 張り直す。ユーザー単位で広く閉じても害がない理由だ(再利用検知のとき、同じ人の他の端末も一瞬切れて張り直す)。
  - 切られた端末 → 更新失敗 → ログイン画面。

### 9.4 正直な限界

| 項目 | 値 |
|---|---|
| 長い接続 — ログイン解除後 | 即時(pub/sub の伝達時間) |
| 長い接続 — トークン期限後 | 即時(予約) |
| 通常の HTTP — ログイン解除後 | 最大 15 分(§7) |
| `iat` が秒単位 | 解除と**同じ秒**に発行された古いトークンは通る — 1 秒以内の窓 |
| Redis 障害 | 解除の印を読めなければ止めない(チャット全体を止めない)。期限への結びつけが引き続き最大 15 分の上限をかける |

### 9.5 テスト

## 10. トークンはハッシュだけを保存する

### 10.1 何が問題だったか

| Redis キー | 前 | 後 |
|---|---|---|
| `<sessionId>` | リフレッシュ JWT の**原文** | 原文の **SHA-256**(hex) |
| `rt:grace:<旧 sessionId>`(20 秒) | 新しいリフレッシュ JWT の**原文** | 新トークンの **AES-256-GCM 暗号文** |
| アクセストークンの「ブラックリスト」 | ログアウト時にアクセストークンの**原文をキーに** — 読む所がなかった | **削除** |

Redis のダンプ(バックアップファイル・誤って開いたポート・スナップショット)が漏れれば、原文を Cookie に入れてそのままログインできた。ハッシュからはトークンを作れない。
比較は受け取ったトークンをハッシュして Lua の中で行う(§2.3 の `ARGV[1]` が今はハッシュ)。JWT は署名によりエントロピーが十分なので、ソルト・遅いハッシュ(bcrypt)は要らない — それは人が選ぶパスワード用だ。

### 10.2 ハッシュと同時更新の猶予がぶつかる理由

同時更新の猶予(§2.5)はこう動く。

1. タブ A とタブ B が**同じ**リフレッシュ Cookie R1 でほぼ同時に更新する。
2. A が先にローテーションする — R1 を消し、新トークン R2 を作る。ブラウザに R2 の Cookie を入れる。
3. B のリクエストは R1 を持って少し遅れて来る。R1 はもうない — 形式上は**再利用**だ。
4. 猶予がなければ B のせいでファミリーが切れ、**正規ユーザーがログアウト**される。新しい R3 を作って渡せば R2・R3 の 2 つが生き、ローテーションの意味がなくなる。
5. だから B には **A が受け取ったまさにその R2** を返す(Cookie ストアは 1 つなので結果も同じ)。

5 が問題だ。サーバーは 20 秒間 R2 の**原文を取り出せなければならない**。ハッシュは一方向なので `SHA-256(R2)` から R2 には戻せない。
したがって「ハッシュだけ保存」しながら猶予を保つには、3 つのうち 1 つを選ぶ必要がある。

| 方法 | 代償 |
|---|---|
| A. 猶予の 20 秒だけ原文を保存 | 「ハッシュだけ」がその 20 秒間は偽。その瞬間のダンプには原文がある |
| **B. 猶予の値だけサーバー鍵で暗号化** ← 採用 | 鍵管理が 1 つ増える — ここでは JWT 秘密から派生するので新しい秘密はない |
| C. 猶予をなくし、フロントがタブ間の更新を 1 つにまとめる(Web Locks・BroadcastChannel) | すべてのクライアントの協力が要る。1 つでも守らなければ(旧バージョンのタブ、アプリ)正規ユーザーが切られる |

### 10.3 B の実装(`GraceTokenCipher`)

- **AES-256-GCM** — 機密性と改ざん検出を同時に。IV は 12 バイトのランダム、タグは 128 ビット。保存形式は `v1:` + base64(iv ‖ 暗号文 ‖ タグ)。
- **鍵は Redis にない** — `HMAC-SHA256(JWT 秘密, "refresh-grace-v1")` で用途別に派生(2FA 待機トークンと同じ方式)。新しい秘密・新しい Secret はない。
- **AAD = 旧セッション id** — 別の猶予キーの暗号文を移し替えると復号できない。
- 復号できなければ(改ざん・形式エラー・鍵の変更) `REJECTED` — 再利用の証拠ではないのでファミリーは切らない。

**残るリスクの大きさ** — Redis のダンプだけを持つ攻撃者: ハッシュと暗号文だけで使えるものがない。JWT 秘密まで持つ攻撃者: すでに**任意のアクセストークンを偽造**できる。
したがって暗号鍵を JWT 秘密から派生しても、攻撃者が新たに得るものはない。これがこの設計が「懸念なし」である理由だ — 原文がストアに留まる瞬間がない。

### 10.4 デプロイ

- §6 と一緒にデプロイすれば追加の影響はない(全員が一度再ログイン)。
- ローテーション(§2)だけ先にデプロイしていた場合: その間にログインした人の Redis の値は原文なのでハッシュと合わない → `REJECTED` → もう一度ログイン。切断はしない。
- ロールバック: 旧バージョンは値が**あるか**だけを見ていたので、ハッシュが入っていてもそのまま動く。

### 10.5 テスト

- `GraceTokenCipherTest` 6 — 往復、保存値に原文なし・毎回異なる暗号文、別セッションでは復号不可(AAD)、1 文字の改ざん検出、別の秘密では復号不可、形式エラーは null。
- `RefreshTokenRotationTest`(実 Redis) +2 — **Redis 全体を走査して**どのキー・値にもトークン原文(署名部分)がない(猶予中を含む)、改ざんされた猶予値は拒否するが切断しない。
  保存を原文に戻すとこのテストが失敗することを確認した。


## 11. タブ間でログイン状態を揃える (2026-10-01)

リフレッシュトークンは HttpOnly Cookie なので **すべてのタブが共有する。** ところがアクセストークンと「ログイン済み」の表示はタブごとのメモリに別々にあり、タブ同士がずれていた。

| 症状 | 原因 |
|---|---|
| あるタブでログアウトしても、他のタブはアクセストークンが切れるまでログイン状態の画面 — その間は注文ボタンも押せた | 他のタブはログアウトを知らない |
| あるタブでログインしても、開いていたタブは再読み込みするまでログイン画面 | 同じ理由 |
| あるタブは「セッション切れ」、別のタブは正常 — 同じ Cookie なのに | タブごとに別々に判断する |
| 🐛 マイページのサイドメニューの「ログアウト」は画面表示だけを消していた — サーバーのリフレッシュトークン · Cookie が残り、再読み込みで再びログイン状態 | サーバーのログアウトを呼んでいなかった |

**原則: ログイン状態はブラウザに 1 つ。タブ間には「変わった」という事実だけを送り、トークンは送らない**(`frontend/src/util/authSync.js`)。

- **ログイン(トークン更新を含む) → `signed-in`(ユーザー id)。** 受けたタブがログアウト状態なら **共有 Cookie で自分のトークンを直接取得する** — 「セッション切れ」で止まっていたタブが、入力中の画面のまま復帰する。同じユーザーでログイン済みなら何もしない — 更新のたびに来る通知が更新の連鎖を起こさないように。別のユーザーに変わっていれば再読み込みする — 前のユーザーのカート · フォームを残さない。
- **ログアウト → `signed-out`。** ログインしていたタブがログアウトするときだけ送る — 初めて開いたタブの復旧失敗(Cookie なし)が、他のタブの正常なログインを切らないように。受けたタブはログアウトして案内を出す。セッションが終わって更新に失敗した場合も同じ経路なので、1 つのタブが知ればすべてのタブが一緒に終わる。
- **受けた通知では再通知しない**(`broadcast: false`) — タブ間のやり取りが止まらなくなるのを防ぐ。初回復旧中(PENDING)のタブは割り込まない — リフレッシュトークンが重なって 2 回ローテーションしないように。
- 🔒 メッセージには種類 · ユーザー id · 送信元タブ · 時刻だけ。BroadcastChannel がないブラウザは localStorage の storage イベントで代えるが、書いた直後に消す — アクセストークンをメモリだけに置く理由(XSS 一回でセッションが渡る)をここで崩さない。
- サイドメニューのログアウトは、ヘッダーと同じ `useLogout`(サーバーのログアウト → 画面 · 他のタブの整理)に変えた。

**ガード**: `authSync.test.js`(トークンが入る場所がない · 自分のメッセージを無視 · storage の代替経路は何も残さない) · `AuthContext.sync.test.jsx`(ログインしていたタブのログアウトだけを通知 · 追従するときは通知しない) · `TokenRefresher.sync.test.jsx`(他のタブに追従してログアウト · ログアウト状態のタブは自分のトークンを取得 · 同じユーザーは無視 · 別のユーザーなら再読み込み · PENDING は割り込まない)。「ログインしていたタブだけ」の条件や `broadcast: false` を外すと該当テストが失敗する。

## 12. ログインの絶対寿命(30 日) · 時計が狂った PC (2026-10-01)

**① 絶対寿命。** リフレッシュトークンは更新のたびに新しく 14 日を得ていた — 時々使うだけで **ログインが終わらなかった。** 盗まれたトークンも、
盗んだ側が定期的に更新すれば永遠に生きる(再利用検知は正規ユーザーが古いトークンを再提示したときにしか働かない)。金融 · ショッピングモールは
通常「最後の利用から N 日」と合わせて「最初のログインから最大 M 日」を置く。

- リフレッシュトークンに **最初のログイン時刻 `auth_time`**(OIDC と同じ名前)を入れ、ローテーションしてもそのまま引き継ぐ。
- 期限 = min(今 + 14 日, `auth_time` + 30 日)。Cookie の Max-Age もトークンの残り寿命で — 30 日目が近ければ 14 日より短い。
- 30 日を過ぎると新しいトークンを作っても既に期限切れなので、更新で延ばせない。ローテーションの直前にも再確認する(運用者が寿命を縮めた場合など) —
  過ぎていればファミリーを切り `refresh token expired`(400) → フロントは「再度ログインしてください」。
- `auth_time` のないトークン(この変更以前の発行)は発行時刻で代える — デプロイの瞬間に誰もログアウトされない。
- 設定: `spring.app.jwtRefreshAbsoluteMs`(環境変数 `JWT_REFRESH_ABSOLUTE_MS`、既定 30 日)。

**② 時計が狂った PC。** 先行更新の時点を `exp(サーバー時計) − Date.now()(PC の時計)` で計算していた。PC の時計がアクセストークンの寿命(15 分)より
進んでいると、受け取ったばかりのトークンも期限切れに見えて **即時更新が無限に続いた** — 更新のたびにリフレッシュトークンがローテーションするので
サーバーも一緒に忙しかった。今は二つの時計を混ぜず、トークンの寿命(`exp − iat`、どちらもサーバー時計)だけ待つ(`refreshDelayMs`)。何がずれても
最小 5 秒の間隔。PC の時計が遅い側は 401 → 更新 → 再試行が受ける。

**ガード**: `AbsoluteLifetimeTest`(新規ログイン 14 日 · 25 日目のログインの更新は残り 5 日 · 31 日目は新しく作ったトークンも期限切れ · 29 日目はまだ) ·
`RefreshTokenRotationTest`(実 Redis: 二回ローテーションしても `auth_time` はそのまま — 引き継がないように変えると失敗を確認 · 寿命を縮めると
SESSION_ENDED でファミリーを切る) · `refreshDelay.test.js`(PC の時計が一日進んでいても即時更新しない — 旧計算に戻すと失敗を確認)。

## 13. 管理者が止めたアカウント · 失敗したログアウト (2026-10-01)

**① 管理者がアカウントを停止 · ロック · 期限切れにしても、ログイン済みのユーザーは使い続けた。** 管理機能が DB の値だけを変え、更新経路は
アカウントの状態を見ていなかった — 止まるのは新規ログインだけで、悪質なユーザーを停止しても最大 30 日、注文 · チャットを続けられた。

- 止めた瞬間にすべてのログインファミリーを切り、チャット · 通知の接続も閉じる(`UserServiceImpl.endSessions` → `revokeAll`)。解除時は触らない。
- 更新経路も `enabled` · `accountNonLocked` · `accountNonExpired` · `credentialsNonExpired` を見直す — 止まっていればそのファミリーを切り 400
  `account disabled`(フロントはログアウト)。切る段階が失敗しても次の更新で切れる。
- **ログイン 5 回失敗の自動ロックは見ない。** それは別のフィールド(`lockExpiresAt`)だ — 見れば、攻撃者がわざとパスワードを間違えて正規ユーザーの
  他の端末のログインまで切れてしまう。

**② ログアウト要求が失敗すると画面がログイン状態のままだった。** 「ログアウトできませんでした」と出すだけ — 共用 PC のユーザーはログアウト
したと思って席を離れる。

- 失敗しても画面(と他のタブ)は **すぐに** ログアウトする。リフレッシュ Cookie は HttpOnly で画面から消せないので、そのままだと次回アクセスの
  自動復旧が再びログインさせる。そこで印(`ecommerce-pending-logout`、値は "1" だけ)を残す。
- 次回アクセスは自動復旧の代わりに **サーバーのログアウトを先に完了** させる — ログアウト API はゲートウェイがアクセストークンを要求するので、
  一度更新して得たトークンで呼び、そのトークンは画面の状態に入れない。サーバーが応答すれば印を消し、ネットワークがまだなら印を残したまま
  ログアウト状態にしておく。
- 新しくログインし始めたら(ログイン成功 · ソーシャルログインのボタン)印を消す — 残すと次回アクセスが新しいログインを切ってしまう。

**ガード**: `AdminBlockEndsSessionsTest`(止めたら切り、解除なら切らない) · `RefreshTokenRotationControllerTest`(停止 · ロック · アカウント期限切れ ·
資格情報期限切れのそれぞれで更新拒否 + ファミリー切断) · `useLogout.test.jsx`(失敗しても画面はログアウト + 印) · `TokenRefresher.pendingLogout.test.jsx`
(次回アクセスでサーバーのログアウトを完了 · 既に終わったセッションなら印だけ消す · ネットワークがまだなら印を残してログアウト状態 · 印がなければ
従来どおり復旧)。各段階を外すと該当テストが失敗することを確認した。

## 14. 2FA 無効化の再認証 · パスワード変更後のこの端末 · TOTP の再利用 (2026-10-02)

**① ログインさえしていれば 2FA を無効にできた。** `POST /api/auth/disable-2fa` が認証コードを受け取っていなかった — 開いたままのタブ一つ、
盗んだアクセストークン一つで二段階認証が消え、本人は気づかなかった。有効化側も、既に有効な状態で `enable-2fa` を再度呼ぶと秘密を作り直して
上書きした — 攻撃者が自分の認証アプリに差し替えられた。

- 無効化には **今の認証アプリのコード** が必要(`disable-2fa?code=`)。正しければ無効にし、秘密も消す。
- 既に有効なら `enable-2fa` は 409 `2FA already enabled` — 秘密を作り直さない。変えたいときは無効化(コード)してから再度有効化する。
- 管理経路のコード試行は **15 分に 5 回**(`auth.totp.max-failures` · `auth.totp.failure-window-ms`)。超えたら 429 `Too many attempts` —
  6 桁のコードは 100 万通りしかなく、制限がなければ盗んだセッションで当たるまで試せる。成功したらカウンターを消す。
- 有効化 · 無効化のときに **通知** を送る(`SecurityAlertProducer.publishTwoFactorChanged` → 通知サービスの「二段階認証が有効 / 無効になりました」)。
  本人の操作でなければすぐ気づけるように。通知には userId と種類だけ — コード · 秘密は載せない。
- 応答の対応: OK 200 · コード誤り 401 · 試行超過 429 · 既に有効 / 有効でない 409。

**② パスワードを変えると、この端末も数分後に弾かれた。** 応答は「他の端末では再ログインが必要です」だったが、更新経路の「パスワード変更前に
発行されたリフレッシュトークンは拒否」が **今の端末のトークンにも** 掛かった — 新しいトークンを渡していなかったので、アクセストークンが切れた
瞬間にログアウト。

- 変更に成功したら **すべてのログインファミリーを切り**(他の端末 · チャット · 通知の接続は即時)、この端末には **新しいファミリーを Cookie で**
  渡す(`UserController.updatePassword` → `revokeAll` + `createRefreshToken`、寿命は `refreshTokenLifetime()`)。
- 変更時刻の比較は **秒単位**(`passwordChangedAt.withNano(0)`)。JWT の `iat` は秒までなので、変更したその秒に渡した新しいトークンが
  ミリ秒の差で「変更前」となり拒否されることがあった。同じ秒に発行された古いトークンは上の `revokeAll` が防ぐ。

**③ 同じ TOTP コードを 30 秒以内に再利用できた。** コードは 30 秒(前後 1 枠の許容で最大 90 秒)有効だ — 肩越しに見たコード、フィッシング
ページが受け取ったコードをその間にもう一度使えば通った。RFC 6238 §5.2 は「検証者は一度通したコードを再び受け入れてはならない(MUST NOT)」とする。

- `TotpService.matchedStep` が **どの時間枠(30 秒単位)で一致したか** を返す。
- `TotpReplayGuard.claim` がユーザーごとに **最後に受け入れた枠** を Redis に置き(Lua 一回で比較 + 保存、5 分保持)、その枠以下なら拒否する —
  同じコードだけでなく **より古い枠のコード** も防ぐ。ログインの 2FA 段階と管理経路の両方がこの検査を通る。
- Redis キーには userId と枠番号だけ — コード · 秘密は保存しない。

**④ あわせて直したもの**: 2FA 待機 Cookie を消すときに `new Cookie(...)` を直接作っていた一箇所を `jwtUtils.createCookie(..., null, Duration.ZERO)`
に変えた — 直接作ると `SameSite` · `Secure` が抜ける(SameSite=Lax 切り替えの節)。`CookieSameSiteTest` の検査も `new jakarta.servlet.http.Cookie(`
のように **パッケージ付きで書いた場合** まで捕まえるよう強化した — 以前の正規表現はこの一箇所を見逃していた。

**フロント**: 今の画面には 2FA 管理 UI がない(API のみ)。よって今回の修正はサーバーだけ — UI を作るときは無効化画面にコード入力欄を置く。

**ガード**: `TotpReplayGuardTest`(同じ枠 · 古い枠を拒否 · ユーザーごとに分離 · 同じコード 8 件の同時要求で一つだけ通過 · 失敗カウンターでロックと解除 — 実 Redis) · `TotpMatchedStepTest`
(前後 1 枠までだけ一致) · `TwoFactorChangeTest`(コードなしでは無効化できない · 誤コード 401 · 5 回超過で正しいコードも 429 · 既に有効 409 ·
有効化 · 無効化で通知 · 無効化で秘密を削除) · `PasswordChangeSessionTest`(他の端末を切る + この端末に新しい Cookie · 失敗なら何も切らない) ·
`CookieSameSiteTest`(強化した正規表現)。各修正を戻すと該当テストが失敗することを確認した。

## 15. ログイン 2 段階の試行上限 · ソーシャル事前乗っ取り · 再設定後のセッション (2026-10-02)

**① ログイン 2 段階のコードを事実上無制限に試せた。** 待機トークンごとに 5 回しか数えず、パスワードで再ログインすれば新しいトークン = また 5 回だった。
2FA が防ぐべき相手はまさに「パスワードを知る攻撃者」だ。6 桁のコードは前後 1 枠まで 3 つが一致するので、1 回で当たる確率は約 3/1,000,000 —
毎秒 5 回なら平均 1 日以内に破られる。

- ログイン 2 段階も管理経路(§14)と **同じユーザー単位の枠** で数える — 15 分に 5 回(`auth.totp.max-failures` · `auth.totp.failure-window-ms`)。
  止まれば正しいコードも受けずに 429、待機トークンを焼き Cookie も消す(`UserService.verifyLoginTwoFactor`)。
- 上限に **達した瞬間に一度** 知らせる(`2fa-failures`) — 「パスワードは合ったのに 2FA が誤り続けた」はパスワード漏えいの合図だ。やること(パスワード変更)を伝える。
- 代償: パスワードを知る攻撃者は持ち主を 15 分間 2 段階で止められる。アカウントを渡すよりはよく、通知が持ち主にパスワードを変えさせる。

**② ソーシャルログインの事前乗っ取り(pre-account hijacking)。** 同じアドレスのアカウントがあればそのまま連結していた。本番はメール認証ゲートが
オフ(`require-email-verification=false`)で、どのアドレスでも登録すればすぐ使える:

1. 攻撃者が被害者のアドレス + 自分のパスワードで先に登録する。
2. 被害者が後で「Google でログイン」— 同じアドレスなのでそのアカウントに連結され、自分のアカウントだと信じて住所 · 決済情報を入れる。
3. 攻撃者は最初に決めたパスワードでいつでも同じアカウントに入れる。

- ソーシャルログインはそのアドレスの **持ち主であることを証明** する。そこで、アドレスが確認されたことのないパスワードアカウント(`emailVerified=false`、
  パスワード登録)に連結するときは、そのパスワードを **解除**(誰も知らない値)し、アドレスを確認済みにし、全ログインを切り(`revokeAll`)、持ち主に
  知らせる(`unproven-password-cleared`) — `SocialAccountLinker`。パスワードログインが必要なら「パスワードをお忘れの方」で新しく決める(そのメールも持ち主にしか届かない)。
- 認証メールを待っていたアカウント(無効 + 認証トークンあり)は、ソーシャルログインが認証を代わりに済ませる — 有効化してトークンを消す。
- **止められたアカウント(管理者停止 · 退会 — 無効で、待っている認証がない)は触らない。** ソーシャルログインが停止を解いてはならない。
- `emailVerified` はこれまで **誰も true にしない死んだ値** だった。今はアドレスの持ち主が証明される 3 か所で立てる: 登録確認リンク · パスワード再設定リンク ·
  ソーシャル登録。そのため **デプロイ後に初めてソーシャルでログインする既存のパスワードアカウントは一度パスワードが解除される** — 正規ユーザーも通知を
  受け、パスワードが必要なら再設定する。誰が決めたパスワードか分からない以上、こちらが安全だ。
- プロバイダーがこのアカウントに **初めて** 連結されたら知らせる(`social-linked`)。「初めて」は Redis の集合 `oauth:linked:<userId>` で見る — Redis が
  空になれば次の連結でもう一度知らせるだけで、Redis が使えなければ通知だけが抜けてログインは続く。

**③ パスワード再設定はセッションをすぐには切らなかった。** 変更時刻だけを残し、リフレッシュは止まってもアクセストークン(15 分)とチャット · 通知の
接続は生きていた。パスワードを取り戻しに来る人の多くはアカウントを盗まれて来る — §14 のパスワード変更とも扱いが違っていた。

- 再設定に成功したら `revokeAll`(全ログイン · チャット · 通知を即時) + 通知(`password-reset` — 本人が要求していなければメールが乗っ取られている) + アドレス確認済み。
- 再設定リンクは **1 時間**(`auth.password-reset.ttl`、既定 `PT1H`)。以前の 24 時間は、メールが乗っ取られたときに使える時間がそれだけ長かった。
  再設定メールの本文には時間が書かれていないので文言はそのまま。

**ガード**: `LoginTwoFactorLimitTest`(止まれば 429 · 待機トークンを焼く · セッションなし、誤りは 401、正しければユーザー単位の確認を通る) · `TwoFactorChangeTest`
(+3: ログイン 2 段階もユーザー単位 · 上限到達時に一度だけ通知 · 成功で記録を消す / 2FA 無効のアカウント) · `SocialAccountLinkerTest`(未確認パスワードの解除 ·
認証待ちの完了 · 止められたアカウントはそのまま · 確認済みアカウントはパスワード維持 + 初回だけ通知 · ソーシャルアカウントは表示のみ · Redis 障害でもログイン) ·
`PasswordChangeTest`(+3: 再設定後の切断 · 通知 · 確認済み、失敗した再設定は何も切らない、リンク 1 時間) · `CustomOAuth2UserServiceTest`(既存アカウントは必ず
連結ルールを通る)。各修正を戻すと該当テストが失敗することを確認した。

## 16. ソーシャル会員の退会 · 退会の最終処理でログインを切る (2026-10-02)

**① ソーシャル会員は退会できなかった。** 退会画面は「ソーシャルログインで登録したアカウントは空欄のままに」と案内するのに、サーバーは
「保存されたパスワードが空ならスキップ」だった。ソーシャル登録はパスワード欄に **誰も知らない乱数** を入れるので空ではない — 空欄だと常に
「パスワードが一致しません」。テストはソーシャルアカウントを `password = null` で作って通っていた(実際には存在しない形)。§15 でパスワードを解除したアカウントも同じだった。

- 本人確認を **パスワード、または最近のログイン** にした(`WithdrawalService.requireReauthentication`)。
  - パスワードを入れたらそれだけを見る — 誤りなら拒否し、別の道には移らない。
  - 空欄ならこのブラウザのリフレッシュ Cookie から **最初のログイン時刻(`auth_time`)** を読み、10 分(`app.withdrawal.reauth-window`)以内かを見る
    (`RefreshTokenService.authTimeOf` — 署名 · 種類 · 期限 · 持ち主 · ファミリーが生きているかまで)。パスワード · ソーシャル · 2FA のうち、その
    アカウントのログイン手続きを今もう一度通ったという意味だ — GitHub · Google の「sudo モード」と同じ考え。長く開いたままの共用 PC のセッションだけでは退会できない。
- 画面の案内も直した — パスワードのないアカウントは空欄にし、もう一度ログインしてから 10 分以内に申請する。

**③ 退会の最終処理がログインをすぐには切らなかった。** 無効にするだけで、開いていたログインは次の更新まで · チャット · 通知の接続は生き続けた。
他の遮断経路(管理者停止 §13 · パスワード変更 §14 · 再設定 §15)と同じく `revokeAll` で今切る。

**ガード**: `WithdrawalServiceTest`(4 件 — うち 1 件は実際と違う形だった旧テストの置き換え: ソーシャルアカウントは乱数パスワード + 最近のログインで申請 · ログインが古ければ拒否 · パスワードが
誤りなら最近のログインがあっても拒否 · 最終処理で `revokeAll`)。各修正を戻すと失敗することを確認した。

## 17. JWT 署名鍵を無停止で交換する — kid · 鍵リング (2026-10-02)

**問題。** 署名鍵が `JWT_SECRET_KEY` 一つだった。変えた瞬間にそれ以前に発行されたすべてのアクセス · リフレッシュトークンの署名が合わなくなり、
**全員が一斉にログアウト** した。そのため鍵の漏えいが疑われても「変えると障害」なので先送りになる — 交換できない鍵は結局永遠に使う鍵だ。

**鍵リング(`common/security/JwtKeyRing`)。** 鍵に名前(kid)を付けて複数を同時に知り、そのうち一つだけで署名する。

| 設定(Secret) | 意味 |
|---|---|
| `JWT_SIGNING_KEYS` | `kid=秘密,kid2=秘密2` — 空なら `JWT_SECRET_KEY` 一つ |
| `JWT_ACTIVE_KID` | 今署名に使う kid — 空なら `legacy`(= `JWT_SECRET_KEY`) |
| `JWT_ACCEPT_LEGACY` | `false` なら `JWT_SECRET_KEY` で署名されたトークンを拒否(引退) — 既定 `true` |

- 発行(user-service)はトークンのヘッダーに `kid` を書く。検証する 3 か所(user-service · ゲートウェイ · chat)はその名前で鍵を選ぶ。
  kid のないトークン(この変更前に発行されたもの)は `legacy` とみなす — デプロイしても誰もログアウトしない。
- 未知の kid · 引退した legacy は拒否する。kid を付け替えても署名は **その kid の鍵** で確認するので通らない。
- 設定が誤っていれば(存在しない kid への切り替え · 32 バイト未満 · 重複 · legacy で署名しつつ legacy を引退)**起動を止める** — 誤った鍵で署名するより起動しない方がよい。
  エラー文言 · ログには kid の名前だけを残し、値と長さは残さない。
- `JWT_SECRET_KEY` は引退後も消さない — 2FA 待機トークン · 猶予暗号の鍵を派生する根だ。

**交換の順序(`ops/46-rotate-jwt-key.sh`)。** 一度にやってはいけない — 新しい鍵をまだ知らない検証者(ロールアウト中の別サービス)が新しいトークンを拒否する。

1. `add` — 新しい鍵をリングに入れて 3 サービスを再起動する。署名はまだ旧鍵だ。
2. `activate <kid>` — 3 サービスの **すべての Pod が今の Secret で起動しているか** を確認してから署名鍵を変える。切り替え時刻を Secret の注釈に残す。
3. `retire <旧 kid|legacy>` — 切り替え後、リフレッシュの絶対寿命(30 日)が過ぎている必要がある。鍵が漏れたなら `--force`(その鍵のトークンは即無効)。

値は画面 · 引数 · ログに残らない — 生成はシェル変数、クラスタには stdin(`kubectl patch --patch-file /dev/stdin`)、ローカルの `k8s/20-secret.yaml` には
環境変数で渡して同じ値を書く(ops/27 のずれ検査が警告しないように)。

**あわせて直したもの — 署名を確認できないトークンが 500 だった。**
- ゲートウェイ: 期限切れだけを捕まえ、それ以外(署名不一致 · 未知の kid)は例外が上がり 500 だった → 401(画面がリフレッシュで新しいトークンを受け取る)。
- リフレッシュ経路: 同じ理由で 500 → 400 + Cookie 削除(画面がログアウト状態に整理される)。
- 鍵を引退させた直後、旧鍵のトークンを持つユーザーが「しばらくしてから再度」を繰り返さないように。
- ガード `ClientTextCoverageTest` が `"…" + (a + 1) + "…"` という形の文言で **終わらなかった**(括弧の深さを二重に数えて同じ場所を回っていた)。
  今回の鍵リングの文言が初めてその形だったので表面化した — 深さは式の読み飛ばしの中だけで数える。

**ガード**: `JwtKeyRingTest`(空の設定 = 従来どおり · 追加 → 切り替え · legacy 引退 · 誤った設定なら起動中止 · 文言に値なし) · `JwtKeyRotationTest`(user-service:
切り替え後も旧トークン · リフレッシュが通る、引退後は拒否、未知の kid · kid 偽装を拒否) · `JwtKeyRingGatewayTest` · `TokenHandlerKeyRingTest`(ゲートウェイ · chat も同じ規則) ·
`RefreshTokenRotationControllerTest`(+1: 確認できないトークンは 400) · `JwtKeyRingWiringTest`(JWT を読むすべてのサービスがリングの 3 値を同じ名前で読む ·
ops/46 が鍵を出力しない)。

## 18. 漏えいしたパスワードを受け付けない — k-匿名性による照会 (2026-10-02)

**問題。** クレデンシャルスタッフィングは、他サイトで漏れた「メールアドレス + パスワード」の一覧をそのまま試す。ユーザーがそのパスワードをここでも
使っていれば、こちらに何の欠陥がなくてもアカウントが奪われる。長さ · 文字種のルールではこれを防げない — `P@ssw0rd!` はルールをすべて満たすが、
漏えい一覧の最上位にある。NIST SP 800-63B も構成ルールの代わりに「既知の漏えい · ありふれたパスワード一覧との照合」を求めている。

**どうやって — パスワードを外に出さずに(`BreachedPasswordChecker`)。**
- Have I Been Pwned の Pwned Passwords range API: パスワードの SHA-1 の **先頭 5 文字だけ** を送り、その接頭辞を持つハッシュの残り数百件を受け取って
  **こちら側で** 照合する。サービス側はどれが自分たちのユーザーのものか分からない(k-匿名性)。
- `Add-Padding: true` — 応答サイズもそろえ、接頭辞ごとの応答の長さからも推測できないようにする。パディング行は件数 0 なので漏えいとはみなさない。
- ローカル一覧(`security/common-passwords.txt`、ありふれたパスワード 100 件ほど — 韓国語キーボード配列の `qwer1234` · `1q2w3e4r` なども含む)は API と関係なく常に防ぐ。
- 拒否の文言に漏えい回数は載せない — 「漏えいしたことがあるか、ありふれていて推測されやすいパスワード」の一種類。

**どこで。** パスワードを決めるすべての経路 — 登録 · 変更 · 再設定(管理経路を含む)。保存する **前に** 見るので、再設定リンクは消費されず再試行できる。
ログイン時は見ない(ログインのたびに外部呼び出しをしない) — 次の段階として「ログインしたパスワードが漏えい一覧にあれば変更を勧める」を置ける。

**API が使えないときは止めない(fail-open)。** 外部サービスの障害で登録 · 再設定が止まってはならない。代わりに指標 `auth.breached_password.unavailable` と
警告ログを残す(拒否は `auth.breached_password.rejected{reason=breached|common}`)。タイムアウト 2 秒(`auth.breached-password.timeout`)、
止めるなら `auth.breached-password.enabled=false`(それでもローカル一覧は防ぐ)。NetworkPolicy は受信側だけを制限しているので追加設定は不要。

**あわせて直したもの — 登録 400 の本文が文字列一つだった。** 画面は `error.response.data.message` を読むのに、本文がただの文字列で「登録できませんでした」
しか出なかった。409 と同じ形(`{message}`)にし、漏えいパスワードのようにユーザーが直せる理由が見えるようにした。

**ガード**: `BreachedPasswordCheckerTest`(漏えいなら拒否 · 文言に回数なし、外に出るのは先頭 5 文字だけ、パディング行 · 不一致は通過 · 大文字小文字を問わない、
API 障害なら通過 + 指標、ありふれたパスワードは無効化しても拒否) · `PasswordChangeTest`(+1: 変更 · 再設定を拒否、リンクはそのまま、ログインは切らない) ·
`RegisterRoleTest`(+1: 登録拒否 · アカウント · イベントなし) · `RegisterDuplicateTest`(+1: 400 も message)。各検査を外すと該当テストが失敗することを確認した。

## 19. リスクベースのログイン — 攻撃信号 + 初めての端末ならメールのコードでもう一度 (2026-10-02)

**問題。** アカウントロック(5 回)と IP のリクエスト制限は「一つのアカウントを叩き続ける」攻撃しか防げない。クレデンシャルスタッフィングは、
他サイトから漏れたリストを **アカウントごとに 1 回ずつ**、複数の IP から試す。アカウントごとの失敗は 1 回なのでロックはかからず、正しい組み合わせは
最初の試行で当たる。§18 が「漏れたパスワードを新たに設定させない」ものなら、この節は **すでにそのパスワードを使っているアカウント** の、その 1 回の「成功」を扱う。

**信号 — 失敗を記録しておく(`LoginRiskGuard`)。** パスワードが間違ったログイン(BadCredentials · 存在しないアカウント)だけを数える。ロック · 無効は数えない。
- **IP の広がり** — この IP から 10 分以内に異なるアカウント 10 個以上が失敗した(`auth.risk.ip-fanout-threshold`)。
- **標的アカウント** — このアカウントが 1 時間以内に異なる IP 3 個以上から失敗した(`auth.risk.account-ip-threshold`)。
- **全体の急増** — 今の分 + 直前の分の全体の失敗が 300 以上(`auth.risk.global-failure-threshold`)。

Redis にはメール · IP の原文を置かない — `JWT_SECRET_KEY` から派生した鍵の HMAC だけ。メールは推測できる値なので、ただのハッシュではリストから逆引きできる。

**判断 — 遮断せず確認する。** パスワードが合った **後に** 見る。
- 既知の端末(`DEVICE` Cookie がこのユーザーの記録済み端末)なら通過。リストで入ってくる攻撃者はその Cookie を持っていない。
- 初めての端末で信号が **一つでも** あれば、トークンの代わりに `PENDING_LOGIN_CHECK`(httpOnly) Cookie だけを付け、`code=login_check_required` で応答する。
  登録アドレスに 6 桁のコードを送る(`LOGIN_CHALLENGE` メール — リンクなし、数字のみ、10 分、1 回)。
- 信号がなければ新しい端末でも通過(新しい端末の通知はそのまま)。2FA アカウントはすでに TOTP を通るのでここには来ない。

遮断しない理由: 同じ IP を使う人々(会社 · キャリアの NAT)と、攻撃の波の最中に入ってきた正規ユーザーが一緒にロックされる。メールのコードは彼らには数秒の手間、
リストしか持たない攻撃者には越えられない壁だ(メールのパスワードまで同じなら越えられる — それは 2FA · パスキーの役目)。

**コードの確認(`POST /user-service/api/auth/public/verify-login-check?code=`)。**
- Redis にはコードの原文ではなく `sha256(待機値 + ":" + コード)` だけを置く — 待機値(256 ビットの乱数)がなければ Redis を読んでもコードは戻せない。
- 待機値ごとに 5 回、**ユーザーごとに 1 時間 10 回**(待機値を新しく受け取っても続けて数える — §15 の 2FA と同じ穴を最初から塞いだ)。正しければ待機値の削除に成功したリクエストだけが通る(同時の 2 回のうち 1 回だけ)。
- 通過したら **そのとき** 端末を記録し(新しい端末の通知を含む) REFRESH Cookie を渡す。その間に停止 · 退会したアカウントならセッションを渡さない。
- 間違いは 401「認証コードが正しくありません」、試行を使い切ったか期限切れなら 401「最初からやり直し」+ 待機 Cookie の削除。

**障害時。** Redis が使えなければ信号は空で通過(fail-open — ログインは止まらない)。ただし信号が **あるのに** 確認メールを発行できなければ 503
「現在ログイン確認メールを送信できません」 — 攻撃中に確認を飛ばすなら、この仕組みがある意味がない。メトリクス: `auth.risk.challenge{signal}`。
