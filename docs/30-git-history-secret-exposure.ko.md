### ⚠️ `REACT_APP_*` 에 든 비밀은 git 문제가 아니다

`REACT_APP_PAYPAL_CLIENT_SECRET`, `REACT_APP_CLOUDINARY_SECRET` 이 프론트엔드 `.env` 에
있었다. Create React App 은 **`REACT_APP_` 접두사가 붙은 값을 빌드 시점에 번들에 그대로
박는다.** 즉 이 두 값은

- git 이력뿐 아니라 **배포된 사이트를 연 모든 방문자의 브라우저**에 전달됐고,
- 그건 **이력을 정리해도 되돌아오지 않는다.** 이미 나간 번들은 회수할 수 없다.

애초에 클라이언트 시크릿을 프론트엔드에 두면 안 된다 — 결제 승인·미디어 삭제 같은 동작은
서버가 해야 한다. **폐기 외에 대응 방법이 없는 유일한 항목**이다.

**노출 기간: 약 2년** (저장소 생성 2024-08-12 ~ 발견 2026-07-29).
저장소는 `public` 이고, **포크는 0개**다 — 이 한 가지가 유일한 다행이다(§4 참조).

현재 HEAD 는 깨끗하다. 문제는 전부 이력에만 있다.

## 2. "이력에서 지우면 되지 않나" — 안 된다

가장 먼저 정리해야 할 오해다. **이력 재작성은 유출을 되돌리지 않는다.**

**(1) 값은 여전히 유효하다.** git 에서 지워도 AWS 키는 AWS 에서, 앱 비밀번호는 Google 에서
그대로 살아 있다. 지우는 것은 *사본 하나*이지 *자격증명*이 아니다.

**(2) 지워도 GitHub 에서 바로 사라지지 않는다.** force-push 후에도 GitHub 은 옛 커밋 객체를
**SHA 로 접근 가능한 상태로 유지한다.** 즉 문제의 URL 은 정리하고 푸시한 뒤에도 열린다.
실제로 닫으려면 GitHub Support 에 GC 를 요청해야 한다(§4).

**(3) 사본은 이미 퍼졌다.** 클론한 사람, 미러, 캐시, 그리고 무엇보다 **자동 스크레이퍼**.
공개 저장소를 실시간으로 훑어 자격증명을 수집하는 봇이 여럿 있고, AKIA 키는 보통 푸시 후
몇 분 안에 잡힌다. 2년이면 "누군가 이미 봤다"를 전제해야 한다.

**(4) 포크가 있으면 영구히 남는다.** GitHub 은 포크 네트워크의 객체를 정리하지 않는다.
이 저장소는 포크 0개라 이 경로는 다행히 닫혀 있지만, 확인 없이 안심할 일이 아니다.

> **결론: 유일한 진짜 해결책은 폐기·재발급이다.** 이력 정리는 그다음의 뒷정리다.
> 순서를 뒤집으면 "치웠다는 느낌"만 얻고 위험은 그대로 남는다.

## 4. 이력 정리 절차

```bash
# 0) 현황 확인 (값은 절대 출력하지 않는다)
ops/20-scan-history-secrets.sh

# 1) 정리 — 신선한 미러 클론에서 돌고, 푸시는 하지 않는다
pip install git-filter-repo
ops/21-purge-history-secrets.sh --workdir /tmp/purge

# 2) 결과를 직접 확인한 뒤 force-push (⚠️ 되돌릴 수 없음)
cd /tmp/purge/repo.git
git remote add origin https://github.com/ruke79/ecommerce-msa.git
git push --force --all origin
git push --force --tags origin

# 3) 기존 클론을 전부 버리고 다시 클론
#    ⚠️ 옛 클론에서 push 하면 지운 커밋이 되살아난다

# 4) GitHub Support 에 GC 요청 — 이게 없으면 옛 SHA 로 계속 읽힌다
#    https://support.github.com/contact
```

### 두 가지 방식 — 어느 쪽을 쓸까

| | `ops/21` (git-filter-repo) | `ops/22` (BFG Repo-Cleaner) |
|---|---|---|
| 하는 일 | 값만 `***REMOVED***` 로 치환 | **파일을 통째로 삭제** + 남은 값 치환 |
| 파일 | 남는다 (그 시점 설정을 볼 수 있다) | 사라진다 |
| 경로 지정 | 가능 (`--path`) | **불가 — 이름으로만 매칭** |
| HEAD 보호 | 없음 (전부 재작성) | 기본 켜짐 |

**BFG 의 함정 두 가지**를 모르면 "돌렸는데 그대로"가 된다.

1. **이름으로 매칭한다.** `--delete-files application.properties` 는 저장소 어디에 있든
   그 이름을 전부 지운다. 이 저장소 이력에는 8개 경로에 있었다. "backend/ 것만"은 BFG 로
   안 된다 — 그게 필요하면 `ops/21` 을 쓴다.
2. **HEAD 커밋을 보호한다.** 현재 커밋에 남아 있는 파일은 지워지지 않는다. 즉 **작업 트리를
   먼저 정리한 뒤에만** 제대로 동작한다. `ops/22` 는 실행 전에 이걸 확인하고, 남아 있으면
   중단한다.

이 저장소는 HEAD 에 `application.properties` 가 0개라 BFG 로 전부 지울 수 있었다.

### 4.5 🚨 force-push 를 했는데도 파일이 그대로 읽힌다 — `refs/pull/*`

**실제로 실행하고 확인한 결과다. 이것이 이 문서에서 가장 중요한 항목이다.**

브랜치 5개를 전부 재작성해 force-push 했다. 브랜치 기준으로는 완벽했다 —
`application.properties` 참조 0건, 문제의 두 커밋 소멸, HEAD 트리는 원본과 바이트 단위 일치.

그런데 원격을 **새로 클론해 보니 커밋이 785개가 아니라 1,299개**였고, 파일이 그대로 읽혔다.

```
refs/pull/1/head   11건
refs/pull/2/head   11건
refs/pull/3/head   18건
refs/pull/4/head   42건   ← 신고된 두 커밋 모두 여기서 도달 가능
```

**닫힌 PR 의 참조가 옛 커밋을 붙잡고 있다.** 그리고 이것은 클라이언트가 손댈 수 없다:

```
$ git push --force origin 'refs/pull/4/head:refs/pull/4/head'
error: RPC failed; HTTP 403
```

`refs/pull/*` 는 **GitHub 이 관리하는 읽기 전용 참조**다. 지울 수도, 덮어쓸 수도 없다.
BFG 는 로컬 클론의 PR 참조까지 제대로 재작성했지만(잔여 0건), **그걸 밀어 넣을 방법이 없다.**

평범한 클론은 `refs/pull` 을 가져오지 않으므로 일반 검사로는 보이지 않는다. 그래서
`ops/20 --remote` 를 만들었다 — 원격을 `--mirror` 로 새로 받아 PR 참조까지 검사한다.
**정리 후에는 반드시 이걸로 확인해야 한다.** 브랜치만 보고 "끝났다"고 하면 거짓 보고가 된다.

#### 그래서 남은 선택지는 셋뿐이다

| 방법 | 효과 | 대가 |
|---|---|---|
| **① GitHub Support 에 GC 요청** | 정석. PR 참조와 미도달 객체를 정리해 준다 | 사람이 처리하므로 즉시가 아니다(보통 며칠) |
| **② 저장소를 비공개로 전환** | **지금 당장** 익명 접근이 끊긴다 | 삭제는 아니다. 협업자·자신은 여전히 볼 수 있다 |
| **③ 저장소 삭제 후 재생성** | 확실하고 즉시. `refs/pull/*` 이 저장소와 함께 사라진다 | PR·이슈·스타 이력이 전부 사라진다 |

이 저장소는 스타 0 · 포크 0이라 ③의 비용이 크지 않다. 다만 열린 PR 2개와 이슈가 사라진다.

**가장 빠른 완화는 ②다.** ①을 접수하고 그 사이 ②로 공개 노출을 끊는 조합을 권한다.

### 정리 방식

값이 아니라 **패턴**으로 치환한다. 유출된 값을 파일에 모아 적는 흔한 방식은, 그 파일 자체가
모든 비밀을 한곳에 모은 목록이 된다 — 정리하려다 오히려 유출 표면을 만드는 셈이다.

파일을 지우지 않고 값만 `***REMOVED***` 로 바꾼다. 이력 구조가 그대로 유지되어 나중에
"이 시점에 무슨 설정이 있었나"를 볼 수 있다.

### 검증에서 잡힌 것 두 가지

스크립트를 실제로 돌려 보지 않았다면 둘 다 놓쳤을 문제다.

**(1) 부분 치환.** 처음 규칙은 값을 `[^\s#]+` 로 잡았다. 그런데 **Google 앱 비밀번호는
`abcd efgh ijkl mnop` 처럼 공백으로 끊긴 네 덩어리로 발급된다.** 첫 공백에서 멈추는 패턴은
첫 덩어리만 가리고 나머지를 남긴다:

```
spring.mail.password=***REMOVED*** ... 나머지 세 덩어리가 그대로     ← 대부분 남았다
```

`[^\r\n]+` 로 고쳤다. **부분 치환은 치환하지 않은 것보다 나쁘다** — 지웠다고 착각하게 만든다.

**(2) 스캐너가 자기 표식에 속았다.** 위 잔여물을 스캐너가 통과시켰다. `***REMOVED` 를
무시 목록에 넣었더니 *앞부분만* 치환된 값까지 넘어간 것이다. 지금은 표식이 **줄 끝에 있을
때만** 무시한다. 정리 완료 보고가 거짓이 되는 실패 방식이라, 가장 위험한 종류였다.

**(3) `\s*` 가 줄바꿈을 먹었다.** 값 패턴을 `client-secret\s*[=:]\s*…` 로 썼더니,
값이 빈 줄에서 `\s*` 가 개행까지 삼켜 **다음 줄 내용을 값으로 물었다.** 주석 한 줄
(`#  client-secret:`)이 유출로 보고됐다. 구분자 뒤는 `[ \t]*` 로 같은 줄에 묶었다.

**(4) 스캐너가 자기 자신을 유출로 보고했다.** 패턴 정의가 곧 패턴에 걸린다. 경로로 거르지
않고 파일 안의 표식(`SECRET-SCANNER-SELF-EXCLUDE`)으로 거른다 — 이름이 바뀌어도, 이력의
옛 버전을 검사할 때도 동작해야 하기 때문이다.

**그리고 이 문서 자체가 한 번 걸렸다.** 위 (1) 의 예시에 실제 비밀번호 조각을 그대로
붙여 넣었던 것을, 커밋 직전 스캐너가 잡았다 — 유출을 정리하는 문서가 유출을 만들 뻔했다.

### BFG 로 다시 하면서 잡은 것 — 가장 위험했던 버그

**정리 규칙이 현재 코드를 망가뜨렸다.**

`jwtSecret: ${JWT_SECRET_KEY}` 는 17자다. JWT 규칙이 "16자 이상"을 잡으므로 걸렸고,
`jwtSecret:***REMOVED***` 가 됐다. `${...}` 를 제외하는 부정형 전방탐색을 넣었는데도 통과했다 —
**역추적** 때문이다. 앞의 `[ \t]*` 가 공백을 하나 덜 먹는 쪽으로 되돌아가면 전방탐색 위치가
공백으로 옮겨져 조건을 피한다.

더 나쁜 것은 **스캐너가 이걸 통과시켰다**는 점이다. 스캐너는 `${...}` 를 오탐으로 무시하도록
되어 있어서, 치환된 뒤에는 애초에 검사 대상이 아니었다. 그대로 푸시했으면 **전 서비스가 기동
불가**가 됐을 것이다.

세 겹으로 막았다.

1. **값을 비공백 문자로 시작하게 고정**(`[^\s\r\n][^\r\n]*`). 역추적으로 공백이 줄어들면
   바로 뒤가 공백이라 매칭 자체가 실패한다 — 전방탐색을 우회할 수 없다.
2. **BFG 의 blob 보호를 되살렸다.** 처음에 `--no-blob-protection` 으로 꺼 두었는데, 그게 바로
   이 사고를 막으려고 있는 기능이었다. HEAD 의 blob 은 손대지 않는다.
3. **HEAD 무결성 검사**를 두 스크립트에 넣었다. 전제는 단순하다 — HEAD 는 이미 깨끗하므로
   정리 후에도 **한 글자도 바뀌면 안 된다.** 바뀌었으면 규칙이 과한 것이고, 스크립트가
   푸시 안내로 넘어가지 않고 중단한다.

이 검사가 없었으면 "재검사 통과"라는 초록 불을 보고 그대로 푸시했을 것이다.

### 알려진 과잉 치환 (이력 한정)

이력의 옛 자바 파일 한 곳에서 `@Value("${kakao.client-secret:...}")` 의 줄 끝까지 지워져
닫는 괄호가 사라졌다. **현재 코드는 영향이 없고**(HEAD 트리가 원본과 바이트 단위로 동일함을
확인했다) 지나간 이력이라 그대로 둔다. 값을 줄 끝까지 먹는 규칙의 대가다.

## 5. 재발 방지

| | |
|---|---|
| `ops/20 --head` | 커밋 전 점검용. 현재 체크아웃만 훑어 빠르다 |
| CI | `.github/workflows` 에 `ops/20 --head` 를 추가하면 새 유출을 PR 단계에서 막는다 |
| GitHub Push Protection | 저장소 Settings → Code security → **Push protection** 을 켜면 GitHub 이 푸시 자체를 막는다. 무료 공개 저장소도 지원한다 |
| `.gitignore` | `kafka-secrets.properties`, `k8s/20-secret.yaml`, `certs/`, `observability/secrets/` 는 이미 제외돼 있다 |
| 설정 규약 | 모든 자격증명은 `${ENV_VAR}` 참조로만. 리터럴은 `k8s/20-secret.example.yaml` 의 `REPLACE_ME` 플레이스홀더만 |

스캐너는 오탐을 적극적으로 걸러 낸다(`${...}`, `secretKeyRef:`, 테스트용 더미 키
`0123456789…`). **매번 같은 항목이 빨갛게 뜨는 스캐너는 아무도 돌리지 않고, 결국
"어차피 오탐이겠지" 하고 진짜 유출을 넘기게 되기 때문이다.**

## 7. 정정 — PayPal 은 시크릿이 아니었다

이 문서는 처음에 `REACT_APP_PAYPAL_CLIENT_SECRET` 을 🔴 로 분류했다. **변수 이름만 보고
판단한 것이고, 값을 확인하지 않았다.** 나중에 확인해 보니 틀렸다.

이력의 값을 (출력하지 않고) 형태만 비교한 결과:

```
REACT_APP_PAYPAL_CLIENT_ID       AS… 길이 80
REACT_APP_PAYPAL_CLIENT_SECRET   AS… 길이 80     ← 같은 값
```

- 두 변수가 **같은 값**을 담고 있었다 — `_SECRET` 쪽에 클라이언트 ID 를 붙여넣은 것이다
- PayPal 클라이언트 ID 는 `A`, 시크릿은 `E` 로 시작한다. 이 값은 `AS…` 다
- 그리고 **백엔드 어디에도 PayPal API 호출이 없었다** — 시크릿을 쓸 소비자 자체가 없었다

클라이언트 ID 는 PayPal JS SDK 가 URL 쿼리로 받는 **공개 값**이다. 프론트 번들에 박혀
모든 방문자가 보는 것이 정상 동작이고, git 에 남아 있어도 유출이 아니다.

### 남아 있는 것 (문제 없음)

이력의 `frontend/dist/main.bundle.js` 에 그 클라이언트 ID 가 들어 있다. **빌드 산출물이므로
정상이다.** 다만 `ops/20` 스캐너가 이걸 잡지 못하는 이유는 알아 둘 것 — 번들 안에서는
`KEY=값` 형태가 아니라 맨 문자열이라 패턴에 걸리지 않는다. 스캐너의 한계이지 버그는 아니다.

### 이 오분류가 가린 진짜 문제

"시크릿이 왜 아무 데도 안 쓰이지?"를 파고들다 훨씬 중대한 것을 찾았다 — **서버가 결제를
검증하지 않고 있었다.** 시크릿이 없던 이유가 그것이었다. docs/35 참조.

> 교훈: 자격증명의 위험도는 **이름이 아니라 값과 용처**로 판단해야 한다. 이름만 보면
> 없는 위험을 만들고(여기), 진짜 위험을 놓친다(docs/35).
