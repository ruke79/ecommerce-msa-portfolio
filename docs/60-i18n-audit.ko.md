# 60. 다국어 전수 조사 — 일본어 화면에 한국어·영어가 남지 않게

[日本語](60-i18n-audit.md) | **한국어**

> 배경: 홈에서 일본어로 바꿔도 메시지가 한국어로 나오거나, 화면에 한국어·영어가 남아 있었다. → 홈만이 아니라 **전 화면**을 조사해 고친다.

## 1. 무엇이 남아 있었나 — 세 갈래

| 갈래 | 규모(조사 시점) | 왜 생겼나 |
|---|---|---|
| **화면에 박힌 문구** — JSX 텍스트, placeholder·title·alt, 토스트·오류 문구, 상태 이름표 | 118개 파일, **1,091곳**(관리자 약 480) | 사전(i18n/messages)은 있었지만 로그인·장바구니 요약 등 일부 화면만 옮겨져 있었다. 한국어 화면에서는 맞는 글자라 리뷰에서 안 보인다 |
| **서버가 보내는 문구** — 오류·안내(`{"message": "장바구니가 비어 있습니다…"}`) | 서비스 9개, **약 290개** | 서버 문구가 전부 한국어로 코드에 박혀 있고, 화면은 받은 문구를 그대로 보여 준다. 요청에 언어 정보도 없었다 |
| **게이트웨이 문구** — 로그인 필요(401), 서비스 불가·시간 초과(폴백) | 5개 | 게이트웨이가 직접 만든다(WebFlux) |

## 2. 화면 — 사전으로

- 사전을 **영역별 파일**로 나눴다(`i18n/messages/areas/{shell,shop,order,user,admin1,admin2}.{ko,ja}.js`, `ko.js`·`ja.js` 가 합친다).
  한 파일에 모으면 여러 사람이 동시에 고칠 때 늘 충돌한다. 같은 키가 두 조각에 있으면 `i18n.test.jsx` 가 실패한다(뒤의 것이
  조용히 덮는다).
- 컴포넌트 안은 `useTranslation().t`, 밖(유틸·토스트·API 래퍼·모듈 수준 함수)은 `translate()` — 부르는 **그 순간**의 언어다.
  모듈 수준 상수(결제수단 목록, 상태 이름표, 정렬 옵션)는 **키를 들고** 그릴 때 번역한다 — 상수는 불러올 때 한 번 계산되므로
  문구를 넣으면 언어를 바꿔도 그대로다.
- 서버로 보내는 값(정렬 값, 상태 코드, 핏 값 "Small"·"True to size")은 그대로 두고 **보여 줄 때만** 번역한다.

## 3. `translate()` — 컴포넌트 밖의 번역

`I18nProvider` 가 지금 언어를 모듈 변수로도 들고 있다(렌더 중에 맞춘다 — 자식의 첫 렌더·첫 요청부터 그 언어여야 한다).
`translate(key, vars)` 는 그 언어로, `getCurrentLang()` 은 언어 코드를 돌려준다.

## 4. 서버 문구 — 요청 언어로

### 요청

화면의 모든 API 요청에 `Accept-Language: <화면 언어>` (`util/api.js` 인터셉터). 스프링은 이것으로 요청의 로케일을 정한다.

### 응답 — `ClientText` + `ClientTextResponseAdvice`(common)

서버 문구를 메시지 키로 바꾸지 않았다 — 250개를 키로 바꾸면 로그·테스트·운영 문서가 모두 키가 되어 한국어 운영자가 로그를 못
읽는다. 대신 **한국어 원문이 키**인 카탈로그(gettext 방식)로 **응답으로 나가는 순간** 바꾼다. 한국어 요청은 아무것도 하지 않는다.

```
# <모듈>/src/main/resources/i18n/client-text.ja.txt
장바구니가 비어 있습니다. 상품을 담은 뒤 다시 시도해 주세요.
= カートが空です。商品を追加してからもう一度お試しください。

재고가 부족해 주문하지 못했습니다: {}. 장바구니에서 수량을 조정해 주세요.
= 在庫が不足しているため注文できませんでした：{}。カートで数量を調整してください。

{}({}) 품절
= {}（{}）売り切れ
```

| 결정 | 이유 |
|---|---|
| `{}` = 이어 붙인 부분, 번역은 `{}` 또는 `{0}`·`{1}`(순서 바꾸기) | 문자열을 이어 붙인 문구가 많다(`"주문 " + id + "을 찾을 수 없습니다"`) |
| 바뀌는 부분도 다시 카탈로그로 찾는다, 쉼표 목록은 조각마다 | "티셔츠(M) 남은 수량 1개, 바지(L) 품절" — 목록 안의 조각도 번역돼야 한다. 상품 이름은 그대로 |
| `= -` 는 운영자용 | 기동 설정 검증·Kafka 직렬화 실패처럼 손님에게 가지 않는 문구. 빠뜨린 것과 일부러 둔 것을 구분한다 |
| 바꾸는 자리는 **응답 봉투만** — 문자열 본문, 맵의 `message·error·detail·reason`, `MessageResponse·ApiError·ApiResponse·ErrorMessage·GenericResponse·CouponResponse·LoginResponse` | `message` 라는 필드는 채팅 메시지·알림 본문처럼 사람이 쓴 글에도 있다. 카탈로그 패턴에 우연히 맞으면 사용자의 글이 바뀐다 |
| 요청 밖(Kafka 리스너·스케줄러)에서는 바꾸지 않는다 | 그 문구는 응답이 아니다 |
| 자동 구성으로 건다 | common 을 컴포넌트 스캔하지 않는 서비스(catalog·user·coupon…)도 받는다. 스캔하는 서비스는 두 번 걸리지 않는다 |

### 가드 — `ClientTextCoverageTest`(common)

각 서비스 소스에서 **응답으로 나갈 수 있는 자리**(예외 생성자, 응답 봉투, `.body(…)`, `Map.of("message"|"error", …)`, 검증
어노테이션 `message=`, `ClientMessage.of` 의 대체 문구, `ErrorCode` 설명)의 한국어 문구를 뽑아 카탈로그와 맞춘다. 빠진 것은
`common/build/client-text-missing/<모듈>.txt` 에 **카탈로그 모양 그대로** 적힌다 — 번역만 채우면 된다. 도우미 메서드가 만들어
변수로 넘기는 문구(재고 부족 목록 등)는 뽑히지 않으므로 패턴으로 직접 적었다.

### 게이트웨이

WebFlux 이고 문구가 다섯 개뿐이라 `GatewayText.pick(exchange, ko, ja)` 로 둘 다 들고 고른다.

## 5. 가드 — `hardcodedText.test.js`(화면)

소스를 **구문 트리**로 읽어 화면에 보이는 하드코딩 문구를 찾는다: JSX 텍스트의 한글·영어, 보이는 속성(placeholder·title·alt·
aria-label·label), 한글이 든 문자열·템플릿(console.* 인자는 제외), 토스트·alert·confirm·setError·Error 로 넘기는 영어 문장,
객체의 label·title·description·message 속성의 영어 문장. 봐주는 것은 `hardcodedText.allow.js` 에만 — 상표·통화 기호처럼
번역하지 않는 것이 맞는 글자뿐이다. 일부만 보려면 `I18N_SCAN_ONLY=pages/admin,components/admin`.

## 7. 남는 것 — 정직하게

- 해결한 것: 채팅 시스템 메시지(§8), 알림 본문(§9), 배송 시뮬레이터의 이력 문구·택배사 이름(§10), 국가 목록(§11),
  포트원 오류 문구(§12), 우체국 상태 낱말·쉼표가 든 상품 이름의 목록(§13).
- **우체국 이력의 장소**(우체국·집중국 이름)는 고유명사라 원문 그대로 나간다. 상태 낱말 밖의 자유 문구도 그렇다.
- **상품·카테고리 이름, 사용자가 쓴 리뷰**는 데이터라 번역하지 않는다.
- **메일·SMS**는 이미 수신자 언어로 두 벌을 가지고 있다(MailTemplates·SmsTemplates).

## 8. 채팅 시스템 메시지

입장·퇴장 안내(`"홍길동 entered."`·`"… leaved."` — 영어), 상담 연결·종료 안내("상담원 ○○ 님이 연결되었습니다", "고객님이 상담을
종료했습니다"), 대체 이름("고객지원팀"·"탈퇴한 사용자"·"회원"·"회원 3f2k")은 서버가 **문구 그대로** 메시지 본문·닉네임으로 저장한다
(Kafka Avro `ChatMessage` → Mongo).

| 결정 | 이유 |
|---|---|
| 메시지에 코드·인자 필드를 더하지 않고, 화면이 **서버의 정해진 모양을 알아보고** 사전으로 다시 그린다(`util/chatNotice.js`) | 필드를 더하려면 Avro 스키마를 두 릴리스에 걸쳐 바꿔야 하고(docs/55), 그래도 **이미 저장된** 메시지는 문구뿐이다. 모양은 서버가 만든 것이라 알아볼 수 있다 — 옛 메시지까지 번역된다 |
| 서버 문구를 한곳(`ChatNotices`)에 모으고, 화면의 `SERVER_FORMATS` 와 글자로 대조(`ChatNoticesContractTest`) | 서버 문구를 바꾸고 화면을 빠뜨리면 일본어 화면에 한국어가 그대로 나온다 — 한국어 화면에서는 멀쩡해 보인다 |
| 🔒 **안내 자리에서만** 번역한다(메시지 유형 TEXT_ENTER·TEXT_LEAVE, 닉네임·상담 목록의 이름·미리보기) | 사람이 쓴 채팅이 우연히 같은 문장이어도 바꾸지 않는다 |
| 안내 속의 이름도 다시 찾는다 | "탈퇴한 사용자 entered." → "退会したユーザーさんが入室しました。" |
| "leaved" 는 틀린 영어지만 그대로 | 저장된 메시지가 이 모양이다. 화면이 번역하므로 손님에게는 보이지 않는다 |

적용한 자리: 친구 채팅 말풍선·새 메시지 알림, 상담 대화의 안내·발신자 이름, 상담 데스크 목록(고객·상담원 이름, 마지막 메시지
미리보기)·새 메시지 토스트, 고객 상담 화면의 상담원 이름.

## 9. 알림 본문

결제·주문·배송·쿠폰·보안·구매 확정·부분 환불·재입고·채팅·상담 답변·친구 접속 알림은 notification-service 가 **한국어 문구로
만들어 DB 에 저장**한다(제목·본문). 알림 종 목록은 그 문구를 그대로 보여 줬다.

| 결정 | 이유 |
|---|---|
| 저장은 한국어 그대로, **목록을 내줄 때** 요청 언어로 바꾼다(`NotificationResponse.localized` → `ClientText`) | 받는 사람은 화면 언어를 언제든 바꾼다. 저장 때 번역하면 그 순간의 언어로 굳는다 — 읽을 때 고르면 **이미 쌓인 알림도** 함께 바뀐다. DB 변경도 없다 |
| 문구를 한곳(`NotificationTexts`)으로 모으고 모양 목록(`FORMATS`)을 둔다 | 리스너 곳곳에 흩어져 있었다(배송 상태별 제목·본문, 보안 본문 등). 모양마다 예시 값을 넣어 일본어로 바뀌는지 보는 `NotificationTextsTest` — 새 문구를 더하고 카탈로그를 빠뜨리면 실패한다 |
| 바뀌는 자리(주문 번호·쿠폰 이름·상품 이름·금액·기기)는 그대로 | 데이터다. 단 "알 수 없는 브라우저"(user-service 의 기기 이름 대체값)는 번역한다 |
| 전체 알림(공지)은 번역하지 않는다 | 관리자가 쓴 글이다 |
| 메일·문자 제목도 | 메일·문자는 이미 수신 지역(KR/JP)별 틀이 있었는데, 틀에 끼워 넣는 제목("주문 123")이 한국어였다 — 일본 지역이면 넣기 전에 바꾼다 |

알림 종은 열 때마다 목록을 새로 받으므로 언어를 바꾼 뒤 열면 바로 그 언어다.

## 10. 배송 이력(시뮬레이터)·택배사 이름

테스트배송(`SimulatedCarrierAdapter`)은 이력마다 장소("대전허브")·설명("이동 중입니다")을 **한국어로 저장**하고, 배송 조회 화면은
그 글자를 그대로 그렸다. 택배사 이름도 `carrier.name_ko` 그대로였다.

| 결정 | 이유 |
|---|---|
| 저장은 한국어 그대로, **조회 응답을 만들 때**(`DeliveryResponse`) `ClientText` 로 바꾼다 | 장소는 이력 중복 제거 키(`DeliveryEvent.dedupKey`)의 일부다 — 언어별로 저장하면 같은 이벤트가 두 번 쌓인다. 읽을 때 바꾸면 이미 쌓인 이력도 바뀐다(§9 와 같은 방식) |
| 문구를 `SimulatedCarrierTexts` 로 모으고 목록(`FORMATS`)을 둔다 | `SimulatedCarrierTextsTest` 가 모든 장소·설명·택배사 이름의 일본어를, 택배사가 만드는 모든 상태의 설명을, 조회 응답의 번역과 저장값 불변을 확인한다 |
| 택배사 이름("우체국택배"·"테스트배송"·"CJ대한통운" 등, V3 시드)도 같은 카탈로그로 | 새 컬럼(`name_ja`)을 만들지 않는다 — 택배사는 시드 다섯 개뿐이다 |
| 실제 택배사의 문구는 카탈로그에 넣지 않는다 | 택배사가 보낸 데이터다. 카탈로그에 없으면 원문 그대로 나간다 — 단계(stage)는 화면이 이미 사전으로 그린다 |

배송 조회·관리자 배송 화면 모두 이 응답을 쓰고, 요청마다 `Accept-Language` 가 붙으므로 프론트 변경은 없다.

## 11. 국가 목록 — 코드로 저장, 이름은 그릴 때

주소 폼의 나라 선택은 영어 이름("Korea, Republic of")을 **값으로** 저장했다. 그래서 일본어 화면에서도 목록·주소 카드·주문 상세가
영어였고, 이름을 번역하면 저장값이 언어마다 달라진다.

| 결정 | 이유 |
|---|---|
| 새로 저장하는 값은 **ISO alpha-2 코드**("KR"), 기본값도 `KR` | 언어와 무관한 값. 배송(delivery-service `CountryCodes`)은 원래 이름·코드를 모두 alpha-2 로 바꿔 저장하므로 서버 변경이 없다 |
| 이름은 브라우저의 `Intl.DisplayNames`(CLDR)로 — `util/country.js` | 250개 나라 이름을 사전에 옮겨 적지 않는다. 없는 환경이면 목록의 영어 이름으로 |
| 선택지는 그 언어의 이름 순서(`Intl.Collator`) | 일본어 이름을 영어 알파벳 순서로 늘어놓으면 찾을 수 없다 |
| **옛 주소(영어 이름)도 읽는다** — `toCountryCode` 가 이름·코드를 모두 코드로 | 이미 저장된 주소·주문을 바꾸지 않는다(DB 변경 없음). 고치는 폼에 넣을 때 코드로 바꾸므로 칸이 비어 보이지 않고, 저장하면 코드가 된다 |
| 목록에 없는 값은 그대로 보인다 | 사람이 직접 넣은 값일 수 있다 |

적용한 자리: 주소 입력(선택지), 배송지 카드, 주문 상세의 배송·청구 주소, 관리자 배송 화면(배송의 나라는 코드다).
테스트: `util/country.test.js`(모든 나라의 일본어 이름·옛 이름 읽기·정렬), `AddShipping`(옛 주소 수정 → 코드 저장, 일본어 목록),
`ListShipping`(일본어 카드).

## 12. 포트원 오류 문구

포트원은 결제창이 실패하면 **PG 가 쓴 문구**를 그대로 넘긴다 — V1 `error_msg`("[결제포기] 사용자가 결제를 취소하셨습니다"),
V2 `message`·`code`. 국내 PG 라 대개 한국어이고 우리가 고를 수 없다. 화면은 그 글자를 그대로 띄웠다.

| 결정 | 이유 |
|---|---|
| **무슨 일인지 알아보고** 사전 문구로 다시 말한다(`util/portoneError.js`) — 취소·시간 초과·잔액/한도·카드 정보·본인 인증 | PG 는 같은 일을 여러 모양으로 쓴다. 가장 흔한 실패(사용자 취소)부터 순서대로 본다 |
| 알아보지 못한 문구: 한국어 화면은 **원문 그대로**, 다른 언어는 일반 안내 + **오류 코드만** | 원문이 원인을 가장 잘 말하지만 일본어 손님은 읽을 수 없다. 코드는 고객센터가 찾을 단서로 남기고 원문은 콘솔에 |
| 서버 응답 속 포트원 원문(`message={}`·`— {}`)은 일본어 번역에서 **뺀다**(order-service 카탈로그) | 조회·환불 거절의 뒷부분은 포트원이 쓴 한국어다. 일본어에는 코드·결제 id 만 남긴다 — 원문은 서버 로그에 있다 |

테스트: `util/portoneError.test.js`(유형 판별 8가지, 일본어에 한글이 남지 않음, 코드만 붙이기, 한국어는 원문),
`OrderClientTextTest.portOneProviderTextIsDropped`.
