# 45. 다국어 — 일본어 추가

[日本語](45-internationalization.md) | **한국어**

> 🕰️ **상태(2026-09-27) — 일부 낡음.** 서버 문구 번역(Accept-Language)과 JPY 표시는 이후 해결했습니다([docs/60](60-i18n-audit.ko.md)).

## 1. 무엇을 했나

화면 문구를 사전으로 분리하고 **한국어 / 日本語** 두 벌을 둔다. 헤더에서 바꾸고, 처음 방문
시에는 브라우저 언어를 따르며, 고른 언어는 기억된다.

이번 범위는 **화면 문구**다. 상품·카테고리 데이터는 그대로 단일 언어다(§5).

## 2. 시작점 — 이미 있던 것과 없던 것

| | 상태 |
|---|---|
| notification-service | 🟢 **이미 2개 국어**. `MailTemplates`·`SmsTemplates` 에 JA 문구가 있고 `NotificationPreference.region`(KR/JP)이 고른다 |
| 프론트엔드 | 🔴 i18n 라이브러리 없음. 문구가 컴포넌트에 직접 박혀 있고 한국어·영어가 섞여 있었다 |
| catalog-service | ⚪ 상품·카테고리에 언어 필드 없음 — 단일 언어 데이터 |

### 🐛 헤더의 언어 전환기는 동작하지 않는 껍데기였다

`pages/header/Language.jsx` 는 Amazon 클론에서 딸려 온 목업이었다. 라디오 버튼에 `name` 도
`onChange` 도 상태도 없었고(`defaultChecked` 만 박혀 있었다), 목록의 언어
(español·العربية·Deutsch)는 이 사이트에 존재한 적이 없다. "Learn more" 는 `href=""` 라
**현재 페이지를 다시 부르는** 링크였다.

즉 "언어를 바꿀 수 있다"고 말해 놓고 누르면 아무 일도 일어나지 않았다. **없는 기능보다
나쁘다 — 없으면 찾지라도 않는다.**

## 3. 왜 라이브러리를 쓰지 않았나

`react-i18next` 를 쓰지 않고 `src/i18n/` 에 직접 만들었다. 근거는 셋이다.

1. **한국어와 일본어는 둘 다 복수형이 없다.** i18next 의 가장 큰 값어치가 복수형 규칙
   엔진인데, "1件"과 "5件"의 형태가 같은 두 언어에서는 그 엔진이 할 일이 없다.
2. 남는 것은 **사전 조회와 변수 치환**뿐이고, 그건 스무 줄이다.
3. 이 저장소에는 **새 의존성을 늘리지 않는다**는 방침이 있다(`jest.config.js` 주석:
   "네트워크가 막힌 환경에서도 바로 돌아야 한다").

> **경계를 적어 둔다.** 언어가 다섯 개로 늘거나 **복수형이 있는 언어**(영어·러시아어 등)가
> 들어오면 그때는 라이브러리가 맞다. 그 판단 기준을 `I18nProvider` 주석에 남겼다.

## 4. 설계에서 의도한 것들

### 언어를 고르는 순서 — 저장된 선택 > 브라우저 > 한국어

저장된 선택이 브라우저보다 **앞선다.** 일본어 브라우저를 쓰는 사람이 한국어를 고를 수
있어야 하고, 그 선택이 새로고침에 살아남아야 한다.

`ja-JP` 처럼 지역이 붙어도 앞 두 글자만 본다. `navigator.languages` 의 선호 순서를 지킨다.

> ⚠️ localStorage 접근은 try/catch 로 감쌌다. 시크릿 창이나 사이트 데이터가 차단된
> 브라우저에서는 **읽기 자체가 예외를 던진다** — 감싸지 않으면 앱이 첫 렌더에서 죽는다.

### 🔴 `<html lang>` 을 실제로 바꾼다

장식이 아니다. 스크린리더가 읽을 발음을 이 값으로 고르고, 브라우저는 줄바꿈 규칙과 기본
글꼴을 여기에 맞춘다. 한국어 페이지에 일본어를 그려 놓고 `lang="ko"` 로 두면 일본어가
**한국어 글꼴로** 렌더돼 글자 모양이 어긋난다(한중일 통합 한자).

### 없는 키는 키 이름을 그대로 보여준다

빈 문자열을 돌려주면 화면에서 글자가 사라져 아무도 눈치채지 못한다. 키가 보이면 즉시
드러난다. 같은 이유로 치환값이 없으면 `{{min}}` 을 지우지 않고 남긴다 — 지우면
"비밀번호는 자 이상이어야 합니다" 처럼 **말이 되는 듯한 문장**이 되어 버그가 숨는다.

### Provider 밖에서 쓰면 던진다

조용히 기본값으로 동작하게 하면, Provider 를 빠뜨린 화면이 한국어로 굳은 채
"일본어 전환만 안 되는" 상태로 배포된다. 대가로 테스트마다 감싸야 하므로 그 한 줄을
`i18n/testing.jsx` 의 `withI18n` 에 모았다.

### 국기를 쓰지 않는다

언어와 국가는 다르다. 국기로 언어를 나타내면 같은 말을 쓰는 다른 나라 사용자를 배제한다.
언어 이름은 **그 언어로** 적는다(endonym): `한국어`, `日本語`.

## 4-1. 2차 — 상품 목록·상세

인증 화면에 이어 상품 쪽을 옮겼다: `browse.jsx`(목록), `HeadingFilter`(필터·정렬),
`Infos.jsx`(상세), `ShippingInfo`, `AccordianProduct`, `BreadCrumb`.

### 🐛 상세 화면이 사실이 아닌 정보를 보여주고 있었다

`ShippingInfo.jsx` 에 Amazon 클론 잔재가 박혀 있었다:

- `Delivery **Thursday, March 23**. Order within 23 hrs 53 mins` — 고정된 날짜와 가짜
  카운트다운. 이 저장소에 배송일을 계산하는 코드는 없다.
- `Deliver to Germany` — 이 서비스는 한국·일본으로 배송한다.
- `Sold by ATUAT` — 존재하지 않는 판매자.

**번역하지 않고 지웠다.** 거짓 정보를 일본어로도 보여 줄 이유가 없고, 없는 것보다 나쁘다 —
사용자는 그 날짜를 믿고 주문한다. 배송일 추정 기능이 생기면 그때 실제 값으로 되살린다.

### 복수형이 없다는 것이 실제로 이득이 된 자리

상세 화면은 리뷰 수를 `{n} {n >= 1 ? "reviews" : "review"}` 로 그렸다. 영어의 단수/복수
분기다. 한국어·일본어에는 복수형이 없으므로 그 분기를 **통째로 없애고** 문구 하나로 바꿨다:
`리뷰 {{count}}개` / `レビュー{{count}}件`. §3 에서 라이브러리를 쓰지 않기로 한 근거가
코드에서 확인된 자리다.

### 서버로 가는 값은 번역하지 않는다

정렬 옵션(`sortingOptions`)은 표시 이름 대신 **문구 키**를 담게 바꿨다. 두 가지 이유다:

1. 이 배열은 모듈 로드 시점에 한 번만 평가된다 — 번역된 문자열을 넣으면 **언어를 바꿔도
   바뀌지 않는다.**
2. `value`(`newest`, `topSelling` …)는 서버로 가는 질의 값이라 그대로 둔다.
   **화면 언어가 API 계약을 바꾸면 안 된다.**

### 🐛 이 화면들에는 렌더 테스트가 하나도 없었다

`browse.test.jsx` 는 순수 함수(`nextPageParam`·`sortProducts` 등)만 검증하고 컴포넌트를
그리지 않는다. 상품 상세 쪽에는 테스트 파일 자체가 없었다. 문구를 옮기면서 `ShippingInfo`
와 `HeadingFilter` 의 렌더 테스트를 처음 만들었다 — 지어낸 정보가 되살아나는 것과 번역
누락을 둘 다 여기서 잡는다.

## 4-2. 3차 — 장바구니·주문

`cart/`(Checkout·Empty·CartHeader·PaymentMethods·Product), `checkout/Summary`,
`order/`(Total·OrderInfo) 의 문구를 옮겼다.

### 조수사 — 복수형이 없다는 것과는 다른 이야기

일본어는 물건을 셀 때 **조수사**를 쓴다. 장바구니의 "선택한 상품 (3)" 은
`選択中の商品（3点）` 이 자연스럽다. 이것은 복수형(1개 vs 여러 개로 형태가 갈리는 것)이
아니라 **단위**라, 수에 따라 문장이 갈리지 않는다 — 문구 하나에 `{{count}}` 만 넣으면 된다.
세는 대상이 달라지면 조수사도 달라지므로(点·枚·本…) 그때는 문구를 따로 둔다.

### 금액은 번역 대상이 아니다

`100000$` 같은 숫자는 두 언어에서 같아야 한다. 일본어 테스트에 그것을 명시적으로 넣어
두었다 — 통화 형식을 손댈 때(§5) 이 가드가 먼저 깨져 알려 준다.

### 🐛 여기도 테스트가 거의 없었다

`cart/Checkout`·`cart/Empty` 에는 테스트 파일이 없었다. 번역과 함께 렌더 테스트를 만들면서
"고른 상품이 없으면 진행 버튼이 잠긴다", "빈 장바구니에서 쇼핑하러 갈 길을 준다" 같은
기본 동작도 같이 고정했다.

## 4-3. 4차 — 프로필

`pages/profile/`(profile·address·orders·payment·security)과 사이드바를 옮겼다.

### 🔴 메뉴 이름이 URL 을 만들고 있었다

`components/profile/sidebar/Item.jsx` 가 메뉴 이름을 그대로 주소에 넣는다:

```jsx
`${link.link}?tab=${index}&q=${slugify(link.name, { lower: true })}`
```

즉 `name` 을 번역하면 **언어에 따라 주소가 달라진다.** 일본어로 보던 사람이 공유한 링크가
한국어 사용자에게서 열리지 않고, 뒤로 가기 이력도 어긋난다.

그래서 메뉴 데이터에 표시용 `key` 를 따로 두고 `name` 은 영어 그대로 남겼다 — 화면에는
보이지 않고 주소에만 쓰인다. 정렬 옵션(§4-1)의 `value` 와 같은 규칙이다:
**화면 언어는 주소나 API 계약을 바꾸지 않는다.**

## 4-4. 5차 — 서버가 만든 문구 (로그인 결과)

화면 문구를 다 옮겨도 **로그인 직후에만 영어가 떴다.**

```jsx
toast.success(response.data.message);   // "Login Success"
```

`message` 는 `AuthLoginFilter` 가 만든 영어 문장이다. 다중 로그인일 때는 이랬다:
`"User attempted to log in multiply, logging out from previous logged in state"`.

### 서버에서 번역하지 않는 이유

**서버는 사용자의 표시 언어를 모른다.** 언어는 브라우저가 고르고 `localStorage` 에
있다(§4). `Accept-Language` 로 추측할 수는 있지만 **사용자가 화면에서 고른 값과
어긋난다** — 일본어 브라우저를 쓰면서 한국어로 보고 있는 사람에게 일본어가 간다.

그래서 서버는 **무슨 일이 있었는지만 코드로** 알리고 문구는 프론트 사전이 고른다.
실패 경로가 이미 쓰던 방식과 같다(`email_not_verified`, docs/46).

| | 전 | 후 |
|---|---|---|
| 서버 | `message` (영어 문장) | `message` + **`code`** (`login_success` / `multi_login`) |
| 프론트 | 그대로 토스트 | `util/loginResult.js` 가 `auth.signin.result.<code>` 를 조회 |

`message` 는 **지우지 않았다.** 코드를 모르는 클라이언트가 아무것도 받지 못한다.

### 🔴 모르는 코드를 그냥 넘기면 안 된다

`t()` 는 없는 키를 받으면 **키 문자열을 그대로 돌려준다**(§4). 서버에 새 코드가 생겼는데
프론트가 아직 모르면 토스트에 `auth.signin.result.xyz` 가 뜬다 — 영어 문장보다 나쁘다.
그래서 `KNOWN_RESULT_CODES` 에 있는 코드만 번역하고, 나머지는 서버 문구로 떨어진다.
가드는 `util/loginResult.test.js`(6건)이며 **실제 ko/ja 사전으로** 조회한다 — 가짜 `t` 를
쓰면 키가 사전에 없는 것을 못 잡는다.

## 5. 이번 범위에 넣지 않은 것

- **상품·카테고리 데이터.** 스키마 변경 + 관리자 입력 화면 + 실제 번역 내용이 필요하다.
  화면 문구와는 규모가 다르다.
- **통화·숫자·날짜 형식.** 지금은 가격이 `$` 접미사 하나로 고정돼 있다. JPY 표시와
  자릿수 규칙은 별도 작업이다.
- **메일·SMS 언어 연동.** 서버에 일본어 문구는 이미 있다. 화면에서 고른 언어를
  `NotificationPreference.region` 으로 잇는 것이 남았다.

## 6. 검증

| | |
|---|---|
| 신규 테스트 | 47건 (i18n 16 + 일본어·렌더 가드 31) |
| 프론트엔드 전체 | **455건 통과** |
| lint | 경고 193 (래칫 198) |

핵심 가드 둘:

- **두 언어의 키 집합이 같다.** 키가 빠지면 폴백 때문에 *일본어 화면에 한국어가 섞이는데*,
  화면은 멀쩡해 보여서 아무도 눈치채지 못한다.
- **일본어로 실제 렌더해 본다.** 키만 바꿔 놓고 컴포넌트가 여전히 하드코딩된 한국어를
  그리고 있어도 한국어 테스트는 전부 통과한다 — 일본어로 그려 봐야 드러난다.

### 🐛 테스트가 통과했는데 운영 빌드가 깨졌다

`webpack.config.base.js` 의 alias 에 `i18n` 을 등록하지 않았다. jest 는
`moduleDirectories: ["node_modules", "src"]` 로 `src` 아래를 전부 해석하므로 **426건이
전부 통과**했는데, webpack 은 alias 에 적힌 것만 본다 — 운영 빌드에서만
`Can't resolve 'i18n/I18nProvider'` 로 깨졌다.

그 파일의 주석이 이미 "새 최상위 폴더를 만들면 이곳에도 등록해야 한다"고 경고하고 있었다.
**테스트 통과가 빌드 성공을 뜻하지 않는 경우**라 기록해 둔다.
