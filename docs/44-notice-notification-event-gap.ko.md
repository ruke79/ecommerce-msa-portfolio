### 1.1 공지 게시 → 알림: 왜 "공지형" 구조가 따로 필요했나

가장 단순한 방법은 공지가 공개될 때 **사용자 수만큼 `notification` 행을 만드는 것**이다.
그 방법을 쓰지 않았다. 사용자가 10만이면 공지 한 건에 10만 insert 이고, 테이블은
사용자 수 × 공지 수로 부풀며, 공지 내용을 고치면 10만 행을 전부 고쳐야 한다.

대신 **공지당 행 하나**(`notification.broadcast_notification`)를 두고, 개인별로는
"읽었는가"만 따로 남긴다(`notification.broadcast_read`). 읽음 행은 **사용자가 실제로
무언가를 했을 때만** 생기므로, 공지를 올려도 즉시 생기는 행은 0개다.

| 조각 | 위치 |
|---|---|
| 발행 — 공지가 **비공개→공개로 전환된 순간에만** | `catalog-service` `NoticePublishedProducer` (커밋 후 발행) |
| 토픽 | `notice-published` (`ops/02` 에 등록 — 가드레일 B-41) |
| 수신 | `notification-service` `BroadcastEventListener` |
| 저장 | `BroadcastNotification` + `BroadcastRead` (`V4__broadcast_notification.sql`) |
| 목록 | `GET /api/notifications` — 개인 알림과 **합쳐서** 시간 역순, 각 항목에 `scope` |
| 배지 | `GET /unread-count` — 두 출처의 합 |
| 읽음·치움 | `PATCH /broadcasts/{id}/read`, `DELETE /broadcasts/{id}` (내 목록에서만 사라진다) |
| 관리자 발송 | `POST /api/notifications/admin/broadcasts` + `/admin/broadcast` 화면 |
| 인가 | `AdminOnlyInterceptor` — `/api/notifications/admin` 접두사 아래는 **읽기까지** 관리자 |

주의할 점 둘:

- **`scope` 를 화면이 반드시 봐야 한다.** 두 테이블이 각자 TSID 를 쓰므로 id 만으로는
  구분되지 않는다. 잘못된 경로로 보내면 404 가 나거나 — 더 나쁘게 — 우연히 같은 id 의
  남의 개인 알림을 건드린다.
- **시각은 UTC 로 통일한다.** 합쳐서 정렬하는 목록이라 한쪽만 시스템 시간대면 그쪽이
  언제나 위로 붙고, 화면은 그것을 UTC 로 해석해 영영 "방금"으로 보여 준다.
  `UtcClockGuardrailTest` 가 이 서비스 전체를 검사한다.

전체 알림은 **메일·SMS 로 나가지 않는다.** 전체 사용자에게 문자를 보내는 것은 요금
사고이고, 단체 메일은 발신 평판을 깎는다. `MailKind`·`SmsTemplates` 의 exhaustive switch
가 새 알림 종류를 추가할 때 이 결정을 강제로 다시 내리게 한다.

## 1. 공지사항 — 있다. 다만 알림과 끊겨 있다

| 계층 | 상태 |
|---|---|
| 모델 `Notice` (title, body, pinned, published, publishedAt) | ✅ `catalog-service/model/Notice.java` |
| `NoticeService` · `NoticeRepository` | ✅ 있음 |
| 관리자 화면 `/admin/notice` | ✅ `pages/admin/Notices.jsx`, 라우트 등록됨 |
| 공개 목록 `/notice`, 상세 `/notice/:id` | ✅ `pages/notice/NoticeList.jsx`, `NoticeDetail.jsx` |

**빠진 것:** 공지를 게시해도(`published = true`) **아무에게도 알리지 않는다.**
`NoticeService` 에 Kafka 발행이 한 줄도 없다. 사용자는 `/notice` 에 직접 들어가야만 안다.

→ 게시 시 `notice` 토픽에 이벤트를 하나 발행하고 `notification-service` 가 받아
`NotificationType.NOTICE_PUBLISHED`(신설) 알림을 만들면 된다. 알림 인프라는 이미 다 있다.

## 2. 알림 — 거의 다 있다. 그런데 **8종 중 3종은 만드는 쪽이 없다**

### 있는 것

| 계층 | 상태 |
|---|---|
| `notification-service` (독립 서비스) | ✅ |
| REST API — 목록·안읽음수·읽음처리·전체읽음·삭제·수신설정 | ✅ `NotificationController` `/api/notifications` |
| 수신 설정 `NotificationPreference` (메일/SMS 채널별) | ✅ |
| 메일 템플릿 `MailTemplates` (KR/JP 이중 언어) | ✅ |
| SMS 템플릿 `SmsTemplates` (KR/JP) | ✅ |
| 휴대폰 인증 `/phone/verification` | ✅ |
| SSE 실시간 푸시 | ✅ `user-service/NotificationController` `/api/sse` |
| 프론트 종 아이콘 | ✅ `NotificationBell.jsx` — **헤더에 마운트돼 있다**(`Header.jsx:69`) |
| 프론트 API 클라이언트 + 테스트 | ✅ `api/notificationApi.js` |

### 🔴 빠진 것: 알림 종류 8개 중 3개는 **생성되는 경로가 없다**

`NotificationEventListener` 가 실제로 듣는 토픽은 넷뿐이다:

| 토픽 | 만드는 알림 |
|---|---|
| `payment` | `PAYMENT_COMPLETED` / `PAYMENT_FAILED` |
| `order` | `ORDER_PLACED` |
| `chat` | `CHAT_MESSAGE` |
| `user-presence` | `FRIEND_ONLINE` |

나머지 셋은 **메일 제목·SMS 문구·수신설정 정책·테스트까지 다 만들어 놓고 만드는 쪽이 없다**:

- **`SHIPPING_UPDATED`** — `delivery-service` 의 `DeliveryStatusPublisher` 가
  `delivery-status` 토픽으로 배송 상태를 발행하고 있다. 그런데 **이 토픽을 듣는 리스너가
  코드베이스 전체에 없다.** 배송 상태가 Kafka 로 나갔다가 그대로 사라진다.
  → `NotificationEventListener` 에 `@KafkaListener(topics = "delivery-status")` 하나면 된다.
  세 줄짜리 작업인데 "배송 출발했습니다" 알림이 통째로 생긴다. **가성비가 가장 좋다.**
- **`COUPON_ISSUED`** — `coupon-service` 가 쿠폰 발급 이벤트를 발행하지 않는다
- **`SECURITY_ALERT`** — 새 기기 로그인 감지 로직 자체가 없다.
  `NotificationPreference` 는 "보안 알림은 사용자가 꺼도 보낸다"는 예외 처리까지 해 뒀다

`useInfiniteScroll` · 커서 페이징(docs/43 D1)과 **똑같은 패턴**이다 — 기반을 다 만들고
마지막 한 칸을 안 이었다.

### 빠진 것: 관리자가 알림을 직접 보낼 수 없다

지금 알림은 **전부 시스템 이벤트에서만** 생긴다. 관리자가

- 특정 사용자에게 개별 알림
- 전체/세그먼트 공지성 알림

을 보내는 경로가 없다. `/admin/notification` 화면 + `POST /api/notifications/broadcast`
(관리자 전용)가 필요하다. 다만 전체 발송은 사용자 수만큼 행이 생기므로, 개인별 행을
만들지 말고 "공지형 알림"은 별도 테이블 + 읽음 표시만 개인별로 두는 설계가 맞다.

## 3. 이벤트 / 기획전 — **이건 정말 없다**

"이벤트"를 세일·기획전·타임딜 같은 판촉으로 보면, 그에 해당하는 개념이 코드에 없다.
가장 가까운 것들:

| 기존 기능 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| `content.home_section` (`/admin/home`) | 홈에 섹션을 배치 | 기간, 대상, 할인율이 없다 |
| `Banner` (`/admin/banner`) | 배너 이미지 + 링크 | 이미지일 뿐 |
| `coupon-service` | 쿠폰 발급/사용 | 자동 발급 조건, 기간 캠페인 없음 |
| `ProductSku.discount` | 상품별 할인율 | 상품마다 직접 고쳐야 한다. 기간도 없다 |

필요한 최소 모델:

```
content.event
  ├ id, title, slug
  ├ starts_at, ends_at          ← 지금 어디에도 없는 것: 기간
  ├ banner_image_url, link_url
  ├ status (DRAFT / SCHEDULED / ACTIVE / ENDED)
  └ event_product (event_id, product_id, discount_rate)
```

관리자 화면(`/admin/event`)에서 만들고, 스케줄러가 `starts_at` 에 `ACTIVE` 로 바꾸면서
`event` 토픽에 발행 → `notification-service` 가 `EVENT_STARTED` 알림을 만든다.

**주의할 점 하나.** 기간 할인을 `ProductSku.discount` 에 덮어쓰면 안 된다. 이벤트가 끝날 때
원래 값을 되돌려야 하는데, 그 사이에 관리자가 상품을 수정하면 복원이 원래 값을 덮는다.
할인은 **이벤트 쪽에 두고 조회 시점에 합성**해야 한다.

### 3.1 구현 — 조회 시 합성

위 경고대로 만들었다. `product_sku.discount` 는 **끝까지 손대지 않는다** — 언제나
"기획전과 무관한 상시 할인" 하나의 뜻만 갖는다.

| 조각 | 위치 |
|---|---|
| 스키마 | `catalog-service` `V11__event.sql` — `content.event` + `content.event_product` |
| 모델 | `Event`(상태·기간) + `EventProduct`(`@Embeddable` 값 타입) |
| 상태 | `EventStatus` DRAFT → SCHEDULED → ACTIVE → ENDED |
| 할인 합성 | `EventPricing` — productId→할인율 맵을 1분마다 갱신, 조회 결과에 얹는다 |
| 전환 | `EventScheduler`(1분) + `EventService.advanceDueEvents` |
| 알림 | `EventStartedProducer` → `event-started` → `BroadcastEventListener.onEventStarted` |
| 관리자 | `/api/content/admin/events` + `/admin/event` 화면 |
| 공개 | `/api/content/events`, `/api/content/events/{slug}` + `/event`, `/event/:slug` |

**합성 지점은 하나다.** `ProductService.convertToDto` — 엔티티에서 DTO 로 가는 유일한
통로다. 예전에는 조회 경로마다 `ProductMapper::toDto` 를 직접 불렀는데, 그러면 새 경로가
생길 때마다 합성을 한 줄씩 더해야 하고 빠뜨리면 **그 화면만 정가를 보여 준다.** 장바구니
경로(`toCartProductInfo`)는 DTO 모양이 달라 따로 얹는다 — 거기가 실제로 청구되는 금액이다.

**상시 할인과 기획전 할인 중 큰 쪽을 쓴다.** 대안 둘 다 실제로 문제를 만든다:

- *기획전이 덮어쓴다* → 상시 40% 상품을 20% 기획전에 넣으면 **가격이 오른다.**
  관리자는 세일을 추가했는데 고객은 비싸진 것을 본다.
- *누적* → 40% 와 20% 가 52% 가 된다. 아무도 그 숫자를 의도하지 않았고, 기획전에 상품을
  담는 것이 위험한 행동이 된다.

**캐시.** 합성된 값이 Redis 에 들어간다. 그대로 두면 기획전이 끝난 뒤에도 TTL 이 지날
때까지 할인가가 보이고 — 더 나쁘게 — 그 가격으로 장바구니에 담긴다. 스케줄러가 상태를
넘길 때(시작·**종료 둘 다**) 상품 캐시를 비운다.

**다중 인스턴스.** 인스턴스가 둘이면 스케줄러도 둘이고, 둘 다 시작 알림을 발행하면 모든
사용자가 같은 알림을 두 개 받는다. `EventRepository.transition` 이
`where status = 'SCHEDULED'` 조건부 UPDATE 라 먼저 도착한 하나만 1을 받고, 그 하나만
발행한다(실제 PostgreSQL 16 에서 두 번째 UPDATE 가 0 을 돌려주는 것을 확인했다).

#### 함께 고친 것 — 🐛 백엔드의 할인가 계산식

`ProductService.toCartProductInfo` 가 `price - price / discount` 를 쓰고 있었다. "정가에서
정가를 할인율로 나눈 값을 뺀다"는 뜻이라 아무 의미가 없고, **할인율이 클수록 할인 폭이
작아졌다** — 10,000원에 50% 할인이면 9,800원(=2%), 70% 할인이면 9,857원(=1.4%).

프론트엔드(`util/pricing.js`)는 이미 고쳐져 있었고 **이 경로만 남아 있었다.** 그래서 상세
화면은 50% 할인가를 보여 주는데 장바구니에 담으면 2% 할인가가 담겼다 — 같은 상품의
가격이 화면마다 달랐다. 기획전 할인도 이 계산을 지나므로 먼저 바로잡았다.

### 3.2 카테고리 대상 · 고객군 · 딸린 쿠폰

§3.1 의 "아직 없는 것" 셋을 이었다. 셋은 따로 보이지만 **하나의 결정**에서 나온다:
세그먼트 할인을 진열가가 아니라 **쿠폰으로** 준다는 것.

#### 🔴 왜 세그먼트로 진열가를 나누지 않는가

가장 직관적인 구현은 "신규 가입자에게만 20% 싸게 보여 주기"다. 쓰지 않았다. 이유가 셋이다.

1. **상품 조회에 신원이 없다.** 게이트웨이의 catalog-service 공개 라우트에는
   `JwtAuthorization` 이 붙지 않는다 — 붙이면 비회원이 상품을 못 본다. 목록과 상세를 그릴 때
   서버는 보는 사람이 누구인지 모른다.
2. **캐시가 세그먼트 수만큼 갈라진다.** 상품 목록은 Redis 에 캐시된다. 사람마다 가격이 다르면
   캐시 키에 세그먼트가 들어가야 하고, 세그먼트가 늘 때마다 적중률이 떨어진다.
3. **화면마다 가격이 달라진다.** 신원을 아는 화면과 모르는 화면이 섞이면, 방금 고친
   "목록에서 30% 를 보고 들어왔는데 상세는 정가" 버그가 **구조적으로** 되살아난다.

그래서 세그먼트 할인은 쿠폰으로 준다. 쿠폰은 결제 시점에 적용되고 그때는 신원이 확실하며,
진열가는 누가 보든 같다. 실제 커머스가 "신규 가입자 추가 20%" 를 쿠폰으로 주는 이유이기도 하다.

#### 카테고리 단위 대상

| | |
|---|---|
| 스키마 | `content.event_category` (V12) |
| 모델 | `EventCategory` (`@Embeddable`, `EventProduct` 와 같은 값 타입) |
| 펼치기 | `EventPricing.expandCategories` — 조회 시점에 상품으로 |

**펼친 결과를 저장하지 않는다.** 저장하면 그 순간 목록이 굳어, 기획전이 시작된 뒤 그
카테고리에 등록된 상품이 빠진다 — 관리자는 카테고리를 걸었다고 생각하는데 신상품만
정가로 남고, 그 사실은 고객 문의로야 드러난다.

상품 단위 지정을 없애지 않았다. 같은 카테고리에서 일부만 더 깎는 경우가 있다. 겹치면
**높은 할인율**이 이긴다 — 순서와 무관하다.

#### 대상 고객군

`AudienceSegment` (ALL · NEW_USER · EXISTING_USER, `common`). **쿠폰을 누가 받을 수
있는가만** 가른다.

판정은 **user-service** 가 한다(`SegmentService`, `GET /api/auth/user/segments`). "신규가
며칠인가" 는 우리 정책이고 가입일도 그쪽만 갖고 있다 — 가입일을 넘겨 각자 계산하면 기준을
30일에서 14일로 바꿀 때 한 곳을 빠뜨린다.

두 가지를 특히 조심했다:

- **가입일이 없으면 신규가 아니다.** `createdAt` 은 감사 필드라 비어 있을 수 있는데, 그때
  신규로 치면 **모든 옛 계정이 신규 전용 혜택을 받는다.** 혜택을 잘못 주는 쪽이 못 주는
  쪽보다 되돌리기 어렵다.
- **세그먼트를 확인하지 못하면 주지 않는다.** user-service 조회가 실패했을 때 통과시키면
  대상이 아닌 사람에게 쿠폰이 나간다.

#### 딸린 쿠폰 — 뿌리지 않고 받아 간다

```
사용자가 "쿠폰 받기"
  → coupon-service  POST /api/coupon/events/{slug}/claim
  → catalog         GET  /api/content/events/{slug}/coupon-offer   (조건·상태)
  → user-service    GET  /api/auth/user/segments                   (대상 판정)
  → coupon 발급
```

**시작할 때 전 사용자에게 발급하지 않는다.** 그러면 사용자 수만큼 coupon 행이 생긴다 —
공지 알림에서 개인별 행을 만들지 않기로 한 것과 같은 문제이고, 게다가 대부분은 쓰지 않는다.
받아 간 사람만 행이 생기면 쓰기량이 실제 관심에 비례한다.

**중복 수령 방어를 새로 만들지 않았다.** coupon 테이블의 `uk_coupon_name_user_id` 가 한
사람이 같은 이름의 쿠폰을 두 번 갖지 못하게 이미 막는다. "이미 받았다"는 **200** 이다 —
사용자 입장에서는 성공과 다르지 않다.

**조건은 받을 때마다 catalog 에 물어본다.** 카프카로 미리 밀어 두면 기획전이 일찍 종료됐을
때 쿠폰 쪽이 모르고 계속 발급한다. 수령은 드문 동작이라 그때 물어보는 편이 항상 옳고 싸다.
상태 판정을 coupon-service 가 다시 하지 않는 것도 같은 이유다 — 같은 규칙이 두 곳에 있으면
언젠가 어긋난다.

**쿠폰의 적용 범위는 기획전 대상을 물려받는다.** 상품을 지정했으면 그 상품에만, 카테고리를
지정했으면 그 카테고리에만. 넓히면 "이 기획전의 쿠폰" 이 무관한 상품에 먹어 관리자가 의도한
할인 폭을 넘는다.

#### 🐛 함께 고친 것 — 이메일로 쿠폰을 발급하는 경로가 동작한 적이 없다

`CouponService.create` 가 중복 검사에서만 이메일을 숫자 id 로 바꾸고, 정작 쿠폰을 만들 때는
`Long.parseLong(request.getUserId())` 를 다시 불렀다 — 이메일을 숫자로 파싱하니
`NumberFormatException` 이다. 검사는 통과하고 저장에서 터지는 모양이라, "이메일로 쿠폰을
발급한다"는 코드가 있는데 실제로는 500 만 났다. 해결한 id 를 끝까지 들고 가도록 고쳤다.

#### 아직 없는 것

- **하위 카테고리 단위 지정** — 대상은 최상위 카테고리다. 쿠폰의 `CouponScope.CATEGORY` 와
  같은 단위로 맞췄다.

## 3.3 구매 이력과 고객 등급

세그먼트가 가입 시점 하나만 보던 것을 **세 축**으로 늘렸다 — 가입 시점 / 구매 이력 / 등급.
막고 있던 것은 판정 로직이 아니라 **데이터**였다. 주문은 order-service 에 있고 등급 기준은
user-service 의 정책이라, 둘을 어떻게 잇느냐가 이 작업의 전부다.

### 등급은 무엇으로 정하는가

최근 **3개월 실결제액**이다. 평생 누적이 아니다 — 5년 전에 크게 한 번 사고 떠난 사람과
지난달에도 사는 사람이 같은 등급이면 등급이 "현재 고객"을 가리키지 못한다. 기준 금액은
설정(`user.tier.*`)이고 기본값은 20만 / 50만 / 150만 원이다.

**아마존을 참고했다는 것**은 이름이 아니라 태도다. 아마존식 등급의 특징은 등급을 자랑거리로
만들지 않는 것 — 점수·배지·"다음 등급까지 남은 금액" 같은 장치로 소비를 압박하지 않고,
등급은 오직 **혜택이 도착하는 형태**로만 드러난다. 그래서 등급 화면을 만들지 않았고,
등급은 기획전 쿠폰의 대상 조건으로만 쓰인다. 강등도 알리지 않는다 — "등급이 떨어졌습니다"
알림은 사용자가 할 수 있는 일이 소비밖에 없는 통보다.

### 🔴 왜 실시간이 아니라 배치인가

세그먼트 조회는 **쿠폰 발급 경로**에 있다. 거기서 order-service 를 동기 호출하면 주문
서비스 장애가 그대로 쿠폰 발급 장애가 된다. 그리고 등급은 원래 실시간일 이유가 없는
값이다 — 실제 등급제는 전부 일/월 단위로 갱신한다.

하루 한 번(UTC 19:10 = KST 04:10) 배치가 `users.users` 에 등급을 찍고, 읽는 쪽은 저장된
값만 본다. 대가는 정직하게 적어 둔다: **오늘 큰 주문을 한 사람은 내일 골드가 된다.**
관리자 화면에도 그렇게 써 놓았다.

### 🔴 절반만 받은 목록으로 강등하지 않는다

order-service 는 **최근 구매가 있는 고객만** 돌려준다. 그래서 "응답에 없다"는 두 가지
뜻이 될 수 있다 — 창에서 빠졌다(강등해야 함), 또는 아직 못 받았다(강등하면 안 됨).
이 둘을 섞으면 **통신 장애 하나로 전 고객 등급이 날아간다.** 이미 발급된 상위 등급 쿠폰은
회수할 수 없으니 되돌릴 방법이 사실상 없는 사고다.

그래서 배치가 끝까지 돌지 못하면 강등을 **건너뛴다.** 커서를 다 소진했을 때만 강등하고,
그 기준은 **회차 시작 시각**이다(끝나는 시각으로 잡으면 방금 승급시킨 사람까지 도로
내려간다). 강등 대상을 찾는 근거가 `tier_computed_at` 이라, 감사 필드처럼 보이지만
지우면 강등이 멈춘다.

### 등급 세그먼트는 전부 "이상"이다

골드 회원은 `TIER_SILVER` 와 `TIER_GOLD` 를 **둘 다** 갖는다. 그래야 받는 쪽이 **단순
포함 검사**만으로 "실버 이상"을 판정할 수 있고, 등급의 높낮이를 아는 곳이 `CustomerTier`
하나로 유지된다. 반대로 했다면 — 골드가 `TIER_GOLD` 만 갖는다면 — "실버 이상 쿠폰"을
골드 회원이 못 받는, 사용자에게 설명할 수 없는 동작이 된다.

덕분에 "일반 등급만" 같은 조건은 이 축으로 만들 수 없다. 의도적이다. 등급이 낮은 사람을
콕 집어 겨냥하는 판촉은 `NEVER_PURCHASED` 처럼 **행동**으로 표현하는 편이 정확하고
사용자에게도 덜 불쾌하다.

### 구매 이력은 평생 기준이다

`PURCHASED` / `NEVER_PURCHASED` 에는 기간 창이 없다. 등급은 최근 3개월을 보므로 오래 쉰
단골은 일반 등급으로 떨어지는데, 그 사람이 **첫 구매 쿠폰**까지 받으면 안 된다. 그래서
강등할 때 `recent_paid_amount` 는 0 으로 되돌리지만 `lifetime_order_count` 는 건드리지
않는다.

`NEW_USER` 와도 다르다. 가입은 2년 전인데 아직 첫 주문이 없는 사람이 `NEVER_PURCHASED`
이고, 어제 가입해서 바로 산 사람은 아니다. 첫 구매 유도 쿠폰의 진짜 대상은 가입일이
아니라 이쪽이다.

### 🔒 전 고객 결제 금액을 긁을 수 없게

`GET /api/order/internal/purchase-stats` 는 `/api/auth/user/id` 와 같은 규칙으로 막는다 —
게이트웨이를 지난 요청에는 `User-Role` 헤더가 붙으므로 **헤더가 있다 = 외부 요청**이고,
그때는 관리자만 허용한다. 개별 주문 조회에는 소유권 검사가 있지만 집계에는 "내 것"이라는
개념이 없어서, 여기서 막지 않으면 막을 곳이 없다.

넘기는 것은 **합계뿐**이다. 주문을 통째로 넘기면 배송지·연락처·상품까지 서비스 경계를
넘는데, 등급을 매기는 데 필요한 것은 합계이지 명세가 아니다.

### 함께 정리한 것 — "결제된 주문"의 정의

매출·구매 이력·등급이 각자 상태를 나열하고 있으면 언젠가 어긋난다. `OrderStatus.PAID_STATUSES`
하나로 모았고, **결제된 쪽을 나열한다** — 상태가 하나 늘었을 때 빼는 방식이면 새 상태가
조용히 매출로 잡히고, 나열하는 방식이면 조용히 빠진다. 돈을 부풀리는 쪽이 훨씬 나쁜
실패다. 프론트엔드의 `util/orderStatus.js` 도 같은 방향이고, 언어가 달라 공유할 수 없으니
서버 쪽에 **상태가 늘면 실패하는 테스트**를 뒀다.

### 3.4 등급 화면 — "내가 왜 이 등급인가"에 답한다

등급 조건 쿠폰이 생긴 이상 "나는 왜 못 받나"에 답할 곳이 필요했다. 프로필 화면 아래
`TierStatus` 섹션으로 넣었다. 별도 탭을 만들지 않은 것도 선택이다 — 탭이 되면 그 화면의
이름이 "등급"이 되고, 등급 자체가 목적처럼 보인다.

#### 🔴 이 화면에 **없는 것**이 설계다

진행 게이지도, "골드까지 32만원 남았습니다"도 없다. 계산해서 넣기는 쉽고, 넣는 순간
화면의 성격이 바뀐다 — **"당신의 혜택"이 "당신이 더 써야 할 금액"이 된다.** 등급을
점수처럼 전시하지 않는 것이 §3.3에서 정한 톤이고, 화면이 그 톤을 지켜야 말이 된다.

대신 **근거는 전부 준다**: 지금 등급, 판단에 쓰인 금액, 기준 금액, 마지막 계산 시각.
"왜 내가 실버인가"에 화면이 답하지 못하면 그 질문은 CS로 간다.

사용자가 그 숫자로 직접 뺄셈하는 것은 막지 않는다. **알고 싶은 사람에게 감추는 것과,
우리가 먼저 들이미는 것은 다르다** — 전자는 설명이고 후자는 유도다. 테스트가 이 선을
고정한다(`/남았습니다|까지 [\d,]+원|더 구매|달성/`이 화면에 없어야 한다).

⏱️ **갱신 시점을 반드시 적는다.** 등급은 하루 한 번 다시 매겨지므로 "오늘 큰 주문을
했는데 왜 그대로냐"가 반드시 나온다. 화면이 미리 답해 둔다.

🔒 본인 것만 본다. 등급은 그 사람의 **소비 규모**를 그대로 드러내는 값이다. 기준 금액도
서버가 내려준다 — 화면에 하드코딩하면 설정을 바꾼 날부터 안내가 거짓말이 된다.

### 3.5 배송비 분리 — 등급 혜택보다 먼저 할 일이었다

"등급별 무료배송"을 넣으려다 확인한 것:

- 배송비는 **상품마다** 붙는다(`product.getShipping()`)
- cart-service가 `computeCartTotal` 에서 `price×qty + shipping` 으로 **합산해 버린다**
- `CartProductDto` 에 **shipping 필드가 없었다** — 장바구니가 다른 서비스로 넘어갈 때
  배송비 정보가 사라진다
- `Order.shippingPrice` 는 선언돼 있지만 **한 번도 채워지지 않았다**(항상 0)
- `OrderDto.shippingPrice` 도 있는데 **옮기는 줄이 없었다** — 두 구멍이 서로를 가려 줬다

즉 주문 시점에 서버가 아는 것은 "배송비가 포함된 총액" 하나뿐이었다. 무료배송 이전에
**사용자가 배송비를 얼마 내는지 결제 화면에서 알 수 없다**는 것이 더 급한 문제였다.

#### 🐛 함께 드러난 것 — 쿠폰이 배송비까지 깎고 있었다

배송비가 총액에 녹아 있으니 scope 에 따라 할인 기준이 갈렸다:

| 쿠폰 | 할인 기준 | 결과 |
|---|---|---|
| 제약 **없는** 쿠폰 | `cartTotal`(배송비 포함) | **배송비까지 할인** |
| 제약 **있는** 쿠폰 | 대상 줄의 `price×qty` | 배송비 할인 안 함 |

같은 장바구니인데 쿠폰 종류만 달라도 할인액이 달랐다. 계산기 주석에도
"cart-service 의 cartTotal 과 줄 합계가 어긋나면(배송비 처리 등)"이라고 적혀 있었다 —
알고는 있었지만 분리할 수 없어 그대로 뒀던 자리다.

이제 **두 경우 모두 대상 줄의 상품 금액 합**이 기준이다. `scope=ALL` 은 "모든 줄이
대상"일 뿐 특별한 경로가 아니라서, 계산기에서 분기가 사라졌다.

⚠️ 이 변경으로 제약 없는 쿠폰의 할인액이 **배송비 몫만큼 줄어든다**. 덜 주는 방향이라
되돌리기 쉽고, 배송비를 할인해 주던 쪽이 의도된 적이 없다.

#### 화면

결제 요약이 **상품 금액 / 배송비 / 합계** 세 줄이 됐다. 0원을 "무료"로 바꿔 말하지
않는다 — 실제로 0원인지 아직 계산되지 않은 것인지 구분되지 않는다.

옛 장바구니 캐시에는 `shipping` 이 없어 `null` 로 온다. 그때는 **0으로 본다** — 배송비를
없는 것으로 보는 쪽이 안전하다. 반대로 추측하면 상품 금액이 실제보다 작게 표시된다.

#### 이제 등급별 무료배송은 한 줄이다

`OrderPricing` 이 배송비를 따로 알고 있으므로, 등급을 물어 그 값을 0으로 만들면 된다.
남은 것은 **판촉 정책**(어느 등급부터, 최소 주문액이 있는지)뿐이다.

#### 상시 할인율은 여전히 쿠폰으로만

진열가를 등급으로 나누는 것은 §3.2의 이유로 불가능하다(공개 라우트에 신원 없음,
Redis 캐시 분할, 화면마다 가격이 달라지는 버그의 재발). 그래서 등급별 상시 할인은
**월 자동 발급 쿠폰**이 현실적인 형태다.

### 아직 없는 것

- **등급별 배송비 면제** — 이제 코드는 준비됐다. 정책만 정하면 된다.
- **등급 쿠폰 월 자동 발급** — 배치 하나면 되지만 할인율·발급일이 정해져야 한다.
- **인스턴스가 여러 개면 배치가 여러 번 돈다** — 결과가 같은 연산이라 망가지지는 않지만
  order-service 를 그만큼 더 부른다. 단일 노드라 지금은 문제가 없고, 늘어나면
  `user.tier.scheduler-enabled` 로 한 인스턴스에서만 켜면 된다.

## 4. `SECURITY_ALERT` — 새 기기 로그인

`NotificationType.SECURITY_ALERT` 는 메일 제목·SMS 문구·메일 종류 매핑은 물론이고,
수신 설정에 **"보안 알림은 사용자가 꺼도 보낸다"**는 예외까지 들어가 있었다
(`NotificationPreference.shouldSendSms`). 전부 갖춰 놓고 **발행하는 쪽만** 없어서,
계정이 털려도 사용자는 알 방법이 없었다.

없던 것은 "이 로그인이 처음 보는 기기인가" 에 답할 근거 — 비교할 이력이다.

| 조각 | 위치 |
|---|---|
| 스키마 | `user-service` `V8__known_device.sql` — `users.known_device` |
| 식별 | `DeviceIdentity` — 기기 쿠키(난수) · 라벨 · IP 마스킹 |
| 판단 | `DeviceRecognitionService` — 새 기기인가, 알릴 것인가 |
| 발행 | `SecurityAlertProducer` → `security-alert` 토픽 |
| 수신 | `NotificationEventListener.onSecurityAlert` |
| 화면 | `GET/DELETE /api/user/profile/devices` + 보안 설정의 `LoginDevices` |

### 기기를 무엇으로 식별하나 — 쿠키 하나

브라우저에 httpOnly 쿠키로 심는 **난수**다. User-Agent 나 IP 로 지문을 만드는 방식은 쓰지
않았다:

- IP 는 모바일에서 수시로 바뀐다 — 지하철에서 로그인할 때마다 "새 기기" 가 된다
- User-Agent 는 브라우저가 업데이트될 때마다 바뀐다

둘 중 하나라도 지문에 넣으면 **알림이 소음이 되고, 소음이 되면 사용자는 진짜 경고도
무시한다.** 쿠키를 지우면 새 기기로 잡히는데 그건 오탐이 아니다 — 쿠키를 지운 브라우저는
서버 입장에서 처음 보는 브라우저와 구별되지 않는다.

### 🔒 토큰을 해시로 저장하는 이유

이 값은 인증 수단이 아니다. 알고 있어도 로그인은 못 한다. 하지만 **보안 알림을 끌 수 있는
값**이다 — 비밀번호를 이미 아는 공격자가 이것까지 알면 알림 없이 조용히 들어온다. DB 가
새더라도 그 능력이 함께 새지 않도록 SHA-256 만 저장한다(가입 확인 토큰과 같은 규칙).
`DeviceDto` 가 그 값을 응답에서 빼는 것도 같은 이유다.

### 소음 조절

- **첫 기기에는 알리지 않는다.** 가입하고 처음 로그인한 사람에게 "새로운 기기" 는 말이 안
  된다 — 비교할 기기가 없다. 첫인상이 쓸데없는 경고면 나중의 진짜 경고도 무시한다.
- **기기 수에 상한을 둔다**(기본 20). 없으면 쿠키를 지우는 브라우저 하나가 이 사용자의
  행을 무한히 늘린다.
- **동시 로그인은 한 번만 알린다.** 같은 사용자가 동시에 두 번 로그인하면 둘 다 "새 기기"
  로 보고 저장을 시도한다. `uk_known_device` 가 한쪽을 막고, 막힌 쪽은 알리지 않는다.

### 개인정보

- IP 는 **마스킹해서 저장한다**(`203.0.113.xxx`). 원문은 어디에도 남지 않는다 — 저장도,
  발행도, 응답도.
- User-Agent 원문 대신 `"Chrome · Windows"` 같은 라벨만 남긴다.
- 로그에 이메일·IP 를 남기지 않는다. 사실(userId, deviceId)만 남긴다.

### ⚠️ IP 는 표시 전용이다

`X-Forwarded-For` 는 클라이언트가 위조할 수 있다 — 게이트웨이의 `CustomUserKeyResolver` 가
같은 이유로 이 헤더를 **버린다**(레이트리밋 우회 시나리오). 여기서 쓰는 이유는 이 값이
오직 알림 문구에만 들어가고 **어떤 판정에도 쓰이지 않기** 때문이다. 위조해 봤자 자기
알림의 IP 표시를 바꾸는 것뿐이고, 새 기기인지는 쿠키가 정한다.

### 어떤 실패도 로그인을 막지 않는다

기기 기록은 로그인에 **부수적**이다. 여기서 예외가 올라가면 비밀번호를 맞게 넣은 사용자가
로그인하지 못한다 — 보안 알림을 붙이려다 서비스를 멈추는 것이고, 그건 훨씬 나쁘다.
발행 타임아웃도 3초로 짧게 잡았다(로그인 응답 경로다).

### ⚠️ "기억 지우기" 는 로그아웃이 아니다

그 기기에 로그인된 상태가 있으면 그대로 남는다. 뜻은 "다음에 그 기기에서 로그인하면 새
기기로 보고 다시 알린다" 뿐이다. 문구가 "로그아웃시킨다" 로 읽히면 사용자는 조치를 했다고
믿고 더 이상 아무것도 하지 않는다 — 정말 필요한 것은 비밀번호 변경이고, 화면이 그렇게
말한다.

### 아직 없는 것

- **소셜 로그인 경로**에는 붙이지 않았다. `OAuth2SuccessHandler` 는 리다이렉트로 끝나는
  다른 흐름이라(액세스 토큰도 만들지 않는다) 같은 자리에 넣을 수 없다.
- **위치(도시·국가)** 가 없다. IP → 지역 변환에는 외부 DB 가 필요하고, 마스킹된 IP 로는
  정확도가 떨어진다. 지금은 마스킹된 IP 만 보여 준다.
- **세션 강제 종료** 가 없다. 알림을 받은 사용자가 할 수 있는 조치는 비밀번호 변경이다.
