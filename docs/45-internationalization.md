# 45. 多言語 — 日本語の追加

**日本語** | [한국어](45-internationalization.ko.md)

> 🕰️ **状態（2026-09-27）— 一部古い。** サーバー文言の翻訳(Accept-Language)と JPY 表示はその後解決しました([docs/60](60-i18n-audit.md))。

## 1. 何をしたか

画面の文言を辞書に分離し、**한국어 / 日本語** の二通りを用意する。ヘッダーで切り替え、初回訪問
時にはブラウザの言語に従い、選んだ言語は記憶される。

今回の範囲は**画面の文言**である。商品・カテゴリのデータはそのまま単一言語である(§5)。

## 2. 出発点 — すでにあったもの、なかったもの

| | 状態 |
|---|---|
| notification-service | 🟢 **すでに 2 か国語**。`MailTemplates`・`SmsTemplates` に JA の文言があり、`NotificationPreference.region`(KR/JP)が選ぶ |
| フロントエンド | 🔴 i18n ライブラリなし。文言がコンポーネントに直接埋め込まれ、韓国語・英語が混在していた |
| catalog-service | ⚪ 商品・カテゴリに言語フィールドなし — 単一言語のデータ |

### 🐛 ヘッダーの言語切替は動作しない抜け殻だった

`pages/header/Language.jsx` は Amazon クローンから引き継いだモックアップだった。ラジオボタンには `name` も
`onChange` も状態もなく(`defaultChecked` だけが埋め込まれていた)、リストの言語
(español·العربية·Deutsch)はこのサイトに存在したことがない。「Learn more」は `href=""` で、
**現在のページを再度呼び出す**リンクだった。

つまり「言語を切り替えられる」と言っておきながら、押しても何も起きなかった。**存在しない機能より
悪い — なければ探しもしない。**

## 3. なぜライブラリを使わなかったか

`react-i18next` を使わず、`src/i18n/` に自作した。根拠は三つである。

1. **韓国語と日本語はどちらも複数形がない。** i18next の最大の価値は複数形ルール
   エンジンだが、「1件」と「5件」の形が同じ二言語ではそのエンジンにやることがない。
2. 残るのは**辞書の参照と変数の置換**だけで、それは二十行である。
3. このリポジトリには**新しい依存関係を増やさない**という方針がある(`jest.config.js` のコメント:
   「ネットワークが遮断された環境でもすぐに動かなければならない」)。

> **境界を書いておく。** 言語が五つに増えたり、**複数形のある言語**(英語・ロシア語など)が
> 入ってきたら、そのときはライブラリが正しい。その判断基準を `I18nProvider` のコメントに残した。

## 4. 設計で意図したこと

### 言語を選ぶ順序 — 保存された選択 > ブラウザ > 韓国語

保存された選択がブラウザより**優先される。** 日本語ブラウザを使う人が韓国語を選べる
必要があり、その選択がリロード後も生き残らなければならない。

`ja-JP` のように地域が付いていても先頭の二文字だけを見る。`navigator.languages` の優先順序を守る。

> ⚠️ localStorage へのアクセスは try/catch で囲んだ。シークレットウィンドウやサイトデータがブロックされた
> ブラウザでは**読み取り自体が例外を投げる** — 囲まないとアプリが初回レンダリングで落ちる。

### 🔴 `<html lang>` を実際に変える

飾りではない。スクリーンリーダーは読み上げの発音をこの値で選び、ブラウザは改行ルールとデフォルトの
フォントをこれに合わせる。韓国語ページに日本語を描いておいて `lang="ko"` のままにすると、日本語が
**韓国語フォントで**レンダリングされ、字形がずれる(CJK 統合漢字)。

### 存在しないキーはキー名をそのまま表示する

空文字列を返すと画面から文字が消え、誰も気づかない。キーが見えればすぐに
露見する。同じ理由で、置換値がなければ `{{min}}` を消さずに残す — 消すと
「비밀번호는 자 이상이어야 합니다」のような**意味が通りそうな文**になり、バグが隠れる。

### Provider の外で使うと例外を投げる

黙ってデフォルト値で動くようにすると、Provider を入れ忘れた画面が韓国語に固まったまま
「日本語への切り替えだけができない」状態でデプロイされる。代償としてテストごとに囲む必要があるので、その一行を
`i18n/testing.jsx` の `withI18n` にまとめた。

### 国旗を使わない

言語と国は違う。国旗で言語を表すと、同じ言葉を使う別の国のユーザーを排除する。
言語名は**その言語で**書く(endonym): `한국어`, `日本語`.

## 4-1. 第 2 弾 — 商品一覧・詳細

認証画面に続いて商品側を移した: `browse.jsx`(一覧)、`HeadingFilter`(フィルター・ソート)、
`Infos.jsx`(詳細)、`ShippingInfo`, `AccordianProduct`, `BreadCrumb`.

### 🐛 詳細画面が事実でない情報を表示していた

`ShippingInfo.jsx` に Amazon クローンの残骸が埋め込まれていた:

- `Delivery **Thursday, March 23**. Order within 23 hrs 53 mins` — 固定された日付と偽の
  カウントダウン。このリポジトリに配送日を計算するコードはない。
- `Deliver to Germany` — このサービスは韓国・日本へ配送する。
- `Sold by ATUAT` — 存在しない販売者。

**翻訳せずに削除した。** 偽の情報を日本語でも見せる理由はなく、ないより悪い —
ユーザーはその日付を信じて注文する。配送日推定機能ができたら、そのとき実際の値で復活させる。

### 複数形がないことが実際に得になった箇所

詳細画面はレビュー数を `{n} {n >= 1 ? "reviews" : "review"}` で描いていた。英語の単数/複数の
分岐である。韓国語・日本語には複数形がないので、その分岐を**丸ごとなくし**、文言一つに置き換えた:
`리뷰 {{count}}개` / `レビュー{{count}}件`. §3 でライブラリを使わないと決めた根拠が
コードで確認された箇所である。

### サーバーへ送る値は翻訳しない

ソートオプション(`sortingOptions`)は表示名の代わりに**文言キー**を持つよう変えた。理由は二つである:

1. この配列はモジュールのロード時に一度だけ評価される — 翻訳された文字列を入れると**言語を切り替えても
   変わらない。**
2. `value`(`newest`, `topSelling` …)はサーバーへ送るクエリ値なのでそのままにする。
   **画面の言語が API 契約を変えてはならない。**

### 🐛 これらの画面にはレンダリングテストが一つもなかった

`browse.test.jsx` は純粋関数(`nextPageParam`・`sortProducts` など)だけを検証し、コンポーネントを
描画しない。商品詳細側にはテストファイル自体がなかった。文言を移しながら `ShippingInfo`
と `HeadingFilter` のレンダリングテストを初めて作った — 捏造された情報が復活することと翻訳
漏れの両方をここで捕まえる。

## 4-2. 第 3 弾 — カート・注文

`cart/`(Checkout·Empty·CartHeader·PaymentMethods·Product)、`checkout/Summary`、
`order/`(Total·OrderInfo) の文言を移した。

### 助数詞 — 複数形がないこととは別の話

日本語は物を数えるときに**助数詞**を使う。カートの「선택한 상품 (3)」は
`選択中の商品（3点）` が自然だ。これは複数形(1 個 vs 複数で形が分かれるもの)では
なく**単位**なので、数によって文が分かれない — 文言一つに `{{count}}` を入れるだけでよい。
数える対象が変われば助数詞も変わるので(点·枚·本…)、そのときは文言を別に用意する。

### 金額は翻訳対象ではない

`100000$` のような数字は二言語で同じでなければならない。日本語のテストにそれを明示的に入れて
おいた — 通貨形式に手を入れるとき(§5)、このガードが先に壊れて知らせてくれる。

### 🐛 ここもテストがほとんどなかった

`cart/Checkout`・`cart/Empty` にはテストファイルがなかった。翻訳と一緒にレンダリングテストを作りながら、
「選んだ商品がなければ進むボタンがロックされる」「空のカートからショッピングへ行く道を示す」のような
基本動作も一緒に固定した。

## 4-3. 第 4 弾 — プロフィール

`pages/profile/`(profile·address·orders·payment·security)とサイドバーを移した。

### 🔴 メニュー名が URL を作っていた

`components/profile/sidebar/Item.jsx` がメニュー名をそのままアドレスに入れる:

```jsx
`${link.link}?tab=${index}&q=${slugify(link.name, { lower: true })}`
```

つまり `name` を翻訳すると**言語によってアドレスが変わる。** 日本語で見ていた人が共有したリンクが
韓国語ユーザーの環境で開けず、戻る履歴もずれる。

そこでメニューデータに表示用の `key` を別に置き、`name` は英語のまま残した — 画面には
見えず、アドレスにだけ使われる。ソートオプション(§4-1)の `value` と同じルールである:
**画面の言語はアドレスや API 契約を変えない。**

## 4-4. 第 5 弾 — サーバーが作った文言 (ログイン結果)

画面の文言をすべて移しても、**ログイン直後だけ英語が表示された。**

```jsx
toast.success(response.data.message);   // "Login Success"
```

`message` は `AuthLoginFilter` が作った英語の文である。多重ログインのときはこうだった:
`"User attempted to log in multiply, logging out from previous logged in state"`.

### サーバーで翻訳しない理由

**サーバーはユーザーの表示言語を知らない。** 言語はブラウザが選び、`localStorage` に
ある(§4)。`Accept-Language` で推測することはできるが、**ユーザーが画面で選んだ値と
ずれる** — 日本語ブラウザを使いながら韓国語で見ている人に日本語が届く。

そこでサーバーは**何が起きたかだけをコードで**知らせ、文言はフロントの辞書が選ぶ。
失敗パスがすでに使っていた方式と同じである(`email_not_verified`, docs/46)。

| | 前 | 後 |
|---|---|---|
| サーバー | `message` (英語の文) | `message` + **`code`** (`login_success` / `multi_login`) |
| フロント | そのままトースト | `util/loginResult.js` が `auth.signin.result.<code>` を参照 |

`message` は**消さなかった。** コードを知らないクライアントが何も受け取れなくなる。

### 🔴 知らないコードをそのまま通してはならない

`t()` は存在しないキーを受け取ると**キー文字列をそのまま返す**(§4)。サーバーに新しいコードができたのに
フロントがまだ知らないと、トーストに `auth.signin.result.xyz` が表示される — 英語の文より悪い。
そこで `KNOWN_RESULT_CODES` にあるコードだけを翻訳し、残りはサーバーの文言にフォールバックする。
ガードは `util/loginResult.test.js`(6 件)で、**実際の ko/ja 辞書で**参照する — 偽の `t` を
使うと、キーが辞書にないことを捕まえられない。

## 5. 今回の範囲に入れなかったもの

- **商品・カテゴリのデータ。** スキーマ変更 + 管理者入力画面 + 実際の翻訳内容が必要だ。
  画面の文言とは規模が違う。
- **通貨・数値・日付の形式。** 今は価格が `$` 接尾辞一つに固定されている。JPY 表示と
  桁区切りのルールは別作業である。
- **メール・SMS の言語連携。** サーバーに日本語の文言はすでにある。画面で選んだ言語を
  `NotificationPreference.region` につなぐことが残った。

## 6. 検証

| | |
|---|---|
| 新規テスト | 47 件 (i18n 16 + 日本語・レンダリングガード 31) |
| フロントエンド全体 | **455 件合格** |
| lint | 警告 193 (ラチェット 198) |

中核となるガード二つ:

- **二言語のキー集合が同じである。** キーが抜けるとフォールバックのせいで*日本語画面に韓国語が混ざるが*、
  画面は正常に見えるので誰も気づかない。
- **日本語で実際にレンダリングしてみる。** キーだけ変えておいてコンポーネントが依然としてハードコードされた韓国語を
  描いていても、韓国語のテストはすべて合格する — 日本語で描いてみて初めて露見する。

### 🐛 テストは合格したのに本番ビルドが壊れた

`webpack.config.base.js` の alias に `i18n` を登録していなかった。jest は
`moduleDirectories: ["node_modules", "src"]` で `src` 以下をすべて解決するので **426 件が
すべて合格**したが、webpack は alias に書かれたものしか見ない — 本番ビルドでだけ
`Can't resolve 'i18n/I18nProvider'` で壊れた。

そのファイルのコメントがすでに「新しい最上位フォルダを作ったらここにも登録しなければならない」と警告していた。
**テスト合格がビルド成功を意味しないケース**なので記録しておく。
