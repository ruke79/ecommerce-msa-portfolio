# 83. 負荷試験 — k6 シナリオ(閲覧・注文・急増)

> **状態(2026-10-17)** — シナリオ・実行器(`ops/53`)・ガードは入り、偽のゲートウェイ(https・テスト CA)で 4 つのシナリオが最後まで回る。
> **実習クラスタでの計測はまだ** — 結果は §5 の表に埋める。

[docs/19](19-local-performance-tuning.md) の `ops/14` は curl で GET のパスを一つ叩く。それではログイン → カート → 注文のような
書き込みの経路(在庫予約 gRPC・注文アウトボックス・Kafka・カートのキャッシュ)を測れない。ここでは画面と**同じアドレス・同じヘッダー**で
お客さまの流れを k6 で回し、結果とそのときの条件(イメージの版・レプリカ・ノード・HPA・流入制限)を一つのフォルダーに残す。

## 1. どこで測るか — 実習クラスタ

- **本番(OCI Ampere)では測らない。** Cloudflare トンネルとインターネット区間の遅延が混ざってコードではなく回線を測り、実際のお客さまの
  サイトを遅くする。`ops/53` は `GATEWAY` が `ysyproject.com` なら拒否する。
- 実習クラスタ(デスクトップ一台の上の VM — サーバー・エージェント・データノード、)の `https://shop.lab` に掛ける。
  負荷は `loadgen` VM から出す — 同じ VM から出すと k6 がサーバーの CPU を食う。
- **絶対値はこのクラスタでだけ意味がある。** 結果を書き写すときは「実習クラスタ(デスクトップ一台の上の VM)基準」を一緒に書く。意味があるのは
  同じ条件での**前後比較**と**どこで折れるか**だ(docs/19 §0)。

## 2. シナリオ — `ops/k6/`

| シナリオ | 1 反復 | 負荷の形(既定) | しきい値 |
|---|---|---|---|
| `browse` | 非会員: ホーム・バナー → カテゴリー一覧 1・2 ページ(フィルター付き)→ 商品詳細 | 到着率の階段 25% → 50% → 100%、最大 `RATE=100`/秒、各段 2 分 | 失敗 < 1%、p95 ホーム 800ms・一覧 1200ms・詳細 800ms |
| `order` | ログインしたデモユーザー: 商品詳細 → カート投入情報 → 投入 → チェックアウト保存 → チェックアウト・配送先 → 注文(Idempotency-Key)→ 注文詳細 → 銀行振込の案内 → 振込の取消・行の削除 | 30% → 100%、最大 `RATE=min(10, USERS)`/秒 | 失敗 < 1%、注文 p95 2s、投入 p95 1s、購入一回全体 p95 6s |
| `spike` | `browse` と同じ | 平常(最大の 10%)2 分 → 20 秒で最大(`RATE=200`)→ 3 分維持 → 引く → 3 分 | 失敗 < 2%、詳細 p99 3s |
| `smoke` | 閲覧一回・注文一回(アカウント一つ) | — | チェック 100%・429 なし |

- **到着率(arrival-rate)で決める** — VU 数ではなくお客さまが来る速さ。VU 固定(閉じたモデル)は、サーバーが遅くなると負荷も一緒に減ってボトルネックを隠す。
- **応答が JSON かを常に見る**(`not_json`)。デモのイングレスが API をフロントへ送っていたころ(2026-10-17 以前)は、すべての API が
  `index.html` 200 で、ステータスコードだけを見るチェックは全部成功だった。開始前(setup)にホームが JSON でなければ、その理由を言って止まる。
- **429 は別に数える**(`rate_limited`) — 制限が働いたのか、サーバーが耐えられなかったのかを分けて読む。
- **注文の最後に振込を取り消す。** 振込待ちの注文はお客さま一人 3 件まで(`bank-transfer.max-pending-per-customer`)で、在庫を 49 時間押さえる —
  そのままだと同じアカウントの 4 回目の反復から 400 になり、何度か回すと在庫が尽きる。一回だけ見るなら `KEEP_ORDERS=1`。
- **ログインは開始前にゆっくり。** ログインの流入制限は IP ごとに毎秒 1・バースト 10 で、変えられない — `setup()` がアカウントごとに一回、10 人目以降は
  1.1 秒間隔でログインする(100 人で約 2 分)。429 を受けたら待って同じアカウントをもう一度。
- **一つのアカウントは一つの VU だけ**が使う(`maxVUs = USERS`)。リフレッシュトークンがローテーションするので、二つの VU が同じトークンで更新すると
  遅い方がそのログインを終わらせる。アクセストークンは 15 分 — 13 分を過ぎたらその VU が更新する。
- **SKU が一つの商品だけをカートに入れる。** 投入情報(catalog)は順序が保証されない Set から `skip(style)` で、カート(cart)は `skus.get(style)` で
  SKU を選ぶ — 両者が同じものを指すと確かなのは SKU が一つのときだけだ。

### 2.1 データ規模 × 到着率

トラフィック(到着率)とデータ量は**別の軸**だ。商品が増えると、インデックスの大きさ・PostgreSQL のキャッシュヒット・一覧のソートと件数の数え上げ・名前検索
(`LIKE '%…%'`、docs/19 §6.1 のフルスキャン)が変わる。そこで**同じ到着率で商品数だけを変えて** p95 をエンドポイントごとに比べる。

| 商品数 | 表 + インデックス(商品あたり 2,108 B、docs/19 §5.1) | 投入(実習 VM の推定) | 見るもの |
|---|---|---|---|
| 1 万 | 約 0.02 GiB | 1 分未満 | 基準線 |
| 100 万 | 約 2 GiB | 20〜30 分 | メモリの内側の端(`shared_buffers` 1.5 GB・キャッシュ 4 GB・Pod 6 Gi、デモのインフラ) |
| 1,000 万 | 約 20 GiB | 3〜5 時間 | **メモリの外** — ディスク読み込みが混ざる。深いページ・名前検索がどこで折れるか |
| ~~1 億~~ | 約 196 GiB(WAL の余裕までディスク約 300 GB) | 28〜46 時間 | 入れられない — data-node のディスクは 97 G |

**データ規模モード**(`PRODUCTS` を渡すと — browse・spike):

- 詳細は ops/44 で入れた範囲(`PRODUCT_ID_OFFSET`+1〜+`PRODUCTS`、既定のオフセット 1000000 = ops/44 の既定値)の**ランダムな商品 id**(`product_cold`)。
  ホームに出た数十件だけを読むと、いつもキャッシュ(Redis 30 分・PostgreSQL のバッファー)から返り、データの大きさが見えない。
- 一覧は 1〜`DEEP_PAGES`(既定 50)ページのうちランダム(`search_deep`)— OFFSET が大きいほどコストが増える。
- `NAME_SEARCH`(既定 0.2)の割合で名前検索(`name_search`)— 検索語は生成器の商品名の名詞だ(結果 0 件を測らないように、ガード)。
- 開始前に範囲の最初・最後の商品があるかを見る — なければ「遅い」ではなく「ない」を測ることになるので止まる。

```bash
for n in 10000 1000000 10000000; do
  PRODUCTS=$n PLACEHOLDER_IMAGE=/logo512.png ./ops/44-bulk-catalog.sh load   # 続きから入れる(--resume)
  PRODUCTS=$n RATE=50 ./ops/53-load-k6.sh browse                                      # 同じ到着率
done
```

- 商品数を増やすときは消さずに続きから入れる(ops/44 は同じ範囲の次の id から)。1,000 万はディスクの余裕を先に見る(ops/44 が点検する)。⚠️ 大きな投入には `FORCE=1` を使わない — ops/44 の `FORCE` はバックアップ時間帯(02〜06 UTC)だけでなく**ディスクの点検まで**飛ばす。その時間帯を避けて回す。
- **ユーザー数はこの軸ではない。** 会員数(users 表の大きさ)はログイン(メールのインデックスを一回)の速さをほとんど変えない — 大きさが
  効くのは管理者のユーザー検索・等級バッチ・クーポン一括発行のようなバッチだ。order の `USERS` は**同時ユーザーのプール**だ: 必要な
  数は「注文の到着率 × 購入一回の時間」(毎秒 20 × 約 6 秒 ≈ 120)— 200 なら毎秒 20、2,000 なら毎秒 100 まで。ログインが毎秒 1 なので
  2,000 人は準備だけで約 37 分、2 万人は約 6 時間だ。

## 3. 手順

```bash
# 0) デモのイングレスが API をゲートウェイへ送るか— 200 application/json
curl -sS --cacert ~/.ecommerce-msa/demo/certs/ca.crt https://shop.lab/catalog-service/api/content/home \
     -o /dev/null -w '%{http_code} %{content_type}\n'

# 1) データ — 商品 1 万・ユーザー 200(docs/79)
FORCE=1 PRODUCTS=10000 PLACEHOLDER_IMAGE=/logo512.png ./ops/44-bulk-catalog.sh load
FORCE=1 USERS=200 ./ops/48-bulk-users.sh load

# 2) 同じ CPU を使うものを止める — CI ランナー
# 3) 点検
./ops/53-load-k6.sh smoke

# 4) 流入制限を一時的に上げる(計測のときだけ — 下記)
./ops/53-load-k6.sh limits load            # 毎秒 2000・バースト 4000

# 5) 計測 — 一つずつ、間に数分休む(HPA が縮み、キャッシュ・コネクションが落ち着くように)
RATE=100 ./ops/53-load-k6.sh browse
USERS=200 RATE=20 ./ops/53-load-k6.sh order
RATE=200 ./ops/53-load-k6.sh spike          # 別の窓で kubectl -n ecommerce get hpa -w

# 6) 戻す — 必ず
./ops/53-load-k6.sh limits default
```

**なぜ流入制限を上げるか。** 非ログインのリクエスト(カタログの読み取り)はバケットのキーが IP だ(`CustomUserKeyResolver`)。デモには Cloudflare がなく、
外からのリクエストはすべて Traefik の Pod の IP 一つに見え、そのバケット(毎秒 20・バースト 40)をすべてのお客さまが分け合う。そのまま測ると結果は
「毎秒 20 で 429」だけだ。そこでゲートウェイの既定の制限を環境変数で変えられるようにした(`GATEWAY_RATE_LIMIT_REPLENISH`・`_BURST`、
既定値はそのまま — `RateLimiterPlacementTest`)。

- `limits` は、このクラスタの `APP_PUBLIC_URL` が本番のアドレスなら拒否し、空でも拒否する。ログインの制限(毎秒 1)は変えられない。
- Deployment の env を直接変えること(`kubectl set env`)は、この計測だけに使う例外だ — 設定は本来 ops/28 でだけ変える。
  マニフェストにはこの変数を置かない(ガードが見る)。上げたままにすると ops/06 のスモークの「429 発生確認」が失敗する — それが戻していない合図だ。
- 上げた値で測った数値は「流入制限を除いたサービスの容量」だ。本番の実際のお客さまは IP ごとにバケットが別なので、この制限には掛からない。

**実行器の環境変数。** `GATEWAY`(既定 `https://shop.lab`)・`CA_FILE`(デモ CA — 検証を切らずにこれを信頼する、`SSL_CERT_FILE`)・
`USERS`・`ID_OFFSET`(ops/48 と同じ番号)・`PASSWORD_FILE`(デモのパスワード — k6 の環境変数でだけ渡し、コマンドライン・結果ファイルにはない)・
`RATE`・`STAGES`(`長さ:目標,…`)・`OUT`(結果フォルダー)・`PROM_RW`(k6 の指標を Prometheus へ — obs-vm を `docker-compose-observability.lab.yml` の上書きで起動すれば受ける)。

## 4. 読み方 — 何を一緒に見るか

k6 の要約は「どれだけ遅かったか」しか言わない。**なぜ**は同じ時間のサーバーの指標にある(Grafana、obs-vm)。サービスの指標はクラスタ内のエージェントが送る(それ以前はデモのサービスの指標が観測 VM になかった)。`PROM_RW` を渡すと k6 の指標も同じ時間軸に来る。

| k6 で見えるもの | 一緒に見るもの | よくある原因 |
|---|---|---|
| ある段から p95 が階段のように跳ねる | `hikaricp_connections_pending`・`tomcat_threads_busy_threads`(÷ `tomcat_threads_config_max_threads`)・処理中のリクエスト数 `http_server_requests_active_seconds_active_count` | DB コネクションプールの枯渇(プール 5 × レプリカ)・スレッドの飽和 |
| 注文だけが遅い・カート投入は大丈夫 | order の gRPC 在庫予約の遅延・catalog のロック待ち | 同じ SKU への集中(行ロック)— 商品数を増やすと解けるか |
| 注文は速いが後ろが詰まる | Kafka コンシューマーの遅延・`payment_outbox_event` の STARTED 行数 | アウトボックスのリレー・コンシューマーの処理量 |
| `rate_limited` が増える | その名前(`name` タグ) | 流入制限 — 上げていないか、ログインした一人のお客さまのバケット(毎秒 20) |
| 急増の直後だけ 5xx | HPA のレプリカ・新しい Pod の Ready 時刻・PostgreSQL の接続数 | 新しい Pod が準備前にトラフィック・コネクション総数が `max_connections` 付近(docs/19 §3) |
| `http_req_failed` は 0 なのに `checks` が低い | 失敗したチェックの名前 | 400(在庫・振込待ちの上限)— データの状態 |

> 🐛 `tomcat_threads_*` は Tomcat の MBean レジストリが有効なときだけ出る(Spring Boot の既定は無効)— 2026-10-18 の実習で空だったので共通設定(`application-common.yml`)で有効にした(`TomcatMetricsConfigTest`)。それ以前のイメージでは処理中のリクエスト数で見る。ゲートウェイ(WebFlux)に Tomcat の指標はない。

## 6. 限界 — 正直に

- 実習クラスタは デスクトップ一台の上の VM だ — ノード間の遅延はデータセンターに近いが、ディスク・CPU は一台の機械を分け合う。
- お客さまの IP がすべて同じ(k6 一台)— 本番の IP ごとのバケット・キャッシュの分布とは違う。
- 決済は銀行振込(外部呼び出しなし)だけを測る。カード・PayPal はプロバイダーのサンドボックスの速さを測ることになる。
- 商品画像はプレースホルダー一枚だ(デモには画像ストレージがない)— 画像の転送量は測らない。
- 一覧は PostgreSQL 検索だ(`SEARCH_ENGINE=postgres`、k8s/10 — デモも変えない)。Elasticsearch の検索は測らない。
