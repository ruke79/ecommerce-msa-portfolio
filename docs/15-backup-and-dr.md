### 0.1 実測 — 事故を起こして元に戻した

`ops/09-restore-drill.sh` は説明ではなく実行である。アーカイブを有効にした PostgreSQL 16 を起動し、
注文データを投入し、base backup を取り、さらにデータを投入し、**`DROP TABLE orders` で事故を起こした後**、
base backup + WAL で事故直前の時点に戻す。このリポジトリで実際に実行した結果:

```
>>> 4/7  백업 이후 주문 300건 추가 → 이 시점까지 복구되어야 한다
    목표 시각 T = 2026-07-28 03:48:22.830766+00
    T 시점 상태: 800건, 합계 170400000.00
>>> 5/7  사고 재현 — DROP TABLE orders
    사고 후 상태: 1건 (쓰레기 데이터)
>>> 7/7  검증
    OK   행 수 800 = T 시점과 일치
    OK   합계 170400000.00 = T 시점과 일치
    OK   원래 스키마(4개 컬럼) 복원 — DROP TABLE 이 되돌려졌다
    OK   사고 이후 쓰레기 데이터 없음
    RTO(실측) : 3초 / 사용한 WAL 6개
```

この訓練が**トートロジーではない**理由: base backup 時点では 500 件、事故後は 1 件だった。
結果が 800 件ということは、WAL 再生が実際に行われ（500→800）、ちょうど目標時刻で止まったという
ことである（800≠1）。止まるのが早すぎても遅すぎても、この検査は失敗する。

RTO 3 秒はデータ 46MB 基準である — 本番規模の RTO ではないが、**手順が動作するという事実**は
規模に関係なく証明される。実際の RTO は本番データで同じスクリプトを実行して測定すること。

MongoDB も同じ方法で確認した: 290 個のドキュメントをダンプして空のインスタンスに復元し、件数を照合 —
`OK 문서 수 일치 — 이 덤프는 복원 가능합니다`。

**レプリケーション（replication）はバックアップではない。** [docs/13 §2](13-secrets-dbha-es-search.md) で追加したストリーミングレプリケーションは*ノード障害*を防ぐが、`DROP TABLE`・誤ったマイグレーション・ランサムウェアは**レプリカにも即座に伝播**する。元に戻すにはポイントインタイムリカバリ（PITR）が必要である。

## 1. 何を失ってはならないか — データ等級

復旧目標はデータごとに異なるべきである。すべてを同じに扱うとコストばかりかさみ、肝心なものを見落とす。

| 等級 | データ | 失うと | RPO（許容損失） | RTO（復旧時間） |
|---|---|---|---|---|
| **C1 金銭** | `orders.*`, `pay.payment`, Outbox 4 種 | 売上紛争・精算不能・法的問題 | **≤ 5 分** | ≤ 1 時間 |
| **C2 アカウント** | `users.*`, `coupon.coupon` | ログイン不能、クーポン消失 | ≤ 1 時間 | ≤ 4 時間 |
| **C3 コンテンツ** | `product.*`（商品/カタログ）、MongoDB チャット | カタログ喪失、会話履歴の損失 | ≤ 24 時間 | ≤ 8 時間 |
| **C4 派生** | Elasticsearch インデックス、Redis キャッシュ | なし — **再生成可能** | バックアップ不要 | 再インデックス/ウォーミング |

> **C4 はバックアップしない。** ES インデックスは `POST /api/products/sync` による再インデックスで、Redis キャッシュはウォームアップで復元される。
> ただし Redis の**リフレッシュトークン**は例外 — 消失すると全ユーザーの再ログインが発生する（致命的ではないが認識が必要）。

## 2. PostgreSQL — PITR（中核）

C1（金銭）データの RPO 5 分を満たすには、**日次ダンプでは不十分**である。WAL アーカイブに基づく PITR が唯一の答えである。

### 2.1 構成
```
[プライマリ] --WAL ストリーミング--> [スタンバイ]        (ノード障害対策, docs/13 §2)
     └------- WAL アーカイブ ---> [オブジェクトストレージ(S3 など)]  (ポイントインタイムリカバリ対策, この文書)
     └------- 週次 base backup -> [オブジェクトストレージ]
```

- **pgBackRest** を推奨（増分・並列・検証を内蔵）。代替: WAL-G、barman。
- 保持: base backup 週 1 回 + WAL 連続 → **直近 14 日の任意の時点**に復旧可能。
- WAL アーカイブの周期を `archive_timeout = 60s` にすると、**最悪 RPO ≈ 60 秒**。

### 2.2 なぜパーティショニングがバックアップを助けるのか
[docs/09](09-postgresql-partitioning-sharding.md) で Outbox を月次パーティションにしたおかげで、古いパーティションは `DETACH` した後**バックアップ対象から除外**できる。バックアップのサイズと復旧時間が、データの総量ではなく**アクティブな区間に比例**するようになる。

### 2.3 k8s 環境
[CloudNativePG](../k8s/80-postgres-cnpg.yaml.example) はバックアップ/PITR を宣言的にサポートする:
```yaml
spec:
  backup:
    barmanObjectStore:
      destinationPath: s3://your-bucket/ecommerce-pg
      s3Credentials: { ... }
      wal: { compression: gzip }
    retentionPolicy: "14d"
```

## 4. 復旧シナリオ別の手順

### DR-1. 誤ってデータを削除（最もよくある）
`DELETE`/`DROP` がレプリカにも伝播した状態。
1. 事故時刻を特定（監査ログ・アプリケーションログ）。
2. **新しいインスタンス**に base backup を復元 → `recovery_target_time = '事故直前'` で PITR。
3. 復旧したデータから**該当テーブルだけ**を抽出して本番に反映（全体のロールバックでは、その間の正常な取引まで失う）。
4. C1 データなら Outbox/Saga の状態の整合性を確認（注文・決済状態の不一致を点検）。

### DR-2. プライマリノード障害
→ バックアップではなく**レプリケーションの failover** の領域: `ops/promote-replica.sh`（docs/13 §2）。

### DR-3. リージョン/クラスター全体の喪失
1. 新規環境のプロビジョニング — [`k8s/`](../k8s/README.md) マニフェストでアプリケーション層を再構築。
2. PostgreSQL: オブジェクトストレージの base backup + WAL で復元（**ここが RTO の大部分**）。
3. MongoDB の復元、Kafka トピックの再作成（`ops/02-create-dlt-topics.sh`）。
4. Elasticsearch: バックアップの代わりに**再インデックス**（`ops/03-enable-es-search.sh`）。
5. シークレットの復元 → サービス起動 → `ops/06-smoke-test.sh` で検証。

### DR-4. 誤ったマイグレーションのデプロイ
Flyway 導入（[docs/09 P0](09-postgresql-partitioning-sharding.md)）以降、スキーマ変更はバージョン管理されている。
- 破壊的マイグレーション（DROP/ALTER）は**デプロイ前のスナップショット**が必須。
- 元に戻せない変更は PITR でしか復旧できない → 危険なマイグレーションの前後で base backup を強制する手順を設けること。

## 5. 必ず守るべき原則

1. **復元をテストしていないバックアップはバックアップではない。** → `ops/09-restore-drill.sh` を CI の週次スケジュールに設定した（`.github/workflows/build.yml` の `restore-drill` ジョブ）。人の記憶に頼らない。
2. **バックアップは本番とは異なる障害ドメインに置く** — 同じアカウント/リージョン/ディスクに置くと同時に失う。`BACKUP_ROOT` をオブジェクトストレージのマウントや別ボリュームに指定すること。
3. **バックアップの成功/失敗を監視する。** 黙って止まったバックアップが最も危険である → `observability/alert-rules.yml` の `backup-health` グループ:
   - `PostgresBackupStale` — 48 時間以内に成功なし
   - `PostgresBackupMetricMissing` — メトリクス自体がない（= 一度も成功したことがない）。「アラートが鳴らない = 正常」という錯覚を防ぐ
   - `PostgresWalArchivingFailing` — archive_command の失敗。放置すると `pg_wal` がディスクを埋めて DB が止まる
   - `MongoBackupStale`
   ops/08・10 の `METRICS_DIR` が node_exporter の textfile メトリクスを書き込む。
4. **RPO/RTO を文書ではなく訓練結果で検証する。** → §0.1 に実測値を記載した。本番データで再測定して更新すること。
