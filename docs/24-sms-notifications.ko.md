# 24. SMS 알림과 2단계 인증

[日本語](24-sms-notifications.md) | **한국어**

> 🕰️ **상태(2026-09-27) — 일부 낡음.** 인증 SMS 는 번호당 제한 외에 계정당 · 전체 일일 상한도 있습니다([docs/57 §10](57-remaining-priorities.ko.md)).

> 새 기능. 주문·결제·채팅·친구접속 등의 이벤트를 알림으로 만들고, 그중 중요한 것만 SMS 로
> 내보낸다. 한국(+82)·일본(+81) 번호를 지원하며, SMS 기반 2단계 인증도 같은 경로를 쓴다.

## 0. "무료"가 적용되는 범위

먼저 분명히 해 둘 것이 있다. **SMS 발송은 한국·일본 어디에도 무료 게이트웨이가 없다** —
통신사가 건당 과금하고, 한국은 여기에 더해 **발신번호 사전등록**이 법으로 요구된다
(전기통신사업법). 무료인 것은 다음이다:

| 무료 | 유료 |
|---|---|
| **libphonenumber** (구글, Apache-2.0) — 번호 파싱·검증·정규화 | 실제 SMS 발송 (건당) |
| 개발용 `LoggingSmsSender` — 실제 발송 없이 전 경로 검증 | 공급자 계정·발신번호 등록 |
| 공급자 무관 HTTP 어댑터 | |

그래서 **기본값이 로깅 발송기**다. 설정이 덜 된 채 배포됐을 때 "아무 문자도 안 나간다"가
"모르는 사이 요금이 나간다"보다 안전하다. 실제 발송은 `SMS_PROVIDER=http` 로 명시해야 켜진다.

## 1. 왜 새 서비스인가

`chat-service` 에 이미 `Alarm` 엔티티·매퍼·DTO 가 있었다. 그런데 **어디에서도 저장되지 않는
죽은 코드**였다 — 리포지토리도 저장 호출도 없다. 채팅 메시지가 전달만 되고 저장은 0건이던
B-24 와 같은 모양이다.

게다가 알림은 주문·결제·쿠폰까지 걸치는 횡단 관심사라 채팅 서비스가 소유할 것이 아니다.
`notification-service` 로 분리하고, 프론트엔드의 SSE 훅(`util/Notification.js`)이 이미 기대하고
있던 알림 목록을 실제로 채운다.

## 2. 전화번호 — 정규식으로 짰다면 반드시 틀렸을 것들

한국과 일본은 규칙이 다르고 둘 다 함정이 있다. libphonenumber 를 쓴 이유가 여기 있다.

**트렁크 프리픽스 0.** 국내 표기 `010-1234-5678` 의 맨 앞 0 은 국내 통화용이라 국제 형식에서
**빠진다** → `+821012345678`. 그대로 붙이면 `+82010...` 이 되어 자릿수가 하나 늘고 발송이
실패한다. 일본도 같다(`090-…` → `+8190…`).

**"010 으로 시작하는 11자리" 정규식이 막아 버리는 유효한 번호들** — 테스트로 확인했다:

| 번호 | 실제 | 흔한 정규식 |
|---|---|---|
| `010-123-4567` (10자리) | ✅ 유효 | ❌ 거절 |
| `019-1234-5678` (구 통신사) | ✅ 유효 (번호이동으로 현존) | ❌ 거절 |

막으면 그 사용자는 가입 자체를 못 한다.

**유선번호는 거른다.** `02-1234-5678`(서울)·`03-…`(도쿄)은 형식상 유효하지만 SMS 가 도달하지
않는다. `getNumberType` 으로 MOBILE 만 통과시킨다.

**저장은 항상 E.164.** 어떤 표기로 입력하든 한 형태로 모이므로 중복 등록을 막을 수 있다.
로그에는 마스킹해서 남긴다(`+8210****5678`) — 로그 열람 권한이 곧 연락처 열람 권한이 되면 안 된다.

## 3. 길이는 곧 요금이다

한글·일본어가 하나라도 섞이면 UCS-2 로 인코딩되어 **70자**가 한 건의 한계다. 한국 사업자는
90바이트를 넘으면 LMS 로 전환해 **요금이 3~4배**가 된다. 그래서 SMS 문구는 앱 안 문구와
별도로 짧게 쓰고(`SmsTemplates`), 경계를 코드로 못박았다(`SmsMessage`).

> 여기서 테스트가 **실제 버그를 잡았다.** `fitsInSingleSms` 는 UTF-16 단위로 세는데(과금
> 기준으로 맞다) `truncate` 는 코드포인트로 세고 있었다. 이모지가 섞이면 자른 뒤에도 여전히
> 한 건을 넘는다. UCS-2 는 BMP 밖 문자를 2단위로 세므로 UTF-16 이 맞고, 대신 서로게이트 쌍을
> 쪼개지 않도록 경계에서 한 칸 물러선다.

## 4. 종류마다 SMS 여부가 다르다

모든 알림을 문자로 보내면 요금 폭탄이고 사용자에게도 소음이다.

| 종류 | 기본 SMS | 이유 |
|---|---|---|
| 주문 접수 · 결제 완료/실패 | ✅ | 돈이 오간 사건 |
| 보안 알림 | ✅ **항상** | 사용자 설정으로도 끌 수 없다 — 공격자가 먼저 알림을 끄고 작업할 수 있다 |
| 배송 변경 · 쿠폰 | ❌ | 앱에서 보면 충분 |
| 채팅 메시지 | ❌ | 대화 한 번에 문자 수십 통이 나간다 |
| 친구 접속 | ❌ | **지금 이 순간**에만 의미가 있다 — 몇 분 뒤 도착하는 문자는 쓸모없다 |

## 5. 중복 발송을 막는 세 겹

Kafka 는 at-least-once 이고 레플리카는 2개다. 방어가 없으면 재전달마다 문자가 한 통씩 더 나간다.

1. **`source_event_id` UNIQUE** — 같은 이벤트로는 알림이 하나만 생긴다. 동시 생성은
   `DataIntegrityViolationException` 을 정상 흐름으로 흡수한다.
2. **컨슈머 그룹 하나** — 레플리카가 늘어도 한 메시지는 한 파드만 받는다
   (채팅 브로드캐스트와 정반대다, [docs/21 §2](21-horizontal-scaling.ko.md)).
3. **`FOR UPDATE SKIP LOCKED` 선점** — 발송 대상을 두 파드가 동시에 집지 않는다.
   아웃박스 폴러에서 결제가 이중 발행되던 것과 같은 구조다([docs/21 §1](21-horizontal-scaling.ko.md)).

알림 생성과 발송을 **분리**한 것도 같은 이유다. 컨슈머가 직접 문자를 보내면 게이트웨이가 느릴 때
Kafka 소비가 밀리고, 전송 실패를 컨슈머 재시도로 처리하면 알림이 중복 생성된다.

## 6. 2단계 인증 — 대부분이 남용 방지 코드다

인증 SMS 는 공격자에게 매력적인 표적이다.

| 공격 | 방어 |
|---|---|
| **문자 폭탄** — 남의 번호로 발송 반복. 요금은 우리가 낸다 | 번호당 60초 쿨다운 + 일일 10회. Redis 에 둔다(레플리카가 2개라 인메모리 카운터는 제한이 2배로 느슨해진다) |
| **무차별 대입** — 6자리는 100만 가지뿐 | 코드당 5회 시도 후 폐기, 5분 만료, 1회용 |
| **DB 유출** | 코드를 **평문으로 저장하지 않는다**. pepper 를 섞은 해시만 남긴다 — pepper 없이 6자리를 해시하면 100만 개 표로 즉시 역산된다 |
| **타이밍 공격** | 상수 시간 비교(`MessageDigest.isEqual`). 일반 `equals` 는 일치하는 앞자리 수만큼 응답이 느려져 한 글자씩 알아낼 수 있다 |

코드는 **어디에도 로그로 남기지 않는다.** 로그를 볼 수 있는 사람이 남의 인증을 통과할 수 있으면
2단계 인증의 의미가 없다.

2FA 는 **인증된 번호가 있어야만** 켤 수 있다. 없이 켜지면 본인도 로그인하지 못한다.

## 7. 프론트엔드

- **알림 종** (`NotificationBell`) — 배지는 안 읽은 개수만 따로 가볍게 가져온다. 목록 전체를
  주기적으로 받으면 알림이 쌓일수록 헤더 하나 때문에 트래픽이 는다.
- **아이콘** (`NotificationIcon`) — 비트맵 대신 `react-icons`(이미 의존성). 해상도 대응 파일을
  따로 관리할 필요가 없고, 색을 CSS 로 바꿀 수 있어 다크모드·읽음 상태에 그대로 대응하며,
  목록 스크롤 시 추가 네트워크 요청이 없다. 결제 실패·보안은 빨강 계열로 먼저 눈에 들어오게 했다.
- **SMS 인증** (`SmsVerification`) — 국가 선택(🇰🇷/🇯🇵)은 **국가코드가 없는 입력을 어떻게
  해석할지**만 정한다. `autocomplete="one-time-code"` 로 OS 가 문자에서 코드를 자동 입력한다.
  형식 검증은 서버에 맡긴다 — 프론트 정규식은 §2 의 유효한 번호들을 막는다.

> 프론트 빌드가 `Module not found: api/notificationApi` 로 깨졌다. `jsconfig.json` 의
> `baseUrl:"src"` 는 **에디터에만** 적용되고 webpack 은 `webpack.config.base.js` 의 alias 로만
> 해석한다. 새 최상위 폴더를 만들면 그곳에도 등록해야 한다.
