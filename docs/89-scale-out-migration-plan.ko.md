## 1. 단계 0 — 목표와 측정

레포에는 **SLO 도 목표 트래픽도 없습니다**(docs/86 §0). 숫자 없이 다음 단계를 고르면 장비 · 관리형의 크기를 짐작으로 정하게 됩니다.

1. **SLO 를 정한다** — 예: 상품 · 검색 GET p99 300ms · 주문 생성 p99 1초 · 월 가용성 99.9%, 행사 피크 초당 N.
2. **스테이징을 운영 모양으로 띄운다** — `external` 오버레이(관리형 데이터 엔드포인트)와 같은 이미지. 실습 수치는 코어를 나눠 쓴 값이라 절대값으로 쓰지 않는다(docs/83).
3. **`ops/53` k6 로 천장을 잰다** — 초당 1,000 → 10,000(docs/87 §5 ②). 각 서비스의 p99 · 오류 · CPU · 커넥션 대기(`hikaricp_connections_pending`) · Kafka 지연을 남긴다.

끝난 조건: 서비스마다 "파드 하나가 몇 요청/초" · "어디서 먼저 막히나" 가 표로 있다. 이 표가 단계 2 · 3 · 4 의 크기를 정한다.

## 2. 단계 1 — 데이터 계층을 노드 밖으로

**순서: Kafka → Redis → PostgreSQL → 백업.** Kafka 가 먼저인 것은 아웃박스 · 사가가 모두 기대고(docs/87 §2), 바꾸는 동안에도 아웃박스가 메시지를 지켜 주기 때문이다(행이 STARTED 로 남는다). PostgreSQL 이 마지막인 것은 되돌리기가 가장 어렵기 때문이다.

목적지는 관리형(docs/87 — MSK · ElastiCache · Aurora) 또는 직접 운영(docs/86 — KRaft 3 · Sentinel · Patroni)이고, 앱 쪽은 이미 `external` 오버레이로 주소만 바꾼다(`patch-external-endpoints.yaml`). ConfigMap 은 `ops/28 --config-only` 로만.

### 2-1. Kafka — 브로커 3 · RF 3

1. **✅ `latest` 컨슈머 정리 — 끝(2026-11-05, 가드 B-110).** 새 클러스터에는 그룹 오프셋이 없다. `latest` 인 그룹은 처음 붙는 순간 **그 전에 들어온 메시지를 건너뛴다.** 남아 있던 일곱 그룹을 `earliest` 로 바꿨다 — 다시 읽어도 안전한 근거는 그룹마다 다르다: catalog `product`(결제 확정 차감 — eventId 처리 원장) · coupon `user-2`(가입 쿠폰 — 같은 이름 · 사용자면 만들지 않음) · `coupon`(쿠폰 보상 — 그 주문이 쓴 쿠폰만) · `coupon-used`(처리 원장) · order `payment-response`(이미 PAID 면 사가가 건너뜀) · `order-delivery-status`(앞으로만 가는 전이) · chat `chat`(같은 `_id` 저장 — 다시 읽은 **10분보다 오래된 레코드는 저장만 하고 뿌리지 · 알리지 않는다**, `chat.consumer.live-window`). coupon 프로듀서 설정에 잘못 들어 있던 컨슈머 키 셋도 지웠다. cart 는 같은 날(docs/38 §2.5). `latest` 는 notification 의 접속 알림 하나만 — 옛 접속을 다시 알리면 안 된다(N-M5). 가드 B-110 이 새 `latest` 와 값을 적지 않은 팩토리(Kafka 기본값이 `latest`)를 빌드에서 막는다. 남은 위험: order 배송 상태의 **배송 취소**(PAID 로 되돌림)는 앞으로만 가는 규칙 밖이라, 새 그룹이 며칠 전 취소를 다시 읽으면 관리자가 배송을 다시 만든 주문이 잠깐 PAID 로 돌아간다(다음 배송 이벤트가 다시 앞으로 보낸다) — order 에는 처리 원장이 없다(docs/21 §3).
2. 새 클러스터에 토픽을 **미리** 만든다 — `ops/02` 를 `REPLICATION=3`, 파티션은 단계 0 의 측정으로. `min.insync.replicas=2`, 프로듀서 `acks=all`(chat 은 이미 명시). 자동 생성(파티션 1)에 기대지 않는다(docs/86 §3-1).
3. **DLT 를 비운다** — 옛 클러스터의 `*.DLT` 는 옮기지 않는다. `ops/56 list` 로 원인을 정리하고 필요한 것은 옛 클러스터에서 다시 보낸 뒤 넘어간다.
4. **전환** — 아웃박스 릴레이가 새 주소로 보내기 시작하면, 컨슈머는 옛 클러스터의 지연 0 을 확인한 뒤 새 주소로. 같은 창에서 `KAFKA_URL` 을 `--config-only` + 재시작. 바꾸는 동안의 메시지는 아웃박스 행으로 남아 있다가 새 클러스터로 나간다.
5. **되돌리기** — 옛 클러스터를 지우지 않고 며칠 둔다. 되돌리면 그 사이 새 클러스터에만 있는 메시지는 아웃박스로 다시 만들 수 없다(이미 PUBLISHED) — 되돌리기는 지연 0 일 때만.

끝난 조건: 브로커 하나를 멈춰도 주문 → 결제 → 배송 사가가 끝난다(브로커 하나를 멈추는 게임데이로).

### 2-2. Redis — 이중화

1. 단일 주소 대신 Sentinel(`spring.data.redis.sentinel.*`) 또는 관리형 클러스터 모드. **클러스터 모드는 여러 키 명령 · Lua 의 키가 같은 슬롯이어야 한다** — 유입 제한 스크립트 · `SingleFlightCache` 의 키를 먼저 확인한다.
2. **잃어도 되는 것과 아닌 것을 가른다** — 캐시(장바구니 · catalog · 필터 메뉴)는 비어도 다시 찬다. **로그인 실패 잠금은 풀린다**(보안 — 전환 공지 · 창을 짧게). 유입 제한은 Redis 가 없으면 통과(fail-open)이므로 전환 순간 제한이 사라진다 — 앞단(Cloudflare) 제한이 받쳐 주는지 먼저 본다.
3. **chat 은 한꺼번에** — 팬아웃 채널(`chat:stomp-fanout`)이 Redis 에 있어, 파드 일부만 새 Redis 로 가면 서로의 메시지를 받지 못한다. chat 은 모든 파드를 같은 창에서 재시작한다.

끝난 조건: Redis 주 노드를 죽여도 로그인 · 장바구니 · 채팅이 수십 초 안에 돌아온다.

### 2-3. PostgreSQL — 이중화와 이전

1. 서비스마다 DB 하나(9개)는 그대로 간다 — 목적지도 DB 마다(docs/88). Flyway 이력(`flyway_schema_history`, catalog 는 `product` 스키마)도 함께.
2. **이전 방법**: 논리 복제(또는 DMS)로 따라잡은 뒤 **짧은 쓰기 정지 창**에서 전환(docs/87 §5 ④). ⚠️ 논리 복제는 **시퀀스를 옮기지 않는다** — 전환 직전 `setval` 로 맞추지 않으면 첫 INSERT 가 기본 키 충돌. 대상 쪽에 운영 백업으로 마이그레이션 리허설을 먼저 돌린다.
3. **풀러** — 관리형이 풀러를 주면 애플리케이션만 그 주소로. transaction 모드는 prepared statement 주의(docs/32 §9 의 `prepareThreshold`), 프로비저닝 · Flyway 는 직결(`ops/25` 경고). 단계 2 의 커넥션 산술이 이것으로 풀린다.
4. **되돌리기** — 옛 PostgreSQL 을 읽기 전용으로 며칠. 역방향 복제를 두지 않으면 전환 뒤의 쓰기는 되돌릴 수 없다 — 그래서 전환 뒤 하루는 큰 배포를 하지 않는다.

### 2-4. 백업 — WAL 을 밖으로

지금은 매일 논리 · 물리 백업이 노드 디스크에 쌓이고 노드 밖 받기가 따로 있다(docs/22 §2). 관리형이면 PITR 이 기본이고, 직접 운영이면 WAL 을 다른 장비로 연속 전송(docs/86 — RPO 5분). 복원 훈련(`restore-drill`)은 목적지에서 다시 켠다.

## 3. 단계 2 — 앱 멀티 노드

1. **노드 3대 이상**(k3s 서버 3 또는 EKS 3 AZ). 서비스 파드는 `topologySpreadConstraints` 로 노드에 흩는다 — `whenUnsatisfiable: ScheduleAnyway`(노드 하나가 NotReady 일 때 Pending 으로 멈추지 않게). PDB(`k8s/70`)는 비우기 때만 지켜 준다.
2. **Eureka 를 뺀다** — k8s Service DNS(게이트웨이 정적 라우트 또는 Spring Cloud Kubernetes). Eureka 쓰기 판정(B-86) · `my-url` 같은 손이 함께 사라진다. 게이트웨이 재시도(B-99)는 인스턴스 목록이 아니라 Service 뒤의 파드로 간다 — 연결 실패 재시도가 같은 Service 로 다시 가는지 확인한다.
3. **커넥션 산술을 다시** — B-32 의 `maxReplicas = 3` · `serverLimit = 200` 은 지금 값이다. HPA 상한을 올리기 전에 가드의 두 상수를 새 값으로 고치고 풀러(단계 1-3) 뒤의 실제 한도로 맞춘다 — 가드가 빌드에서 막는다.
4. **HPA 상한을 올린다** — 단계 0 의 "파드 하나가 몇 요청/초" 로. 노드 자동 증설(Karpenter 등)은 HPA 가 파드를 못 놓을 때를 받는다.
5. **chat** — 이미 1 ~ 3(B-107). 남은 제약은 SockJS xhr 폴백이 같은 파드로 가야 하는데 고정 세션이 없다는 것(docs/21 §2-1). 늘리기 전에 앞단의 고정 세션 또는 WebSocket 만 허용을 정한다.

끝난 조건: 앱 노드 하나를 꺼도(드레인이 아니라 전원) 오류율이 SLO 안.

## 4. 단계 3 — 읽기를 앞단으로

1. **CDN 캐시** — 상품 목록 · 상세 · 홈 GET 을 앞단에서 30 ~ 60초(docs/87 §3-1). ⚠️ 지금 catalog · 게이트웨이 응답에는 **`Cache-Control` 을 다는 곳이 없다** — 앞단 규칙만으로 캐시하면 로그인 응답 · 장바구니까지 섞일 위험이 있다. 캐시해도 되는 경로에만 서버가 `Cache-Control: public, max-age=…` 를 달고 앞단은 그것만 따르게 한다.
2. **재고를 따로** — 카드 응답마다 재고를 다시 읽는다(`HomeViewCache` 도 재고만은 응답마다). 재고만 작은 API 로 빼면 카드 본문은 캐시할 수 있다.
3. **검색을 ES 로** — docs/07 의 로드맵(R-C1 · R-C3): 검색 전체(필터 · 정렬 · 쪽)를 ES 에서, 색인 대기열 · 대사로 정합성. 순서는 배포 → 전체 재색인 → 플래그 비율(docs/74 §3). 되돌리기는 비율 0(재시작 없음). 필터 메뉴의 ES 집계와 nori · kuromoji 품질 확인이 남아 있다.
4. **읽기 복제본** — catalog · 주문 조회만. 지금 코드는 읽기 · 쓰기 데이터소스를 나누지 않는다(catalog 의 두 데이터소스는 데이터 · 배치 메타) — 라우팅을 더해야 하고, 복제 지연이 있는 곳(방금 바꾼 상품 · 방금 만든 주문)은 쓰기 쪽을 읽는다.

끝난 조건: 행사 피크 모양의 부하에서 catalog 파드 수가 단계 0 의 "캐시 없이 필요한 수" 의 몇 분의 1.

## 5. 단계 4 — 쓰기 확장

1. **파티션 수 · 컨슈머 동시성** — 주문 이벤트의 키는 주문 번호(`OrderCompletedKafkaPublisher` 등)라 같은 주문의 순서는 파티션 안에서 지켜진다. ⚠️ **파티션 수를 늘리면 키 → 파티션 대응이 바뀐다** — 진행 중인 주문의 이벤트가 다른 파티션으로 가 순서가 깨질 수 있다. 지연 0 인 창에서 늘리거나, 새 토픽을 만들어 옮긴다. 상태 토픽(`order-saga-state` · `order-timeline`)은 order 토픽과 같은 수로(`ops/02 STATE_PARTITIONS`).
2. **재고 핫스팟** — 인기 상품의 행 잠금에 주문이 몰린다(docs/87 §3-2). gRPC 재고 예약(docs/66)을 출발점으로 원자 차감(Redis Lua 등)을 먼저 받고 DB 확정은 비동기로. 결제 확정 차감은 이미 아웃박스(`product-update`) · 멱등(eventId)이다.
3. **큰 표** — 아웃박스는 이미 월별 파티션(order · pay · user · cart `V1__partition_*`). 주문 · 주문 줄은 수억 건 전에 같은 방식으로. 열 · 인덱스 변경은 docs/85 §8-1(expand → contract · `CREATE INDEX CONCURRENTLY` · `VACUUM (PARALLEL 0)`), 외래 키 열의 인덱스는 order V28 · catalog V22 · cart V8 의 점검을 다른 서비스에도.
4. **샤딩은 그 뒤** — 서비스마다 DB 는 이미 기능 분할이다(docs/88). 한 서비스의 쓰기가 DB 한 대를 넘을 때 그 서비스만 키(고객 · 주문)로 나눈다.

## 6. 단계 5 — 운영 체계

단계 1 과 함께 시작한다 — 나중으로 미루면 이행 중의 장애가 보이지 않는다.

- **관측을 클러스터 밖으로** — 지금은 운영 노드의 compose(B-95 · B-106). 관리형 또는 별도 장비, 경보 전달(B-96)은 그대로. 꼬리 샘플링 상한(B-102)은 트래픽이 늘수록 중요하다.
- **배포** — `ops/28` 손 배포 → 파이프라인(GitHub Actions OIDC → 레지스트리 → Argo CD) · 카나리. ROLLBACK-UNSAFE(B-54) · expand → contract 규칙은 그대로 가져간다. 수동 실행 원칙(B-75)은 운영 러너가 운영 자격증명을 가진 동안 유지한다.
- **게임데이** — 단계마다 끝난 조건을 게임데이로 실제로 끊어 본다: 브로커 하나 · Redis 주 노드 · DB 장애 조치 · 앱 노드 전원.
- **DR** — 처음부터 멀티 리전은 하지 않는다. 백업 · 스냅샷만 다른 리전(docs/87 §3-5).

## 8. 하지 않는 것

- **처음부터 멀티 리전** — 비용 · 복잡도가 크게 뛴다(docs/87 §3-5). 3 AZ(또는 랙 셋) + 다른 리전 백업으로 시작.
- **서비스를 더 잘게 나누기** — 지금의 경계(서비스마다 DB)로 충분하다. 늘어나는 것은 조인 · 정합성의 비용이다(docs/88).
- **측정 전의 장비 · 관리형 구매** — 단계 0 의 표 없이 정하지 않는다.

## 9. 정정 — 다른 세션의 요약에서 고친 것

2026-11-05 다른 세션이 cart 리뷰 끝에 덧붙인 확장 요약을 이 문서의 출발점으로 썼다. 대조해 고친 것:

- "chat-service 는 인메모리 STOMP 브로커라 `replicas: 1` 에 묶여 있다" — **틀림.** 2026-11-01 부터 Redis 팬아웃(B-107)으로 HPA 1 ~ 3 이다. 운영이 1개인 것은 `ops/28 local` 이 `k8s/70` 을 적용하지 않기 때문이고, 남은 제약은 SockJS xhr 폴백의 고정 세션이다(docs/21 §2-1).
- 그 밖의 인프라 서술(데이터 파드 다섯이 `replicas: 1` Deployment · local-path, HPA 최대 3, Kafka `PARTITIONS=3` · `REPLICATION=1`, 풀 5 · B-32, 관측이 운영 노드의 compose)은 매니페스트와 맞다.
- 더한 것: 새 Kafka 클러스터로 옮길 때 문제가 되는 `latest` 컨슈머 8곳(§2-1 — 같은 날 정리, B-110; 그중 하나는 프로듀서 설정에 잘못 든 키였다), 앞단 캐시 전에 필요한 `Cache-Control`(§4), 논리 복제의 시퀀스(§2-3), 파티션 수를 늘릴 때의 순서(§5).
