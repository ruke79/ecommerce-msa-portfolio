# 50. `/browse` 精密分析 — 直したもの、残したもの、レコメンド・セマンティック検索を載せるには

**日本語** | [한국어](50-browse-analysis.ko.md)

背景: 今後、商品レコメンドやセマンティック検索などの機能を追加する前に、`/browse` 画面の問題点と
改善点を徹底的に調べる。目に見える症状は **商品の価格範囲設定 UI のバグ** だった。

価格範囲を辿ってみると**1 つのバグではなく 5 重**になっており、その 5 重がフロント 2 箇所と
サーバー 2 箇所に分かれていた。1 層だけ直すと、症状が形を変えて残る類のものである。

---

## 1. 🔴 価格フィルターが「すべて表示」にひっくり返っていた経路

ユーザーが見る症状は 1 つだった — **価格帯を絞るほど商品が減っていき、ある瞬間にカタログ
全体が戻ってくる。** 原因は 4 つが鎖のようにつながっていた。

| # | どこ | 何 |
|---|---|---|
| ① | `HeadingFilter` | 「500 以上」ボタンが `price=500_` を作る（上限なし） |
| ② | `browse.jsx` | `Number("") \|\| 0` — 空の上限が **0** になる → `500 ~ 0` |
| ③ | `ProductSkuRepository` | `between 500 and 0` → **1 行も出ない** |
| ④ | `SearchService` | 空のリストなら**条件を丸ごと捨てる** → 全商品 |

④ が核心である。条件はこうだった:

```java
if (productIdsFromSku != null && !productIdsFromSku.isEmpty()) {
    builder.and(product.productId.in(productIdsFromSku));
}
```

**「合うものがない」が「制限がない」にひっくり返る。** 価格だけでなく色・サイズも同じクエリを
通るので、在庫にない色を選ぶとやはり全体が出てきた。

`null`（フィルターをかけていない）と `空のリスト`（かけたがマッチなし）は別の意味である。今は分けてある —
空のリストなら不可能な条件（`productId = -1`）を入れる。ES 経路がすでに使っていた方式である。

### 副次効果: 条件のないフルスキャンがなくなった

以前は価格・色・サイズを**1 つも選ばなくても**、その SKU クエリを毎回実行していた。条件が
ないので結果は「全商品の id」であり、それがそのまま `in (...)` に入っていた。商品が増えるほど
大きくなる、何もしないフルスキャン + 巨大な IN 句である。今はかけたときだけ実行する。

### 開いた範囲を表現できるようにした

```sql
-- 以前: どちらか一方でも null なら価格条件が丸ごと消える
where ((:low_price is null or :high_price is null) or b.price between :low_price and :high_price)

-- 現在: 2 つの境界を別々に見る
where (:low_price is null or b.price >= :low_price)
  and (:high_price is null or b.price <= :high_price)
```

そしてフロントは空の境界を**送らない**（0 ではない）。axios が `undefined` をクエリから
除き、サーバーは `null` を「その境界なし」と読む。`500 이상` · `50 이하` が今は表現できる。

## 2. 価格範囲設定 UI — 目に見えていた 3 つ

### ① 価格欄を空にできなかった

```jsx
value={minPrice || (priceParam)?.split("_")[0]}
```

消した欄は空文字列で、**空文字列は falsy** である。そのため URL の古い値がすぐに蘇る —
数字を消すと、その場所に今消した値が再び現れる。入力欄の持ち主を state 1 つに
整理し、外側で URL が変わるとき（Clear All · 戻る · 価格帯ボタン）だけ effect が合わせる。

### ② 上限欄が正の数を拒否していた

```jsx
<input type="number" placeholder="최대" max="0" />
```

上の欄の `min="0"` をコピーしながら**名前だけ変えた**ものである。「最大価格は 0 以下」という制約なので、
正の数を入れた瞬間に入力欄が無効な状態になり、ブラウザのスピナーが 0 より上に上がら
ない。

### ③ どの価格帯を選んだのか分からなかった

5 つのバーボタンに選択表示がなかった。押してもツールチップが出るだけで画面はそのまま —「押せたの
かな」を商品一覧でしか判断できなかった。`aria-pressed` と色で表示する（そして、その
おかげでテストが「何が選択されているか」を問えるようになった）。

> 5 セットコピーされていた `<Tooltip>` ブロックを `PRICE_RANGES` 配列 1 つに畳んだ。②のような
> コピー＆修正のミスが 5 回起こりえた場所である。

## 3. 🔴 有効にならなかったフィルター 2 つ

### 星評価 — 名前を直した後にも 1 層残っていた

docs/40 で `searchParams.get("rate")` → `"rating"` に直した。ところがリクエストを作るとき:

```js
const rating = ratingQuery !== "" ? { rating: Number(ratingQuery) } : {};
return { ..., shipping: shipping.shipping, rating, ... };
//                      ^^^^^^^^^^^^^^^^^ 展開して送る   ^^^^^^ オブジェクトのまま
```

axios はそのオブジェクトを **`rating[rating]=4`** とシリアライズする（実測）。サーバーには `rating` という
パラメータが届かず、Spring は float のデフォルト値 0 でバインドし、`getRating() != 0.0f`
は偽 — 条件が付かない。すぐ隣の `shipping` は展開して送っていたのに、星評価だけ抜けていた。

> このバグを**テストが固定していた。** `expect(...rating).toEqual({ rating: 4 })` — 間違った
> 形を回帰テストで固めていたのである。今は数値であることを検査する。

### 送料無料 — サーバーが受け取るだけで使っていなかった

`SearchParamsRequest.shipping` はフィールドとして存在し、リクエストにも載っていたが、
`buildSearchPredicate` に**その値を読む行がなかった。** チェックボックスは URL を変え、画面は
再描画されるのに結果はそのままである。星評価と同じ形の欠陥である。

条件を付けるが `shipping <= :value` にしておく — 画面は 0（無料）しか送らないが、後で「3,000 ウォン
以下」を付けるときにサーバーを直し直さなくてよい。送料が `null` の商品は除外される:
**分からない値を無料とは言わない。**

### チェック状態が一度もオンにならなかった

```js
const shippingParam = Number(searchParams.get('shipping'));  // 数値
...
defaultChecked={shippingParam === "0"}                       // 文字列と比較
```

`0 === "0"` は常に偽である。URL にフィルターがかかった状態で再読み込みすると、**商品一覧は絞り込まれて
いるのにチェックボックスはオフになっている。** しかも `defaultChecked` なので逆方向も壊れる — 一度オンにした
後に Clear All を押してもチェックが残る。

## 4. 🔴 フィルター名を正規表現として読んでいたコード

`browse.jsx` の `replaceQuery` — 複数選べるフィルター（`색상=Red_Blue`）で値を 1 つ
オン・オフする関数である。中身はこうだった:

```js
const valueCheck = existedQeury?.search(value);
```

[`String.prototype.search`](https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/String/search)
**の引数は RegExp である。** 文字列を渡すとブラウザが正規表現としてコンパイルする。結果:

| 値 | 何が起きるか | |
|---|---|---|
| `"C++"` · `"*Star"` · `"?"` | `SyntaxError: Nothing to repeat` | **フィルターを描画中なので画面が死ぬ** |
| `"A+B"` · `"(Pack)"` | 例外を投げない | 爆発する値とそうでない値が**目で区別できない** |
| `"C.C"` | 静かに間違える | `.` が任意の 1 文字にマッチし、`"CXC"` も「選択済み」 |
| `"Gre"` | 部分一致を選択と読む | `색상=Green` のとき `Gre` がオンになっているように見える |

値はもともと `_` でつなげた**リスト**である。リストとして扱えば上の 4 つが一度に消える —
文字列検索をする理由は最初からなかった。ブランド名は商品データから来るので、これは
**データが埋める入力**であり、URL からも直接入れられる。

## 5. 🔴 ES モードで新商品が検索に出なかった理由

`ProductIndexService` は「バッチ再インデックスの合間のギャップを埋める」という目的で作られた。ところが:

| | 対象 |
|---|---|
| **書き込み**（`ProductDocumentRepository`） | `@Document(indexName = "products")` → インデックス **`products`** |
| **読み取り**（`EsProductSearchService`） | エイリアス **`product-alias`**（実体は `products-<타임스탬프>-products`） |

**書く場所と読む場所が別のインデックスだった。** 新しく登録した商品は、次の全体再インデックスまで検索に
出てこない — このクラスが埋めようとしていたまさにそのギャップである。しかも誰も読まない `products`
インデックスが動的マッピングで静かに作られて育つ。**失敗ログも残らない。保存が成功した
からである。**

今はエイリアスに直接書く。エイリアスがまだなければ（全体再インデックスを一度も実行していないデプロイ）
**書かずに警告だけ残す** — その名前で書くと ES が同じ名前の*インデックス*を作り、そうなると
後でバッチのエイリアスのロールオーバーが**永久に**失敗する（同じ名前のインデックスとエイリアスは共存できない）。

## 6. 直さずに残した構造的な問題

ここからはバグではなく**設計の限界**である。レコメンド・セマンティック検索を載せるときに正面からぶつかる
ものなので、先に書いておく。

### ① ソートがサーバーにない —「価格の安い順」が嘘をつく

`catalog-service` の検索はソートパラメータを受け取らない。ソートは**ブラウザがすでに受け取っている
リストの中で**行う（`sortProducts`）。無限スクロールなので、そのリストは「これまでスクロールした分」である。

つまり**「価格の安い順」は全体の最安値ではなく「自分が見た中での最安値」である。** 10 個しか見ていなければ
10 個の中でのソートである。ユーザーはそれを知る術がない。

ソート・ページングは**同じ層にあるべき**である。サーバーがソートしてページングしないと、ページ境界で
順序が崩れ、それを隠すためにフロントが再ソートする今の形になる。

### ② offset ページング — レコメンド/関連度と根本的に合わない

`offset/limit` はソート基準が安定しているときにしか合わない。関連度スコアやレコメンドスコアは**リクエストごとに
変わりうるので**、3 ページ目を受け取る間に 1 ページ目の商品が押し下げられて再び出てくる。今
`products` を結合するときに `seen` Set で重複を除くコードが、その症状の絆創膏である。

関連度ベースにするなら **search_after（カーソル）ページング**が事実上必須である。

### ③ ファセットに件数がなく、他のフィルターを反映しない

`getColors/getSizes/getDetails` は **`categoryId` 1 つだけで**キャッシュされる。つまり「今の条件で
選べる色」ではなく「このカテゴリのすべての色」である。件数もない。

そのため**選ぶと 0 件になる選択肢**がそのまま残る — 上の ④ のバグがその状態で
「全商品」にひっくり返っていたので、ユーザーの立場ではさらに混乱した。ES の aggregation に
移せば、件数と「今の条件基準」が一緒に解決する。

### ④ アクセシビリティ — フィルターにキーボードで届かない

カテゴリチップは `<span onClick>`、サブカテゴリは `<h5 onClick>` である。Tab で移動できず、
Enter で押せず、スクリーンリーダーがボタンとして読まない。`cursor-pointer` しかないので
**押せるように見えるだけである** — サブカテゴリが実際に動作しなかった頃の
印象と同じ根である（docs/40）。

### ⑤ テキスト検索の Postgres フォールバックは前方ワイルドカードの LIKE である

`like '%검색어%'` はインデックスを使えない。ES を切ると静かにフルスキャンに落ちる。
今は商品数が少ないので表に出ていない。

## 7. 商品レコメンド・セマンティック検索を載せるには

今のコードで**何がすでにできていて、何が妨げているか**だけを書く。

### すでにできていること

- **ES 経路が「関連度検索 → id リスト → Postgres ハイドレーション」に分離されている。**
  この形が重要である — スコアを付ける主体を変えても（BM25 → ベクトル → レコメンドモデル）**呼び出し側が
  そのままである。** `SearchService` は「誰かがくれた id リスト」しか知らない
- ES 障害時のフォールバックがある。新しいエンジンを載せても、落ちたときに画面が死なない
- 韓/英/日のマルチフィールド（`nori` · `standard` · `kuromoji`）がすでにマッピングされている
- エイリアスロールオーバー方式の無停止再インデックスがある — **新しいマッピングを入れる道がすでに開いている**

### 妨げているもの

| | なぜ妨げるか |
|---|---|
| **ソートがサーバーにない**（⑥①） | セマンティック検索の出力は**スコア順**そのものである。その順序をフロントが再ソートしたら、もはや検索結果ではない |
| **offset ページング**（⑥②） | スコアベースの順序ではページがずれる |
| **`ES_CANDIDATE_LIMIT = 1000` の後に Postgres で再フィルター** | ES が上位 1000 件を返し、その後でフィルターをかけると、**フィルターで除かれた分だけ結果が空く。** 今は商品が少ないので見えない。フィルターを ES に下ろすか、候補数を条件に応じて増やす必要がある |
| **行動ログがない** | レコメンドの原料はクリック・カート追加・購入である。`/browse` は今何も残していない |
| **`@Cacheable("search_cache")`** | パーソナライズされた結果を入れると**他人のレコメンドが混ざる。** パーソナライズされた応答はこのキャッシュを通ってはならない |

### 載せる順序（提案）

1. **ソート・ページングをサーバーへ** — 他のすべての前提である。今は `sortProducts` がフロントに
   あり、それを消すのが第 1 段階である
2. **カーソル（`search_after`）ページング** — スコア順をページをまたいで維持する
3. **ファセットを ES aggregation に** — 件数が付き、「0 件になる選択肢」が消える
4. **行動ログ** — `product-viewed` · `cart-added` イベント。すでに Kafka・Outbox があるので
   **新しいインフラは不要である。** レコメンドをいつ作るにしても、そのときにデータがなければならない。最初に
   始めてよい唯一の項目である
5. **セマンティック検索** — `ProductDocument` に `dense_vector` フィールドを追加し、kNN を BM25 と
   混ぜる（ハイブリッド）。エイリアスロールオーバーがあるので**マッピング変更が無停止で出せる。**
   埋め込み生成はインデックスパイプラインの中に置く — 検索時点で作ると応答時間がモデルに縛られる
6. **レコメンド** — 4 番が蓄積された後。「一緒に見た商品」のようなものはモデルなしで集計だけでも始められる

> ⚠️ 5 番を 1・2 番より先にやると、**セマンティック検索の順序が画面でひっくり返る。** ベクトル検索が
> うまく動いても、ユーザーは「検索がおかしい」と見る。順序が重要である。

| ✅ 修正 | 価格欄を空にできなかったこと · 上限欄の `max="0"` · 価格帯の選択表示 |
| ✅ 修正 | フィルター値を正規表現として読んでいた `replaceQuery` |

### 🔴 カテゴリを選ぶと 500 — `CAST(:ids AS BIGINT[])`

`/browse?category=1` が 500 だった。色・サイズメニューのネイティブ SQL が

```sql
where a.product_id IN (SELECT unnest(CAST(:productIds AS BIGINT[])))
```

だったが、Hibernate はコレクションパラメータを `(?, ?)` に展開する。PostgreSQL は
`CAST((1, 2) AS BIGINT[])` を受け取り、**"cannot cast type record to bigint[]"** で拒否する。
このクエリはカテゴリ id があるときだけ実行され（`getColors(categoryId)`）、しかも**そのカテゴリに
商品があって初めて**リストが空でなくなる。空の DB では通るのでコンテナ起動テストが捕まえ
られず、本番に商品が入ってから初めて爆発した。ローカルの PostgreSQL に接続して `findColorsByProductId(
List.of(1L, 2L))` で再現した。

`in (:productIds)` に変えた — Hibernate の展開がそのまま正しい SQL になる。空のリストはサービスが
あらかじめ除く（`in ()` は SQL エラー）。おまけに、カテゴリがないときに `null` を渡していたのは
`unnest(NULL)` = **空のリスト**なので、全体画面の色・サイズメニューが常に空だった —
`findAllColors / findAllSizes` に分けた。

**ガード**: `CatalogServiceApplicationTests.colorAndSizeMenuQueriesRunWithIds` — 空でない
id リストで実際の PostgreSQL 上で実行する（`-PwithContainers`）。データは不要である。古い SQL は
パース段階で死んでいた。

**ガード**: `SearchServiceUnitTest`（+3）· `browse.test.jsx`（+8）· `HeadingFilter.test.jsx`（+10）。
サーバー 2 件とフロント 3 件は**古いコードに戻して失敗することを確認**した。

### 🔴 カテゴリを選ぶと他のフィルターがすべて消えていた — そしてその逆も（2026-09 追加）

ユーザー報告: `/browse?category=3` で「選択するとフィルターがちゃんと効かない」。

ハンドラーは自分のフィルター **1 つだけ**を渡す — `filter({ category })`。残りの 12 個は
`undefined` である。元のトグルは値がなければ何もしなかったが、「同じ値をもう一度押してオフにする」
を付けたコミット（24d06b4）で、`!param` なら**消す**ように統合された。それ以降、何を押しても
**それ 1 つだけが残った**: `?category=3` で色を選ぶとカテゴリが外れて全体が出て、
検索語を入れてカテゴリを選ぶと検索語が消えた。カテゴリは一瞬かかって次のクリックで
外れるので、「効かない」ように見えた。

`applyFilter(searchParams, changes)` に切り出してルールを固定した: **言及しないフィルター
（`undefined`）には触れない**、空の値（`{}`・`""`・`null`）は消す、同じ値はオフにする、違う
値はオンにする。上位カテゴリが*別のものに変わったら*下位は消す — 前の上位の下位と AND で
結ばれると何も出てこない。上位を*オフにするだけ*なら下位は残る（下位だけでも有効な条件）。
おまけにパンくずの `searchParams.get('category') !== ""` — なければ `null` なので常に真で、
空の矢印が残っていたもの — も直した。

**ガード**: `browse.test.jsx` `applyFilter` 9 件。サーバー側（`SearchService.buildSearchPredicate`）は
`category=3` を `product.category.categoryId = 3` として正しくかけていた — 今回の件はすべて
フロントである。

## 9. サブカテゴリーのフィルターが見当違いの商品を表示していた件 — データだった（2026-09-27）

「fashion → men's clothing」を押すと、ベッドフレーム・『アラバマ物語』・チョコチップクッキーが出てきた。他のサブカテゴリーも同じだった。

- **コードは正しかった。** フロントは `subCategory=<id>` を送り、サーバーは `product_subcategory` で正しく絞り込んでいた。
- **シードデータがランダムだった。** `product_subcategories.csv` の紐付け 499 件のうち **404 件（81%）が商品と別カテゴリー**の
  サブカテゴリーで（オリーブオイルが「テーブル・スマートフォン・飲料」）、同じカテゴリー内の紐付けも合っていなかった。正しい
  サブカテゴリーに入っていた商品は 250 個中 87 個だけだった。

直したもの：

| 対象 | 方法 |
|---|---|
| シード CSV | 商品名 → **同じカテゴリーの**サブカテゴリーで作り直した（220 件、196 商品）。合うものがない商品（TV・スピーカー・オリーブオイル・ラグ …）は紐付けない — サブカテゴリーは任意である |
| 本番データ | `V16__fix_product_subcategory_links.sql` — シード商品（slug で識別）は新しいマッピングだけを残し、すべての商品から別カテゴリーの紐付けを消し、足りない紐付けを追加する。スキーマ変更なし、2 回実行しても同じ。旧 CSV を実際の PostgreSQL 16 に入れて実行して確認（別カテゴリーの紐付け 404 → 0、管理者が登録した商品の正しい紐付けは維持） |
| 登録経路 | `ProductService` が、商品のカテゴリーに属さないサブカテゴリーを拒否する |
| ガード | `SeedCsvConsistencyTest`（CSV のすべての紐付けが同じカテゴリー — 旧 CSV で失敗することを確認）、`ProductServiceTest` |

⚠️ 検索結果は Redis（`search_cache`、60 分）にキャッシュされる。デプロイ直後の 1 時間は古い結果が見えることがある。
