## 0. 原則 — 構造的な事実と環境的な数値を区別する

「パフォーマンステストは本番でしか意味がない」という言葉は半分だけ正しい。パフォーマンスの問題には 2 種類あり、
**一方はノートパソコンで正確に捉えられる。**

| | 構造的な事実 | 環境的な数値 |
|---|---|---|
| 例 | SQL クエリの **個数**、コネクションプールの **総和**、キャッシュヒットの **有無** | レイテンシ ms、スループット RPS、GC の一時停止 |
| ハードウェア依存 | ❌ なし | ✅ 絶対的 |
| ローカルでの測定 | **正確** | 参考用（相対比較のみ） |
| CI での固定 | **可能** | 不可能（不安定） |

このドキュメントは **構造的な事実だけをビルドで固定** し、環境的な数値については測定ツールだけを提供する。

## 1. ローカルで捉えられるもの / 捉えられないもの

**✅ ローカルで十分なもの**
- **N+1 クエリ** — 商品 20 件に対して SQL が 1 回か 81 回かは、どこで測っても同じ
- **コネクションプールの見積もり** — 算数である。`データソース × プール × レプリカ ≤ max_connections`
- **キャッシュのキー・TTL・無効化** — ロジックの問題
- **インデックスの使用有無** — `EXPLAIN` が Seq Scan か Index Scan か
- **Kafka コンシューマーの処理構造** — `max.poll.records`、concurrency、バッチコミット
- **エラーの変曲点** — 並行数 N で 5xx が出始めるなら、それは構造的な限界だ

**❌ ローカルの数値を信じてはいけないもの**
- 絶対的なレイテンシ/スループット（CPU・ディスク・ネットワークが異なる）
- サービス間のネットワーク遅延（ローカルは事実上 0 → タイムアウト値の検証は不可）
- ~~実データのカーディナリティ~~ → **§5 で解決。** シード CSV を増殖させれば、分布を保ったまま
  規模を大きくできる。ただし **実トラフィックのクエリ分布**（どのカテゴリをどれくらい頻繁に見るか）は
  依然としてローカルでは分からない
- 持続的な負荷下での GC の挙動

## 2. 発見 ① — 商品一覧の N+1（実測）

`Product` は LAZY コレクションを 4 つ持つ: `subcategories`・`details`・`questions`・`skus`。
そして `ProductMapper.toDto` が **4 つすべてを走査** する。バッチフェッチがなければ

```
商品 N 件の取得 = 1(一覧) + 4N(コレクション) クエリ     → 20 件なら 81 回
```

コードにはこんな痕跡が残っていた:

```java
//@BatchSize(size = 10) // 10 個の Product の details を一度に取得
```

**コメントアウトされたまま。** 問題に気づいた人はいたが、有効化はされなかった。
`ProductSku` だけは、今回の作業の序盤に `MultipleBagFetchException` を直した際に偶然付いただけだ。

### 検証方法 — 時間ではなく個数を測る

`ProductQueryCountTest` が Hibernate の `Statistics.getPrepareStatementCount()` で、実際に発行された
SQL の数を数える。3 つの点を見る:

| 検査 | 捉えるもの |
|---|---|
| 商品取得の SQL 数 < 商品数 | 「商品ごとに最低 1 回」という N+1 の定義への違反 |
| 4 つのコレクションに `@BatchSize` の宣言が存在 | データが少なくて偶然通過するケース |
| 繰り返し呼び出してもクエリ数が増えない | キャッシュ・フェッチ戦略が意図どおりに動作しているか |

2 つ目の検査が重要だ — 1 つ目だけだと、**テスト DB の商品が少ないときに静かに通過** してしまう。

### 結果

```
修正前:  FAIL  Product.subcategories に @BatchSize がない
修正後:  PASS  3/3
```

4 つのコレクションすべてに `@BatchSize(size = 20)` — 一覧ページのサイズに合わせた。これでコレクションごとに 1〜2 回の
`IN (...)` クエリにまとめられる。

## 3. 発見 ② — コネクションプールの総和がサーバーの上限を超過（算数）

プールの設定が **どのサービスにもなかった。** つまりすべて HikariCP のデフォルト値 10 である。総和を数えると:

| | 計算 | 結果 |
|---|---|---|
| PostgreSQL データソース | user 1 + catalog 2 + cart 1 + order 1 + pay 1 + coupon 1 + chat 1 | **8 個** |
| レプリカ 1 のとき | 8 × 10 | 80 |
| HPA `maxReplicas: 3` なら | 8 × 10 × 3 | **240** |
| PostgreSQL のデフォルト `max_connections` | | **100** |

**レプリカが 2 つになるだけで 160 > 100 となり超過する。** そのとき現れる症状は「遅くなる」ではなく、
遅れて起動した Pod の `FATAL: sorry, too many clients already` — 起動失敗だ。HPA が負荷に反応して
スケールアウトするまさにその瞬間に爆発する点が特に悪い。

### 対処

```yaml
hikari:
  maximum-pool-size: ${DB_POOL_SIZE:5}
  minimum-idle: ${DB_POOL_MIN_IDLE:2}
  connection-timeout: 5000        # プール枯渇時に 30 秒待たず素早く失敗
  leak-detection-threshold: 20000 # 返却されていないコネクションをログに出す
  max-lifetime: 1200000
```

`8 × 5 × 3 = 120`。サーバーの `max_connections` を **200 に上げることが前提** だ
（デフォルトの 100 では足りない）。`postgresql.conf`:

```
max_connections = 200
```

> プールは大きければ速いわけではない。PostgreSQL はコネクションごとにプロセスを 1 つ立ち上げるので、プールを大きくすると
> DB 側のメモリとコンテキストスイッチも一緒に増える。コア数の 2〜4 倍が通常の推奨ラインで、
> それ以上は PgBouncer のようなコネクションプーラーで多重化するほうが正しい。

`connection-timeout: 5000` も意図的だ。デフォルトの 30 秒だと、プールが枯渇したときに **リクエストスレッドを 30 秒ずつ
拘束し**、Tomcat のスレッドまで枯渇させる — 1 つのサービスの DB 遅延が全体停止に波及する経路だ。

### ガードレール

`ConfigurationGuardrailTest` の B-32 が `データソース × プール × レプリカ ≤ 200` をビルドごとに検査する。
データソースを追加したりプールを大きくしたりすると、総和が自動的に再計算される。

## 4. 負荷ハーネス — `ops/14-load-test.sh`

並行数を段階的に上げながら、レスポンスコードの分布とパーセンタイルを記録する。curl ベースなので k6/JMeter の
インストールを前提としない。

```bash
GATEWAY=https://localhost:8000 ./ops/14-load-test.sh
CONCURRENCY="1 5 10 20 50" DURATION=15 ./ops/14-load-test.sh
```

### 読み方

- **429 は正常だ** — レートリミッターが仕事をしているということ（ops/06 が検証するその動作）。
- **5xx/無応答が特定の並行数で突然** 現れるなら、構造的な限界だ。疑う順番:
  1. DB コネクションプールの枯渇 — ログの `Connection is not available, request timed out`
  2. サーキットブレーカーの開放 — `/actuator/metrics/resilience4j.circuitbreaker.state`
  3. Tomcat スレッドの飽和 — `/actuator/metrics/tomcat.threads.busy`
- **p99 が並行数に対して線形** ならキューイング、**階段状に跳ねる** ならタイムアウト/再試行だ。

絶対的な数値は本番には移植できない。**同じマシンでコード変更の前後を比較** するときにだけ使うこと。


## 5. 大量データの生成 — `ops/tools/generate-catalog-data.py`

§1 で「実データのカーディナリティはローカルでは作れない」と書いたが、**部分的に間違っていた。**
リポジトリにはすでに実際のシード CSV がある（商品 250 · SKU 509 · サイズ 1,290）。それを
**テンプレートとして増殖** させれば、値の分布を保ったまま規模だけを大きくできる。

```bash
# 5 万商品（55 万行）を 25 秒でロード
./ops/tools/generate-catalog-data.py --products 50000 \
    --copy "postgresql://product:pw@host:5435/productdb"

# バッチジョブでロード経路まで検証したい場合は CSV で
./ops/tools/generate-catalog-data.py --products 50000 --out /tmp/bigcsv
```

値をでっち上げないことが肝心だ。`product-00001` のような合成文字列は、インデックスの選択度と
シリアライズのコストを歪める。このジェネレーターはシードのブランド名・説明文・画像パスを再利用し、
SKU/サイズの比率もシードから **実測して** それに従う（商品あたり SKU 2、SKU あたりサイズ 3）。

`created_at` は 730 日に均等にばらまく — 1 つの日付に集中すると、パーティションプルーニングの効果を
測定できないからだ（[docs/09](09-postgresql-partitioning-sharding.md)）。

### 作る過程で明らかになったスキーマの事実 2 つ

**① `ProductSku.color` が `@OneToOne` だった — 設計ではなくマッピングのミス。**
JPA の規約上、`@OneToOne` の所有側の FK には **UNIQUE** が付くため、Hibernate が `color_id` に
グローバルな UNIQUE を掛ける。1 つの色の行をただ 1 つの SKU しか参照できないということだ。シードが
SKU 509 = 色 509 で制約を **ちょうど飽和** させていたため、商品を 1 つ追加しただけで
`duplicate key value violates unique constraint` で弾かれた。

これが意図された設計なのかミスなのかは、リポジトリの残りのコードが教えてくれる — どれも色を
**共有の語彙** として扱っていた:

| 根拠 | 共有を前提としているという意味 |
|---|---|
| `ProductSkuRepository.findColorsByProductId` → `select DISTINCT b.color` | DISTINCT は色が繰り返されるときにしか意味がない |
| `ProductColorRepository.findByColor(String)` → `Optional<ProductColor>` | 色名が行を識別する = マスター語彙 |
| `frontend/.../ColorsFilter.jsx` | 色フィルターのファセット — 色 1 つにつき商品 1 つなら無意味 |
| `ProductColor` 内のコメントアウトされた `@OneToMany(mappedBy="color")` | 原作者も「複数が 1 つを参照する」モデルを意図していた痕跡 |

そこで `@ManyToOne` に正し、既存 DB の制約は
[`V4__relax_product_sku_color_unique.sql`](../catalog-service/src/main/resources/db/migration/V4__relax_product_sku_color_unique.sql)
で解除する。既存データは色の値がすべて一意なので、**緩める方向** の変更はどの行にも違反しない。

このマイグレーションからさらに 2 つ学んだ:

- **制約名をハードコードできない。** Hibernate が作った名前は
  `ukf0mvdc9aqf8t23p9di0hn9lpy` のようなスキーマ由来のハッシュで、環境ごとに異なる。名前ではなく
  **定義**（`product_sku` の `color_id` 単一カラムの UNIQUE）で `pg_constraint` から探して削除する。
- **Flyway は Hibernate より先に回る。** このテーブルはマイグレーションではなく `ddl-auto` が
  作るため、空の DB（Testcontainers・新規環境）ではマイグレーションの時点でテーブルがまだ
  存在しない。ガードなしで実行したら `relation "product.product_sku" does not exist` でコンテキストの
  ロードが丸ごと壊れた — テスト 4 件がすべて失敗。`to_regclass(...) IS NULL` なら何もしないように
  し、新規スキーマの `color_id` インデックスはエンティティの `@Table(indexes=...)` が作るように移した。
  （UNIQUE 制約がインデックスを兼ねていたため、制約だけを消すと色の結合が Seq Scan になる。）

回帰テスト（`ProductQueryCountTest.색상은 여러 SKU 가 공유할 수 있어야 한다`）は、アノテーションの
宣言と **DB に UNIQUE が残っていないか** の両方を見る — `ddl-auto: update` は既存の
制約を削除しないため、エンティティだけを直しても実環境は良くならないからだ。

**② `product_sku.images` は `text[]` だ。** CSV には `"a.jpg,b.jpg"` として入っているため、
`COPY` が配列リテラルとしてパースしようとして失敗する。バッチジョブは DTO で split して渡すので、
この違いが表に出ない。ジェネレーターが配列リテラルに変換する。

どちらも、データを **大量に入れてみるまでは** 出会うことのない事実だ。

### 5.1 数千万件 — 百貨店型の分類 · チャンク投入 · 容量の実測 (2026-10-01)

2,000 万件で負荷テストをしようとして、生成器の限界が 4 つ見つかった。直したうえでローカルの PostgreSQL 16 に **50 万件を実際に入れて**
測り、2,000 万件に外挿した。

| 問題 | 影響 | 直したこと |
|---|---|---|
| すべての行をメモリに載せてから一度に COPY | 2,000 万件なら行は 1 億 3 千万 — メモリで止まる | 2 万件のチャンクごとに作って COPY · コミット。メモリはチャンク 1 つ分。途切れたら `--resume` が続きから入れる |
| シードの分類(小分類 15)に増殖 | 小分類 1 つに 130 万件 — 現実と違うボトルネックを測る | 大型ショッピングモール型の分類を内蔵(大分類 20 · 小分類 99)。シードと同名の大分類はその id を使い、小分類を足す。オプション(衣料サイズ · 靴のサイズ · ストレージ容量 · 重量 · 入数 · 書籍の形態)と価格帯が小分類ごとに違う |
| `--copy` が画像にクラスパスのパス(`images\food\…`)を入れていた | 投入した商品の画像が画面ですべて壊れる | シードのバッチが S3 に上げた URL を大分類ごとに再利用 |
| `--copy` が V17 の `sku_code` を空のままにしていた | カート · 注文がサイズ別 SKU コードなしで記録される | V17 の関数と同じ規則で生成器が埋める(DB 関数を 6 千万行に走らせない) |

ほかに: 販売数はロングテール(パレート)、価格は対数一様、ブランドは大分類ごとに 400。投入後に ID 列のシーケンスを入れた id の後ろへ
動かす — そうしないと管理者の登録がいつか同じ id にぶつかる。`--purge` で生成範囲だけを消す。

**実測 — 50 万件(インデックスがある状態で投入、運用と同じ条件)**

| テーブル | 商品あたりの行 | テーブル + インデックス |
|---|---|---|
| product | 1 | 330 MiB |
| product_sku | 1.70 | 318 MiB |
| product_size | 3.02 | 301 MiB |
| product_subcategory | 1 | 56 MiB |
| **合計** | | **1.0 GiB = 商品あたり約 2.1KB** |

インデックス 14 個が全体の約 45% を占める。最大は `uq_product_size_sku_code`(90 MiB)と `idx_product`(名前 · ブランド · slug ·
カテゴリの複合、84 MiB)。投入速度は 4 コア x86 · `synchronous_commit=off` で毎秒約 3,000 件。

**2,000 万件への外挿** — `--estimate` が同じ計算をする。

| 項目 | 値 |
|---|---|
| 行数 | 商品 2,000 万 · SKU 3,400 万 · サイズ 6,040 万 · 紐づけ 2,000 万 |
| PostgreSQL | **約 39 GiB**(投入中の WAL まで約 59 GiB の空きが必要) |
| Elasticsearch | 約 19〜30 GiB(推定 — 測っていない) |
| 投入時間 | 4 コアで約 2 時間、2 コアのノードで 6〜9 時間 |

**⚠️ 運用ノードにそのまま入れてはいけない理由**

- ノードは 2 OCPU / 12GB、ブートボリュームは無料枠の合計 200GB。DB + インデックスだけで 60〜90GB になる。
- PostgreSQL ポッドのメモリ上限は 512Mi、Elasticsearch のヒープは 512MB(k8s/90)。39 GiB のテーブルをそのメモリで読めば、ほぼすべての
  照会がディスクに行く — 測るのはアプリではなくディスクになる。512MB のヒープで 2,000 万件(nested を含め約 7 千万の Lucene 文書)を
  索引すると、メモリ不足で止まる可能性が高い。
- 投入する数時間のあいだ、運用トラフィックとディスクを奪い合う。バックアップの CronJob もそのぶん大きくなる。

推奨: 2,000 万件は **別の負荷テスト環境**(PostgreSQL のメモリ 4GB 以上、ES ヒープ 2〜4GB)で。運用ノードで測るなら **200 万件**(約 4 GiB +
索引 2〜3 GiB)が現実的な上限。終わったら `--purge` のあと `VACUUM`。

## 6. 実測 — 5 万商品での実行計画

ロード後に `EXPLAIN (ANALYZE)` で測った結果。これで **インデックスの選択度** を実際に見られる。

| クエリ | 結果 | 判定 |
|---|---|---|
| カーソルページネーション（`product_id < N ORDER BY DESC LIMIT 21`） | `Index Scan Backward`、0.13ms、13 buffers | ✅ 設計どおり |
| **名前検索 `LIKE '%Olive%'`** | **`Seq Scan` 8ms、48,800 行を破棄** | 🔴 §6.1 |
| カテゴリの結合 | 21 件の返却に 120 行をスキャン（読み取り増幅 5.7 倍） | 🟠 §6.2 |

### 6.1 名前検索がフルスキャンである（CAT-1 の実際のコスト）

```
Seq Scan on product (actual time=0.021..7.960 rows=1200)
  Filter: ((name)::text ~~ '%Olive%'::text)
  Rows Removed by Filter: 48800
```

[docs/06 CAT-1](06-catalog-search-issues.md) が「検索が Elasticsearch を使っていない」と
指摘したその経路だ。5 万件で 8ms は耐えられそうに見えるが、**線形に増える** — 50 万件なら
80ms、しかもこれはキャッシュが空のときではなく **すべてのリクエストごと** だ。先頭ワイルドカード（`%...`）なので
B-tree インデックスでは解決しない。選択肢は 3 つ:

1. **ES に切り替える** — すでに準備はできている（`SEARCH_ENGINE=es`、[ops/03](../ops/03-enable-es-search.sh)）。王道。
2. `pg_trgm` GIN インデックス — ES なしで部分一致をインデックス化する。中規模までは十分だ。
3. 前方一致検索に制限する（`LIKE 'Olive%'`）— そうすれば通常の B-tree で解決するが、UX が変わる。

**この測定がなければ「いつか遅くなるだろう」という推測だった。** 今は数字がある。

### 6.2 カテゴリ結合の読み取り増幅

カーソルページネーションが `product_id` で先にソートしてからカテゴリで絞り込むため、21 件を返すのに
120 行を読む（5.7 倍）。カテゴリが 5 個なので平均 5 倍という計算 — 算数と合う。カテゴリが増えたり
まばらなカテゴリを照会したりすると、増幅は大きくなる。`(category_id, product_id DESC)` の複合インデックスが
王道の解決策だが、実トラフィックのカテゴリ分布を見て決めることなので、ここでは **測定だけ** しておく。

## 7. まだ測定していないもの（正直に）

| 項目 | なぜやらなかったか |

| GC チューニング | 持続的な負荷が必要。現在はヒープの上限だけを指定 |
| Kafka コンシューマーのスループット | 構造は検証したが、バッチサイズの最適値は実メッセージのサイズ次第だ |
| ES クエリのパフォーマンス | nori 未適用の状態なので、韓国語検索の品質・パフォーマンスともに未測定 |
| フロントエンドのバンドルサイズ | CI はビルドするが、サイズ予算はない |

## 8. まとめ

ローカルでのチューニングで **2 つの実際の欠陥** を捉えた。どちらも本番では、負荷がかかった瞬間になって初めて
表に出ていたであろう類のものだ:

| 欠陥 | 症状が現れていたはずの時点 | 現在 |
|---|---|---|
| 商品一覧の N+1（1+4N） | カタログが大きくなるほど一覧 API が遅くなる | `@BatchSize` + クエリ数テスト |
| コネクションプールの総和 240 > 100 | **HPA がスケールアウトする瞬間** に Pod の起動失敗 | プール 5 + 総和のガードレール |
| 名前検索のフルスキャン | カタログの規模に比例して線形に遅くなる | 測定完了（§6.1）— ES への切り替えまたは `pg_trgm` |
| SKU が色の数（509）に縛られる | 商品を増やした瞬間にロード失敗 | 制約を文書化、ジェネレーターが色も一緒に生成 |

前の 2 つは時間ではなく **個数を数えて** 見つけたので、CI に固定した。
後の 2 つは **規模を大きくしてみて初めて** 表に出た — シード 250 件ではどちらも見えない。

> ここで得た教訓: 「ローカルではパフォーマンスは分からない」という通念は、実際には **三層** になっている。
> 構造的な事実は今すぐ測れ（クエリ数・プールの算数）、データに依存する事実は
> **シードを増殖させれば** 測れ（インデックスの選択度）、トラフィックに依存する事実だけが
> 本当に本番を必要とする（クエリ分布・GC・実レイテンシ）。前の二層をローカルで取り除けば、
> 本番で出くわす驚きはその分だけ減る。
