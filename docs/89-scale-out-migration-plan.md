# 89. 単一ノードから数百万人へ — 段階的な移行計画

**日本語** | [한국어](89-scale-out-migration-plan.ko.md)

> 📝 **状態（2026-11-05）— 判断材料であり決定ではない。**「今の構造で数百万人まで伸ばすには、何をどの順で変えるか」をリポジトリ（2026-11-05）のマニフェスト · ガード · 実測から整理しました。**目標構成** はすでにあります — AWS 版 [docs/87](87-aws-at-scale.md)、自前データセンター版 [docs/86](86-self-hosted-datacenter.md)、機能分割の限界 [docs/88](88-federation-tradeoffs.md)、レプリカを増やすときの安全 [docs/21](21-horizontal-scaling.md)。この文書はその目標まで **今のノード一台から移っていく順序** — 各段階の入る条件 · 無停止の手順 · 戻し方 · 終わった条件 — を扱います。規模の仮定（会員 300 万 · 催事ピーク毎秒 5,000 〜 10,000）は docs/87 §0 をそのまま使います。

|---|---|---|---|---|
| **0** 目標 · 測定 | SLO を決め、ステージングで今の天井を測る | — | p99 · エラー率の目標 · 毎秒処理の天井が数字である | 該当なし |

## 0. 今なにが先に壊れるか

## 1. 段階 0 — 目標と測定

リポジトリには **SLO も目標トラフィックもありません**（docs/86 §0）。数字なしに次の段階を選ぶと、機材 · マネージドの大きさを当て推量で決めることになります。

1. **SLO を決める** — 例: 商品 · 検索 GET p99 300ms · 注文作成 p99 1 秒 · 月間可用性 99.9%、催事ピーク毎秒 N。
2. **ステージングを本番の形で立てる** — `external` オーバーレイ（マネージドのデータエンドポイント）と同じイメージ。実習の数値はコアを分け合った値なので絶対値として使わない（docs/83）。
3. **`ops/53` の k6 で天井を測る** — 毎秒 1,000 → 10,000（docs/87 §5 ②）。サービスごとの p99 · エラー · CPU · コネクション待ち（`hikaricp_connections_pending`）· Kafka の遅延を残す。

終わった条件: サービスごとに「Pod 一つで何リクエスト/秒」「どこで先に詰まるか」が表になっている。この表が段階 2 · 3 · 4 の大きさを決める。

## 2. 段階 1 — データ層をノードの外へ

**順序: Kafka → Redis → PostgreSQL → バックアップ。** Kafka が先なのは、アウトボックス · サガがすべて頼っていて（docs/87 §2）、切り替えの間もアウトボックスがメッセージを守ってくれるから（行が STARTED のまま残る）。PostgreSQL が最後なのは戻すのがいちばん難しいから。

移行先はマネージド（docs/87 — MSK · ElastiCache · Aurora）または自前運用（docs/86 — KRaft 3 · Sentinel · Patroni）で、アプリ側はすでに `external` オーバーレイでアドレスだけを変える（`patch-external-endpoints.yaml`）。ConfigMap は `ops/28 --config-only` だけで。

### 2-1. Kafka — ブローカー 3 · RF 3

1. **✅ `latest` のコンシューマーの整理 — 済み(2026-11-05、ガード B-110)。** 新しいクラスターにはグループのオフセットがない。`latest` のグループは最初につながった瞬間に **それ以前に入ったメッセージを飛ばす。** 残っていた七つのグループを `earliest` にした — 読み直しても安全な根拠はグループごとに違う: catalog `product`(決済確定の減算 — eventId の処理台帳)· coupon `user-2`(加入クーポン — 同じ名前 · 利用者なら作らない)· `coupon`(クーポンの補償 — その注文が使ったクーポンだけ)· `coupon-used`(処理台帳)· order `payment-response`(すでに PAID なら Saga が飛ばす)· `order-delivery-status`(前にしか進まない遷移)· chat `chat`(同じ `_id` で保存 — 読み直した **10 分より古いレコードは保存だけで配信 · 通知しない**、`chat.consumer.live-window`)。coupon のプロデューサー設定に誤って入っていたコンシューマーのキー三つも消した。cart は同じ日(docs/38 §2.5)。`latest` は notification の接続通知だけ — 古い接続を再通知してはいけない(N-M5)。ガード B-110 が新しい `latest` と値を書かないファクトリー(Kafka の既定が `latest`)をビルドで止める。2026-11-07: order の配送状態にも処理台帳（V30 — 配送番号 · 状態）を付けた — 同じ配送の同じ状態は一度だけ、配送を作り直すと配送番号が新しくなるので新しい配送は除かれない（以前のリスク: 配送キャンセル（PAID に戻す）は前にしか進まない規則の外で、新しいグループが数日前のキャンセルを読み直すと、作り直した配送の注文が PAID に戻った）。
2. 新しいクラスターにトピックを **前もって** 作る — `ops/02` を `REPLICATION=3`、パーティションは段階 0 の測定で。`min.insync.replicas=2`、プロデューサー `acks=all`（chat はすでに明示）。自動作成（パーティション 1）に頼らない（docs/86 §3-1）。
3. **DLT を空にする** — 旧クラスターの `*.DLT` は移さない。`ops/56 list` で原因を整理し、必要なものは旧クラスターで再送してから移る。
4. **切り替え** — アウトボックスのリレーが新しいアドレスへ送り始めたら、コンシューマーは旧クラスターの遅延 0 を確かめてから新しいアドレスへ。同じ枠で `KAFKA_URL` を `--config-only` + 再起動。切り替え中のメッセージはアウトボックスの行として残り、新しいクラスターへ出ていく。
5. **戻し方** — 旧クラスターを消さずに数日残す。戻すと、その間新クラスターにだけあるメッセージはアウトボックスで作り直せない（すでに PUBLISHED）— 戻すのは遅延 0 のときだけ。

終わった条件: ブローカーを一つ止めても注文 → 決済 → 配送のサガが終わる（ブローカーを一つ止めるゲームデーで）。

### 2-2. Redis — 冗長化

1. 単一アドレスの代わりに Sentinel（`spring.data.redis.sentinel.*`）またはマネージドのクラスターモード。**クラスターモードでは複数キーのコマンド · Lua のキーが同じスロットでなければならない** — 流入制限スクリプト · `SingleFlightCache` のキーを先に確認する。
2. **失ってよいものとよくないものを分ける** — キャッシュ（カート · catalog · フィルターメニュー）は空になっても埋まり直す。**ログイン失敗のロックは解ける**（セキュリティ — 切り替えの告知 · 枠を短く）。流入制限は Redis がなければ通す（fail-open）ので、切り替えの瞬間に制限が消える — 前段（Cloudflare）の制限が支えるか先に見る。
3. **chat は一斉に** — ファンアウトのチャネル（`chat:stomp-fanout`）が Redis にあるので、Pod の一部だけが新しい Redis に行くと互いのメッセージを受け取れない。chat は全 Pod を同じ枠で再起動する。

終わった条件: Redis のプライマリを落としてもログイン · カート · チャットが数十秒で戻る。

### 2-3. PostgreSQL — 冗長化と移行

1. サービスごとに DB 一つ（9 個）はそのまま — 移行先も DB ごと（docs/88）。Flyway の履歴（`flyway_schema_history`、catalog は `product` スキーマ）も一緒に。
2. **移行方法**: 論理レプリケーション（または DMS）で追いついてから **短い書き込み停止の枠** で切り替え（docs/87 §5 ④）。⚠️ 論理レプリケーションは **シーケンスを移さない** — 切り替え直前に `setval` で合わせないと、最初の INSERT が主キー衝突。移行先で先に本番バックアップでのマイグレーションリハーサルを回す。
3. **プーラー** — マネージドがプーラーを提供するならアプリケーションだけそのアドレスへ。transaction モードは prepared statement に注意（docs/32 §9 の `prepareThreshold`）、プロビジョニング · Flyway は直結（`ops/25` の警告）。段階 2 のコネクションの算術はこれで解ける。
4. **戻し方** — 旧 PostgreSQL を読み取り専用で数日。逆方向のレプリケーションを置かなければ切り替え後の書き込みは戻せない — だから切り替え後一日は大きなデプロイをしない。

### 2-4. バックアップ — WAL を外へ

今は毎日の論理 · 物理バックアップがノードのディスクに溜まり、ノード外への取得が別にある（docs/22 §2）。マネージドなら PITR が標準で、自前運用なら WAL を別の機材へ連続転送（docs/86 — RPO 5 分）。復元訓練（`restore-drill`）は移行先で入れ直す。

## 3. 段階 2 — アプリのマルチノード

1. **ノード 3 台以上**（k3s サーバー 3 または EKS 3 AZ）。サービスの Pod は `topologySpreadConstraints` でノードに散らす — `whenUnsatisfiable: ScheduleAnyway`（ノードが一台 NotReady のとき Pending で止まらないように）。PDB（`k8s/70`）は drain のときしか守らない。
2. **Eureka を外す** — k8s の Service DNS（ゲートウェイの静的ルートまたは Spring Cloud Kubernetes）。Eureka の書き込み判定（B-86）· `my-url` のような手間も一緒に消える。ゲートウェイの再試行（B-99）はインスタンス一覧ではなく Service の後ろの Pod へ行く — 接続失敗の再試行が同じ Service にまた行くかを確かめる。
3. **コネクションの算術をやり直す** — B-32 の `maxReplicas = 3` · `serverLimit = 200` は今の値。HPA の上限を上げる前にガードの二つの定数を新しい値に直し、プーラー（段階 1-3）の後ろの実際の上限に合わせる — ガードがビルドで止める。
4. **HPA の上限を上げる** — 段階 0 の「Pod 一つで何リクエスト/秒」から。ノードの自動増設（Karpenter など）は HPA が Pod を置けないときを受ける。
5. **chat** — すでに 1 〜 3（B-107）。残る制約は SockJS の xhr フォールバックが同じ Pod へ行く必要があるのにスティッキーセッションがないこと（docs/21 §2-1）。増やす前に前段のスティッキーセッションか WebSocket のみ許可かを決める。

終わった条件: アプリノードを一台落としても（drain ではなく電源断）エラー率が SLO 内。

## 4. 段階 3 — 読みを前段へ

1. **CDN キャッシュ** — 商品一覧 · 詳細 · ホームの GET を前段で 30 〜 60 秒（docs/87 §3-1）。⚠️ 今の catalog · ゲートウェイの応答には **`Cache-Control` を付ける所がない** — 前段の規則だけでキャッシュすると、ログイン応答 · カートまで混ざる危険がある。キャッシュしてよい経路だけにサーバーが `Cache-Control: public, max-age=…` を付け、前段はそれだけに従うようにする。
2. **在庫を別に** — カード応答ごとに在庫を読み直している（`HomeViewCache` も在庫だけは応答ごと）。在庫だけを小さな API に分ければカード本体はキャッシュできる。
3. **検索を ES へ** — docs/07 のロードマップ（R-C1 · R-C3）: 検索全体（フィルター · 並べ替え · ページ）を ES で、索引キュー · 突き合わせで整合性。手順はデプロイ → 全件再索引 → フラグ比率（docs/74 §3）。戻すのは比率 0（再起動なし）。フィルターメニューの ES 集計と nori · kuromoji の品質確認が残っている。
4. **読み取りレプリカ** — catalog · 注文照会だけ。今のコードは読み · 書きのデータソースを分けていない（catalog の二つのデータソースはデータ · バッチメタ）— ルーティングを足す必要があり、レプリケーション遅延がある所（今変えた商品 · 今作った注文）は書き込み側を読む。

終わった条件: 催事ピークの形の負荷で、catalog の Pod 数が段階 0 の「キャッシュなしで必要な数」の数分の一。

## 5. 段階 4 — 書き込みの拡張

1. **パーティション数 · コンシューマーの並行度** — 注文イベントのキーは注文番号（`OrderCompletedKafkaPublisher` など）なので、同じ注文の順序はパーティション内で守られる。⚠️ **パーティション数を増やすとキー → パーティションの対応が変わる** — 進行中の注文のイベントが別のパーティションへ行き、順序が崩れうる。遅延 0 の枠で増やすか、新しいトピックを作って移す。状態トピック（`order-saga-state` · `order-timeline`）は order トピックと同じ数で（`ops/02 STATE_PARTITIONS`）。
2. **在庫のホットスポット** — 人気商品の行ロックに注文が集まる（docs/87 §3-2）。gRPC の在庫予約（docs/66）を出発点に、原子的な減算（Redis Lua など）で先に受け、DB の確定は非同期に。決済確定の減算はすでにアウトボックス（`product-update`）· 冪等（eventId）である。
3. **大きなテーブル** — アウトボックスはすでに月別パーティション（order · pay · user · cart の `V1__partition_*`）。注文 · 注文行は数億件になる前に同じ方式で。列 · インデックスの変更は docs/85 §8-1（expand → contract · `CREATE INDEX CONCURRENTLY` · `VACUUM (PARALLEL 0)`）、外部キー列のインデックスは order V28 · catalog V22 · cart V8 の点検を他のサービスにも。
4. **シャーディングはその後** — サービスごとの DB はすでに機能分割である（docs/88）。一つのサービスの書き込みが DB 一台を超えたとき、そのサービスだけをキー（顧客 · 注文）で分ける。

## 6. 段階 5 — 運用体制

段階 1 と一緒に始める — 後回しにすると移行中の障害が見えない。

- **観測をクラスターの外へ** — 今は本番ノードの compose（B-95 · B-106）。マネージドか別の機材へ、アラート配信（B-96）はそのまま。テイルサンプリングの上限（B-102）はトラフィックが増えるほど大事になる。
- **デプロイ** — `ops/28` の手作業 → パイプライン（GitHub Actions OIDC → レジストリ → Argo CD）· カナリア。ROLLBACK-UNSAFE（B-54）· expand → contract の規則はそのまま持っていく。手動実行の原則（B-75）は本番ランナーが本番の資格情報を持つ間は維持する。
- **ゲームデー** — 段階ごとに終わった条件を ゲームデーで実際に切ってみる: ブローカー一つ · Redis プライマリ · DB のフェイルオーバー · アプリノードの電源。
- **DR** — 最初からマルチリージョンにはしない。バックアップ · スナップショットだけ別リージョンへ（docs/87 §3-5）。

## 7. すでにあるものはどこまで有効か

| すでにあるもの | どこまで | 増やすときに見直すもの |
|---|---|---|
| アウトボックス（月別パーティション）· サガ | ブローカーが変わってもメッセージを守る | リレーの処理量 · パーティションの保持（古い月の掃除） |
| 冪等台帳（catalog · coupon · cart · order の配送状態 · `ProcessedEventPurger`） | 再配信 · オフセットのリセットに安全 | 台帳のないグループ（§2-1） |
| 機能フラグ（docs/74） | 検索エンジンの比率 · 戻しは再起動なし | フラグの期限（B-76） |
| 検索の隔壁 · 時間上限（docs/83 §2.8） | DB を使う検索がプールを食い尽くさない | プールの大きさを変えたら隔壁の数も |
| コネクションガード B-32 | 合計が上限を超えるとビルドが止まる | 定数二つ（最大レプリカ · サーバーの上限）を新しい値に |
| ノード分散 · PDB | 分散 · drain | ノード障害には分散だけ |
| `external` オーバーレイ | データのアドレスだけを変える | Sentinel · クラスターモードは設定キーが違う |
| chat の Redis ファンアウト（B-107） | 1 〜 3 | スティッキーセッション · Redis の切り替えは一斉に |
| 流入制限（B-84） | ルートごと · JWT の後 | Redis 障害 = 通す（fail-open）。`CF-Connecting-IP` の信頼は前段が変わったら直す（docs/86 §2-1） |
| テイルサンプリングの上限（B-102） | トレースの暴走を防ぐ | トラフィックに合わせた上限 |
| expand → contract · ROLLBACK-UNSAFE（B-54） | 無停止のスキーマ変更 | そのまま |

## 8. やらないこと

- **最初からマルチリージョン** — 費用 · 複雑さが大きく跳ねる（docs/87 §3-5）。3 AZ（またはラック三つ）+ 別リージョンのバックアップで始める。
- **サービスをさらに細かく分ける** — 今の境界（サービスごとの DB）で十分。増えるのは結合 · 整合性のコストである（docs/88）。
- **測定前の機材 · マネージドの購入** — 段階 0 の表なしに決めない。

2026-11-05、別セッションが cart レビューの最後に付け加えた拡張の要約をこの文書の出発点にした。照合して直したもの:
