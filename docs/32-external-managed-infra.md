# 32. インフラをクラスターの外へ — マネージドの無料ティア

**日本語** | [한국어](32-external-managed-infra.ko.md)

背景: クラスターを軽くするため、OCI の無料 PostgreSQL（HeatWave/Autonomous）、Upstash Redis、
Confluent Cloud の無料ティアへインフラを移す案を検討した。

まず、最初に置いた前提の事実誤認を正すところから始める。**候補 3 つのうち 2 つが間違っていた。**

| 候補 | 実際 | このリポジトリでは |
|---|---|---|
| OCI 無料「PostgreSQL」 — HeatWave | **MySQL** である | ❌ 使えない |
| OCI 無料「PostgreSQL」 — Autonomous Database | **Oracle Database** である | ❌ 使えない |
| Upstash Redis | Redis で合っている | ❌ 移さないことにした（§6） |
| Confluent Cloud | Kafka で合っている | ⚠️ 恒久的な無料ではない（§3） |

だからこのドキュメントは移行作業の記録ではなく、**何が実際に可能かを確認した結果** である。

---

## 1. コードが実際に要求するもの

移せるかどうかを判断するには、まずコードが何に縛られているかを知る必要がある。数えてみた。

| | 根拠 | 結論 |
|---|---|---|
| PostgreSQL 固有の機能 | `FOR UPDATE SKIP LOCKED` 38 ファイル、`jsonb` 23 か所、`PARTITION BY RANGE` 4 か所、`GENERATED BY DEFAULT AS IDENTITY` 22 か所、`PostgreSQLDialect` 34 か所 | **PostgreSQL でなければならない。** MySQL・Oracle は候補から脱落 |
| 拡張（extension） | `CREATE EXTENSION` **0 件** | マネージドで塞がれていても無関係 ✅ |
| Redis | RedisTemplate 79、Redisson 53、`@Cacheable` 23、`RequestRateLimiter` 4 | キャッシュだけでなく **分散ロック** が絡んでいる |
| Kafka | 21 個の設定クラス、トランザクショナル・プロデューサー、DLQ | トピックの自動作成・トランザクションのサポートが必要 |
| Elasticsearch | `ops/03` が `korean_analyzer`（nori）の存在を検証 | **プラグインのインストールが必要** |
| Kafka Connect | ルートの `*-outbox-connector-*.json` は **どのマニフェストにもない** | Outbox はアプリケーションのポーラーが回す（docs/21）。マネージドコネクタへの依存なし ✅ |

`SKIP LOCKED` が決定的だ。Outbox ポーラー、メールディスパッチャー（docs/29）、SMS ディスパッチャーはすべて
「複数のレプリカが同じテーブルからそれぞれ別の行を取る」をこれで実装している。なければレプリカ
2 つが同じメールを 2 回送る。

## 2. ところで — 何を節約しようとしているのか

「クラスターがずっと軽くなる」という前提をまず検証した。`kustomize build` の結果から計算した
**CPU・メモリのリクエスト合計** だ。

| 構成 | CPU リクエスト | MEM リクエスト | 4 OCPU / 24GB | 2 OCPU / 12GB |
|---|---:|---:|---|---|
| prod（HPA min=2） ＋ クラスター内インフラ 5 種 | 5,950m | 10,048Mi | 🔴 超過 | 🔴 超過 |
| prod（HPA min=2）、アプリのみ | 5,300m | 8,192Mi | 🔴 超過 | 🔴 超過 |
| **external**、すべて 1 レプリカ ＋ Kafka・ES・Redis | **3,350m** | **5,824Mi** | ✅ | 🔴 超過 |
| **oci オーバーレイ** ＋ Kafka・Redis（ES 除く） | **1,000m** | **3,520Mi** | ✅ 余裕あり | ✅ |

> ⚠️ **上限はテナンシーごとに異なる。** 2026-06-15 付で Always Free Ampere の上限が
> 4 OCPU/24GB → 2 OCPU/12GB に縮小されたと、告知なしにドキュメントだけが変わったが、**実際には
> 4 OCPU/24GB がそのまま確保できるアカウントもある。** だから「もう 2/12 だ」と断定せず、
> **自分のインスタンスで確認** すること: `nproc` と `free -g`。
>
> そのためオーバーレイが 2 つある。`external` は 4 OCPU を前提とし、`oci` は 2 OCPU でも
> 収まるように絞ったものだ（docs/33 §4・§8）。

**4 OCPU / 24GB を確保できたなら `external` は収まる。ただし余裕はほとんどない。**

⚠️ **実測が見積もりより大きかった。** 上の表の 3,350m はアプリケーションのマニフェストだけを足した値だ。
実際の 4 OCPU ノードで測った値は **3,980m（99%）** だった。抜けていたものがあった:

| | CPU リクエスト |
|---|---:|
| external のアプリ 13 個（Java 11×250m ＋ frontend 100m ＋ **cloudflared 2×50m**） | 2,950m |
| 残るインフラ（redis 50 ＋ kafka 200 ＋ **elasticsearch 200**） | 450m |
| **k3s 内蔵**（CoreDNS 100 ＋ metrics-server 100） | 200m |
| 実測との差 — ノードで直接確認すること | ~380m |
| **実測合計** | **3,980m / 4,000m** |

**解釈: 99% は「CPU が忙しい」ではなく「スケジューラーの予約台帳が埋まった」という意味だ。**
リクエストは予約であり、実際の使用量とは無関係だ。Spring Boot のサービスはたいていアイドル時に 10〜50m を
使う程度なので、実使用率はずっと低い。メモリ 37% も、上限 555% 超過も正常だ —
**上限はノード容量を超えてもよい。**

だから今すぐ落ちるわけではない。ただし **次の一点は必ず詰まる:**

> ⚠️ **ローリングアップデートが止まる。** `kubectl rollout restart` やイメージの差し替えは、既存の Pod を
> 消す **前に** 新しい Pod を立ち上げる（maxSurge）。残り 20m の状態では新しい Pod が `Pending` で
> 止まり、ロールアウトが永遠に終わらない。HPA も当然スケールアウトできない。

### → オーバーレイで解決した

`external` オーバーレイが **CPU リクエストを 100m に下げる**（`patch-java-requests.yaml`）。
上限はそのまま 1,000m だ。結果:

| | CPU リクエスト |
|---|---:|
| アプリ 13 個（Java 11×100m ＋ frontend 100m ＋ cloudflared 2×50m） | 1,300m |
| インフラ（redis 50 ＋ kafka 200 ＋ elasticsearch 200） | 450m |
| k3s 内蔵（CoreDNS ＋ metrics-server） | 200m |
| **合計** | **約 1,950m / 4,000m** |

余裕が 2,000m ほど残るので、ローリングアップデートも、中核サービスの 2 レプリカも可能だ。

⚠️ **この値を `kubectl patch` で変えないこと。** 次の `kubectl apply -k` で上書きされる —
実際にそうして 99% に戻り、Pod が `Insufficient cpu` でスケジュールされなかった。
変える必要があるなら `patch-java-requests.yaml` で変える。

### それでも足りなければ — 効果の大きい順

```bash
# まず今何が占有しているかを見る
kubectl get pods -A -o json | jq -r '
  .items[] | select(.status.phase=="Running")
  | [([.spec.containers[].resources.requests.cpu // "0"] | join("+")),
     .metadata.namespace + "/" + .metadata.name] | @tsv' | sort -rn | head -20
```

| 手段 | 節約量 | 代償 |
|---|---:|---|
| **Java のリクエストを 250m → 60m**（`oci` オーバーレイがやっていること） | **~2,090m** | 負荷が集中すると Pod 同士が CPU を奪い合う。単一ノードではどのみちそうなる |
| Elasticsearch の削除 | 200m | 韓国語形態素（nori）の検索経路を通れない |
| cloudflared 2 → 1 | 50m | トンネルのロールアウト時に短い切断 |

いちばん大きいのは 1 つ目だ。**250m を予約しておいて 20m しか使わないのが無駄** で、暴走を防ぐのは
リクエストではなく上限（1,000m）だ。リクエストだけ下げて上限はそのままにすればよい:

```bash
kubectl -n ecommerce get deploy -o name | grep -E 'service|server' | xargs -I{} \
  kubectl -n ecommerce patch {} --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/requests/cpu","value":"80m"}]'
```

⚠️ これは命令型のパッチなので、次の `kubectl apply -k` で上書きされる。使い続けるなら `k8s-overlays/oci` を
使う（上限も一緒に絞られる）か、別のオーバーレイを作る。

### レプリカ 2 は今はできない

**レプリカ 1 では、このリポジトリがレプリカ 2 で捕まえてきた並行性バグを再現できない**
（docs/31 §3）。もともと 4 OCPU の余裕で中核の 2〜3 個を 2 に上げられると書いたが、
**実測の余裕が 20m なので不可能だ。** 上の方法でリクエストを下げてはじめて可能になる:

```bash
kubectl -n ecommerce scale deploy order-service catalog-service --replicas=2
```

⚠️ **HPA を適用していれば `kubectl scale` は元に戻される。** CPU が目標値を下回っていれば、HPA が
安定化ウィンドウ（デフォルト 5 分）の後に `minReplicas` まで再び下げる。そのときは HPA を直す必要がある:

```bash
kubectl -n ecommerce patch hpa order-service -p '{"spec":{"minReplicas":2}}'
```

⚠️ サービス名は `catalog-service` だ — **`product-service` というものは存在しない。**

インフラ 5 種のリクエスト合計は **650m / 1,856Mi** で、そのうち外に出せる
PostgreSQL・MongoDB は **200m / 512Mi** にすぎない（Redis は残す — §6）。

> **インフラを外に出すだけでは到底足りない。** 4 OCPU の頃も超過分の主犯は
> インフラではなく **アプリケーションのレプリカ** だったし、2 OCPU になった今は差がさらに開いた。
> 実際に効果の大きい順はこうだ:
>
>   1. **レプリカを 1 に**（HPA 未適用） — 5,300m → 2,900m
>   2. **リクエスト・上限を減らし、JVM ヒープを明示**（oci オーバーレイ） — 2,900m → 750m
>   3. **Elasticsearch を外す** — 200m/768Mi。どのみち `SEARCH_ENGINE=postgres` がデフォルトだ
>   4. インフラの外部化 — 200m/512Mi。**いちばん小さい**
>
> それでも外部化する理由は、リソースではなく以下のデータの寿命のためだ。

`ops/23-oci-ampere-bootstrap.sh` の以前のコメント（「1 台に収まる規模だ」）は間違っていた。
今回計算して直した。

それでも外部化には、リソース節約とは別の利点がある — そして実はそちらのほうが大きい:

- **データがノードの寿命から切り離される。** 今の `90-dev-infra.yaml` の PostgreSQL は
  `emptyDir` だ。Pod が再起動するとデータが消える。無料ティアのインスタンスが再起動したら終わりだ
- **バックアップ・PITR・アップグレードが provider の責任になる**（ただし §7 の代償を見よ）
- ES・Kafka はどのみち残るので、ノードは依然としてステートフルだ — 完全な分離ではない

## 3. 何が実際に外に出せるか

| | 候補 | 判定 |
|---|---|---|
| PostgreSQL | Neon / Supabase / Aiven | ✅ **出せる。** 3 つとも本物の PostgreSQL で、拡張は不要 |
| MongoDB | Atlas M0 | ✅ **出せる。** chat-service はドキュメントの保存しかしない |
| Redis | Upstash | ❌ **残す。** 得られるのが 50m/64Mi だけなので、リスクを負う理由がない — §6 |
| Kafka | Confluent / Redpanda / Aiven | ❌ **残す。** 恒久的に無料のマネージド Kafka が見つからなかった |
| Elasticsearch | Bonsai / Elastic Cloud | ❌ **残す。** nori プラグイン |

### Kafka を残す理由

Confluent Cloud は「無料クレジット」であって無料ティアではない。Basic クラスターは基本料金がない
代わりに **スループット・ストレージ量で課金** され、クレジットカードが必要で、クレジットを使い切ると請求される。
Redpanda Serverless・Aiven も事情は似ている（試用期間または従量課金）。

ポートフォリオ規模のトラフィックなら、実際の請求額は小さいかもしれない。しかし **「無料」と書いておいて
カードが切られる** のは、このドキュメントがやってはいけないことだ。だからデフォルトはクラスター内の Kafka だ。

その代わり、**移したくなったら移せるようにはしておいた** — §4 の SASL サポートがそれだ。

> ⚠️ 無料ティアの条件はよく変わる。この表は判断の根拠であって、登録時点の事実ではない。
> 登録前に各 provider の現在の料金ページを直接確認すること。

### Elasticsearch を残す理由

`ops/03-enable-es-search.sh` が `korean_analyzer` の存在を検証しており、それには
`analysis-nori` プラグインがインストールされている必要がある。マネージド ES の無料ティアは、たいていカスタムプラグインの
インストールを許可しない。プラグインなしで繋ぐと、インデックス作成が失敗するか — もっと悪いことに —
韓国語検索が静かにひどい品質になる。

## 4. コードを直す必要があったもの — すべて同じバグだった

マネージドに繋ごうとして、**4 か所で同じ形のバグ** に出くわした。

> プライベート CA で発行した証明書のパスが **空でも無条件にロードする。**

ローカルは平文（PLAINTEXT / `ssl.enabled=false`）なのでこのコードはそもそも実行されず、
クラスター内ではパスが実際のファイルを指していた。そのため **マネージドに繋いだ瞬間にだけ** 爆発する。
マネージドサービスはどれも *公開 CA の証明書 ＋ パスワード（または API キー）* で、クライアント証明書が
ないからだ。

| 箇所 | 症状 | 直し方 |
|---|---|---|
| Kafka 設定クラス **24 個** | `ssl.truststore.location=""` をそのまま入れて空のパスを開く | `KafkaSecuritySettings` 一つに集約し、**空なら入れない** |
| `RedissonConfig`（cart・chat） | `new File("")` → カレントディレクトリをトラストストアとして渡す | パスがあるときだけ設定 |
| `RedisCacheConfig`（catalog・order） | 空のパスを `resourceLoader` で開いて `FileNotFoundException` | パスがあるときだけ `SslOptions` を生成 |
| `MongoSslConfig`（chat） | `mongodb+srv` は TLS がデフォルト → プライベート CA を組み立てる経路に入る | パスが空なら JVM デフォルトのトラストストアで TLS |

### 24 個の複製の整理

Kafka 設定クラス 24 個が、この 6 行をそのまま複製していた:

```java
.put(SslConfigs.SSL_KEYSTORE_LOCATION_CONFIG,   checkPath(keyStoreLocation))
.put(SslConfigs.SSL_KEYSTORE_PASSWORD_CONFIG,   keyStorePassword)
.put(SslConfigs.SSL_KEYSTORE_TYPE_CONFIG,       keyStoreType)
.put(SslConfigs.SSL_TRUSTSTORE_LOCATION_CONFIG, checkPath(trustStoreLocation))
...
```

今はすべて `.putAll(securityProps())` の 1 行で、実際の計算は
`common/.../config/KafkaSecuritySettings.java` が行う。ルールは 3 つだ:

1. プロトコルに **必要なキーだけ** を入れる。PLAINTEXT なら `security.protocol` 一つだけだ
2. ストアのパスが空なら **入れない** → JVM デフォルトのトラストストア（公開 CA）
3. `SASL_*` なら `sasl.mechanism` ＋ `sasl.jaas.config` を作る。
   資格情報がなければ **起動時点で落ちる** — ブローカーが返す `Authentication failed` には
   原因の手がかりがないからだ

シークレット内の `"` と `\` はエスケープする。マネージド API のシークレットには実際に含まれていて、そのままに
しておくと JAAS パーサーが文字列をとんでもない場所で切り、`Unable to find login module` という
**まったく無関係な** エラーを出す。

キー名は Kafka の定数ではなく文字列だ — common に依存するモジュールの中に Kafka をまったく
使わないもの（eureka-server、config-server）があり、定数一つのために kafka-clients を
そちらのランタイムまで引きずっていく理由がない。代わりに、その文字列が実際の定数と同じかどうかは
`KafkaSecuritySettingsTest` が **テストのクラスパスでだけ** kafka-clients を取り込んで検証する。

ガードレール `B-35` がこの整理が再び散らばるのを防ぐ: `KafkaSecuritySettings` 以外の
どの `src/main` ファイルでも `SslConfigs.` / `SaslConfigs.` を使うとビルドが失敗する。

## 5. オーバーレイ — `k8s-overlays/external`

```
k8s/                      マニフェストの原本（ベース）
k8s-overlays/dev/         レプリカ 1、リクエスト縮小、ローカルイメージ
k8s-overlays/prod/        replicas 削除（HPA が所有）、レジストリのイメージ、cloudflared
k8s-overlays/external/    ← prod を継承してエンドポイントだけ差し替える
k8s-overlays/oci/         ← external を継承して 2 OCPU/12GB に合わせて絞る（docs/33 §4）
```

`external` は `../prod` をベースにする（ディレクトリベースなので参照できる — docs/31 §2 の
制約はここでは引っかからない）。変えるのは `ecommerce-config` ConfigMap **1 枚** だけだ。

それが可能なのは、ベースが JDBC URL をこう書いていたからだ:

```yaml
value: "jdbc:postgresql://$(POSTGRES_HOST):$(POSTGRES_PORT)/userdb?sslmode=require"
```

`POSTGRES_HOST` だけを変えれば **10 個のデータソースが一斉についてくる。** Deployment には
一つも触れない。

変えるキー:

| キー | なぜ |
|---|---|
| `POSTGRES_HOST` / `POSTGRES_PORT` | マネージドのエンドポイント |
| `DB_POOL_SIZE: 3` | 10 データソース × 3 × レプリカ 3 = 90。デフォルトの 5 だと 150 になり、無料ティアの上限を超える |
| `SPRING_DATA_REDIS_*` | マネージドに移すときだけ。デフォルト構成はクラスター内の Redis なのでそのままにする（§6） |
| `SPRING_DATA_REDIS_SSL_{TRUSTSTORE,KEYSTORE,CACERT}: ""` | **§4 の核心。** 空にしてはじめて公開 CA で検証する |
| `SPRING_DATA_MONGODB_{CACERT,KEYSTORE}: ""` | 同じ理由 |

### 2 OCPU の箱に載せるなら — `oci` オーバーレイを使う

`external` は依然として prod のリソース値（250m/384Mi × HPA min=2）を使うので、**2 OCPU には
収まらない**（§2 の表）。その上に `k8s-overlays/oci` を重ねる:

```bash
kubectl apply -k k8s-overlays/oci
# ⚠️ k8s/70-autoscaling.yaml は適用しない — replicas フィールドがなければデフォルト値は 1 だ
```

⚠️ **レプリカ 1 では、このリポジトリが経験した並行性バグは再現されない**（docs/31 §3）。
それは `ops/12-staging-rehearsal.sh` で別途確認する必要がある。

### 残るインフラだけを立ち上げる

```bash
kubectl apply -f k8s/90-dev-infra.yaml     # 単体ファイルなのでオーバーレイから参照できない
kubectl -n postgres delete deploy postgres
kubectl -n mongodb  delete deploy mongodb
# ⚠️ redis は消さない — クラスターに残す（§6）
```

## 6. Redis はクラスターに残す — 決定

最初は「確認してみないとわからない」として残しておいたが、確認コストと利点を並べてみれば、決定が先だ。

### 何が引っかかるか

`RedisTemplate`・`@Cacheable`・`RequestRateLimiter` は普通のコマンドなので問題はない。
問題は **Redisson** だ（cart・chat の 2 サービス、53 か所）。分散ロックが単純な `SETNX` ではない:

- ロックの取得・解放を **Lua スクリプト**（`EVAL`/`SCRIPT LOAD`）でアトミックにする
- 待機中のクライアントを起こすのに **pub/sub** を使う
- コネクション初期化時に `CLIENT SETNAME`、`INFO replication` のようなコマンドを送る

マネージド Redis がこれらすべてを無料プランでサポートしているかは、**アカウントなしには確認できない。**

### だから決定

| | |
|---|---|
| 外に出して節約できるもの | **50m CPU / 64Mi** — インフラ 5 種の中でいちばん少ない |
| 失いうるもの | カートへの追加・チャットが **ロックの段階で落ちる。** しかもデプロイした後で |
| Redis が抱えているもの | キャッシュ · ロック · レートリミットのカウンター — **すべて再構成可能** |

最後の行が核心だ。PostgreSQL・MongoDB を外に出した本当の理由はリソースではなく、
**`emptyDir` なので Pod が再起動するとデータが消えるから** だった（§2）。Redis にはその理由が
当てはまらない。キャッシュは飛んでもまた埋まるし、ロックはそもそも揮発性だし、レートリミットの
カウンターが初期化されるのは再起動時の一度だけだ。

**利点がいちばん小さくリスクがいちばん大きいものを、あえて移す理由はない。** Redis は残す。

### 後で移したくなったら

コードはすでに準備できている — §4 で `RedissonConfig`・`RedisCacheConfig` の空の証明書パスの
問題を直し、`k8s-overlays/external` の ConfigMap に Redis のキーがコメント付きで入っている。
決定を変えるだけでよい。確認方法は一つだけだ:

```bash
KEEP=1 ./ops/13-k3s-deploy.sh
# cart-service だけをその provider で動かし、カートへの追加（ロック経路）を押してみる
```

`ERR unknown command` や pub/sub のタイムアウトが出たら、その provider は使えない。
コマンド数の上限も一緒に見ること — `@Cacheable` 23 か所とレートリミッターがカウンターを速く消費する。

## 7. 外部化で **失う** もの

| | クラスター内 | マネージドの無料ティア |
|---|---|---|
| レイテンシ | 同じノード、0.1ms | インターネット往復。**リージョンが違えば数十 ms** |
| バックアップ | `ops/08` `ops/10` が回る | provider の責任。無料ティアは保存期間が短いかゼロ |
| `ops/09-restore-drill.sh` | 動作する | **動作しない** — 対象がクラスター内の PG だ |
| `k8s/85-backup-cronjobs.yaml` | 動作する | **動作しない** |
| 露出面 | クラスター内部のみ | **インターネットに開いたエンドポイント**。パスワードが防衛線 |
| アイドル停止 | ない | 無料ティアは数日アイドルだと停止する（最初のリクエストがコールドスタート） |

レイテンシには特に注意すること。このリポジトリは 1 リクエストで何度も DB を往復し、N+1 ガード
テスト（docs/19）まで置いている。同じノードで 0.1ms だった往復が 30ms になると、
**クエリ 20 個のリクエストが 2ms から 600ms になる。** 必ず OCI インスタンスと **同じリージョン** に
プロビジョニングすること。

そしてアクセス IP の制限をかけること（Neon: IP Allow、Aiven: Allowed IP）。無料ティアで制限が
できないなら、それはパスワードが唯一の防衛線だという意味だ。

**確認できていない（アカウント・環境がない）**

- **Neon・Supabase・Aiven のどこにも実際に繋いでいない。** 検証は PostgreSQL 16
  コンテナを「マネージドのふり」をさせて立てて行った。プーラー（PgBouncer）経路のプリペアドステートメント
  問題（§ 下記）はコンテナでは再現されない
- **Upstash に Redisson を繋いでいない。** だから §6 は「検証した」ではなく **「移さないことに決めた」** だ。移すならその検証が先だ
- **マネージド Kafka に繋いでいない。** SASL のコード経路は単体テストでしか検証していない
  （JAAS 文字列の生成・エスケープ・空のストアの省略）。実際のブローカーとのハンドシェイクは未確認
- MongoDB Atlas は未検証
- 無料ティアの条件（容量・コマンド数・アイドル停止）は **ドキュメント基準** で、登録時点では異なる可能性がある

**既知の未解決 — プーラー（pooler）エンドポイント**

Neon・Supabase のプーリングエンドポイントは PgBouncer の transaction モードだ。このモードは **サーバーサイドの
プリペアドステートメントと衝突** する（pgjdbc は同じ文を 5 回実行すると自動的にサーバー
プリペアに切り替わる）。症状は散発的な
`ERROR: prepared statement "S_1" already exists` だ。

**デフォルト構成は直結（direct）エンドポイントなので、これには該当しない。** コネクション数の計算も合っている —
10 データソース × `DB_POOL_SIZE=3` × レプリカ 1 = 30 で、無料ティアの上限内だ。

マニフェストに `$(JDBC_EXTRA_PARAMS)` のような差し込み口をあらかじめ仕込んで **おかない** 理由: その ConfigMap
キーがなければ `$(...)` が文字どおり残り、**10 個のデータソースの URL がすべて壊れる。** 今
必要でもない機能のために新しい罠を作ることになる。

プーラーが実際に必要になったら（レプリカを増やしてコネクションが足りなくなったとき）、30 秒で有効化できる:

```bash
# 10 個のデータソース URL に &prepareThreshold=0 を付け足す
for d in user-service catalog-service cart-service order-service pay-service \
         coupon-service chat-service notification-service delivery-service; do
  kubectl -n ecommerce get deploy "$d" -o json \
    | python3 -c '
import json,sys
d=json.load(sys.stdin)
for c in d["spec"]["template"]["spec"]["containers"]:
    for e in c.get("env",[]):
        if e.get("name","").startswith("SPRING_DATASOURCE") and e["name"].endswith("_URL") \
           and "prepareThreshold" not in e.get("value",""):
            e["value"] += "&prepareThreshold=0"
json.dump(d,sys.stdout)' \
    | kubectl apply -f - 
done
```

⚠️ 症状が **散発的** だという点が罠だ。pgjdbc は同じ文を 5 回実行した後になってはじめてサーバー
プリペアドに切り替わるので、デプロイ直後は問題なく、トラフィックが積み上がった後に爆発する。
